Performance investigation

Why boot & foreground feel slower than before

An interactive map of the three startup flows and where the time goes. The hang is gone, but startup now throws a large concurrent herd of work at the first second, and NSE-staged mail is gated behind full AI completion — so the “message pops in at 10ms” behaviour was lost. Open each flow to click through every job.
✓ Update 2026-06-26 (b) — a cooperative PriorityGate so the background herd yields to the merge.
Why the merge was still slow. An on-device trace showed a warm-foreground merge of a pushed email taking 3185ms (mergeNSEStagingData: DONE in 3185ms). The cause: a deep backfill (historical-archive body fetch) was mid-flight from a prior background cycle — back-to-back 50-item batches whose write step holds the GRDB + FTS writers and saturates the cooperative thread pool. The earlier “merge before herd” only gates this foreground's own sync herd; it does nothing to a backfill that's already running. So “privileged” held against other merges but not against the backfill.

The proper fix — cooperative quiescence. You can't preempt an in-progress SQLite transaction or reserve the cooperative pool, and QoS only deprioritizes (tried & reverted). So PriorityGate (a small actor) lets the privileged path raise a count-based flag (privileged { }), and every heavy background loop calls await yield() at a SAFE boundary (between batches, before it grabs the writer) — parking until the gate clears. Wired into backfill body (twice: batch top + right before the write), backfill AI, all three embedding queues, and the header walk. Bound: a batch already mid-flight runs to its next boundary, so the merge waits at most ~one batch instead of the whole backfill run. It's the GRDB/FTS analogue of the IMAP priority lock (ADR-IOS-014).
✓ Update 2026-06-26 — the NSE→inbox merge is now a privileged, single-threaded boot step.
New finding (the remaining lag). With the NSE long finished, a freshly pushed message could still take 3–5s to appear — and tapping its notification could stall 3–5s before the deep link opened it. Two structural causes:
  • Visibility gate. The inbox query filters headerComplete == true, but a brand-new merged header is inserted headerComplete = false and only flipped later inside a detached FTS flush that posted no reload signal — so the row stayed invisible until some unrelated later notification happened to fire.
  • Uncoordinated merges. Six call sites (deep-link tap, foreground, syncStartup step-0, foreground-push, silent push, AI queue) each opened the staging DB and fought the 2s/5s busy lock + the single GRDB writer — concurrently with the sync/backfill/AI herd. The deep-link tap awaits the merge on its navigation critical path, so that contention is the 3–5s tap delay (the post-merge lookup itself is not headerComplete-gated).
The fix — make the merge special.
  1. Serialize via NSEMergeCoordinator — all six callers funnel into one in-flight, single-threaded run (a serial task chain); no two merges ever fight the locks.
  2. Synchronous FTS flip — the merge now awaits the flush, so headerComplete=1 (and bodyComplete=1, from the NSE's pre-rendered body) is set before it signals; the row is visible and opens with no body-load flash.
  3. One immediate post at the end — the whole merge (header→body→summary→action→FTS→removals→tasks) emits a single .inboxDataDidChange, flagged to bypass the 500ms debounce. The debounce stays for the noisy background producers (sync/backfill/AI); the merge is privileged.
  4. Merge before the herd — the foreground awaits the full merge before spawning sync/backfill/AI, so the writer is free while it runs and it stays near-instant.
✓ Implemented 2026-06-25 — the two focused changes.
1 — Gradual NSE staging. The NSE now stages header → body → summary → action incrementally, flipping populated=1 at the header stage. The merge applies each piece idempotently and keeps the row until AI completes, so a foreground surfaces NSE mail ~17s earlier instead of waiting for all AI. opt #1

2 — Foreground reorder. The first foreground after a cold launch yields + settles 0.35s so the inbox paints before the merge + sync herd starts. opt #2

3 — Cold-boot first paint (found via on-device BootProfiler). The orphan DemoSeed.wipe ran unindexed LIKE 'demo-account:%' full-table scans on the writer before first paint — gating the inbox by ~10s on a large mailbox. Now gated on a 1ms indexed existence check (skipped when there's no demo data) and the wipe's scans converted to index-using range queries. opt #3

The remaining optimizations below were intentionally deferred as overkill for now. A DEBUG-only BootProfiler (kernel-process-start timeline) was added to measure all of this.
✓ Measured on device (2026-06-26 BootProfiler / NSE os_log).
Cold boot → inbox: 22.2s → 6.6s — db.built → FIRST PAINT went from 10.3s (DemoSeed full scans) to ~14ms; the remainder is pre-main dyld load (debug+debugger-inflated, smaller on Release). DB build itself was always fast (220ms).
NSE gradual staging: header staged (populated=1) at +519ms vs delivery at 5623ms — message surfaces ~5s before AI finishes. Real AI: summary ≈2.7s, action ≈1.8s (no reply in NSE).
Foreground reorder: 0.35s settle → inbox first → NSE merge surfaced the staged message in 64ms; the ~6s sync herd runs behind the visible inbox.
Two findings explain the regression.
1 — The foreground herd. scenePhase → .active launches the unified startForegroundPolling pipeline: mergeNSEStagingData ×2, two full sync passes (backgroundSyncAll + foregroundSyncAll), 6 queue repopulations, push re-subscribe, FTS self-heal, and whoami ×3–4 — all in the first ~1–2s, contending the single GRDB writer, the reader pool, the network and the CPU exactly when SwiftUI's ~1.3s first-render stall needs them.

2 — NSE mail is gated behind AI. The merge shows only populated=1 rows, and the NSE writes that flag after summary + action (≤24s of LLM) — even though the header+body were ready ~5s in. Foreground while the NSE is mid-AI ⇒ the message is invisible until the NSE finishes or the app's own (slower) sync re-fetches it. Exactly the “staging should catch up in 10ms” behaviour you remember, now lost.

What's already well-placed (don't regress)

  1. DB build off init, splash-gated, version-gated. the original foreground-hang fix.
  2. SearchIndex FTS open + WebKit warm-up deferred to post-isReady+500ms. No longer mid-render.
  3. EmbeddingService eager .utility (lands late, after paint; kept eager so background launches still build embeddings). QoS-lever to lower these was tried & reverted.
  4. NSE staging schema upkeep off the isReady gate + version-gated (no cross-process lock in steady state).
  5. NSE↔main-app AI lease (ADR-IOS-037) prevents duplicate LLM spend — keep it; the split-write fix coexists with it.

How to get real numbers

All timings in these pages are architectural estimates from the code paths (durations are representative, not profiled), except where a device-log number is cited. To confirm on a Release / TestFlight build (the debugger inflates WebKit/CoreML 3–4×):

  1. BackgroundSyncLogger fgReturn[+Nms] lines (fgStep in startForegroundPolling) — the warm-foreground herd timeline.
  2. BackgroundSyncLogger syncStartup[+Nms] (stepLog) — each step's offset.
  3. MainActorStallDetector output — pinpoints which main-actor op blocked >200ms.
  4. NSE os_log — NSE step6a/6b timings and the final DELIVERED (Nms) line.
  5. AppStartup database ready in Nms — confirms DB build is (not) the cost.
