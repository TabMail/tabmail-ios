## Audit, Review, and Agent-Supervision Rules

> **Role assignment lives in the global `../CLAUDE.md` § "Common Cross-Model Workflow" and is
> deliberately model-agnostic: whichever model owns the main session is the coordinator, and the
> other model is the independent read-only vetter.** Nothing below re-assigns those roles. These are
> the iOS-specific process rules, each learned from a concrete failure in this repo; read
> "coordinator" and "reviewer" as the global file defines them.

**A1. SEARCH THE PREVIOUS RELEASE FIRST. AUTHOR ONLY IF ITS ARCHITECTURE IS INAPPLICABLE OR NONEXISTENT.** For ANY fix, the first move is `git show <release-tag>:<path>` on the code that **owns** the problem. Authoring is the FALLBACK, not the default. The order is:

1. Find how the shipped release handled this problem. It is proven-adequate — smoke-tested by the owner and real users. That is empirical evidence no on-paper reasoning outranks.
2. If it handled it and the approach still applies ⇒ **restore that behaviour**, keeping any genuine improvement added on top. State explicitly what you kept and why.
3. Author something new ONLY if the shipped architecture is genuinely **inapplicable** (the surrounding design changed such that it cannot work) or **nonexistent** (the shipped release never did this). **Say which, in the plan.**

   **This supersedes the trigger of rule A2**, which fires only after a design has already spiralled — too late. In one session A1 went four for four, and every miss was expensive: a durable compare-and-swap, an outcome enum and a restructured send hold were designed for an Undo-Send defect *the shipped release does not have*; a Gmail draft-resource-id route was built that the shipped app never needed and that is still in the tree, unchanged, simply never reached; a read-state restoration was reported as "no undo path ever did this" because HEAD was searched instead of the release, when the release does it via a full-row save with a comment saying so; and a notification-action principle was re-derived when the shipped enum's own documentation states it outright.

   **The tell that you skipped this step:** you are designing a mechanism, weighing trade-offs, and the design keeps growing. Stop and run the `git show`. A fix grounded in shipped behaviour needs no trade-off analysis, because the trade-off was already decided by a release that worked.

   **Applies to plan files too:** every fix plan opens with a "SHIPPED BEHAVIOUR" section quoting the release with file and symbol, before any proposal. A plan without one is not ready to vet.

   **AND THE VET MUST BE TOLD TO CHECK IT INDEPENDENTLY.** Every vet prompt must include: *"Does this solution already exist in the previous release? Check `git show <release-tag>:<path>` yourself. Is the plan's account of shipped behaviour TRUE, is it quoting the function that actually owns the problem, and did the release solve this in a way the plan has not considered?"* An unchecked "SHIPPED BEHAVIOUR" section is an assertion by the author, which is exactly what adversarial review exists to test — and it caught one.

   - **Corollary 1 — quote the function that OWNS the problem**, not an adjacent one that merely mentions the same field. Grounding in the wrong shipped line is worse than not grounding at all, because it carries false authority.
   - **Corollary 2 — quote the SEQUENCE; do not paraphrase the intent.** Both grounding errors made while already following this rule were summaries that read as faithful and were not: "shipped cancelled first" was written when the real property was **unconditionality, not ordering**. A one-line summary of shipped behaviour is a hypothesis; the numbered order of operations is the evidence. Write the steps.
   - **Corollary 3 — the shipped release is a floor, not a ceiling.** Confirm what shipped actually GUARANTEED before citing it as authority; one cited function returned no confirmation, swallowed errors and logged success after a refusal. Restore the property shipped genuinely had; do not inherit its weaknesses or credit it with strengths it lacked.

**A2. WHEN A DESIGN SPIRALS, GO READ THE LAST SHIPPED RELEASE.** If a plan/spec needs repeated adversarial rounds — 3+ vet rounds still returning blockers, or each fix creating the next problem — **both models must stop and independently compare against the previous release tag**, and the vet prompt must say so. A design much more complicated than the shipped code carries a burden of proof: *what defect in the shipped behaviour justifies the complexity?* If nobody can name one, the complexity is speculative. Real case: an undo/drafts redesign consumed 15 vet rounds and escalated to a SQLite C-API enforcement substrate before anyone checked the release — where the mechanism at issue **did not exist at all** and the shipped path simply retired and recreated. State the release-behaviour comparison in the plan itself so the burden of proof is visible to every later reader.

**A3. SPOT COMPENSATING-MECHANISM DEVIATIONS EARLY — BEFORE WRITING THE CODE, NOT AFTER 10K LINES.** **The tell:** a mechanism whose PURPOSE is to restore, re-derive, or undo state that a **sibling path** destroyed eagerly. Every edge case of the destruction becomes an edge case of the restoration. **Ask BEFORE building:** *"what would this cost if the sibling simply didn't do that yet?"* If the honest answer is "this mechanism would not need to exist", the deviation is **the sibling's timing**, not the missing mechanism — fix the timing. The case that produced this rule grew a reservation CAS, a state pair, a derived identity, a five-field snapshot with new columns, tombstones and resource-ownership activation — roughly 10k lines and eight review rounds — to reconstruct a draft the send path had deleted while the send was merely *queued*. **When two halves of one operation disagree about timing, that disagreement IS the bug.** A3 fires at design time; A2 fires after you have already paid.

**A4. THE DIFF REVIEW MUST RUN ON THE EXACT COMMIT CANDIDATE — re-run it after every fix round.** A fix for review findings routinely grows the diff beyond what was reviewed, and the new surface is *unreviewed*. Real case: round 1 reviewed 7 files / +1045; fixing its 3 blockers grew it to 10 files / +1731 **including a brand-new schema migration the gate had never seen**. **Rule:** after each red-first logical round is green, create its own separate signed local commit so unrelated rounds cannot accumulate into an unreviewable pile; review that exact commit/range before counting a clean round. If review produces a fix, commit the fix separately, compare the new range against what the reviewer actually read, and re-run the gate. **Fix rounds are where NEW risk enters, not where risk is only removed.**

**A5. COMMIT BODIES NEED EXECUTIVE SUMMARIES — and one signed commit per green logical round.** The executive-summary requirement itself is the global `../CLAUDE.md` Git & Commit rule 5 (outcome, user-visible or invariant impact, verification performed, accepted limitations/follow-ups); it is not restated here. What is iOS-specific and additional: **exact-diff review runs against those isolated commits or ranges, never against a mixed working-tree pile** (that is A4's mechanism), and history compaction must preserve each logical unit's summary rather than replacing it with a subject-only squash commit.

**A6. DATABASE-PERFORMANCE AUDIT LENS (mandatory).** Every plan, exact-diff review, and full-range review that changes a database **query, transaction, schema, or index** must enumerate this lens and compare against both the parent and the shipped base: mechanically census changed query count and placement; prove bounded cardinality, index coverage with `EXPLAIN QUERY PLAN` **on the current schema**, and realistic row-count sensitivity; inspect N+1/full-scan/hot-path risk; account for async reader/writer transaction hold time and QoS/UI contention; and explicitly justify every migration or index addition. **A round is not CLEAN with a candidate-attributable unjustified hot-path scan, extra per-row query, longer blocking write, or measurable regression.** The round that introduced this lens caught an account-index history scan and an unnecessarily global `ANALYZE` before either reached a commit.

**A7. ASK "INSTANCE OR CLASS?" AND ENUMERATE THE CLASS MECHANICALLY** before fixing a named site. A defect confirmed at one call site is a lead, not a scope. Every audit-found bug also gets a test that proves the violated **system property** red on pre-fix behaviour (global Testing rule 12).

**A8. HARD CAP: at most FIVE plan-vet rounds before implementation.** One round = one frozen plan candidate submitted for independent review; parallel reviewers on that same exact candidate count as **one** round, not several. After the fifth round returns, freeze the plan permanently: fold every confirmed concrete finding into the implementation checklist, then implement with red-first invariant tests. Do not create a sixth plan version or request another plan-only vet. Resolve later uncertainty against actual code, failing tests, the shipped-release sequence, and exact-diff review — where findings are concrete and executable rather than another hypothetical-plan loop.

**A9. THE MAIN SESSION IS A SUPERVISOR — IT DOES NOT IMPLEMENT. This gets forgotten after every compaction; re-read it on resume.** Spec the change, delegate it, verify the result. Do NOT hand-edit source, fix a compile error inline, run a red-proof yourself, or "just quickly" restore something because delegating feels slower. Editing directly is how the coordinator's context fills with implementation detail and stops being able to coordinate at all. **The exceptions are narrow:** process/governance files (`CLAUDE.md`, `PLAN_*.md`, memory, skills), and reading code to VERIFY an agent's work.

   **Why the arrangement exists at all, and why it is repo-specific:** the iOS build needs the gitignored signing config, so an isolated worktree cannot build and pointing an external tool at the live tree would expose that file. Hence the external reviewer either **reviews**, or **emits a patch**, and a subagent — not the main session — applies, builds and red-proofs it. *(This precedence was left ambiguous once, with two live rules contradicting each other and nothing marking which won; the supervision clause wins.)*

   **Implementation subagents use a correctness-capable model at high reasoning.** Never trade away reasoning quality on concurrency, identity, durability, migrations, red-proofing, or release blockers merely to save tokens. A weaker agent once declared a red-proof complete on a **FALSE GREEN** — a method-level `-only-testing` filter selected ZERO tests and still exited 0 — while leaving deliberately inverted code in the tree.

   **Supervising means verifying, not trusting.** Read the landed code, not just the agent's report.

**A10. ONE SMALL CONFINED JOB PER AGENT — NEVER resume an agent across review rounds.** Implementation subagents get ONE narrow, self-contained task and then finish. Do not resume the same agent for round after round of review fixes: doing exactly that in this repo grew one agent from 192k → 436k → 622k → 691k → 932k tokens across six fix rounds until it WEDGED mid-edit, and recovery cost a full stall investigation; a fresh, narrowly-scoped agent for the same codebase used **76k**. **Continuity lives in the BRIEF, not in the agent's context.** Each round = a NEW agent whose brief states the current state, the exact change wanted, and the scope boundary ("touch only X", "do not refactor", "**if you find a bug, STOP and report — do not fix**"). A side benefit: a fresh agent re-reads the CURRENT code instead of trusting a stale memory of what it wrote earlier. Subagents never own the review loop, never decide design, and never chain their own follow-ups.

**A11. STALL DISCIPLINE — check agents every turn, and make agents check themselves.** Subagent stalls have been the single largest time sink in this repo's long sessions (three in one session; one went 76 minutes unnoticed). **Coordinator side — verify liveness EVERY turn while work is in flight**; do not wait for a completion notification to discover a stall. Check the transcript's mtime (silence beyond ~10 min with no build running = wedged), whether a build process is actually running, and the last completed build marker. An agent that is ACTIVE but making no tool calls is **wedged, not finished**. On any suspected stall: run the inversion sweep immediately (a mid-red-proof stall strands deliberately-sabotaged code that COMPILES), establish the tree's build state yourself rather than assuming, and nudge with an explicit poll-your-marker instruction. **Agent side — every implementation brief MUST include a self-stall clause:** never end your turn waiting for a build notification; poll your marker file in successive calls; if two consecutive polls show no progress, report that explicitly instead of going silent; and before ending any turn, state what is DONE / IN PROGRESS / NOT STARTED. A partial honest report is far more useful than silence.

- **Codex liveness is LOG GROWTH — measured across an interval — and nothing else.** Not `ps` (a wedged codex stays `S`/`SN` and alive), not CPU% (it idles at 0.0 between streamed chunks), and specifically **not the presence of `ERROR codex_models_manager::manager: failed to renew cache TTL: missing field 'base_instructions'`**. That error looks fatal and has twice coincided with a genuine wedge at a similar log size, which is exactly what makes it a trap: measured on the healthy 2026-08-13 gate run it appears **21 times**, first at line 2,204 of 29,184, with **92% of the entire log produced after it**. It is routine noise on a run that goes on to complete. The correct probe is two `stat -f %z` samples ~20 s apart: `delta > 0` ⇒ alive, full stop. Coincidence at a memorable byte count is not causation, and killing a healthy multi-hour review leg on that signal costs the whole round.
  - ⚠️ **Check the PID is yours before acting on any of this, and note that `pgrep -x` is NOT sufficient.** Name matching can include unrelated long-running tools, so it cannot distinguish the launched review from another process with the same executable name. Key both exit and liveness checks on the exact PID you launched (`ps -p <pid>`), and perform the **exit** check before treating a flat log as a wedge: completion and a stall both present as no further growth.

**A12. WHEN REPEATED ATTEMPTS AREN'T CONVERGING, ASK THE REVIEWER TO AUTHOR THE ARTIFACT — THEN THE COORDINATOR VERIFIES IT.** The default is the opposite: the reviewer gives **findings**, and the coordinator **re-authors**. That friction is a FEATURE, not a cost — re-authoring forces the coordinator to re-think the problem instead of transcribing a conclusion, which is where recognising that an enumerated fix needs to become a closure invariant, settling "either/or" design choices, and spotting a defect pattern recurring across layers actually happens. Patch mode short-circuits exactly that, making the coordinator an applier rather than the owner of the design. Always-patch was tried and reversed the same day.

   **Trigger for the swap:** the same artifact has taken ~3+ gate rounds without converging **and** each round's findings are landing on the re-authoring rather than on the underlying design. Symptom: the verdicts keep changing shape (too big → underspecified → wrong premise) instead of shrinking. **Then swap, then swap back.**

   **Audit-FIX work is the standing exception.** For a CONFIRMED finding with a file:line and a failing scenario there is no abstraction worth preserving, translation loss is a measured cost (six consecutive spec rounds failed their gate, each round's findings landing on the restatement rather than the design), and both models must converge anyway. **The verification burden moves; it does not disappear:** the author emits a complete unified diff plus its tests under a read-only sandbox; the coordinator **greps every symbol the patch names** and checks every premise against real code and the shipped release, rejecting anything unproven (a prior subagent invented a function complete with a precise file:line citation); a fresh implementation subagent applies, builds, red-proofs and runs the required suite; and **the other model still reviews the result.** Authoring a patch never makes a model its own reviewer.

**A13. NEVER point an external reviewer at secret-bearing files** — `Secrets.xcconfig`, `*.env*`, `*.dev.vars*`, private keys. This is the PRIME DIRECTIVE in the global `../CLAUDE.md` and it overrides every rule above. `tabmail-ios` is a **public** repo, so app-source egress for review is acceptable; the signing config is not app source.

**A14. A REVIEWER THAT REFUSES DID NOT REVIEW — the leg is ABSENT, and the round is simply a one-model round.** (Owner, 2026-08-12.) Codex over-refuses on security-adjacent code — auth, crypto, parsing untrusted input, anything that pattern-matches as offensive security — and answers with `ERROR: This content was flagged for possible cybersecurity risk`. **A refusal is not a finding and not a clean pass.** Never report "Codex flagged a security problem" when Codex actually declined; never count the leg as clean; never let it block the gate.

- **Detection — the shell status LIES.** Codex **exits 0 when it refuses**, and it may refuse *after* doing substantial real work (measured: 107k tokens and a full probe run before the refusal, on the round-10 attachment-filename candidate). Check on **every** codex run before reading the output as a verdict; a refusal can also appear mid-log rather than at the tail.
  - **Use the ANCHORED predicate: `grep -c '^ERROR: This content was flagged' <log>`.**
  - ⛔ **The bare-phrase form is DEFECTIVE, and self-referentially so.** This rule names a literal string, and writing the rule down puts that string into the corpus the rule searches: `CLAUDE.md` documents it, every codex run reads `CLAUDE.md`, so a bare `grep -c 'flagged for possible cybersecurity'` scores ≥2 on a **perfectly healthy** run. Measured 2026-08-12: one healthy run scored 2 on the bare phrase with zero real refusals, while a genuinely refused run also scored 2 — same number, opposite meaning. **Generalisation worth carrying beyond this rule: when a rule keys on a literal string, anchor the match or search a corpus the rule cannot enter.**
  - **Instruct codex to PRINT ITS FULL REPORT AS ITS FINAL MESSAGE, and plan to recover it from the log.** A refusal can land *after* the work is complete and block only that final message, leaving a large log and no verdict — so the log is the artifact you design around, and a file write is a bonus, never the plan.
    - ⛔ **This bullet said the opposite until 2026-08-13 — "have codex WRITE ITS REPORT TO A FILE … a `-s read-only` run can still write to the scratchpad" — and that is FALSE.** `--sandbox read-only` blocks **every** write, including to the scratchpad; it is not a workspace restriction. With `approval: never` there is no escalation, so the write fails with `patch rejected: writing is blocked by read-only sandbox`. **Codex has never once written its report file.** The false claim cited recovered runs as having done so, which cost five rounds of treating a deterministic refusal as a flake. One run's own log said *"the target remains absent"*, and the recovered report's mtime postdated the log's last write — the supervisor had written it by hand while recovering. Giving codex a writable dir means `--sandbox workspace-write`, which also lets it write to the repos — acceptable only against a disposable worktree, never the primary checkout.
    - **The generalisation, which is why this is recorded rather than just corrected:** the recipe cited *its own past runs* as evidence, and no one re-checked whether those runs had actually produced the artifact. A procedure that reports its own success is a claim, not a measurement — verify the artifact exists (`ls -la`, and compare mtimes against the log's last write) before writing "this worked" into a recipe.
- **Response — reframe once, then drop it.** Re-run a single time with defensive framing: state that it is a review of the owner's own public repository, requested by the owner, to confirm that a defensive routine handles malformed input correctly; replace "attack"/"adversarial"/"attacker-controlled" with "correctness questions"/"untrusted (network-sourced)"; and explicitly disclaim exploit-payload construction ("describe any input class that would break a stated guarantee — do not construct payloads"). The `ask-gpt` skill documents this reframe. **If it refuses again, drop the leg and move on** — do not keep re-rolling, and do not rewrite the review scope to appease it, because a scope narrowed to clear a refusal no longer reviews what the gate is buying.
- **Gate arithmetic — this is the point of the rule.** A refused leg degrades the round from two-model to one-model; it does **not** invalidate the round and does **not** reset the counter. So under the global `../CLAUDE.md` final-gate rule: **Claude clean + Codex refused, twice consecutively on the same unchanged commit, SATISFIES the gate**, exactly as two same-model clean rounds do. Any *fix* still resets the counter to zero — a refusal is not a fix.
- **Why it is safe to proceed on one model here:** the missing property is *independence*, and the substitute for it is already specified — a second consecutive clean round on an unchanged candidate. A refusal costs independence, not rigour, and the existing one-model rule already prices that. What would NOT be safe is counting the refused leg as a pass, which is why it is recorded as absent rather than clean.
- Related standing facts: Codex's mechanisms are reliable but its **severity classifications are not** (one train returned 8/8 "BLOCKING", 0 of which held), and it will report the *held* side of a two-sided invariant as a defect. Judge its findings on mechanism, never on its severity label.
