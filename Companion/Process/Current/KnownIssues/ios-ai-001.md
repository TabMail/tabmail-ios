## Full detail

Arm 6 of the AI result write-through admission admits an UNSTAMPED but unreplaced row on the strength of its RFC Message-ID being unchanged (`unstampedButUnreplacedRowStillWritesThrough`). **One reviewer's position:** a *different* physical message can carry a duplicate RFC Message-ID — aliases and list rewriters make this reachable — so the row occupying that PK may be a REPLACEMENT that satisfies arm 6, and an AI summary computed for X then lands on Y. That is wrong-message content. **The other reviewer's position, and the coordinator's adjudication:** this is not a candidate regression and not a stop condition, because it reduces to a duplicate-RFC collapse this repository already ACCEPTS and actively depends on — FTS keying, body storage and `MessageIdentity.contentKey` all treat one RFC identity as one content. If a duplicate RFC is unacceptable for an AI summary it is equally unacceptable for the stored body the summary describes, and that is a pre-existing design question about the content-key scheme (see `PROJECT_MEMORY`'s "TWO keying schemes on purpose": actions key by provider id to distinguish copies, content keys by RFC because the content is the same). Recorded here so a later reader finds the disagreement rather than re-deriving it. **Do not close this by narrowing arm 6 alone** — that would leave the same premise load-bearing everywhere else.

✅ **CLOSED AS A DECISION (2026-08-04) — arm 6 stays exactly as written, and the reason is STRUCTURAL rather than a judgement call between two reviewers.** **The decision:** an AI write-back may be admitted on RFC 822 Message-ID equality alone, because **in this codebase one RFC identity IS one content**. **The basis is in the tree, not in principle:** `MessageAICache.key` is `"{accountId}:{folderPath}:{rfc822MessageId}"`, FTS records key by `ContentKey(rawValue: header.id)` with body text stored under one RFC identity, and `MessageBody` is keyed by `ContentKey`. Body storage, FTS and AI therefore collapse a duplicate RFC identity **identically**. For an admitted summary to describe content the user is not shown, body storage and the AI cache would have to disagree about which physical message occupies an RFC identity — **and they cannot, because they consult the same key**. A path that writes a body under one content key and an AI result under another for the same header was searched for and **none exists**. **That settles the reviewers' disagreement rather than splitting it:** the hazard the first reviewer named (two physically distinct messages sharing a Message-ID via aliases or list rewriters) is real, but its consequence is not the one claimed. **Accepted cost:** where two distinct messages do share a Message-ID, they share one stored body, one FTS record and one AI summary — the summary is correct for the body the user is actually shown, and wrong only about which of the two collapsed messages authored it. **Why that cost is acceptable:** it is not C3. C3 misattribution requires derived content presented against a message whose OWN content differs, and the shared content key forecloses exactly that. **The instruction above stands and is now the operative reason, not a caveat:** narrowing arm 6 alone would leave the same premise load-bearing in body storage, FTS and threading while making AI the one inconsistent consumer — a worse state than either answer. The governing design is `PROJECT_MEMORY`'s *"TWO keying schemes on purpose"* (actions key by provider id to distinguish copies; content keys by RFC because the content is the same) and ADR-IOS-068. **The same premise governs `IOS-BACKFILL-002`**, and if it is ever revisited both must move together.

📌 **BASIS CORRECTED (2026-08-05) — THE ROW'S STRUCTURAL PREMISE WAS FALSE, AND THE ACCEPTED COST WAS STATED BACKWARDS. THE DECISION ITSELF IS UNCHANGED.** The 2026-08-04 text above is preserved verbatim as superseded history; everything from here governs. **The premise that is false:** *"they cannot [disagree], because they consult the same key."* They do not consult the same key. Verified at HEAD: `MessageAICache` is keyed by `MessageIdentity.aiCacheKey` = `"{accountId}:{folderPath}:{rfc822MessageId}"` — **RFC identity**; `MessageBody.id` is a `ContentKey` minted by `ContentKey.forHeader`, which carries the banner *"⚑ INERT AS OF STAGE B — this returns `messageHeader.id` verbatim"* and therefore yields `MessageIdentity.headerId` = `"{accountId}:{folderPath}:{providerMessageId}"` — the **provider address**; and FTS keys the same way, which **this row already said in its own words** (*"FTS records key by `ContentKey(rawValue: header.id)`"*) immediately before concluding the opposite. `MessageIdentity.contentKey`, the RFC-aware mint the original argument depends on, has **NO production call site** — every non-definition hit in the tree is a comment or a test, and `ContentKeyByteIdentityTests` describes itself as the suite that *"will go RED"* when the swap lands, which is direct evidence it has not. So the AI cache collapses by RFC while body and FTS collapse by provider address; `ContentKey.forHeader` stays inert pending **Stage E1**. **The accepted cost, restated the right way round:** two distinct messages sharing a Message-ID at DIFFERENT provider addresses keep **different** stored bodies and **different** FTS records while sharing **one** RFC-keyed AI cache row — so the summary the user is shown can describe the *other* message. That is the inverse of *"one stored body … the summary is correct for the body the user is actually shown"*. **The decision does not change, and neither does the standing instruction.** This is **not candidate-introduced**: shipped `v1.6.38` had the same two keyings **and no identity recheck at all** at the AI write-back, so HEAD is strictly safer on this axis. And *"Do not close this by narrowing arm 6 alone"* remains right for exactly the reason it gives — the divergence is between two key SPACES, so narrowing the one consumer that notices leaves the same divergence load-bearing everywhere else. Closing it properly is Stage E1's job, not arm 6's. **`IOS-BACKFILL-002` shares this premise by this row's own statement and was corrected in the same edit.**
