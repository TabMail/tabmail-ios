## Full detail

**THE FIX.** `ComposeAttachmentCarryGate` counts every original-attachment fetch and releases waiters only when the whole concurrent batch settles. Send visibly becomes “Preparing attachments…” while work is outstanding; explicit Save and every alternate Send entry wait at the same authoritative boundary; compose-agent admission is disabled until a complete snapshot is available. A fetch failure blocks all three producers until the aggregate failure alert is acknowledged, so a failure landing during an already-waiting action cannot dismiss or send a partial set. `DynamicIslandChat.autoSaveDraft` then reads the live post-boundary attachment binding, copy-on-write stages it, and makes both its first-save and update branches adopt that directory; a losing generation deletes only its own staging directory. Focused red evidence covered all three producers, early-release, and first-save adoption; the implementation candidate passed 71 compose/draft/attachment tests. No provider identity or fetch authority changed.

**HISTORICAL DEFECT MECHANISM (retained).** `prepopulate` kicks off `carryForwardAttachments`, which spawns unstructured Tasks and returns immediately; chips appear in the attachment list as each download lands. Nothing gates the Send button on that work being finished, and `send` snapshots the live `attachments` array into both `DraftMessage` and `AuthoredSendSnapshot` before its first suspension. So a Send tapped while fetches are still in flight commits whatever prefix has arrived — possibly zero — and the outbox owns that snapshot. `saveDraftAndDismiss` has the same hole, and `DynamicIslandChat.autoSaveDraft`'s first-save branch creates a draft with no `attachmentsDirName` at all; on reopen, `loadDraftOrPrepopulate` finds the row and does NOT re-run `carryForwardAttachments`, so a truncated set is indistinguishable from a message that never had attachments.

**WHY IT IS REGISTERED HERE RATHER THAN FIXED IN THIS CHANGE.** It is **not** introduced by the body/attachment address gate — shipped `v1.6.38` spawns the same unstructured per-attachment Tasks with the same unguarded Send, so the race is identical there. The gate's first cut *did* make it materially worse by serializing the loop (turning an ~N/10 makespan into ~N on Gmail/Outlook and widening the window several-fold); that regression was found in the same audit round and reverted. ⚠️ **The window is NOT byte-for-byte the shipped one, and saying so was an overclaim** (caught in a later round): every fetch now passes through `attachmentFetchIsBlockedByPendingAddress` first, which awaits a `dbPool.read`, so each attachment carries one extra suspension point that shipped `v1.6.38` does not have. ⚠️ **The replacement characterization was ALSO an overclaim and was corrected a second time.** Calling it "a point read on a warm pool — microseconds to low milliseconds" reads the query and ignores the wrapper: `dbPool` is `PrioritizedDatabase`, whose async `read` awaits `NSEDataBridge.mergeIfStagingPending()` BEFORE the query, and that contract records a measured 7.6-second cold-I/O case. The common case really is warm — `loadDraftOrPrepopulate` has just read through the same wrapper — so the honest statement is **usually negligible against the network round trip it precedes, with a rare merge-bound tail** if a notification stages mail between that draft read and the per-attachment guard. Either way it is nothing like the several-fold serialization regression. The point of stating it twice is that a *reachability* claim is load-bearing in both directions, so "negligible" has to be earned per suspension point rather than assumed from the SQL. Stated precisely rather than as "identical" because a reachability claim is load-bearing in both directions. What remains is a pre-existing compose-subsystem defect whose fix — gating Send and the save/auto-save paths on carry completion, or persisting an expected-attachment count so a reopen can resume the carry — is a change to outbound send semantics with its own review surface. Landing it inside a release scoped to the wrong-body defect would put an unreviewed change to the send path in a shipped-bound candidate.

**WHAT THE GATE'S CHANGE DID IMPROVE — STATED WITH ITS TIMING, WHICH IS NOT "IMMEDIATELY".** A carry-forward failure that the user is still present for is no longer silent: `CarryForwardFailureAlert` names every file that failed and gives cause-specific advice. ⚠️ **This paragraph claimed the alert appears "within one run loop turn … almost immediately" and that "failures that land before the user sends are no longer silent"; both were too strong and were corrected by a later round.** Publication is deliberately deferred to a completion boundary — `carryForwardOutstanding` counts the batch down and only the last task to settle assigns `carryForwardFailures` — so ONE alert lists the whole batch instead of N alerts racing each other, at the price of waiting for the slowest sibling. And "one run loop turn" was never true: each fetch now awaits `attachmentFetchIsBlockedByPendingAddress`, itself an awaited `dbPool.read`, so even the deterministic all-refused mid-move case spans multiple suspensions. What is true: the mid-move case fails on local reads rather than the network, so it settles fast; a batch containing a slow network sibling holds the alert until that sibling finishes or times out (HTTP has a 300s resource ceiling, IMAP commands time out at the command level); and a send or save issued before the boundary is reached is still silent, which is exactly what this row covers.

**RECOVERABILITY — THE NON-RECOVERING CASE, NAMED.** Not recoverable. Once the send is admitted the recipient has an incomplete message and no local state records what was missing; once a truncated draft is saved, no marker distinguishes it from a complete one. This belongs to the dropped-user-intention class, which is why it is filed as an OPEN DEFECT rather than an accepted limitation. Reachability is bounded by how fast the user taps Send relative to the attachment downloads — small for one small attachment on a fast link, materially larger for several large ones.

**WHAT WOULD CLOSE THIS ROW:** gating Send / save / auto-save on carry completion (with a visible "preparing attachments" state), or persisting the original's expected attachment count so a reopened forward can detect the shortfall and resume the carry. Either is its own change with its own review.
