## Full detail

**The backfill's UID-remap re-key resolves an RFC-duplicate multi-hit by taking the highest UID, which is a guess, not proof.** `confirmGoneAtThreshold` (`TabMail/Services/Sync/BackfillBodyQueue.swift:864`) probes by `rfc822MessageId`; if the stored UID is absent but the search returns others it picks `uids.max`, commented *"the highest UID is the newest copy"*. That is sound for a genuine remap of one message, but when **two distinct messages share a Message-ID** in the same folder — the exact `IOS-IMAP-002` scenario D4 exists to forbid — the local header re-keys onto the **wrong copy** and then fetches that copy's body under this header's identity, carrying the original's derived AI state onto it. **Why this is NOT the D4 violation B1 fixed, stated precisely:** the address produced here is a **local** header address for a body *fetch*, never a wire mutation target — no `STORE`, no `EXPUNGE`, no queued operation is authorized by it. D4 forbids search-derived **mutation** targets; this is a search-derived read address, which is why `currentUIDs` remains on the ADR's normative exempt list. **Why REGISTRABLE:** shipped behaviour (this re-key is the 2026-06-09 FTS body-loss fix, and removing the `MessageExistenceProbe` conformance would convert every backfill miss into deleting the user's local header — strictly worse); it requires duplicate Message-IDs in one folder; and it is recoverable, since a later full sync reconciles the folder's UIDs and a body refetch corrects the content. **Not adjudicated as clean — deliberately deferred to the final train** rather than fixed mid-round.

✅ **CLOSED AS A DECISION (2026-08-04) — a search-derived READ address is not a mutation address, and the rejected alternative deletes the user's header.** **The decision:** `BackfillBodyQueue.confirmGoneAtThreshold` keeps resolving an RFC-duplicate multi-hit by `uids.max`. Three grounds, in the order that decides it. **(a) D4-clean by KIND, not by care.** The address produced is a **local header address for a body FETCH** — never a `STORE`, an `EXPUNGE` or a queued-operation target — and ADR-IOS-068 keeps `currentUIDs` on its normative exempt list for exactly that reason. D4 forbids search-derived *mutation* targets, and this is not one; the distinction is the whole reason this looks like C3 and is not. **(b) The rejected alternative is strictly worse.** Removing the `MessageExistenceProbe` conformance converts every backfill miss into **DELETING the user's local header** — and this re-key IS the 2026-06-09 FTS body-loss fix, shipped in `v1.6.38`, so the heuristic is load-bearing shipped behaviour rather than an unexamined guess. **(c) No available field resolves the tie.** The population is duplicate Message-IDs *within one folder*, and this is the same conclusion `IOS-DRAFT-009` reached for the reply resolver, for the same reason: the fields that would separate two messages sharing a Message-ID are exactly the fields this path does not yet have. **Accepted cost:** with two distinct messages sharing a Message-ID in one folder, the local header re-keys onto the wrong copy and fetches that copy's body under this header's identity, carrying the original's derived AI state onto it — **misattribution of DERIVED content**, which is the same duplicate-RFC content-key premise `IOS-AI-001` records this repo as already accepting everywhere (body storage, FTS, `MessageAICache`). **If that premise is ever revisited, this row and `IOS-AI-001` must move together.** **Recoverability:** a later full sync reconciles the folder's UIDs and a body refetch corrects the content. **The state where that reconciliation cannot run was searched for** — it needs the folder to be reached by a sync pass, and per `IOS-EPOCH-001`'s round-8 correction on-demand navigation reaches any folder — **and none that is permanent was found**; the worst case is deferred until the user opens the folder.

📌 **PREMISE CORRECTED (2026-08-05), MOVING WITH `IOS-AI-001` AS THIS ROW REQUIRED. THE DECISION IS UNCHANGED.** The cited premise — *"the same duplicate-RFC content-key premise `IOS-AI-001` records this repo as already accepting everywhere (body storage, FTS, `MessageAICache`)"* — is preserved above as superseded history and is **FALSE at HEAD**: body storage and FTS collapse by the **provider address** (`ContentKey.forHeader` is `⚑ INERT AS OF STAGE B` and returns `messageHeader.id` verbatim), while `MessageAICache` collapses by **RFC identity** (`MessageIdentity.aiCacheKey`). See `IOS-AI-001`'s *BASIS CORRECTED (2026-08-05)* for the full derivation. **What that changes here, and what it does not.** It does **not** change the decision, the D4-clean-by-KIND ground (a), the strictly-worse-alternative ground (b), or the no-available-field ground (c) — none of them depends on how the content stores are keyed. It changes only the **shape of the accepted cost**: when `confirmGoneAtThreshold` re-keys a header onto the wrong RFC-duplicate copy, the misattributed derived content is the **address-keyed body and FTS record** that ride along with the re-keyed header id, and separately the **RFC-keyed AI cache row**, which was already shared between the two copies before the re-key. Both remain corrected by the same later full sync + body refetch this row already names.
