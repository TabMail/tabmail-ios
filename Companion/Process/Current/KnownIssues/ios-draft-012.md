## Full detail

**What can still be lost:** a `DraftSessionRegistry.register` that lands **between** `evictImpl`'s final generation read (the last statement inside its write transaction) and the transaction's own commit is still invisible to the sweep, so that compose's draft row, its authored compose chat turns and its attachment directory are deleted. **Why it is not closed:** closing it requires holding a lock across a DB write, which the resilience rules forbid, or a durable table/column, which the owner's standing cheap-migrations requirement forbids. **Reachability, stated honestly:** it requires (a) more drafts than the eviction cap, (b) the user opening a compose for a draft that is beyond the cap, and (c) that open landing inside the commit instant itself — microseconds of straight-line code, not the whole sweep. **What the fix did change:** the exposure was `[pre-transaction snapshot .. commit]` before round 2, `[this row's own live check .. commit]` after round 2, and is now `[final generation read .. commit]`. The justification previously written at the site — *"the compose holds the draft in memory and its next save re-inserts the row"* — was **FALSE and is retracted**: `ComposeView` calls `register(draftId)` **before** its asynchronous `loadDraftOrPrepopulate()`, so the compose that loses the race is one that is still OPENING and holds nothing to re-save.

Do **not** close it with a lock held across a DB write (forbidden by the resilience rules) or with a durable claim column (forbidden by the owner's standing cheap-migrations requirement). **Do not implement this direction off the back of this paragraph.**

**⚑ PRODUCER INTERACTION ADDED 2026-08-06 (round-11 R11-L) — recorded so the next round does not re-derive it. There is NO code change here and none is proposed.** `DraftStore.evictImpl` has exactly TWO exemptions — a draft with an active `DraftSessionRegistry` session, and a reply/forward whose original is still in the inbox (resolved by primary key, then by `rfc822MessageId`) — and **none for a draft that has a queued `.saveDraft` `PendingOperation`**. So the cap can evict the `draft` ROW out from under a durable Save intention that is still in the queue. **What then happens to the op is the part worth writing down:** the next drain calls `DraftStore.pushDraftToServer`, whose entry guard fails at `load(id:)` — the row is gone — and returns `.notApplied`; `AccountManagerQueue`'s `.saveDraft` arm treats **every** returned disposition as a retirement (its own comment: *"EVERY DISPOSITION THAT REACHES THIS LINE IS A RETIREMENT"*), so the op leaves the queue through the GENERIC SUCCESS ARM on a purely LOCAL row-state test, having never contacted the provider. **This is not a second defect on top of the eviction; it is the same one, seen from the queue.** The content loss is already adjudicated by this row — the cap destroys the draft, that is shipped, deliberate behaviour — and once the row is destroyed there is nothing left for the op to push, so retiring it is the only coherent outcome; keeping it queued would wedge the lane on work that can never complete. **The reason to record it anyway:** read from the queue side alone, `.notApplied` on a `.saveDraft` looks like exit 3 (a newer generation won the CAS) when in this path it is really "the producer's subject no longer exists", and an auditor who finds it without this note will file it as a never-drop violation. Shipped `07a4bb703` has the identical structure. **What would make it actionable:** the eviction cap gaining a queued-op exemption (then the two mechanisms would genuinely disagree), or `.notApplied` ever being reachable on a draft whose row still EXISTS and whose intention has not been superseded.
