## Full detail

**What the user observes:** on an IMAP or iCloud account, a gesture made against a brand-new folder *during that folder's very first sync* appears to do nothing — the message does not animate away, the flag does not stick, and no error is shown. Repeating the gesture once the folder has finished its first sync works normally. **Why:** a durable IMAP action is refused when the target folder's `Folder.lastKnownUidValidity` is nil, because `MessageHeader.stableId` falls back to a bare numeric UID for any header lacking an `rfc822MessageId` and `IMAPProvider.resolveUID` treats a numeric id as a literal UID — executing that under an unknown epoch risks mutating a DIFFERENT message (constraint C3). Failing closed is always acceptable; mutating the wrong message is not. The refusal is a **silent no-op** by owner decision §9 D6(a) — no dialog, no toast. **The bound:** T1.2b (`7c71f6c7b`) persists the epoch from the `Mailbox.Selection` of SELECTs the sync and folder-open paths already perform, and `OK [UIDVALIDITY n]` is core IMAP4rev1 rather than a UIDPLUS extension, so every server reports it on SELECT even when it never answers a UIDVALIDITY STATUS. Audit round 7 closed a hole in that bound: a **custom NON-FAVOURITE folder** is excluded from `syncableFolders`, so no *scheduled* pass (full sync, delta sync, self-heal) ever SELECTs it, while `runBackfill` crawls it and makes its mail account-wide searchable — on a non-UIDPLUS server its epoch stayed nil and every gesture on it was refused. ⚠ **Round 7 called that refusal PERMANENT and a "brick"; round 8 RETRACTS the absolute.** On-demand navigation reaches ANY folder: `InboxView.onAppear` → `InboxViewModel.startSync()` → `performSync()` → `AccountManager.syncFolders(_:)` (`AccountManagerFetch.swift`, filtering on `!folder.path.isEmpty` alone — no role, no favourite predicate) → `SyncEngine.syncFolderMessages` → `syncMessages` → `runSyncMessages`, which carries the T1.2b SELECT-sourced bootstrap; `SyncEngineFullSync.swift` states it three lines under the `syncableFolders` construction (*"Custom non-favorited folders sync on-demand when the user navigates to them"*). The refusal was therefore **indefinite until the user opens that folder**, not permanent — still a real bug for mail reachable only through account-wide search in a folder the user never opens, which is why the crawl-sourced bootstrap stays. **Round 8 also replaced the VALUE that bootstrap writes.** Round 7 took ONE post-walk sample of `IMAPProvider.lastObservedUidValidity`, and the walk's own SELECTs were raw, so the mirror held the epoch observed when the pinned connection was CREATED and tracked no turnover during the crawl — on a resumed crawl it could be an epoch the mailbox rolled to AFTER an earlier pass's headers were written, and since this guard tests only for nil it then ADMITTED bare-UID gestures that resolved against a different message (C3). The crawl's three SELECTs (`getUidNext`, `searchExistingUIDs(folder:from:to:)`, `fetchMessageHeaders(folder:uids:…)`) now route through `IMAPProvider.selectMailboxTracked`; the walk captures its epoch ONCE at walk start, refuses (never confirms) any chunk whose own SELECT disagrees, and stamps through `SyncEngine.bootstrapCrawledFolderUidValidity`, which is **bootstrap-only AND gated on the folder holding no local header yet** — evaluated inside the write transaction, so the epoch it asserts is the epoch of every UID it unlocks. A folder that already holds rows of unproven epoch is NOT stamped: v3 has not ported ADR-IOS-061's purge-and-resync reaction, so failing closed there is the only C3-safe answer (C6).
