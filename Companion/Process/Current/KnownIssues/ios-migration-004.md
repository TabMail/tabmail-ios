## Full detail

**The lever.** `v70_dropMessageBodyHeaderFK`'s `DROP TABLE messageBody` is super-linear and was measured as one of the three residual body costs past ~200k headers (`IOS-MIGRATION-002`). The obvious follow-up is to stop dropping: rename the table aside as a relic and let a later background pass remove it, moving the cost off the launch path. **It was measured before being adopted, and it is WRONG — by a factor of two, in the wrong direction.**

**How it was measured, without editing an immutable migration.** Data Integrity rule 5 freezes `v70`, so the counterfactual could not be produced by changing it. Instead a throwaway harness built the relic's *post-state directly in the fixture* and ran the real `AppDatabase.runMigrations` over both, under `MigrationTimingGate.forcedForTesting` for per-migration `bodyMs` / `postBodyMs` attribution. Fixture: **200k headers + 120k bodies × 14,700 bytes**, seeded at `v67`. **BASELINE** = rows present in `messageBody`, `v70` drops it as shipped. **RELIC** = `messageBody` empty and a `messageBody_v70_dead` table carrying the FK the drop exists to remove (`id TEXT PRIMARY KEY REFERENCES messageHeader(id) ON DELETE CASCADE`). The two fixtures are the same size to within 12 KB (2,092,392,448 vs 2,092,404,736 bytes), and the post-state was confirmed per run (relic table present: 0 baseline / 1 relic).

**The measurement, two runs.** Whole-chain wall: **3,257.9 ms → 6,546.0 ms** (2.01× worse) and **3,339.7 ms → 6,626.4 ms** (1.98× worse).

**The mechanism, which is the transferable part.** The lever does exactly what it promises at `v70` — that body goes **2,876 / 2,951 ms → 0 ms**. It then loses far more, twice, somewhere else: `v71` `postBodyMs` **286 / 303 ms → 3,092 / 3,173 ms**, and `v82` `postBodyMs` **19 / 17 ms → 3,154 / 3,156 ms**. Both are `foreignKeyChecks: .deferred`, so GRDB runs a trailing **whole-database** `PRAGMA foreign_key_check` inside each — and a relic that still *declares* an FK is walked by **both** gates, on the same launch, at 120k FK-bearing rows apiece. **Keeping a table to avoid dropping it means paying to validate it once per deferred gate downstream.** `v70` is not merely a cleanup: dropping the table is what makes `v71`'s gate cheap, which is the whole reason `v71`'s gate sits where it does (see `IOS-MIGRATION-002` and `v71`'s own comment — its justification is POSITION).

**Why this is a decision and not a deferred task.** The lever was refused on evidence, and `IOS-MIGRATION-002` already records that *a lever refused without a durable artifact gets re-proposed*. No code changed; that is the correct outcome, not an unfinished one. **The non-recovering case, named per `MIS-IOS-008`:** none — nothing was built, so there is no mechanism that can fail. This row named its own expiry condition: *"The only way this conclusion goes stale is if **both** `v71` and `v82` stop being `.deferred`, which `IOS-MIGRATION-002` forbids for an independent reason."* ⚠️ **FULLY MET 2026-08-06 — BOTH `v71` and `v82` are now `.immediate`, and `IOS-MIGRATION-002` no longer forbids it** (see that row's superseded paragraph and the two registration comments: 12,083 ms and 7,228 ms of the owner's 27,601 ms device upgrade, guarding bodies of 1 ms and 7 ms). **This row's 2× figure is therefore about a chain that no longer exists and MUST NOT be quoted as current.** Its mechanism — *"keeping a table to avoid dropping it means paying to validate it once per deferred gate downstream"* — depended entirely on there being deferred gates downstream, and the `v68…v83` range now has none. What survives unchanged is the METHOD (build the counterfactual post-state in the fixture rather than editing an immutable migration, and measure before adopting) and the fact that the lever was refused on evidence. **If the relic lever is re-proposed, it must be RE-MEASURED against the current all-`.immediate` chain, not re-argued from these numbers.** ⚠️ Note what this does *not* imply: the relic is not thereby shown to be a good idea — it is shown to be **unmeasured** under the current chain, which is a different state from refuted. ⚠️ **Stated negatively (`MIS-019`):** this does **not** say relic tables are always slower. It says a relic **that declares a foreign key** is, in a chain with two downstream whole-database gates. A relic with its FK stripped at rename time was not measured and is not covered here — measure it before claiming it.
