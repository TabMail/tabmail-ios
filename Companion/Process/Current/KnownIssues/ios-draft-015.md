## Full detail

**What the fix changed, and why.** `DraftStore.pushDraftToServer`'s catch arm used to call `applyTerminalPushFailure` — stamping `serverPushStatus = "unconfirmed"` — and **return** `.terminalUnconfirmed`. A normal return is what `AccountManagerQueue.executeSingleOp`'s success path reads as completion, so it ran `PendingOperation.deleteOne` and **retired the user's Save intention after one provider throw** — an ordinary mobile network failure. Nothing re-enqueues on `serverPushStatus` (`IOS-DRAFT-011` says so outright), so only a later authored edit could mint a fresh producer. A thrown provider call is none of the four exits: it is an *unknown*, and `CLAUDE.md` clause 2 names a thrown read as retryable, never authoritative. Shipped `07a4bb703` awaited the throwing call directly, so the error reached the queue's retry arm and the op survived — the candidate was a **regression from shipped**. The fix restores the row to `"dirty"` (keeping the exact-ownership guard unchanged, so a losing racer still no-ops) and **rethrows**. Both halves are load-bearing: keeping the op queued while leaving the row `"unconfirmed"` would make every retry fall out of the entry guard with `.notApplied` forever — the **wedge corollary**, which is in the non-recoverable set.

**THE ACCEPTED RESIDUAL.** The two-generals case: an attempt that **actually committed on the server** before its response was lost. The retry still carries the pre-attempt `previousIdentity` (the push never reached `applyPushCompletion`, so `Draft.serverDraftId` was never advanced), so the old-copy delete addresses the identity from *before* the lost attempt and the copy that lost attempt created is not deleted. **One stray server draft per lost-response attempt.**

**Why it is accepted rather than mechanised.** This is the same accounting `IOS-DRAFT-011` already accepts for `.unaddressable`, for the same reason: the strays are **ordinary messages in the Drafts folder**, synced with real server UIDs by `SyncEngine`, so the ordinary message-delete path addresses them by their own synced UID and needs no `APPENDUID` and no new identity. The recovery gesture is the user deleting a stray by hand — one ordinary gesture — and the failure mode that would break that (a stray inheriting the refusal that created it) does not arise, because a lost *response* says nothing about the server's ability to report UIDs on a later FETCH/SELECT. Suppressing the residual would need a durable pre-attempt receipt or an RFC-keyed redrive — `v2final` recovery machinery this tree deliberately does not have, and which THE MANTRA forbids building for a rare recoverable edge. The standing ranking is stated three times over in this register — `IOS-IMAP-001`, `IOS-IMAP-006` ("duplicated mail is recoverable … preferred to both a dropped intention and a wedge") and Outbox Reliability Rule 4 ("Duplicate email >> lost email") — and a stray draft is the draft-side instance of exactly that ranking.

**Bound.** Unlike `IOS-DRAFT-011`'s K, this residual is bounded by the number of attempts whose response was lost *after the server committed*, not by the number of saves: a throw before the server acted leaves no stray at all, and a throw after it leaves at most one per such attempt. Durable actions retry without a cap, so the bound is the network's, not the queue's — but each retry that reaches the server and returns replaces rather than adds, because `applyPushCompletion` then advances `serverDraftId` and the next `priorIdentity` names the copy that exists.

The latter **replaces a blessing test** (MIS-014): `providerThrowThenAuthoredEdit` asserted `first == .terminalUnconfirmed` and `serverPushStatus == "unconfirmed"`, i.e. it asserted the never-drop violation was correct, so its premise was the defect and it was rewritten rather than repaired.
