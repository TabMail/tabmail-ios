That distinction matters: permanent growth would feed `StorageEstimator.totalSizeMB()` → `isOverBudget()` → `SyncEngine.runPruneIfOverBudget`, which deletes `MessageHeader` **rows** — a schema migration causing message pruning. It does not. **Reachability:** a device with under ~300 MB free cannot complete the migration, `AppDatabase` init throws, and the app sits at the "Updating…" splash — this app's documented boot-hang shape (see the `PLAN_HANG_FIX` note in `AppDatabase.swift`). **Recovery is one ordinary user gesture:** free space and relaunch. Nothing is corrupted; GRDB rolls the failed migration back and the chain resumes from the last committed identifier. **Why it is not "fixed":** both bodies are already single-pass; chunking either into committed batches would break the atomicity `v82`'s id rewrite depends on and would leave a database half-rewritten between batches, which is strictly worse. ⚠️ **Stated negatively (`MIS-019`):** this row does **not** say every migration needs 300 MB — the other 14 are `ALTER TABLE`/`CREATE INDEX` shapes with negligible WAL — and it does **not** license widening either body into a second full-table pass without re-measuring the peak.

**THE NON-RECOVERING CASE, NAMED (2026-08-05, `MIS-IOS-008`) — a different question from the `MIS-019` clause above, which bounds the CLAIM rather than the RECOVERY.** *"Free space and relaunch"* is a gesture only the **user** can perform, and the app cannot substitute for it on this path: the one mechanism that would free headroom (`StorageEstimator.totalSizeMB()` → `isOverBudget()` → `SyncEngine.runPruneIfOverBudget`) is reached from `SyncEngine`, i.e. only **after** the database is open, and `v82` fails before that. So the state where recovery does not fire is a device that cannot free ~300 MB by any action available to its owner: there the app sits at *"Updating…"* indefinitely, which is the mantra's **brick** shape. **Three facts keep it registrable rather than promoting it into the non-recoverable set.** (1) The failure is a precondition of the environment, not a defect in either body — both are already single-pass, and chunking `v82` into committed batches would leave the database half-rewritten between batches, which is strictly worse. (2) GRDB rolls the failed migration back, so nothing is corrupted and the chain resumes from the last committed identifier the moment headroom exists — the state is *blocked*, never *damaged*. (3) The precondition is transient by measurement, not by assumption: `v82` was 3,385.4 MB before and after, with the pages returning to the freelist. **What is NOT a recovery, said so that nobody offers it as one (`MIS-024`):** delete-and-reinstall clears the requirement by destroying the local database, taking local-only state with it — drafts, chat sessions and attachment working directories have no server copy to restore from. **A1 — NONEXISTENT:** `git show 07a4bb703:TabMail/Services/AppDatabase.swift | rg -c 'v81_|v82_'` → **0**. Both migrations are new work, so there is no shipped behaviour to compare against and the floor is silent here.
