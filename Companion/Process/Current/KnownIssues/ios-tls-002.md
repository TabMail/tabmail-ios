## Status

Accepted user-visible consequence of the TLS 1.2 floor; its stated REQUIREMENT was UNMET at the tip and is ✅ **FIXED by `b150f7ee6`**

## Subsystem and search terms

TLS 1.0; TLS 1.1; legacy IMAP server; self-hosted; connect failure; error message

## Full detail

A server that cannot negotiate TLS 1.2 no longer connects. This is a **minimum**, not a pin — any server supporting 1.2/1.3 is unaffected, and modern servers already negotiate 1.3. Affected servers are genuinely unsafe (a network attacker on a TLS 1.0 session can realistically reach mail credentials). Requirement: the failure must surface as a **clear, actionable error naming the TLS floor**, never a silent or generic connection failure.

✅ **FIXED by `b150f7ee6`, "Name the TLS floor when a server is refused for being below it". The requirement above was a REQUIREMENT, and it was UNMET at the tip** — no TLS-floor string existed anywhere in `TabMail/`, `Shared/` or the NSE, so both halves of the promise were broken: the user got `"The operation couldn't be completed. (NIOSSL.NIOSSLError error 0.)"`, which names nothing and suggests nothing while describing a PERMANENT condition no retry can clear, and on the send path `isTransientSendError` read the connection/TLS shape as transient, so a message addressed to a server that can never accept it stayed `.queued` indefinitely with none of the Retry/Discard agency Outbox Rules 7/9 promise. **The invariant that now holds:** a below-floor server produces `IMAPTransportSecurityError.tlsFloorNotMet(host:)` at both connect sites this provider owns (`createServer`'s IMAP connect and `send(draft:)`'s SMTP connect), rendering the same human sentence on both surfaces — it is `CustomStringConvertible` *and* `LocalizedError`, because `OutboxView` prints `errorMessage` (stored as `String(describing:)`) while the account-connect views render `userFacingDescription` — and `isTransientSendError` classifies it explicitly and FIRST, so the send stops silently retrying and the actionable message reaches the Outbox row.

🔎 **THE MATCHER IS DELIBERATELY ONE TOKEN WIDE, AND THAT IS THE FINDING — not an implementation shortcut.** The failure shapes were **measured**, against local `openssl s_server` endpoints, rather than guessed: a TLS 1.0-only server and a TLS 1.1-only server both yield `handshakeFailed(…sslError…TLSV1_ALERT_PROTOCOL_VERSION…)` — **and so does a TLS 1.3 server presenting an untrusted certificate**, arriving in the byte-identical `handshakeFailed(...sslError...)` wrapper and differing ONLY in the BoringSSL reason token (`CERTIFICATE_VERIFY_FAILED`). So the outer shape is not the discriminator: a `handshakeFailed`-or-error-domain matcher would have told a user whose certificate merely expired that **their server is too old**. `IMAPProvider.mapTransportSecurityFailure` therefore matches `TLSV1_ALERT_PROTOCOL_VERSION` and nothing else, in the rendered description rather than by importing NIOSSL so a re-wrapped rethrow still carries it — the technique `SyncEngine.isConnectionError` already uses for NIO's error families — and every unrecognised shape is returned **UNCHANGED**. Fail-to-generic is the deliberate direction: recognising too little leaves a send retrying, recognising too much labels a recoverable failure permanent and stops a send that would have gone through.

⚠️ **THE DELIBERATE NON-COVERAGE, STATED because an absolute needs its negative case (MIS-019):** a below-floor server that answers a version mismatch by returning a **lower ServerHello** instead of a `protocol_version` alert produces a different BoringSSL reason (`UNSUPPORTED_PROTOCOL`). **That case was not reproducible here, so it is NOT matched** and keeps its existing generic, retryable treatment rather than being matched on an unverified string. A user on such a server still gets the generic failure this row's requirement forbids. That is accepted: guessing the token would risk mapping something else onto the TLS-floor sentence, and this row's whole point is that the wrong confident message is worse than a vague one. Also accepted: the version named in the sentence tracks SwiftMail's `MailTLSMinimumVersion` default (`.tlsv12`), so if that default moves the sentence must move with it — a comment at the string says so.

**Amended 2026-11-27: a server that offers no encryption is named too.** With STARTTLS required on every port but 993 and 465 (`MailTransportPolicy`, see `IOS-TLS-001`), a server that does not offer it is refused by SwiftMail before the password is sent: IMAP `IMAPError.connectionFailed("Server did not advertise STARTTLS on port N")`, SMTP `SMTPError.tlsFailed("STARTTLS required but not advertised by server")`. Unmapped, the IMAP form reads as "Connection failed" (`SyncEngine.isConnectionError`, i.e. offline) and the SMTP form as a transient send error, so the row stayed `.queued` for good. `mapTransportSecurityFailure` now also recognises those two refusals (`IMAPProvider.isStartTLSNotOffered`: the exact library error case with its exact reason text, never the rendered description, so text a server sends can never be taken for this refusal) and returns `IMAPTransportSecurityError.noEncryptedConnection(host:port:encryptedPort:)`, whose sentence names the server, the refused port and the implicit-TLS port to try. It is permanent for the outbox (`error is IMAPTransportSecurityError`, the bounded three attempts, then Failed), is not read as offline, and is the password-update alert's line. The floor is still matched first. Both refusal kinds are typed first in `SyncEngine.isConnectionError` and `AccountManager.isTransientSendError`, so a server name that contains a network-error word cannot make either look offline or transient. The inbox banner shows one fixed line for both kinds (`InboxErrorBanner.encryptionMessage`: TabMail could not open an encrypted connection; check the server and port in Settings); the account setup and password-update alerts keep naming the server, the port and, for the floor, TLS 1.2.

⚠️ **Accepted limits of the amendment (each recovers by itself or with one refresh):** (1) a refusal raised when SwiftMail reopens a pooled connection by itself inside a command is not mapped, because the app's connect step (`IMAPProvider.createServer`, which every connection the app opens goes through, the change reader's included) is not on that stack: it reads as offline for that refresh, and the next fresh connection names it. The change reader's connection never reopens inside a command (`setReconnectsInsideCommands(false)`): it fails instead, and its next connection goes through `createServer`. Reaching this needs a server that offered encryption earlier in the session and stopped. (2) While a server refuses, the body readers and foreground IDLE keep retrying at their normal pace, as they do for any server that keeps failing; tracked as #1638. The backfill walk takes its connection backoff (5, 10, 20, 40, then 60 s) for either refusal, as for a server it cannot reach (`SyncEngine.runBackfillWalk`'s outer catch, pinned by `BackfillEncryptionRefusalTests`); before, a folder with no walk position was picked straight back with no wait. A walk worker whose range SEARCH is refused stops, as on a lost connection, and the folder is declined for the call; before, a folder with a walk position and no UIDVALIDITY stamp had every range below its position asked once, one refused connection each. (3) On SMTP STARTTLS ports the floor token is still read from the rendered error; the typed underlying error arrives with the SwiftMail change in the known gap below.

✅ **CLOSED 2026-11-28 (amendment below). Known gap, SMTP over STARTTLS:** SwiftMail wraps a failed STARTTLS upgrade as `SMTPError.tlsFailed("STARTTLS upgrade failed: \(error.localizedDescription)")`, and `NIOSSLError` has no localized description, so the `TLSV1_ALERT_PROTOCOL_VERSION` token is lost and a below-floor or bad-certificate server on an SMTP STARTTLS port (587, and since this amendment also 25 and 2525) stays a transient `.tlsFailed`: the send keeps retrying, with no strike and no sentence. Implicit TLS (465, 993) and IMAP STARTTLS (143) keep the token. The fix belongs in SwiftMail (keep the underlying error in that message), then a re-pin; it is not part of this amendment.

**Amended 2026-11-28: a failed SMTP STARTTLS upgrade keeps its cause, and only a failure that can clear stays queued.** Measured against SwiftMail's scripted server before the change: a server that accepts STARTTLS and then answers the ClientHello with a protocol_version alert, or with plain text, both reported `STARTTLS upgrade failed: SMTP connection failed: Command failed: … (NIOCore.ChannelError error 5.)`. The client sends its next EHLO without waiting for the handshake; NIOSSL reports the handshake's cause on the pipeline's error path and then closes the channel, so the EHLO only saw the closed channel. Interpolating the error (the fix the gap above proposed) would therefore have shown only the closed channel. The pinned fork now installs a small recorder right after the TLS handler (`TLSHandshakeErrorRecorder`, added before it because adding the TLS handler starts the handshake at once). Until the handshake completes it keeps the first error the channel reports, and a failed upgrade reports that error; after it completes nothing is recorded, so a server's own reply, such as a 421 followed by a close without a TLS close notification, stays the result: `STARTTLS upgrade failed: handshakeFailed(…TLSV1_ALERT_PROTOCOL_VERSION…)`. It adds no wait, no timeout and no reordering. The same fork change keeps errors as themselves in `Command failed: …`, and reads EHLO keywords in any case (`starttls`, `8bitmime`, `auth plain`; RFC 5321 section 4.1.1.1).

So on 587, 25 and 2525 a below-floor server now gets `tlsFloorNotMet`, through the existing token match: permanent, with the floor sentence. `AccountManager.isTransientSendError` judges any other failed upgrade whose cause came from the TLS layer exactly as the same error is judged on 465, where it arrives bare (`isTransientSTARTTLSFailure`, then `isTransientTransportText`). A certificate that does not verify, a plain-text answer, or a hang-up during the handshake therefore takes the three strikes and ends Failed with Retry/Discard and the generic text. A certificate failure gets no sentence of its own and no certificate token is matched (ruling 2026-11-27). The failures SwiftMail reports with one of its own SMTP errors after the prefix stay transient, as before: the server refusing STARTTLS (a 454 asks to try later), and the STARTTLS and EHLO timeouts. Every `SMTPError` renders starting with "SMTP ", and that is how the rule tells them apart. Accepted (ruling 2026-11-28): a handshake ended by an unclean shutdown, or by a wrong device clock, now costs strikes, as on 465; such a send never went out before either. Tests: SwiftMail `SMTPStartTLSFailureTests`; app `MailTransportEncryptionTests+STARTTLSFailures.swift` (end to end through the real Outbox drain and the pinned library, red on the old pin). Accepted limit (3) of the 2026-11-27 amendment is closed by this.
