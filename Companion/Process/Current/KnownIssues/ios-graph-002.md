## Full detail

**THE ADDRESS PROBLEM in the Graph id space, with the IMAP half fixed and the Graph half never enumerated.** `ExchangeProvider.moveMessage` is `let _ = try await request(path: "/messages/\(encodedId)/move", method: "POST", body: jsonData)` — Graph's `/move` returns the moved message **with its new `id`**, and the response is bound to `_`. `Prefer: IdType="ImmutableId"` appears **nowhere** in the tree (the only `Prefer:` header is `outlook.timezone` in `ExchangeCalendarProvider`), so the account runs on Graph's default mutable ids, which Microsoft documents as changing when an item moves between folders. Nothing re-learns the new id: `EmailProvider.move(ids:from:to:)` returns `Void`, `executeOperation`'s `.move` non-IMAP arm returns `ExecutedOperation.allMembers` (`provenDestinations: []`), and `MessageHeaderRekey.finishMove` early-returns on `guard … !destinations.isEmpty`. So the local row keeps the dead id, and `admittedOrdinaryActionTargets`' non-IMAP arm — `messages.filter { !$0.messageId.isEmpty }`, `nil` epoch — happily admits it into the **next** operation. **This is `59423bb7d` ("Finish the IMAP move locally using the COPYUID already in hand") applied to one coordinate system only.** That commit states the invariant outright — *"A move changes a message's address, the server reports the new one … and the drain threw it away"* — and Graph is the second address space where that sentence is true verbatim. Recorded as `MIS-006` instance 5 and `MIS-IOS-003`.

**THE LOSS.** The next op reaches the wire naming the dead id, Graph answers `404 ErrorItemNotFound`, `AuthedHTTP` surfaces it as `ProviderError.networkError(HTTPError.networkError(statusCode: 404))`, `isMessageNotFoundError` matches, and the single-message arm executes `PendingOperation.deleteOne` under the log *"Conflict: `\(opType)` — message not found, dropping"*. **A 404 is a fact about the ADDRESS, not about the WORK.** Three different world states produce it — the message was permanently deleted (the op is genuinely moot, exit 2); the message MOVED, by us or by Outlook desktop or by a server rule (the op is neither done nor inapplicable — it needs re-addressing); or Graph is transiently inconsistent right after a change, which Microsoft documents. The arm collapses all three. That is `MIS-IOS-004` — *"could not determine" read as "provider says done"* — and **the file already contains the correct precedent one screen away**: `isPermanentlyInvalidError`'s doc says *"🚨 A BARE STATUS CODE IS NOT A CLASSIFICATION … 'the request was rejected and we do not know why' is an absence of evidence"*, and its predecessor was deliberately narrowed for exactly this reason. **Exit 4 does not cover it either** — exit 4 needs a **proven** reset disagreeing with the op's **durable** `observedUidValidity`, which on Graph is always `nil`, and it is scoped to an address *space*, not one item's id.

**WHY THIS IS BLOCKING AND `IOS-QUEUE-006` IS NOT — the distinction is the signal, and it is the whole verdict.** `IOS-QUEUE-006` is registrable because *"the local mutation and the durable op are the same transaction … a non-admitted id gets no local mutation either … the message therefore stays visible where the user left it"*, so the user sees the failure and re-swipes. **Here the local mutation LANDS and is never rolled back.** The user swipes to Trash, the row animates away and is written to Trash locally, and then the durable half is silently destroyed. The UI shows success; the server shows the message still in Archive; nothing anywhere tells the user, the AI tool or the notification router that the gesture died. The mantra's recovery test allows *"one ordinary user gesture"* — but a user who has been shown success has no reason to make one.

**AND THE STATE THAT RESTORES THE SIGNAL IS DATE-WINDOWED, so it is not guaranteed to fire.** The only thing that re-addresses the row is a sync that materialises the message under its new id and sweeps the remnant. `SyncEngineFullSync.canonicalizeLocalRows` cannot do it — it selects on `Column("messageId") == messageId && Column("folderId") == folderId` and the churned id is by construction absent, with the RFC discriminator *"deliberately SUBTRACTED"*. `selectStaleHeaders`' `.date` arm (Exchange's `staleWindowMode`) is `candidates.filter { $0.date >= floorDate && !remoteIds.contains($0.messageId) }` with `floorDate = fetched.map(\.date).min()`, and Graph orders by `receivedDateTime` — so a message **older than the destination folder's newest-N window is neither re-fetched under its new id nor swept**, unless the fetch reports `coverage.spansEntireFolder`. Exchange delta covers only ONE folder: `SyncEngineDeltaSync` mints the cursor with `getCurrentDeltaLink(folderId: inboxFolder.path)`, so `exchangeDeltaSync`'s `toDelete` sweep repairs remnants for **moves out of Inbox** and for nothing else — and even then it is a **DELETION predicate downstream of the drop** (`MIS-024` instance 5): it restores the *message*, never the *gesture*. For an Archive→Trash or folder→folder move of older mail, the remnant persists, every repeat of the gesture enqueues the same dead id, 404s and is dropped identically — the mantra's Q1 answers **NO**, which is the definition of the non-recoverable set.

**REACHABILITY — ordinary use, no unusual server.** Any Outlook/Exchange account, any two gestures on one message before the destination folder syncs: offline triage drained together on reconnect; a swipe in Inbox followed by a swipe in Archive; an undo of a drained move (undo is a reverse move, so it names the same dead id); and the `IOS-QUEUE-008` lane split makes the two ops **concurrent**, so one of the pair races the other's churn regardless of user timing. **Gmail does NOT share this shape** — `GmailProvider.move` is `messages.modify` add/remove label, the resource id never changes, and a Gmail 404 therefore really does mean gone. IMAP does not share it either, and for a reason worth stating because it is the trap: the *same* root cause exists on IMAP but is **caught by a second guard** — `admittedOrdinaryActionTargets`' IMAP arm refuses a row whose `observedUidValidity` the optimistic move nil'd, so the dead address never reaches the wire (fail-CLOSED). The non-IMAP arm has no such gate, so the identical defect is fail-OPEN. A guard that makes a bug benign in one arm is not a guard the other arm has.

📋 **IMPLEMENTATION BRIEF — do not implement from this row; hand it to a fresh implementation agent.** **The invariant to encode:** *a durable action leaves the queue only on one of the four exits; a `404` naming an address the app itself invalidated is not exit 2* — and the way to satisfy it is **not** to reclassify the error but to **stop discarding the address the wire already gave us** (`MIS-IOS-003`, `CLAUDE.md` § THE ADDRESS PROBLEM). **Files/symbols:** `TabMail/Providers/ExchangeProvider.swift` — `moveMessage(id:destinationId:)` (decode the response's `id`) and a `move(ids:from:to:)` overload returning an outcome, mirrored on the shape `IMAPProvider.move(ids:from:to:admittedUidValidity:) -> MoveOutcome` already has; `TabMail/Services/Account/AccountManagerQueue.swift` — `executeOperation`'s `.move` case, which already type-tests `provider as? IMAPProvider` and needs the sibling `as? ExchangeProvider` arm so `ExecutedOperation.provenDestinations` is populated; `TabMail/Services/MessageHeaderRekey.swift` — `ProvenDestinationAddress` is IMAP-shaped (`destinationUid: UInt32`, `destinationUidValidity: UInt32`) and a Graph destination is a `String` id with **no** epoch, so the type needs a provider-neutral id and a nil-able epoch. **ADR-IOS-068 is satisfied, not strained:** the new key is the provider's own native id from the response to the mutation this op issued — attempt-correlated, no RFC consulted, no `SEARCH` result promoted to a mutation target. **Fail direction: leave the epoch stamp NIL for Graph.** `finishMove`'s G2 is already written for this — a nil `observedUidValidity` is `.retainedForRetry` (recoverable), a *positive* disagreement is `.terminalStale` (the only terminal arm), so stamping anything invented would terminally drop the next gesture, which is the mirror image of the bug. Graph has no epoch space; nil is correct and is also the safe value. 🚨 **MIRROR-IMAGE RISKS (`MIS-005`, ×4, and it CHAINS — name both in the fix's commit body).** **(1) Reclassifying the 404 as retryable WITHOUT re-keying converts a silent drop into a lane wedge.** The op would name the dead id forever, fail identically forever, and — with `buildLanes` keying on `accountId:folderPath:messageId` (`IOS-QUEUE-008`) and `IOS-QUEUE-003` item 4's starvation concern — block every later op that shares its lane. The wedge corollary says a starved op has not been preserved, so that "fix" trades one never-drop violation for another. The re-key is what makes retry *terminate*. **(2) `Prefer: IdType="ImmutableId"` is NOT a free win and must not be the first move.** It changes id format **account-wide**, so every value already minted under the mutable scheme becomes non-resolvable at once: `MessageHeader.messageId` and every `MessageIdentity.headerId` built from it, `PendingOperation.messageIds`, `MessageIdentity.aiCacheKey`, `nse_processed_message.id`, `MessageContentStore` content keys, and `Folder.path` (Graph mail-folder ids), plus the NSE's separate `Shared/API/GraphAPI` client, which would have to send the identical header or the two halves of the app would disagree about what a message id is. That is a one-way per-account migration plus a full re-sync, and Microsoft still documents the immutable id as changing on a move to an **archive mailbox** or an export/re-import — so it narrows the churn, it does not abolish it. Evaluate it as a follow-up on top of the re-key, never instead of it. **(3) Do not "fix" this by widening `isConfirmedGoneError` or by adding a Graph-specific retry cap** — a cap is a discard on a timer. **RED-FIRST TEST (global Testing rule 12 — pin the INVARIANT, not the mechanism).** The seam exists: `ExchangeProvider` takes an injectable `testSession` and `TabMailTests/Providers/ExchangeProviderMockTests.swift` drives it through the `FakeHTTP` `URLProtocol`. Script the fake Graph server to (i) answer `POST /messages/{old}/move` with `200` **and a body whose `id` is new**, and (ii) answer `404` to any later request naming `{old}`. Drive two queued gestures on one message (A→B, then B→C) through `drainPendingQueue`. **Assert the system property, not the re-key:** after both drains, either the wire received a move of that message to C, **or** a `PendingOperation` for it is still durably queued — never *"`pendingOperation` is empty and the server still has the message in B"*. Pre-fix that assertion is RED (zero rows, message in B). A test that asserts "the header was re-keyed to the new id" is a mechanism test and will stay green on a wrong spec (`MIS-015`). Add the symmetric non-vacuity leg: with the fake server returning the SAME id from `/move`, the same scenario must stay green (`feedback_non_vacuity_must_be_two_sided`).

✅ **CLOSED 2026-08-04 — the address is no longer discarded.** `ExchangeProvider.moveMessage` now decodes the `id` off Graph's `/move` response, and `moveProvingDestinations(ids:from:to:) -> MoveOutcome` carries it per member into `ExecutedOperation.provenDestinations` through the sibling `provider as? ExchangeProvider` arm in `executeOperation`'s `.move` case — **reusing `MessageHeaderRekey.finishMove`, not writing a second re-key.** `ProvenDestinationAddress` became provider-neutral (`sourceProviderId` / `destinationProviderId` as `String`, `destinationUidValidity` optional) and `MoveOutcome` moved out of `IMAPProvider` to sit beside it; the IMAP arm's guards are untouched and the values it writes are the same decimal UID strings as before. **The epoch is left NIL for Graph**, as this brief required — G2 gives a provider with no epoch space the same arm as an unknown epoch, because an invented stamp would be the *positive* disagreement that is `.terminalStale`. **When Graph's response names no id, nothing is substituted:** that member is returned in `provenIds` with no entry in `provenDestinations`, byte-for-byte IMAP's no-`COPYUID` shape, and the row keeps its old address rather than being re-keyed onto a guess. **A batch that fails partway returns its proven prefix**, routed through the existing `retirePartiallyCompletedOp` contract, rather than discarding an address the wire had already supplied — throwing would have re-created this same defect one mid-batch failure later; it rethrows only when nothing at all was proven, and rethrows `CancellationError` unconditionally. **Neither mirror-image trap was taken:** the 404 classification is untouched, so no lane wedge is introduced (the re-key is what makes retry *terminate*), and `Prefer: IdType="ImmutableId"` was NOT adopted. `IOS-GRAPH-003` is deliberately left open. **RED PROOF** — `TabMailTests/Services/FinishTheMoveLocallyGraphTests.swift`, with `moveMessage`'s re-learned id re-discarded inside the build lock: *"✘ Test "A second gesture on a just-moved Outlook message still reaches the server" recorded an issue … Expectation failed: (landed → false) || (stillQueued → false) ↳ the user's second gesture was DESTROYED: the server still has the message at ["graph-archive-folder"] and no PendingOperation survives to retry it"*, preceded on the wire by *"[Exchange] HTTP 404 POST …/messages/graph-1/move"*. The symmetric non-vacuity leg — *"Two gestures still work when the tenant's Graph ids survive a move"* — **passed in that same inverted run**, so the red is the churn and not the harness. ⚠ **What the tests deliberately do NOT exercise:** the destination `Folder` rows are omitted so `drainPendingQueue`'s post-drain sync is skipped, because that sync is a repair strictly downstream of the drop (`MIS-024`) and against a one-message fake server it would mask the defect entirely. The date-windowed reachability described above is therefore unchanged by this commit — the re-key is what makes that repair unnecessary, not a fix to it.

📌 **THE NO-ID ARM, ADJUDICATED (2026-08-04) — re-raised as a possible residual of this very fix, and the answer is that it must stay as written.** The observation: in `moveProvingDestinations`, `provenIds.append(id)` is UNCONDITIONAL while `provenDestinations.append` is conditional on a decodable `id`, so a 2xx whose body names none retires the op while contributing no destination address; the local row keeps the old provider id and a later gesture 404s. **The two appends answer two different questions, and only the second is unanswered here.** `provenIds` answers *"did the work happen?"* — settled by the 2xx alone, since `moveMessage` throws on any non-2xx, so reaching that line means Graph performed the move. `provenDestinations` answers *"where did it land?"* — settled only by a decodable id. Retiring the op is therefore **exit 1, provider success** — the first and most ordinary queue exit, not a discard. 🚨 **THIS IS NEVER A "WE COULD NOT DETERMINE" CASE, and that is the whole distinction from `MIS-IOS-004`: the SUCCESS is determined; only the new ADDRESS is unknown.** Conflating the two is what would make fail-closed look principled here. **Fail-closed is NOT available at the same cost; it is strictly worse, and it manufactures the very defect `cfe6720be` closed.** Withholding `provenIds` leaves a member queued whose work has ALREADY happened; its retry re-addresses the id Graph just invalidated and 404s into the `isMessageNotFoundError` arm, which deletes the `PendingOperation` — and here, unlike the second-gesture path `IOS-GRAPH-003` refutes, **the local header goes too**: a retry of the move op carries the op's own SOURCE `folderPath`, which is exactly the segment baked into the row's primary key, so `deleteConfirmedGoneHeader` matches and destroys the header, its `MessageBody` and its FTS row. That is `IOS-GRAPH-003` path (1) reached deliberately by a "fix". Changing the 404 classification as well does not rescue it — that is MIRROR-IMAGE TRAP 1's lane wedge, since the re-key is what makes a retry TERMINATE. **Attribution class: pre-existing-shape residual, NOT candidate-introduced, and a STRICT IMPROVEMENT** — at `07a4bb703` and `e28dd4edb` no destination was produced for ANY move, so this arm was 100% of moves; it is now the exception. **Reachability: not produced by Graph's documented contract at all** (`POST /messages/{id}/move` returns the moved message resource), so it needs a non-conforming gateway or proxy; and it is recoverable — the row keeps a valid old address, the destination folder's sync re-materialises the message, and one repeated gesture completes the work. **What DID change (`cfe6720be` follow-up):** the asymmetry is now stated at the append site instead of reading as an oversight, with the reason it must not be "fixed". **Do not build a receipt, a reconciliation pass or an outcome enum for it** — that is machinery for an arm the provider's contract does not produce, and the mantra declines it.
