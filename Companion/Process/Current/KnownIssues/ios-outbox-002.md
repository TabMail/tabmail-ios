## Full detail

A genuinely future-held queued row can be shadowed by an earlier past-held or legacy-NULL row when the wake query examines only the first ordered row, so no timer is armed for the future row. The durable send is not lost: a later ordinary foreground/provider-sync drain sends it. Keep the live expected-issue pin as the regression oracle, but do not widen Outbox scheduling during this release train.

✅ **FIXED by `792048ebd`.** **The invariant that now holds:** the post-loop wake query returns the earliest **genuinely future** hold, so a future-held row can no longer be shadowed by a NULL or already-elapsed one and left with no timer armed. The old query ordered `holdUntil ASC` with no future-hold predicate, and SQLite sorts NULL first under ASC while a past instant sorts before a future one, so `fetchOne` returned the wrong row, the caller's `hold > Date()` re-check failed, and no timer was set even though a future-held row existed behind it. The query is now `AccountManager.earliestFutureHoldWakeTarget(now:db:)`. **It NARROWS the timer query and widens nothing:** rows with a NULL or elapsed hold are already handled by the drain loop that runs above the timer, and only `.queued` is considered, so Outbox Rule 8 (`.failed` needs an explicit user Retry) is untouched. **A THIRD BLESSING TEST WAS FOUND AND RE-SCOPED, NOT DELETED** — recorded here because this row's defect is the one it blessed. `ComposeThrottleTests.PostLoopWakeUpQueryTests.guardAgainstPastHold` asserted `earliest?.id == "past"` and `shouldSchedule == false` **with a future-held row in the same table**: it encoded this defect as the expected behaviour. It could only do so because the suite ran against a **REPLICA** of the query written out in its own helper — and a replica cannot go red on a defect in the original. The helper now calls the production function, which makes every case in that suite an assertion about the app rather than about itself; the old expectation is replaced by the invariant it violated, and the previous display name is recorded inline. This is the same class as the blessing tests re-scoped for `IOS-DRAFT-009` (round 3), `IOS-ROUND3-D6` (`6b689890d`, three of them) and `IOS-TEST-005` (`459786db1`) — and the mechanism here, *a test asserting against a copy of production rather than production*, is the one worth carrying forward: it makes a blessing test undetectable by red-proof. **A1:** `07a4bb703` carries the identical unfiltered `.order(Column("holdUntil").asc)` query, so the fix is authored against the floor rather than restored.

⚠️ **ONE CLAUSE OF THE CLOSURE ABOVE WAS TOO STRONG — corrected in place, not deleted, because a register that overstates its own closure is a recorded defect class here.** The *query* half is true and unretracted (`AccountManager.earliestFutureHoldWakeTarget(now:db:)` does return the earliest genuinely future hold, and a NULL or elapsed row can no longer shadow it). What was too strong is the outcome clause *"…and left with no timer armed"*: that end state stayed reachable by a **different mechanism** — the caller's `hold > Date()` re-check runs at a FRESH instant with an `await dbPool.read` in between, so a deadline that elapsed during that read was future at selection and past at the re-check, and the guard fell through and armed nothing. Closed by `1a1962207` and registered separately as **`IOS-OUTBOX-005`**. **The two are cross-referenced rather than merged** — same symptom class (a held row ends a drain with no autonomous wake), different mechanisms (query ORDERING versus a two-instant handoff race), and **neither fix would have closed the other** — which is the same treatment `IOS-TEST-006` and `IOS-TEST-008` were given, for the same reason.
