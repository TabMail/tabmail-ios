## Full detail

**An outbox row held behind an undo-send deadline could end a drain with NO wake-up timer armed at all, leaving the user's queued send waiting for an unrelated external trigger.** `AccountManager.drainOutbox` selects its wake target with `earliestFutureHoldWakeTarget(now:db:)`, whose predicate is `holdUntil > now`, and then re-checked `hold > Date()` against a **FRESH** instant with an `await dbPool.read` in between. A deadline that elapsed **during that read** was future at selection and past at the re-check, so the guard fell through and armed nothing — while the drain loop above it had already finished. The row stayed `.queued` until a foreground, a sync, a network change or another `queueSend` happened along. ⚠️ **This is a DIFFERENT mechanism from `IOS-OUTBOX-002`** (which was the query's ORDERING) and neither fix would have closed the other; that row's *"left with no timer armed"* clause is corrected in place there. **Why REGISTRABLE and not blocking:** it is a **liveness** defect, not a correctness one — nothing is dropped, nothing is sent twice, no wrong message is mutated, and the durable row survives; an ordinary later trigger drains it, so it is recoverable in the sense THE MANTRA requires. **The invariant that now holds:** a queued row whose hold expires is either claimed by the current drain or covered by an autonomous future drain — **never dependent on an unrelated trigger**. `AccountManager.wakeUpDelay(for:at:)` (a new `nonisolated static` on `AccountManager`, in `AccountManagerOutbox.swift` — ⚠️ **the file name is not the type qualifier**; `AccountManagerOutbox.wakeUpDelay` greps as nothing) clamps the interval at zero, so **an already-elapsed deadline means "drain now", never "do nothing"**. 🚨 **The clamp is INDEPENDENTLY LOAD-BEARING: the caller converts with `UInt64(interval * 1_000_000_000)`, and converting a NEGATIVE `Double` to `UInt64` is a runtime TRAP, not a saturating conversion.** **The re-drive terminates and claims the row:** the drain loop's admission filter is `(holdUntil ?? .distantPast) <= Date()`, so the next pass admits the elapsed row instead of falling through again, and `earliestFutureHoldWakeTarget` filters `holdUntil > now`, so that row is no longer a wake target and no second timer can be armed. A still-future deadline is unaffected — `max(0, positive) == positive` — so the ordinary path is byte-identical. **The decision takes an INSTANT PARAMETER rather than reading the clock inline, for the same reason its sibling query does:** `PostLoopWakeUpQueryTests`' own doc comment records that an inline clock is precisely why a replica test stayed green while `IOS-OUTBOX-002` shipped. **A1:** shipped `07a4bb703` carries this same residual — an order-only query plus the identical `hold > Date()` re-check — **plus** the NULL/past-row shadowing defect `792048ebd` already fixed; nothing to restore, so the branch's improvement is kept and the residual closed on top. **Verification:** three tests added, pinning the INVARIANT rather than the mechanism. Red-first proof recorded — with the clamp inverted, *"A deadline that elapses while the wake query is in flight still gets an autonomous drain"* failed with `(delay -> nil) != nil`, and in that same red run the two pre-existing blessing tests (`futureHeldRowIsNotShadowed`, `PostLoopWakeUpQueryTests.guardAgainstPastHold`) **both PASSED**, which is the mechanical measure of the gap they were blind to. Neither was modified or weakened. No wire behaviour, no schema change.
