## Full detail

**`stageHeader` re-proves identity before REUSING payload already on the row; these are the writers that ADD payload to it, and they carried no identity term at all.** `IOS-NSE-005`'s brief was deliberately scoped to *"`stageHeader` and only it"*, and its closure recorded the negative case: *"a ZOMBIE run 1 resuming from its AI await after run 2 has re-headed the row can still write its summary onto the successor … the zombie checkpoints (`OneShotFlag.hasFired()`) are the only thing standing in front of it."* **Those checkpoints do not close it, and the reason is that they answer a different question.** `deliveredFlag` is per-RUN — it asks *"did MY run's watchdog already deliver"* — which says nothing about whether a LATER run has since re-headed the row; a predecessor whose watchdog never fired passes every checkpoint and writes.

**THE THREE WRITERS, enumerated by the PROPERTY rather than by the two the finding named (`MIS-006`: the class is *a writer keyed on an ADDRESS assuming it still names the same message*).** (1) `stageBody` — the predecessor's body becomes the successor's `MessageBody`, is indexed under the successor's header id, and sets `bodyComplete = 1`, which the body queue (`bodyComplete = 0`) never revisits and `BodyFetchProcessor`'s `onConflict: .ignore` would preserve anyway. (2) `stageSummary` — the worse half: the summary/todos/reminder are merged onto the successor's header AND cached in `messageAICache` under the **successor's RFC key**, so the poisoning survives every later UID re-key and is a permanent HIT, and the merge queues a `setTag` `PendingOperation` putting the predecessor's action tag **on the wire** against the successor. (3) `persistProcessedMessage` — the third writer, guarded here rather than left as the one exception; its damage DIFFERS and is stated rather than assumed: `INSERT OR REPLACE` rewrites the WHOLE row, so it does not splice mixed identities — it **destroys the successor's staged push outright** (a dropped message) and resurrects a predecessor the address no longer holds.

**THE FIX — one predicate, reused, no new machinery.** All three now call the SAME `stagedIdentityPositivelyDiffers` helper `stageHeader` already uses, inside the SAME write transaction as their statement (a check outside it is a TOCTOU seam a concurrent re-head slips through). Doors and precedence are `NSEDataBridge.nseMergeIdentityConfirmed`'s: **(a) RFC first and unconditional**, **(b) epoch only when (a) cannot adjudicate**. **NO schema change, NO migration, no generation counter, no run token, no lease** (A3 / `MIS-003` — the identity needed to decide this was already on the row).

🚨 **THE FAIL DIRECTION IS THE MIRROR OF `stageHeader`'s, and getting it backwards is the trap.** There the question is *may I KEEP payload already on the row*, so the safe answer to an unanswerable identity is RETAIN. Here it is *may I ADD payload to it*, so the safe answer is **WRITE**. Suppressing the write on absence of evidence would stop an rfc-less, epoch-less message ever accumulating a body or summary across wakes, and would make `persistProcessedMessage` drop whole legitimate runs — `MIS-IOS-004`'s "could not determine ≠ authoritative" in its other direction. Only POSITIVE evidence of a different message suppresses a write; an ABSENT row also writes (the ordinary first insert). **The refusal is not silent** (`IOS-NSE-005`'s own lesson about a dropped write): each writes an `NSELog.error` naming the id and the row — the NSE's durable file channel, not a detached console (topic 105). **The dropped payload is safe to drop precisely because the guard fired:** it was computed for a message provably no longer at that address, and whoever holds the address now re-fetches its body and computes its own AI through paths that already work.

**A1 — AUTHORED, not restored.** Shipped `07a4bb703` and the `v2final` sibling `e28dd4edb` both have `stageBody`/`stageSummary` as bare `UPDATE … WHERE id = ?` with no identity term, byte-identical to v3's; both **share the defect** and `07a4bb703` is strictly weaker (`observedUidValidity` does not exist at that tag, so door (b) is unavailable). There was no guard to port.

**Verification — red-first on both halves, two-sided.** Five tests in `TabMailTests/NSE/NSEStagingZombieWriterTests.swift` drive the REAL writers and the REAL `NSEDataBridge.mergeNSEStagingData`. Three pin the defect by sweeping durable state for a token unique to the predecessor (never by asserting "the refusal arm ran" — `MIS-015`); two are ANCHORS holding the opposite direction, and the mirror-image "suppress unless identity positively AGREES" fix turns `unanswerableIdentityWritesRatherThanRefuses` RED while leaving the defect tests green.

✅ **RE-RAISED AND REFUTED (2026-08-05, final audit train).** The codex half reported this row's three writers as a BLOCKING C3 misattribution — *"treats an unanswerable identity as permission to write"* — with a reachable UIDVALIDITY-turnover scenario and *"recovery: none"*. **The mechanism is real and the classification is wrong**: it is the residual on the CHOSEN side of the two-sided trade this row already states, and the proposed fix is verbatim the mirror-image trap named above. Refuted by three independent checks: this row; `stageBody`'s own doc comment carrying the same reasoning; and the anchor test `TabMailTests/NSE/NSEStagingZombieWriterTests.swift` `unanswerableIdentityWritesRatherThanRefuses()`, which exists precisely to go RED if the proposed fix is applied. The Claude half read the same code independently and agreed. **No change made.** Recorded as `MIS-026` — a blessing test and an anchor test are the same artifact seen from opposite sides of a decision, so the discriminator is never the assertion's text but *what breaks if it goes the other way*.

⚠️ **RETRACTED 2026-08-05 — the "deliberately NOT changed" carve-out for `getCachedResult` was WRONG, and it is now the FOURTH member of this class.** **What it said, verbatim, so the error stays searchable:** *"**Deliberately NOT changed, so the census is accountable.** `getCachedResult` keeps its `WHERE id = ? AND aiCompleted = 1` with no identity term: `stageHeader` runs strictly before it in `NotificationService.process`, so the row's identity is already this run's — adding a second term would be the redundant machinery A3 forbids, and the ordering is the guard (do not move that call later)."* **Why it is false: the ordering establishes only that `stageHeader` was CALLED, never that it LANDED.** `stageHeader` returns `Void` and wraps its whole write in `do { … } catch { NSELog.error("stageHeader failed: \(error)") }` — a thrown write is logged and **swallowed**, and no caller can observe it. The staging DB is a **non-WAL, cross-process App Group** database, so `SQLITE_BUSY` under contention is a live outcome. When that write throws, the predecessor's `aiCompleted = 1` row survives untouched at the address, `getCachedResult` hits on address alone, and `NotificationService` hands `EmailNotificationBuilder.fill` the successor's `senderName`/`senderEmail`/`subject` together with the **predecessor's** `summaryBlurb`, `actionTag` and reminder — including an `actionTag == "reply"` that escalates the banner to active + sound for a message it was never computed for. **Non-recoverable:** the notification has been delivered and seen, and no later sync un-shows it. `MIS-024` in its purest form — reading a mechanism proves it is CORRECT, never that it RAN, nor that it ran BEFORE the damage. **✅ FIXED (final audit train, 2026-08-05):** `getCachedResult` now takes the incoming `NSEMessageMetadata` and consults the same `stagedIdentityPositivelyDiffers` the three writers use, with the SAME fail direction as `stageHeader` — this is a *may I REUSE payload* question, so an unanswerable identity still SERVES and only POSITIVE evidence of a different message turns a hit into a miss. The mirror-image trap ("unknown ⇒ miss") is pinned RED by `unanswerableIdentityWritesRatherThanRefuses` and by `NSEStagingIdentitySplicingTests.unanswerableIdentityRetainsRatherThanClears`. Red-first evidence: `NSEStagingZombieWriterTests.cachedAiIsNeverCombinedWithADifferentMessagesHeader()` fails on the pre-fix code with `(delivered.contains(token) → true) == false` and `(active → true) == false`. The ordering remains load-bearing for the *write* half — still do not move the `stageHeader` call later in the run — it is simply not a substitute for the read's own identity term. `AIOwnershipLease`'s writers are left alone: their predicates are `WHERE id = ? AND aiOwner = ?`, they write lease bookkeeping rather than payload, and **the lease is not this guard** — `tryClaim` gates the right to COMPUTE, not the right to WRITE, and both generations use `.nse`, so it is generation-blind. Aiming the fix there would have left the real hole open.
