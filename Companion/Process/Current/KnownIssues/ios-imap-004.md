## Historical defect

**Without `COPYUID` there was no proof our own COPY landed**, so a move interrupted after the COPY could not safely clean up the source, and with aliases a pre-existing sibling copy in the destination is indistinguishable from our own.

## Closed by

Closed by the SwiftMail upstream sync: `copy()`/`move()` now return a server-verified `CopyUID` carrying the destination UIDVALIDITY and a source→destination mapping. **Where the server advertises UIDPLUS, `COPYUID` is the only accepted witness — no weaker one is substituted.** ⚠️ **Narrowed, audit round 3 (2026-08-03).** The original sentence was categorical and, read that way, forbade source cleanup on any server without UIDPLUS — which wedged that entire class permanently (they can *never* furnish `COPYUID`, so the op could never reach a never-drop exit and starved every later gesture on that message). **Adjudication: on a non-UIDPLUS server the COPY's own tagged `OK` authorizes source cleanup.** It answers the question cleanup actually asks — *did my copy land?*: RFC 3501 §6.4.7 requires an unsuccessful COPY to restore the mailbox, and in the SwiftMail fork a tagged `NO`/`BAD` throws (`BaseIMAPCommandHandler.processResponse` → `BaseIMAPCommandHandler.handleTaggedErrorResponse`, overridden by `CopyHandler.handleTaggedErrorResponse` → `IMAPError.copyFailed`) and cannot return normally. `COPYUID` additionally says *where* the copy landed, which cleanup does not need. The rationale's second half — *"with aliases a pre-existing sibling copy is indistinguishable from our own"* — concerns a destination **SEARCH**, which this path never performs; it stays ADR-IOS-068/D4-clean. **Accepted cost:** without `COPYUID` the source UIDs cannot be named, so the source copy is left visible-and-`\Deleted` rather than expunged (a folder-wide `EXPUNGE` is forbidden by `IOS-IMAP-001`) until something else expunges the folder. The superseded fallback — *"drop the op and let sync reconcile"* — is **not** available under NEVER DROP USER INTENTION and must not be reinstated. ⚠️ **CORRECTED TWICE MORE, audit round 4 (2026-08-03).** (a) The round-3 wording above **overclaimed**: it said the tagged OK settles the question *"conclusively"* and, at the code, that it proves *"the whole named set"* copied. It does not. The command is a `UID COPY`, and RFC 3501 §6.4.8 states that *"a non-existent unique identifier is ignored without any error message generated. Thus, it is possible for a UID FETCH command to return an OK without any data or a UID COPY or UID STORE to return an OK without performing any operations."* A named-but-absent UID is simply not one of *"the specified message(s)"* §6.4.7 speaks about, so the OK is silent about it — and the op was retired as provider success anyway, which in a batch let an absent member ride out of the queue on a present sibling's OK. (b) The claim that `COPYUID` *"is the only accepted witness"* wherever UIDPLUS is advertised was itself a permanent wedge for part of that class: RFC 4315 §3 makes the response code a SHOULD **"with limited exceptions, discussed below"** — a mailbox the client may COPY or APPEND to but not SELECT or EXAMINE (*"SHOULD NOT send"*), and a `UIDNOTSTICKY` mail store (*"MAY omit"*) — both properties of the mailbox rather than of the attempt, so for those servers it never arrives, the op reached none of the four never-drop exits, its lane halted on every drain, and each drain re-issued the COPY and seated another destination duplicate. **What the fix now guarantees, per member and per mutation kind:** a source copy is marked `\Deleted` only when the member is proved to have been *in the source mailbox at the moment the COPY ran* — either because `COPYUID` names it, or because a `UID FETCH` of the op's own source UIDs (no `SEARCH`, no Message-ID: D4-clean) still returns it after the COPY, which under RFC 3501 §2.3.1.1's "MUST NOT refer to any other message … forever" and strictly-ascending UIDs means it was present during the COPY and so was covered by the tagged OK. A source copy is `UID EXPUNGE`d only on `COPYUID`; the widened evidence never authorizes an irreversible deletion, so against a non-conforming server the worst case is a message left `\Deleted`-but-present, never one destroyed. A member the `UID FETCH` proves is no longer in the source is the provider stating there is nothing left to move — exit 2, zero mutation, retired — which is what shipped `v1.6.38`'s `idempotentMove` did with its `if srcUIDs.isEmpty { … return }` early return. Every member therefore reaches a permitted exit on every attempt, so no move op can wedge its lane for want of evidence.
