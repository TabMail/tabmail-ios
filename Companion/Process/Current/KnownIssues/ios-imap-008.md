## Full detail

**The `\Deleted` filters are insert-prevention only, and an EXISTING row below the merge floor has no eviction path.** `selectStaleHeaders` removes a local row only when it is in `candidates` — and in `.uid` mode without `coverage.spansEntireFolder` that requires `uid >= floorUID`, the minimum UID the fetch materialised. A `\Deleted` row whose UID sits below that floor is never a candidate. The crawl cannot evict it either: in `insertBackfillBatchGuardable` the `if info.isDeletedOnServer { continue }` sits **above** `if existingIds.contains(info.messageId)`, so the row is skipped before the existing-row branch is reached. Deletion reconcile does not help — `UID SEARCH` finds the UID (it is still on the server) and `selectGhostUIDs` correctly refuses to call it absent, and IMAP `STATUS` still counts `\Deleted` messages so the count-mismatch trigger need not fire. The row therefore stays visible for as long as the server keeps the flag without expunging. **Two one-shot states are consumed on the way past:** the v10 cc/bcc update is skipped for that row while `ccBccBackfillDone` is still latched by the completing crawl, and `UIDWalkCursor.confirmRange` confirms the range regardless, so `Folder.backfillComplete` is set with that UID never materialised. **The cc/bcc half is already decided** — `Companion/Memory/Current/101-isdeletedonserver-has-four-materialisation-paths.md` records it as *"correct as is; moving it below would spend a write on a row the merge is about to delete"*. **This row adds the part that decision did not cover: the merge does NOT always reach it.** **Why REGISTRABLE.** Display-only. No message is deleted, mis-addressed or dropped; no wire operation depends on it; the row's content is the user's own real (soft-deleted) mail. **Recoverability, with the non-firing case named:** any sync pass where the server reports `coverage.spansEntireFolder` takes the floor-free branch and removes it — the ordinary case for a folder smaller than the fetch limit — and a server-side expunge removes it via `VANISHED` / count-mismatch reconcile. The case that does **not** self-heal is a large folder on a non-UIDPLUS server, where soft-deleted move sources accumulate below the floor indefinitely. **Do not close this by filtering `\Deleted` at the FETCH site**: the fetch's cardinality and UID floor measure COVERAGE and must keep counting `\Deleted` records, or the `ADR-IOS-042` / `MIS-IOS-002` mass-deletion shape returns.
