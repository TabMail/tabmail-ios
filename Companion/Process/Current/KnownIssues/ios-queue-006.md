## Full detail

**`.retainedForRetry` is a REPORT, not a retry. No production consumer stores, schedules or redrives it.** Census at HEAD, restated so it reproduces (`MIS-007`/`MIS-008`): `rg -n 'pendingIds' TabMail/ Shared/ TabMailNotificationService/` returns **17 lines in 4 files**, and the number that matters is **FOUR reads of the PROPERTY** — `AppDelegate.swift` twice (`NotificationActionRouter.execute`'s ARCHIVE and DELETE arms, `archiveOutcome.pendingIds.contains(header.id)` / `deleteOutcome.pendingIds.contains(header.id)`, each selecting an `else if` arm whose entire body is a `log(...)` string) and `admission.pendingIds` once each in `EmailArchiveTool` / `EmailDeleteTool`, bound to `pendingHeaderIds`. ⚠️ **An earlier wording of this row said "exactly five production reads", which does not reproduce:** the fifth counted hit is the DECLARATION itself (`AccountManagerActions.swift`, `var pendingIds: Set<String> { ids(with: .retainedForRetry) }`), and the remaining twelve are a **same-named LOCAL variable shadowing it** inside the two tools (`let pendingIds = zip(resolvedNumericIds, resolved)…` — the numeric ids that get serialised into `result["pending_ids"]` alongside the message *"…are still outstanding — their outcome could not be confirmed. Do not repeat the action."*). A bare-symbol grep cannot separate a property read from a shadowing local; enumerate by the STATE "reads `RoleMoveAdmission.pendingIds`", not by the name. **The substantive claim is unaffected: none of the four reads stores, schedules or redrives the work.** So when `performCoordinatedRoleMove` classifies an id `.retainedForRetry` — a swallowed or thrown `resolveHeadersForAction`, a thrown absence probe, a thrown role-folder lookup, an account with no folder for the role, or an id dropped by the fresh re-resolve inside the queued closure — **no `PendingOperation` row is inserted and nothing will ever try again**, while the agent is instructed not to repeat.

⚠️ **`IOS-QUEUE-003` item 2 said this was already closed, and its basis does not survive reading.** It reads: *"It has an owner at the tip: `AccountManagerActions.RoleMoveDisposition.retainedForRetry` is produced by `roleMoveRejectDispositions` at five guards and consumed by `pendingIds`."* **Being consumed by `pendingIds` is not having a retry owner** — `pendingIds` is a computed filter (`ids(with: .retainedForRetry)`) whose only consumers print or serialise it. That is `MIS-024`'s exact shape ("covered by X" discharged without greping what X does), and it is recorded there as instance 2. **Item 2's disposition is corrected to OPEN and superseded by this row.**

**Why this is REGISTRABLE and not BLOCKING.** The local mutation and the durable op are the *same* transaction — that is what `durablyAdmitted` asserts — so a non-admitted id gets **no local mutation either**, and every optimistic overlay entry is released on both exits (`releaseOverlayEntry` runs for `droppedByFreshResolve` and for `freshIds`). The message therefore stays visible where the user left it. Nothing is destroyed, nothing is mis-addressed, and no queued row is dropped (none was created). Recovery is **one ordinary user gesture** — the user swipes again — which is exactly the mantra's test. **The state where that does not fire is named:** the AI-tool and notification-action paths, where the *reporter* is not the user, so nobody is prompted to re-issue. The user still sees the unarchived message in their Inbox; they simply are not told the agent failed. **If this is fixed later, fix the report or add an owner — do not make `retainedForRetry` terminal.** Promoting "we could not determine" to a terminal disposition is `MIS-IOS-004`, this codebase's most repeated defect, and the rank lattice in `RoleMoveAdmission` exists specifically to make that promotion impossible.
