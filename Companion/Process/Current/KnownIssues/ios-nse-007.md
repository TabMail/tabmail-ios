## Full detail

**The claim:** *"the NSE converts an RFC 822 `SEARCH` result into notification mutation authority"*, evidenced by `EmailNotificationBuilder.fill` "still exporting the chosen UID" via `info["messageId"] = messageId`. ⚠️ **THIS ROW'S ORIGINAL GROUNDS WERE FALSE AND ARE REPLACED HERE (2026-08-05, found independently by three round-5 auditors).** It asserted the cited symbol did not exist. It does — `Shared/Notifications/EmailNotificationBuilder.swift:26` declares `enum EmailNotificationBuilder` — and `project.yml`'s `TabMailNotificationService` target lists `- path: Shared` among its `sources`, **so that file is compiled INTO the NSE**. The original census was scoped to `TabMailNotificationService/` and structurally could not see a file in `Shared/`; the row then instructed the next auditor to repeat that same scoped grep. Corrected limbs: **(1) FALSE** — the NSE's `c.userInfo` writes are not only `reconnect_state`: `EmailNotificationBuilder.fill` sets `info["messageId"]` and `info["accountId"]` (`EmailNotificationBuilder.swift:168-169`) and the NSE calls `fill` at four sites (`NotificationService.swift` 296, 648, 694, 1010). **(2) FALSE on the `imap_new_mail` path** — there `msg` comes from `fetchIMAPMessage` → `NSEIMAPConnection.fetch`, which issues `UID SEARCH` by RFC 822 Message-ID and then derives `messageId = IMAPFetchMapping.messageIdString(from: info)` from the FETCH for the UID that SEARCH returned, so the delivered `userInfo["messageId"]` on that path **is** the SEARCH result (the push payload carries the RFC 822 Message-ID as the head id; Gmail/Outlook pass their own provider id straight through, and for them the original limb 2 does hold). **(3) TRUE, AND IT CARRIES THE DISPOSITION — but the safety claim it was written with was TOO STRONG and is CORRECTED here (2026-08-05, audit round 7, codex `A1-R7-001`).** The consumer, `NotificationActionRouter.execute(actionId:messageId:accountId:)`, does resolve through `resolveAfterMerge(messageId:accountId:)` rather than treating the exported id as an address, and its archive/delete arms do carry `expectedIdentities: ExpectedMessageIdentity.map([header])` as a C3 content witness. ⚠️ **What that witness closes, and what it does NOT, stated as two classes because the previous wording implied it closed both.** It DOES close the **late** class — the address turned over between capture and execution (a UID renumber, a different message now sitting at that UID); that is real and load-bearing. It does **NOT** close the **initial-selection** class: `NSEIMAPConnection`'s `performFetch` issues `UID SEARCH` by RFC 822 Message-ID and takes the FIRST hit (`guard let uidSet = await searchMessageId(...), !uidSet.isEmpty, let uid = uidSet.toArray().first else`), and the witness the action path later carries is captured **from the row that same id resolved to**. So for two INBOX messages sharing a Message-ID the witness equals the sibling's RFC *by construction* and cannot refuse — the two copies are identical in the only field it compares. **The earlier phrasing — that the exported id is "an INPUT to a re-resolution that re-proves identity, never an authority" — is therefore true of the late class only.** **Why this is still ✅ NOT A DEFECT, both legs verified rather than asserted. (a) Attribution: PRE-EXISTING, byte-identical to shipped.** `git show 07a4bb703:TabMailNotificationService/NSEIMAPConnection.swift` carries the same `uidSet.toArray().first` guard, with the same surrounding comment, so this is not candidate-attributable. **(b) Recoverability (THE MANTRA):** the two copies are *the same message*. `MARK_READ` is re-markable; `ARCHIVE`/`DELETE` move a **duplicate** to Archive/Trash, and for mail TabMail never permanently deletes — so one ordinary user gesture reaches the correct state. Recoverable ⇒ fail closed, register it accurately, and **do not build a mechanism** (no fail-closed-on-multi-hit, no deterministic tie-break, no new column). **Re-raise rule — REPLACED AGAIN, because the previous one read as IMPOSSIBLE and this one is merely BOUNDED.** The prior rule admitted re-raise only on evidence the witness was weakened or bypassed, which no observation about initial selection could ever satisfy. The rule is now: re-raise on evidence that the witness has been weakened or bypassed, **OR** that the initial-selection residual has become **non-recoverable** — e.g. a notification action path that permanently DESTROYS rather than moves, or a duplicate-RFC pair that is not in fact the same message. 📌 **This is the SECOND time this row has pointed the next auditor away from a live seam** — the first was the directory-scoped census its own correction above already records — and that recurrence is precisely why the rule is being LOOSENED rather than tightened. A re-raise rule that cannot fire is not a safeguard; it is a silencer. The original `MIS-024` instance-8 attribution (*zero callers* → *zero existence*) is **withdrawn**: the symbol exists, and the real class is `MIS-007` — a census inherits its search shape.
