## Full detail

**Shipped `v1.6.38` let Outlook accounts load, create, apply and remove user labels LOCALLY; the candidate hides them entirely.** In the shipped release `UserLabelMenuView` operated for Outlook and the Exchange executor logged that remote mutation was unsupported while still completing the queue operation, so the local `UserLabel` / `MessageUserLabel` state stayed visible and usable. On v3, `UserLabelMenuModel.supportsRemoteUserLabels` and its four call sites exclude Outlook, so **existing local labels on Outlook accounts become invisible**. **This is the one genuine feature drop the whole-tree sweep found** — 0 production files deleted, 0 files with a net decrease in `guard` count, 0 user-visible UI strings removed, and every other removed function traced to a rename or a documented subtraction with a live replacement. **Why REGISTRABLE:** no data is lost — the rows are neither migrated away nor deleted, so restoring an explicit local-only policy would reveal them again. The user-visible cost is that an Outlook user's existing labels stop appearing until that decision is made. **Owner-facing:** whether Outlook labels should be local-only or absent is a product call, not a correctness one.

✅ **FIXED by `e265428ff`, "Propagate Outlook user labels to Graph as message categories". ⚠️ THE ROW ABOVE FRAMED THIS AS A PRODUCT CALL — "local-only or absent" — AND THE ANSWER TURNED OUT TO BE NEITHER, because the framing hid a live NEVER-DROP VIOLATION.** The queue's two Exchange arms were `print("[Queue] addUserLabel not yet supported for Exchange")` followed by `return .allMembers`: **the durable op was RETIRED AS SUCCESSFUL having done nothing.** That is not a missing feature, it is **exit-2 abuse** — nothing provider-authoritative said the work was done or inapplicable, so the user's gesture left the queue on no evidence at all. The row's *"no data is lost"* framing was true of the LOCAL rows and silent about the queue. **The invariant that now holds:** Outlook user labels behave like IMAP's and Gmail's — visible, creatable, and they REACH THE SERVER; both Exchange arms now execute a real mutation, so the op leaves the queue only on provider success. An Outlook user label IS a Graph message `category` (there is no separate label resource on Graph), so add/remove is a `categories` PATCH via the new `ExchangeProvider.setUserLabel(messageId:category:add:)`, which is **READ-FILTER-WRITE and never a blind PATCH** — Graph REPLACES the whole array, so a blind write would destroy categories set by Outlook desktop, Outlook web or a server-side rule; it shares one `mutateCategories(id:transform:)` helper with `stripLegacyCategories`, and the PATCH is skipped when the array would be unchanged. `ExchangeProvider.parseGraphMessage` now maps `categories` into `userLabelIds` (the data was already on the wire and already decoded — only the mapping was missing). **A1:** shipped `07a4bb703` had NO provider gate at all and carried the same `print("… not yet supported for Exchange")` verbatim, so **the shipped release SHOWED Outlook labels and silently never sent them**; `supportsRemoteUserLabels` does not exist there — it is a `v2final` invention, and `v2final` returns `false` for `.outlook` too. Remote Outlook propagation is NONEXISTENT in the shipped architecture, so this is authored, and shipped's visible-but-inert labels are explicitly **not** restored. **THE ONE DELIBERATE DEVIATION FROM IMAP:** the Outlook label id is the category display name **VERBATIM, not lowercased** — IMAP lowercases because RFC 3501 keywords are case-insensitive, whereas Graph category names are case-SENSITIVE display strings, so minting a lowercased id would give a user-created `Receipts` and the server's echoed `Receipts` two different `UserLabel.id`s and a duplicate menu row. **Wire values stay bare (`IOS-LABEL-001`/D10):** `PendingOperation.userLabelId` carries `UserLabel.providerLabelId`, never the account-prefixed `UserLabel.id`, because a prefixed value would write a wrong category name onto the user's real message. **THREE ACCEPTED COSTS, stated by that commit:** (1) a category TabMail creates is not registered in the user's Outlook master list, so Outlook may render it without a colour until the user adds it there — exactly an IMAP keyword's position (registered nowhere), fixed by one ordinary gesture; **no OAuth scope was added, deliberately**, since `/me/outlook/masterCategories` needs `MailboxSettings.ReadWrite` and adding it would force every existing Outlook user through re-consent, while message-level `categories` PATCH works within the `Mail.ReadWrite` the app already has. (2) read-modify-write loses an update racing a concurrent Outlook client between the GET and the PATCH — **pre-existing**, `stripLegacyCategories` has had this race since it shipped; recovery is one ordinary sync pass and no mechanism was built. (3) `NSEDataBridge.filterUserLabels`'s `"outlook"` arm still returns `[]`, so an **NSE-delivered Outlook message carries no label rows until the next main-app sync** (which now materializes them); that file was owned by another live agent and was deliberately not touched. Cost (3) is the only live remainder and is recoverable by sync.

✅ **THAT LAST REMAINDER IS NOW CLOSED TOO, by `592f7202f`'s second item — the row carries NO live remainder.** `NSEDataBridge.filterUserLabels`'s `"outlook"` arm returned `[]`, and after `e265428ff` made `ExchangeProvider.parseGraphMessage` map Graph `categories` into `userLabelIds` it was the only path still dropping them; its comment still cited the `userLabelIds: []` that commit had deleted. It now returns `rawLabels.filter { !ExchangeProvider.isLegacyActionTagCategory($0) }` — the **SAME** predicate the main-app read path filters with and `stripLegacyCategories` deletes the server's `tm_*` categories with, not a second copy, so a category one path erases can never be surfaced by the other as a label the user owns (ADR-IOS-036: action tags are local-only). 🚨 **THIS ARM KEEPS GRAPH CATEGORY NAMES VERBATIM AND MUST NEVER BE LOWERCASED** — the IMAP arm directly above it lowercases because RFC 3501 keywords are case-INsensitive, while Graph category names are case-SENSITIVE display strings, so copying the sibling would derive a second `UserLabel.id` for one category and grow a duplicate menu row. **A1:** `git show 07a4bb703:TabMail/Services/NSEDataBridge.swift` has the arm returning `[]` verbatim, and in the shipped release that was CORRECT because its `parseGraphMessage` also returned `userLabelIds: []` — the arm's contract (*"match what the main-app read path derives"*) is the shipped one and is restored; only the value it must produce changed underneath it. **ACCEPTED LIMITATION:** this is a LATENCY fix, not a correctness one — the NSE is best-effort and must never be the only path carrying a durable guarantee, and the main-app sync already materialized these labels, so the pre-fix gap closed on the next sync pass. No migration, no new column, no change to the staging projections. A blessing test was re-scoped rather than deleted: `NSEMergeFullHeaderTests`' *"Outlook merge inserts NO user-label rows (categories not yet surfaced)"* (`outlookNoUserLabels`) asserted `count == 0` and encoded the defect; it is now *"Outlook merge keeps Graph categories verbatim and drops only tm_*"* (`outlookCategoriesBecomeUserLabels`), with the previous display name and the reason recorded inline.

📝 **NOTE (final audit train round 3, Claude reviewer) — `userLabelIdsAreAuthoritative: true` on Exchange is INERT but UNENFORCED.** Census re-verified against the tree at documentation time: **1 declaration** (`MessageHeaderInfo.userLabelIdsAreAuthoritative`, `TabMail/Providers/EmailProvider.swift`), **2 producers** (`GmailProvider`, from `userLabelCatalog.isAuthoritative`; `ExchangeProvider.parseGraphMessage`, hardcoded `true`), and **0 production readers** — every remaining occurrence in the tree is a test assertion. So the flag asserts a `$select` property of the Graph call sites (the reviewer counted **seven**) that is **argued in prose and pinned by nothing**. **No defect today** — with no consumer, a wrong value cannot mislead anything. **Recorded because the moment a reconcile consumer lands, that prose argument becomes load-bearing**: a consumer that treats `true` as *"this header carries the message's COMPLETE label set"* would strip labels from every header produced by a `$select` that omits `categories`. Pin the property before adding the first reader, not after.
