## Full detail

**THE MECHANISM IT REPLACES — A DURABLE WRONG-ATTACHMENT WRITE.** `fetchAttachment` addresses the wire by `(message.folderPath, message.messageId)`, which is precisely the pair `optimisticMoveToFolder` leaves inconsistent: `folderPath` is already the destination while `messageId` is still the SOURCE UID. On IMAP each folder owns its own UID space, so mid-move that pair names a DIFFERENT message and the provider returns a stranger's attachment bytes. `AttachmentListView.downloadAndPreview` then previews those bytes AND caches them through `BodyAssetStore.writeAttachment` under `ContentKey(message.id)` — the victim row's key — stamped with the victim's own identity from `AttachmentCacheIdentity.stamp(for:)` (rung 1, its RFC 822 Message-ID, which the move does not disturb). The wrong bytes therefore carry the right proof: every later read check passes and the stranger's attachment is served as this message's attachment indefinitely. This is the same defect class as `IOS-BODY-001`, in the sibling reader, and it was present in shipped `v1.6.38`.

**WHY THE GUARD IS FAIL-CLOSED WHILE ITS BODY SIBLING IS FAIL-OPEN.** `bodyFetchIsBlockedByPendingAddress` may fail OPEN because a dropped pre-filter costs only a wasted round trip — `BodyFetchProcessor.process` refuses again authoritatively before anything is written. **The attachment path has no downstream refusal at all**; this check is the only thing between the wire and a cached, identity-stamped write. Reusing the fail-open version would have been a fail-open seam feeding a guard, which is fail-dangerous (`feedback_port_safe_only_if_consumer_direction_same`), so `attachmentFetchIsBlockedByPendingAddress` refuses when the account row cannot be read or the provider cannot be determined. The suite's third case pins that direction specifically, because it is the one that could silently flip during a later refactor.

**WHAT IS ACTUALLY LOST.** Only the attachment download, and only on IMAP/iCloud (`addressCanResolveToAnotherMessage` returns false for Gmail/Outlook/Demo, so their attachments are untouched). ⚠️ **The window is NOT bounded by the drain, and this row said "only while the move is undrained" while its own recoverability paragraph below said otherwise** (audit). It is bounded by the drain AND by the detail view being rebuilt: an open view keeps the pre-move header after `finishMove`, so its taps stay refused until the user returns to the list and reopens. The message, its body and its attachment LIST all still render. ⚠️ **The cache exception here said flatly that "a previously cached attachment still opens, because the cache read happens before this guard on the `storedURL` branch", and that is only half true** (audit). Two different caches are involved and they behave oppositely across the re-key: a file already materialized into the view's own `downloadedFiles` map opens forever — `AttachmentListView` hands it to `AttachmentQuickLook.present` without calling `fetchAttachment` at all — whereas the DURABLE manifest hit stops working the moment `publishRekeys` runs `BodyAssetStore.rekeyContentKey`, which moves the row to the destination content key while this stale view keeps asking `attachmentAssetId` for the old one. So the durable cache saves the user BEFORE the re-key and misses AFTER it, and only the view-local copy is unconditional.

**RECOVERABILITY — THE RECOVERING EVENT, NAMED, AND IT IS REOPEN RATHER THAN RE-TAP.** `MessageHeaderRekey.finishMove` re-keys the row on `COPYUID` proof, typically within seconds — but `AccountManagerQueue.publishRekeys` updates Undo, FTS and `BodyAssetStore` and does NOT push the re-keyed row into an already-open `MessageDetailViewModel`. `AttachmentListView` is handed that view model's in-memory `MessageHeader`, so a second tap in an unchanged open view re-submits the SAME stale (destination folder, source UID) value and stays refused even after the database has settled — the same stale-open-view condition as `IOS-BODY-004`. **Going back to the message list and opening the message again** resolves against the current row and the download proceeds normally. One ordinary gesture, and `ProviderError.addressPendingMove.errorDescription` says exactly that. ⚠️ **That string took THREE attempts, and each wrong one was caught by a separate audit round.** "Try again in a moment" was wrong — a bare re-tap resubmits the same stale in-memory header. "Close it and open it again" was AMBIGUOUS — one of the three catches that renders it is `EmlAttachmentPreview`, a sheet showing a nested `.eml`, where the nearest referent for "it" is that sheet while the stale header is the PARENT message, so dismissing the sheet recovers nothing. Naming the message list is unambiguous from all three surfaces. An inaccurate recovery instruction is worse than none, because the user repeats a gesture that cannot work — and a stale copy of a corrected claim left in a neighbouring document is the same failure one step removed, which is why this row's status column was re-checked against the shipped string rather than assumed to match. THE MANTRA's fail-closed-and-let-it-be case.

**WHAT WOULD RE-OPEN THIS ROW:** the decline becoming durable (moves commonly parking undrained), a deferred-download mechanism landing that replays the tap once the address settles, or `fetchAttachment` gaining a downstream identity check that would make a fail-open pre-filter safe here.
