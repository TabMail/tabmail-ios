## Full detail

**CURRENT NARROWING (2026-08-08, `dd51c74ff`).** The ten-site app-induced class described below now exists only when the route snapshot has no `MOVE` and TabMail runs its owned `UID COPY` sequence. The `MOVE` route issues one atomic-only command and has no client-side COPY followed by awaited cleanup. A smaller residual remains: a server-side partial failure may leave a member in both source and destination even though RFC 6851 advises against that outcome; retrying by the still-live source UID can then duplicate it. That is not repaired with Message-ID search, guessed destination identity, or fallback after the atomic attempt. It is registered and accepted as provider-behavior risk, while the original one-duplicate-per-drain decision continues to govern the no-`MOVE` route.

**HISTORICAL RECORD (retained).** ⚠️ **THE `4e08ff720` CORRECTION ROW'S ROUND-4 CLAIM IS OVERSTATED AND IS RETRACTED HERE.** It reads: *"both costs are now **unreachable rather than bounded** — the throw site is deleted … so neither the duplicate-per-drain nor the duplicate-per-pass can be incurred by a move."* What `ede315ed8` actually made unreachable is **those two specific producers**: `IMAPMoveEvidenceUnavailable.noCopyUidEvidence` is deleted, and `retirePartiallyCompletedOp` has no current producer because `IMAPProvider.move` now dispositions every member. The CLASS is not unreachable. **The residual, stated as the class rather than as an instance:** `IMAPProvider.move` issues `server.copy(messages: sourceUIDs, to: destination)` and then performs further awaited work; ANY throw after that point leaves the op requeued (`.haltLane` in both the `ProviderEvidenceUnavailable` arm and the generic connection arm), and the next drain re-enters `move` from the top and re-issues the same `UID COPY` against a source copy that is still present — seating a second copy at the destination. `evidenceRefused` bounds this to at most one duplicate per DRAIN, which is exactly the bound the retracted sentence says can no longer be incurred. **The real count is TEN post-`COPY` throw sites, not five** (enumerated by step, in order): (1) the `Task.checkCancellation()` immediately after the COPY; (2) `throw IMAPDestinationEpochRefusal.movedAcrossCopy`; (3) the liveness probe `liveSourceUIDs` (a `UID FETCH`, so any network or parse failure); (4) A4's source re-SELECT (`selectMailboxTracked`); (5) A4's `requireUidValidity`; (6) the `\Deleted` `server.store`; (7) the second `Task.checkCancellation()`; (8) A5's source re-SELECT; (9) A5's `requireUidValidity`; (10) `server.expunge(messages: purgeAuthorizedUIDs)`. Sites 4–10 are byte-for-byte the same sites that stood at `2cfc4d979`. **Concrete reachability:** an IMAP move to Archive on a server without UIDPLUS; the COPY succeeds; the connection drops during the `liveSourceUIDs` FETCH or during A4's re-SELECT; the generic drain arm requeues the op and marks the account failed for this drain; the next drain re-runs the COPY and the user now has two copies in Archive, with the original still in INBOX. The source copy is never wrongly destroyed (the purge stays gated on `serverSupportsUIDPlus` AND per-member `COPYUID`), which is why this is a duplicate, not a loss. **Attribution.** The class is **C/B** — sites 4–10 predate the range and the shape (COPY, then more awaited work, then requeue-on-throw) is inherent to owning the sequence, which `v1.6.38` did not do (it delegated to SwiftMail's `move`). The range's **class A** increment is site 3: on the NON-UIDPLUS hot path the probe is always reached (`copyProvenUIDs` is empty, so the equality branch is never taken), and at `2cfc4d979` that class had NINE post-COPY throw sites, because the deleted `noCopyUidEvidence` guard was unreachable for it (`authorizedUIDs = serverSupportsUIDPlus ? copyProven… : sourceUIDs` was never empty there). Across all server classes the range is net-neutral (one site deleted, one added); on the non-UIDPLUS path it is +1. For a UIDPLUS server naming every member both the base and the tip have nine, because the tip skips the probe entirely on the `copyProvenUIDs.count == sourceUIDs.count` branch. **Scope of this row:** the RESIDUAL class only — "a post-COPY throw for network reasons still costs a duplicate on the next drain". The liveness probe's own oversized-FETCH and unparsed-UID defects were fixed separately (`8b7e7044c`) and are NOT this row; that fix does not narrow the class — site 3 remains a throw site (its new `IMAPLivenessProbeInconclusive` refusal joins the class rather than widening it, since `evidenceRefused` bounds it to one attempt per drain) and sites 1–2 and 4–10 are untouched. **Why REGISTRABLE:** duplicated mail is recoverable by the user and this repo's stated ranking (`IOS-IMAP-001`, `retirePartiallyCompletedOp`'s doc, the never-drop rule) prefers it to both a dropped intention and a wedge; no message is destroyed and no mutation lands on a different message.

✅ **CLOSED AS A DECISION (2026-08-04) — the class is INHERENT to owning the sequence, and removing it would trade a C3 guard for a UX nicety.** **The decision:** a post-`COPY` throw is allowed to cost at most one duplicate at the destination per drain. **Why it cannot be closed as written:** any COPY followed by further awaited work, with requeue-on-throw, can re-COPY — the ten enumerated throw sites ARE that shape, and sites 4–10 are byte-for-byte the ones that stood at `2cfc4d979`. The only construction that removes the class is atomic `UID MOVE`, which `IOS-IMAP-003` deliberately gave up in exchange for the five epoch assertions on **C3** grounds; reversing that trade to remove a *recoverable duplicate* inverts this repo's ranking outright. Everything short of it — a durable "COPY already issued" receipt — is exactly the receipt/alias machinery `MIS-IOS-003` and `CLAUDE.md` § *THE ADDRESS PROBLEM* forbid. **Accepted cost:** a duplicate at the destination with the original still in the source. `DrainContext.evidenceRefused` bounds the evidence-refused subset to one attempt per drain, and the generic connection arm additionally inserts the account into `failedAccounts`, stopping it for the rest of that drain. **Recoverability:** one ordinary gesture — delete the duplicate. **The state where the duplicate cannot be deleted was searched for:** it would require the destination folder's epoch to be unknown (the `IOS-EPOCH-001` window) — **and in that window the original move would not have been admitted either**, so the state does not arise from this path. **None found.** The source copy is never wrongly destroyed, because the purge stays gated on `serverSupportsUIDPlus` AND per-member `COPYUID`, so the worst case is duplication and never loss. **The round-4 retraction this row carries stands unchanged and must not be re-flattened**: `ede315ed8` made two specific PRODUCERS unreachable, not the class.
