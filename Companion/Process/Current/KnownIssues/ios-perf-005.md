## Full detail

**What moved and why.** `v83`'s body was one `CREATE INDEX IF NOT EXISTS messageHeader_unreadSweep ON messageHeader(folderId, id) WHERE isRead = 0`, and on the owner's device `MigrationTimingLedger` attributed **5,050 ms** to it — paid before any UI appears, on a launch the user is staring at. Its `ANALYZE` half had already moved to the background pass a day earlier under ADR-IOS-029's 2026-08-05 amendment (owner directive: *"startup migrations should really have only things that are absolutely necessary and blocking. Other things should happen durably in the heal/sync/background queues."*). This is the other half. The DDL now lives in exactly one place, `SyncEngine.deferredIndexes`, and is executed by `SyncEngine.runBuildDeferredIndexesIfMissing` from `runWALMaintenance`.

**THE ACCEPTED WINDOW — what a user can actually observe.** Between an upgrade launch and the first background maintenance pass, `InboxViewModel.markAllAsRead`'s three statements satisfy their `WHERE` from a `date`-ordered index and then SORT, once per 50-row page, over the whole remaining unread set — the O(U²/50) shape `v83` exists to remove. Measured at 100,000 unread on a 360k-row database with the statistics a shipped device actually carries: **199,425 ms without the index vs 6,300 ms with it**. It is SLOW, never WRONG — identical rows in identical order.

🚨 **THE ACCEPTANCE ARGUMENT THIS ROW WAS FIRST WRITTEN WITH WAS FALSE, AND IT IS CORRECTED HERE RATHER THAN DELETED (R16-4, 2026-08-06).** The row used to continue *"That is the pre-`v83` behaviour, i.e. every shipped release up to and including `v1.6.38`, so the window is **no worse than shipped** and strictly better once the pass runs."* **It is not shipped behaviour.** Shipped `markAllAsRead` (`07a4bb703:TabMail/ViewModels/InboxViewModel.swift`, quoted against an immutable tag) fetched `.filter(Column("folderId") == fid && Column("isRead") == false).limit(batchSize)` with **no `ORDER BY` at all** — it never sorted, so it never had the O(U²/50) shape. The ordered keyset sweep (frozen upper-bound probe + `id > ? AND id <= ?` cursor pages) was introduced **IN-RANGE** by `a790dd61d` (2026-08-03, *"Report every skipped gesture id instead of silently hiding rows"*); `git merge-base --is-ancestor a790dd61d 07a4bb703` exits **1**, i.e. not an ancestor of the shipped tag. On a second fixture (357,400 rows / 100,000 unread / fresh-install `sqlite_stat1`) the three shapes are **shipped unordered, no index: 7,889 ms · current, index present: 4,610 ms · current, index absent: 43,296 ms** — **5.5× worse than shipped**, or 86.6–173.2 s at this repo's standing 2–4× Mac-understates-device factor, and squarely against the owner's standing *"DB work must be super quick and instant"*. (The 199,425 ms figure above is SHAPE M — 5 accounts × 8 folders, unified 5-INBOX sweep — and is not in conflict; different fixture, same direction.)

**THE DEFERRAL IS STILL ACCEPTED, ON THE BASIS THAT ACTUALLY HOLDS.** Not equivalence-to-shipped, which is false, but that the window is **transient and self-healing** and the alternatives are worse in both directions: restoring `v83`'s body re-imposes 5,050 ms before first paint on the very launch the row exists to fix, and restoring shipped's *unordered* fetch removes the `ORDER BY` that IS the sweep's loop variant (a non-terminating sweep is a worse defect than a slow one). What the correction changes is the STATED MAGNITUDE and the reason — a reader who quotes "no worse than shipped" to license the next deferral would be quoting a false fact.

**A SECOND FALSE NUMBER FROM THE SAME CLASS, recorded because it was used in a review.** Round 14's supervisor claim that the index's absence *"costs 7.7 ms in both statistics regimes"* is one point on a quadratic — 7.3 ms at U=500, 2,974 ms at U=20,000 — and the tree's own measurement table in `AppDatabase.swift` (the `stats / U / no index / with this index / read-phase only` block in the `v83` banner) records `stale 100,000 → 199,425 ms` four orders of magnitude away, in the same file. The string *"7.7 ms"* appears **nowhere** in `TabMail/`, `Shared/`, `KNOWN_ISSUES.md`, `DECISIONS.md`, `PROJECT_MEMORY.md` or `Companion/` (exit 1), so there is no in-tree site to correct; it is recorded here so the number cannot be re-quoted from the round-14 transcript as if it had survived review.

**SHRINKING THE WINDOW FURTHER — EVALUATED AND DECLINED, with the reason, because the obvious next move is "kick the build at first foreground".** Two findings. (i) **The window is already one foreground sync pass, not "minutes".** `SyncScheduler.startForegroundPolling` calls `poll()` **immediately** and only then installs the repeating `foregroundInterval` timer, and `poll()` calls `manager.syncEngine.scheduleMaintenanceInBackground(includePrune: true)` unconditionally at the end of its body — outside the `!fastSyncModeActive` guard. So the first build is scheduled at the end of the FIRST poll, behind `foregroundSyncAll` (~60–70 s on the owner's device), never behind the 300 s repeat. (ii) **Moving it ahead of `foregroundSyncAll` trades a small win for a bad one.** SQLite has a single writer and `DatabaseWriteQueue` cannot preempt a write that has already started, so the 5,050 ms `CREATE INDEX` would hold the writer during the upgrade launch's first sync — exactly when every header insert, folder upsert and user gesture wants it — and, being background-tier, it would contend with that sync's writes rather than complete promptly, so it may not even land earlier in wall-clock terms. The remedy costs latency at the most visible moment to shave seconds off a transient, self-healing window. **Declined; no code change.** What would re-open it: the first `poll()` becoming timer-gated, or `scheduleMaintenanceInBackground` moving inside the `!fastSyncModeActive` branch — either would put the build behind the 300 s interval and make the original premise true.

**Recoverability, with the non-recovering case named (`MIS-IOS-008`).** The pass runs from BOTH the foreground poll and the `.full` BGProcessing drain, needs **no user gesture**, records nothing on failure, and re-arms itself on every launch until it succeeds — so a device that is killed, suspended or offline mid-build simply retries. Per THE MANTRA that makes it recoverable, therefore fail-closed-and-register rather than mechanise. **The non-recovering case:** a device on which the maintenance pass NEVER completes (permanently suspended before it reaches the step, or a persistently failing write) keeps the unindexed sweep forever. It is deliberately not promoted into the non-recoverable set: nothing is corrupted, no user intention is dropped, and no wrong message is touched. ⚠️ This clause used to end *"and the outcome is exactly the shipped release's"* — the SAME false equivalence corrected above, a second time inside this one row, which is why R16-4 was run as a class census rather than a single edit (`MIS-006`). The true statement is that the outcome is **5.5× slower than the shipped release** on the measured fixture, and it is accepted anyway because it is slow rather than wrong and costs no data, no intention and no correctness.

**CONVERGENCE — why emptying an already-applied migration body is admissible here (Data Integrity rule 5).** Rule 5's two prohibited shapes are APPENDING statements to an applied body (they never execute on a database that already ran it) and RENAMING it (GRDB re-runs the whole body and fails on the existing objects). This is neither: the identifier is frozen and the body only SHRANK. Three populations, all converging on the identical schema — a database that ran `v83` before the change already has the index and the empty body does not re-run; a fresh install or a not-yet-upgraded database gets it from the first pass; and `CREATE INDEX IF NOT EXISTS` is a no-op on the first and a build on the second.

**ORDERING IS LOAD-BEARING, and it is a convergence property, not a style choice.** The index build runs BEFORE the `ANALYZE` step in `runWALMaintenance`. `CREATE INDEX` is DDL and bumps SQLite's `schema_version`, which is precisely the marker `runRefreshPlannerStatisticsIfStale` latches on. Built first, the analysis reads the POST-index version and settles it, so **one pass converges**. Built after, the analysis would record version N, the index bump it to N+1, and the next pass would pay a second whole-database `ANALYZE` (up to 8.5 s at 500k headers) for nothing. Pinned by `DatabaseIndexTests.DeferredIndexBuildTests.indexBuildBeforeAnalyzeConvergesInOnePass`, which asserts the second pass reports `.alreadyPresent` **and** `.alreadyFresh`.

**⚠️ WHAT THIS DOES NOT LICENSE — the negative case, because this row is the sentence a future migration will quote.** An index may be deferred ONLY if its absence degrades PERFORMANCE and nothing else. A column, a data repair a reader assumes, a UNIQUE index a write depends on, or an index a query names in an `INDEXED BY` clause (SQLite **errors** when such an index is missing) all stay blocking. `messageHeader_unreadSweep` qualifies exactly: every one of the three sweep statements returns the same rows without it, no write depends on it, and it is named in no `INDEXED BY` clause anywhere in `TabMail/ Shared/ TabMailNotificationService/` — a checked fact (the three `INDEXED BY` sites name `messageHeader_triage_display`, `messageHeader_folderId_messageId` and `messageHeader_rfc822MessageId`), and the check to re-run before deferring the next one.

**Pinned non-vacuously, both sides in the same run.** `migrationChainDoesNotBuildTheDeferredIndex` asserts the index is ABSENT straight after the chain — which is what fails if somebody "restores" `v83`'s body, and without which every other assertion here would be vacuous — and `maintenancePassBuildsTheDeferredIndexAndConverges` asserts the pass produces it and reports `.alreadyPresent` the second time, so a pass that rebuilt on every foreground poll (a worse defect than the one this fixes) turns it red.
