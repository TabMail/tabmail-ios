## Full detail

**What was wrong.** The cursor was `beforeDate: Date?` and the SQL filter `date < ?`. Two messages arriving in the same second are ordinary, so any row tied with the last row of a page was excluded from the next page and never rendered. In **triage** mode the primary sort key is `tagSortOrder`, not `date`, so a date-only cursor is not merely lossy — once the first bucket's oldest row is passed, every row in every later bucket has a newer date and the walk terminates with whole buckets unreachable.

**What now holds.** `InboxPageCursor(tagSortOrder:date:id:)` names the **full ordering key**, and both the SQL and the in-memory composer compare against all three components. The SQL is deliberately spelled `range AND (range OR tie)` — `date <= ? AND (date < ? OR id > ?)`, and in triage `tagSortOrder >= ? AND (tagSortOrder > ? OR date < ? OR (date = ? AND id > ?))` — because a top-level `OR` is not sargable and would force a folder scan (A6: the leading range term keeps SQLite on the composite index). Both `ORDER BY`s gained the matching `id ASC` tie-break so the cursor and the sort agree.

**Counterfactual discharged.** The naive repair is `<` → `<=`. It is wrong: `excludeIds` is applied in `compose` (step 2.5) and again by a view-model belt, so boundary duplicates would consume SQL `LIMIT` slots and be filtered afterwards — recreating exactly the filter-after-`LIMIT` shape `IOS-SCROLL-002` registers, where a post-filter survivor count is read as a statement about the source. A keyset cursor over the whole key admits each row exactly once, so no slot is spent on a duplicate.

**Verification.** Three new `InboxListReaderIntegrationTests`: `normalModePagingReachesTiedBoundaryRows()` (7 rows, 4 tied on one second, pageSize 3 — red pre-fix: the paged set was missing a row), `triageModePagingReachesLaterTagBuckets()` (red pre-fix: the entire later bucket was unreachable), and `pagingDoesNotDuplicateBoundaryRows()` as the negative case with `excludeIds` deliberately NOT supplied (red pre-fix: 2 of 6 rows). A blessing-test search was run first and found none.

⚠️ **THE 'ACCEPTED RESIDUAL' PARAGRAPH THIS ROW SHIPPED WITH IS OBSOLETE, AND IT IS KEPT VERBATIM BELOW RATHER THAN DELETED because a residual that has been closed is exactly the kind of stale caveat a later reader treats as still-live risk (round-13 U8).** It named the BINARY-vs-Swift collation gap, and `33b4d3cf6` closed that gap outright: `InboxOrdering.areInIncreasingOrder` now compares `id.utf8` (`lexicographicallyPrecedes`), i.e. the same byte order SQLite uses, and it is the SINGLE definition every comparator in the list calls. **Obsolete text, retained as history:** *"Accepted residual. Not observed; header ids are `accountId:folderPath:providerMessageId`."*

**THE SECOND WAY THE ARRAY LEAVES THE READER'S TOTAL ORDER, FIXED IN ROUND 13 (U14).** The round-12 fix named exactly one — a comparator without the tie-break — and closed it. There is another: the array is correctly sorted when BUILT and becomes mis-ordered AFTERWARDS, because `tagSortOrder` is not immutable for a loaded row (the AI queue, delta sync, full sync and manual tagging all change it) and `reloadMessages` Pass 1 writes the fresh row into the STALE row's index without repositioning it. `rg 'loadedMessages\.sort'` → no matches. In triage a loaded row re-tagged into a later bucket then sorts after `.last`, is re-admitted by the keyset predicate, burns a SQL `LIMIT` slot, and is dropped by `excludeIds` AFTER the limit — the short page flips `hasMoreMessages` false with the rest of the mailbox unreachable. Shipped's cursor read only `date`, which never changes for a row, so its Pass-1-in-place was harmless; `3b31fdb4d` put a MUTABLE field into the key without giving Pass 1 a reposition. **Fixed at the cursor, not in Pass 1**: `loadMoreMessages` now takes `loadedMessages.max` under `InboxOrdering`. Repositioning during a reload is what Pass 1's in-place write and its `if existing != assigned` skip exist to prevent (`@Observable` churn → scroll-position jumps); taking the maximum is one O(n) pass over an already-bounded window and changes no render behaviour. Pinned by `InboxPaginationCursorTests`, which asserts the OUTCOME (the next page is full, holds no already-loaded row, and leaves `hasMoreMessages` true) and asserts the PREMISE — that the reload really did leave the array out of order — so it cannot go quietly vacuous if Pass 1 ever starts repositioning.
