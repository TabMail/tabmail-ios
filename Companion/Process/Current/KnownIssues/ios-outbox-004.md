## Full detail

**A forward that is undone and re-sent is recorded, locally and on the server, as a REPLY.** `UndoReopenCompose.composeView(for:)` builds `ComposeView(account:prefillDraftId:retainedDraftAuthority:)` and supplies **no** `isForward`, so the view's `isForward` property takes its `= false` default. The compose still LOOKS and QUOTES like a forward, because `loadDraftOrPrepopulate` reads the persisted row (`quoteIsForward = draft.isForward`, and `resolvedForward = replyTo != nil ? isForward : draft.isForward` — `replyTo` is nil here, so the ROW wins) — but `ComposeView.send` captures the **view** property into `AuthoredSendSnapshot.isForward`, and that snapshot is what both durable consumers read. **Concrete reachability:** IMAP/iCloud account; user opens a message and taps Forward (`MessageDetailView` → `ComposeView(replyTo: msg, isForward: true)`, and `MessageDetailView+Actions` for the swipe entry); sends; taps Undo on the send toast inside the hold window. `PendingSendService.undo()` RETAINS the `Draft` row (it returns a `RetainedDraftAuthority`; it does not delete) and `RootView` presents `UndoReopenCompose`. The user taps Send again. **Wrong outcome, four parts:** (1) `AccountManagerOutbox.persistQueuedSend` takes the `else` arm and runs `UPDATE messageHeader SET isReplied = 1` on the parent instead of `isForwarded`; (2) the same arm CLEARS a `reply` action tag the parent legitimately carried (the user forwarded, they did not reply); (3) `OutboxMessage.isForward` is stored false, so on delivery `AccountManagerOutbox.deleteCompletedSendAtomic` queues `PendingOperation(type: .markReplied)`; (4) `IMAPProvider.markReplied` STOREs `[.answered]`, so the server gets **`\Answered`** and never `$Forwarded` (`IMAPProvider.markForwarded`'s `.custom("$Forwarded")` is never reached). Sync does not repair it — `SyncEngineDeltaSync`/`SyncEngineFullSync` assign `header.isForwarded = info.isForwarded` from server flags, so the next pass CLEARS the locally-correct forwarded badge (set optimistically by the FIRST, discarded send) and leaves the wrong `isReplied`. **Attribution.** The missing argument is **class B** — `UndoReopenCompose.swift` is byte-identical at `2cfc4d979` and HEAD. The HARM is **class A**: before `a1f17499a`, `ComposeView.send` passed `replyTo?.id` (nil on this path) as `replyToHeaderId`, so `persistQueuedSend`'s `guard let originalId = replyToHeaderId` short-circuited and NO flag, tag or op was written at all; `a1f17499a` correctly restored the parent (`snapshot.resolvedReplyTarget?.id`) and thereby armed the wrong-flag branch. **Shipped `v1.6.38` does NOT have this defect** — `git show 07a4bb703:TabMail/Views/Compose/UndoReopenCompose.swift` passes `isForward: snapshot.isForward` and `PendingSendService.ReopenSnapshot` there carries an `isForward` field, populated from `draft.isForward`. The v3 reopen was re-shaped around `RetainedDraftAuthority` and the mode was not carried across. **A SECOND, wider consequence of the same capture, not previously reported:** `ComposeView.send`'s save-before-send writes `ownedDraft = Draft(… isForward: snapshot.isForward …)`, so the resend also FLIPS the persisted row's `isForward` to false while its primary key stays `forward:<accountId>:<stableId>`. A later reopen of that row then renders reply attribution for a forward, and `Draft.resolveReplyToHeader`'s Strategy 2 dead-ends on `guard draftKey.hasPrefix(prefix)` (prefix `"reply:"` against a `"forward:"` key), which can escalate a later send from mis-flagged to BLOCKED. That write is class B (present at `2cfc4d979`), but it is only reachable through the class-A activation above. **Why REGISTRABLE and not BLOCKING:** the mutation lands on the correct message (`resolveOriginalMessage` resolves the real parent), no queued op is dropped or wedged, the forward itself is delivered with its own body and attachments, and nothing is misattributed to a different message — so it is outside the non-recoverable set. It is registered rather than shrugged off because sync converges on the WRONG answer rather than repairing it, and the user has no in-app way to clear a server-side `\Answered`. **Test coverage does not reach it:** `ComposeSendReplyTargetTests.undoSendReopenSendsAndThreads` (suite type `ComposeSendReplyTargetTests`, file `TabMailTests/Views/ComposeSendReplyTargetTests.swift`) constructs `draftId = "reply:acc1:orig@example.com"` with `insertDraft`'s default `isForward: false` and drives its send through `driveSend`, whose own `isForward` is an independent parameter defaulting to false — so the suite never models a forward, and never models the view-property-versus-row divergence at all.

✅ **FIXED by `f2e918a4e`, "Restore the forward mode on Undo reopen; guard the reply-target read".** **The invariant that now holds:** the mode a resend is recorded under is the mode of the **persisted draft row**, on every compose entry point including the Undo-Send reopen — so a forward that is undone and re-sent is recorded as a **forward**, locally and on the server, and the parent gets `isForwarded` + `$Forwarded` rather than `isReplied` + `\Answered`, with no legitimate Reply action tag cleared. **A1 — this is RESTORATION, not authoring:** shipped `07a4bb703:UndoReopenCompose.swift` builds the reopened compose with `isForward: snapshot.isForward`, its `ReopenSnapshot.isForward` populated from `draft.isForward`; v3's `ReopenSnapshot` is `{ id, authority }`, so the SAME source of truth — the retained row's own `isForward` column — is read in the one `dbPool.read` that already ran for `Account`. **A7 census re-run independently:** production sites that bind a persisted `Draft` row are exactly two — `DraftComposePresenter` (which already passed the mode) and `UndoReopenCompose` (which passed none); `ReopenSnapshot` has exactly one consumer; every other `ComposeView(` site supplies `replyTo` and, for forwards, `isForward: true`, and a fresh reply/forward derives its draft key FROM `isForward`, so property and row agree by construction. **The instance IS the class: one site.** **ONE addition on top of the restoration** (A1 corollary 3 — the release is a floor, not a ceiling): shipped read the mode through a `try?`, and a thrown read there would silently supply `false` and re-create this exact defect, so the retained-authority branch of `loadDraftOrPrepopulate` now **fails closed** when the row's `isForward` disagrees with the mode the view was constructed with — a disagreement that can only mean *"we could not read the mode"*, never a fact about it. Scoped to the retained-authority path deliberately, so a row already flipped by the superseded bug still opens normally everywhere else.
