## Full detail

**THE MECHANISM, IN ONE SENTENCE.** `AccountManagerOutbox.attemptSentAppend` looks up the account's `Folder` row with `role == FolderRole.sent`; when there is none it logs a warning and calls `markAppendedToSent`, which sets `appendedToSent = 1` — and `finalizeOutboxMessage` gates on exactly `fresh.sentAt != nil, fresh.appendedToSent` before running `deleteCompletedSendAtomic`, so the durable `OutboxMessage`, its attachments directory and the owning `Draft` directory are all removed. SMTP delivery already happened, so the recipient has the mail and the sender has no copy of it anywhere — not locally, not on the server — and no ordinary sync can reconstruct it, because there is no server-side artifact to sync FROM.

**REACHABILITY — CORRECTED, BECAUSE THE REPORTED PREMISE WAS WRONG AND THE CORRECTION IS THE DIFFERENCE BETWEEN "ordinary IMAP" AND A NARROW EDGE.** The finding as reported claimed role detection *"omits `\Sent`"*. It does not. `IMAPProvider.mapRole` checks the RFC 6154 SPECIAL-USE attributes **first** — `if attributes.contains(.inbox) { return .inbox }` / `if attributes.contains(.sent) { return .sent }` — and only then falls back to the four-name English list `["sent", "sent messages", "sent items", "sent mail"]` in `IMAPProvider.canonicalNames`. So this is NOT reachable on any server that advertises SPECIAL-USE, which is the ordinary modern case. It requires a server that advertises **no** SPECIAL-USE **AND** names its Sent folder outside that four-name English list — e.g. a localized Sent folder on an older or minimally-configured IMAP daemon. Real, but narrow. ⚠️ **A premise that widens a row's reachability is load-bearing in both directions**: had it been accepted, this would have been registered as an ordinary-configuration data loss and would very likely have been *fixed* rather than accepted, on a false picture of who it affects.

**BASIS IN THIS CODEBASE — SHIPPED, WITH ONE CORRECTION TO THE "byte-identical" CLAIM.** `mapRole` **is** byte-identical to shipped `v1.6.38` (`git show v1.6.38:TabMail/Providers/IMAPProvider.swift`), attribute checks first and the same four-name fallback — so the reachability above is shipped behaviour, not a v3 regression. The `guard let sentPath else` arm is **NOT** byte-identical, and the difference makes v3 **stricter**: shipped ran `await markAppendedToSent(outboxId:)` and then `return true` **unconditionally**, while the current arm is `return await markAppendedToSent(outboxId:)` — it returns the write's own result, so a failed `UPDATE` no longer reports success. The LOSS is identical in both; only the honesty of the return value changed. Recorded this way rather than as a flat "byte-identical to `v1.6.38`" because that sentence would have been false at the line that matters, and a false provenance claim is exactly what `IOS-DOC-002` is about.

**THE COUNTERFACTUAL, PER `MIS-026` — stated because the obvious alternative is worse, not because it is unattractive.** Returning `false` here instead of marking the append complete would preserve the sender's copy — and would **wedge** the outbox row. `finalizeOutboxMessage` would never fire, the row would sit with `sentAt != nil, appendedToSent == false` forever, and `drainPendingSentAppends` would re-attempt on every pass an append that cannot succeed because there is no Sent folder to append to. **A wedge is in the non-recoverable set** (the never-drop wedge corollary: a lane that starves forever is not recoverable by sync or by one ordinary gesture), whereas this is a **bounded** loss of the sender's own copy of a message that was **successfully delivered**. Under THE MANTRA the bounded, already-delivered case is the one to accept. **The two candidate behaviours are inverses of each other**, which by `MIS-005` is the signal that neither is the fix — and it is why this is registered rather than patched.

**WHY THIS IS AN `ACCEPTED LIMITATION` AND NOT A `CLOSED AS A DECISION`.** There is no defect to adjudicate in the send path: it does exactly what it says. What is missing is a **capability** — TabMail has no way to discover, select, or create a Sent destination for an account whose server offers neither a SPECIAL-USE `\Sent` attribute nor an English-named Sent folder. **The real remedy is product work outside this refactor**: a Sent-folder picker in account settings, an IMAP `CREATE` of a Sent mailbox at account setup, or widening `canonicalNames` with localized names (the weakest of the three — it trades one hard-coded English list for a longer hard-coded list, and still fails on the next language).

**RECOVERABILITY, WITH THE NON-RECOVERING CASE NAMED (`MIS-IOS-008`).** Partially recoverable **before** finalization and **not at all** after: the window is between `markAppendedToSent` and `deleteCompletedSendAtomic`, and nothing user-facing exists in it. Once finalized there is no local copy and no server copy, so the non-recovering case is simply **the ordinary case for an affected account** — which is why it is registered with its reachability rather than dismissed as rare. It does NOT enter the blocking set, because nothing is misattributed (no wrong message is mutated), no user intention is dropped (the SEND intention was executed — the message was delivered), nothing bricks, and no secret is exposed. The user loses their own record of a message the recipient received.

**NOT OWNED BY AN EXISTING ROW — re-verified with two differently-shaped searches, per the brief.** (1) Symbol-shaped: `grep -n 'attemptSentAppend|markAppendedToSent|sentPath' KNOWN_ISSUES.md` → **0 hits**. (2) Prose-shaped: `grep -in 'no sent folder|no recognized sent|sent copy|role == .sent|Sent mailbox' KNOWN_ISSUES.md` → **2 hits**, neither this mechanism — `IOS-IMAP-011` (the removed same-RFC sibling read-flag expansion) and `IOS-SETTINGS-001` (index-wipe consent copy). The two adjacent outbox rows own **different** mechanisms: `IOS-OUTBOX-001` is a row stranded in `sending` with `sentAt == nil` after a status-write exhaustion (durable message and attachments both still present); `IOS-OUTBOX-006` is the reconciliation latch that could return an in-flight send to `.queued` and let it be discarded. Both are about a message whose SEND state is uncertain; this row is about a message whose send **succeeded** and whose sender-side COPY does not exist.

**AMENDMENT 2026-11-11 (tabmail-ios #533, partial): THE REACHABILITY ABOVE WAS UNDERSTATED IN TWO WAYS, BOTH NOW FIXED; THE LOCALIZED-NAME CASE STAYS ACCEPTED.** (1) `mapRole` was given the FULL mailbox name, so on a server that keeps every folder under INBOX (`INBOX.Sent`, `INBOX/Sent`) and sends no attributes, even an ENGLISH Sent folder got no role. The name fallback now matches a folder directly under INBOX or the personal-namespace prefix (`IMAPProvider.roleMatchName`; a first version matched the last segment of any path, which let user folders such as `Clients/Sent` take roles, and was narrowed in review on 2026-11-12); any other nested folder is compared whole and stays ordinary, and INBOX still matches only as the whole name. (2) `fetchFolders` used a plain LIST, where RFC 6154 §2 makes the special-use attributes a MAY; only `LIST ... RETURN (SPECIAL-USE)` must carry them. `IMAPProvider.listMailboxesWithSpecialUse` now calls the fork's `listSpecialUseMailboxes()` when the server advertises `SPECIAL-USE` and `LIST-EXTENDED` (the RETURN option belongs to the extended LIST) and merges its attributes onto the plain listing by name; without the capability it is NOT called, because on such a server it guesses attributes from name substrings. What remains is exactly the original narrow case: no SPECIAL-USE at all AND a Sent folder named outside the English list. Creating a Sent folder for that case was an open owner decision when this paragraph was written; it is now built (next amendment). Both fixes reach only folder rows created after the change: `fullSync` never rewrites an existing row's role, and an affected existing account can assign the role in Settings > Folder Roles. Tests: `IMAPFolderRoleDiscoveryTests` (FakeIMAPServer, red-first).

**AMENDMENT 2026-11-12 (tabmail-ios #533): FIXED BY THE SECOND REMEDY, "an IMAP `CREATE` of a Sent mailbox".** Owner ruling: when the server has no Sent folder (none found by SPECIAL-USE or by name), create a folder named "Sent" on the user's IMAP server and put the copy there; no further fallback chain. `AccountManagerOutbox.attemptSentAppend` no longer has the `guard let sentPath else { markAppendedToSent }` arm: it passes `sentFolderPath: nil` to `EmailProvider.appendToSentFolder`, and `IMAPProvider.sentFolderPathCreatingIfNone` first asks the SERVER for its Sent folder with the same discovery folder sync uses (`listMailboxesWithSpecialUse` + `discoveredRoles`), because a missing local Sent row does not mean the server has none: `fullSync` never rewrites a stored role, so an existing account's real Sent folder can still be stored as an ordinary folder, and the first send can precede the first folder sync. A Sent folder found there takes the copy and no CREATE is sent, so no duplicate Sent folder is made. Only when the server has none does it CREATE "Sent" in the personal namespace (`INBOX.Sent` under an `INBOX.` prefix), then append with the usual Message-ID dedup. A refused CREATE is not an error (the usual cause is that the folder already exists); the APPEND's SELECT decides, and if the folder really is missing the append throws, `appendedToSent` stays false, the row is NOT finalized, and `drainPendingSentAppends` retries on the next drain. **The wedge counterfactual above no longer applies**: it assumed "there is no Sent folder to append to" was permanent, and now the first append makes one; a server that refuses CREATE on every drain leaves the row owed and retried rather than finalized without a copy, which keeps the sender's copy recoverable instead of losing it. Gmail and Exchange ignore the nil path (their APIs save the copy). The created folder gets the Sent role by name on the next folder sync. Tests: `OutboxSentFolderCreationTests` (real drain + `IMAPProvider` against `FakeIMAPServer` with `requireExistingMailboxes()` and CREATE, red-first).
