## Full detail

When an IMAP server omits `INTERNALDATE`, the existing parser may fall back to the message-authored `Date` header. That exceptional fallback predates this work and remains byte-identical to v1.6.38; normal IMAP `INTERNALDATE`, Gmail `internalDate`, and Graph `receivedDateTime` remain authoritative.

✅ **CLOSED AS A DECISION (2026-08-04) — the authored `Date` is the deliberate last-resort fallback, and every alternative is worse.** Verified at the tip in `IMAPProvider`: `if let internalDate = info.internalDate { date = internalDate } else if let parsed = info.date { … }`, with a third arm that treats "both sources failed" as a fetch failure. `INTERNALDATE` is authoritative whenever present; the authored header is reached **only** when the server returns none. **Basis:** `Date()` (arrival-now) would make an old message the newest thing in the Inbox — a *silent* corruption of the sort order, which is worse than a wrong one you can see; a nil or epoch-0 date buries it forever. The authored `Date` is the only remaining evidence of when the message existed, and the code is byte-identical to shipped `v1.6.38`, so it has been smoke-tested by real users. **Accepted cost:** a possibly-wrong sort position for messages from a nonconforming server. **Recoverability:** there is no durable wrong state to recover — the value is re-derived on every fetch, so a server that starts reporting `INTERNALDATE` self-corrects on the next sync. **The negative case that was searched for** is a state in which the wrong date drives a durable wrong DECISION. The one that would matter is IMAP sync windowing, and Data Integrity Rule 4 / ADR-IOS-042 already forbid date-windowed sync — `SyncEngine.selectStaleHeaders` gates on `provider.staleWindowMode`, `.uid` for IMAP — so the authored date can never reach a fetch/keep/delete/cursor decision. **None found.** ⚠️ **THIS CLOSURE AMENDED THE FILE'S CLOSING *Mandatory final review guard*.** Read literally, its absolute (*"never substitute the message-authored `Date` header"*) forbade what the shipped code does, which is the `feedback_absolutes_need_the_negative_case` / MIS-019 failure class live in this file. The guard now names the one exception it always had. See that section for the correction and its reasoning.

⚠️ **SCOPE WIDENED 2026-08-05 — this row's verification was scoped to `IMAPProvider`, and the class is larger than that (`MIS-006`: a confirmed site is a LEAD, not a scope).** `NSEDataBridge.insertNewHeaderFromStaging` builds its header with `let msgDate = msg.date.map { Date(timeIntervalSince1970: $0) } ?? Date()` — i.e. on a NULL-dated staged row it stamps **arrival-now**, which is precisely the substitution the *Basis* paragraph above names as the **worse** option ("would make an old message the newest thing in the Inbox — a *silent* corruption of the sort order"). The sibling `StagedMessage.toInboxRow()` does the same for the ADR-IOS-049 display projection. **No code change, and no regression:** both are **byte-identical to shipped `07a4bb703`** (same statement, at `:2679` and `:3029` there), so they have the same real-user smoke-testing the `IMAPProvider` arm relies on. The reasoning above still holds for them with one substitution — the NSE has **no authored `Date` header to fall back to**, because a staged row's `date` is already the parsed value and a nil there means the push payload carried none at all, so the choice is arrival-now or nothing rather than arrival-now or authored. **Recoverability is the same and is what keeps this closed:** the staged row is superseded by the ordinary sync's own header for that message, which carries the provider's authoritative date, so a wrong NSE-stamped date is corrected on the next sync rather than persisted. It also cannot reach a durable decision for the same Rule-4 reason — IMAP sync windows by UID, never by date. **The non-recovering case:** a message that is *only* ever seen through the NSE and never re-fetched by a sync pass would keep the arrival-now stamp; no such path is known, because every staged row is a notification for a message the next sync enumerates.
