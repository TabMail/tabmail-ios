## Full detail

**Provider-registry teardowns that are never AWAITED, so the registry can still hold the stale provider when the next test starts.** `AccountManager` is an `actor`, so an unregister launched from a `defer { Task { … } }` is **merely enqueued** — the test returns before the actor runs it. That is the exact shape all three of the retired `withRegisteredProvider` doc blocks documented as wrong, and which the consolidated `TestProviderRegistry.withRegisteredProvider` (`TabMailTests/Infrastructure/ProcessGlobalTestState.swift`) exists to prevent: its own doc says *"🚨 The unregister MUST be awaited on BOTH exits — never `defer { Task { … } }`."* ⚠️ **THE CENSUS IS TWELVE SITES ACROSS SIX SUITES — corrected here, because the figure this row was raised with was wrong twice over.** The report said *"seven sites across six suites"* while its own enumeration listed **nine across five**, and **both the count and the enumeration missed `AccountManagerQueueDrainTests` entirely**. Re-censused directly against the tree: `BackfillOnlyFolderEpochTests` **4**, `AccountManagerQueueDrainTests` **3**, `InboxGestureActionTests` **2**, `NotificationFolderNativeIdentityTests` **1**, `OutboxStrandedClaimTests` **1**, `QueueCoreInvariantTests` **1** — **12 sites, 6 suites.** Eleven are literally `defer { Task { await …unregisterProviderForTesting… } }`; the twelfth (`QueueCoreInvariantTests`' private `finish(_:)` helper) is a bare un-awaited `Task { }` in a synchronous teardown, which is the same defect through a different shape — recorded distinctly so a mechanical `defer { Task {` grep does not miss it. Every OTHER `unregisterProviderForTesting` call site in the corpus is correctly `await`ed. **Attribution:** none is candidate-introduced; all predate this push. **Why REGISTRABLE and not BLOCKING — accepted cost stated plainly:** it has produced **no observed failure of its own**, but it is the same **cross-suite process-global leakage class** as `IOS-TEST-006`, which has already produced two, and `.serialized` does not compose across suite boundaries so ordering cannot contain it. A stale provider surviving into the next suite is precisely how a test asserts against something other than what it thinks it registered. **Do NOT fix it in this push:** awaiting the teardown changes those tests' setup semantics, which is a behavioural change to six suites and belongs in its own scoped task after the audit train. The fix shape is to route all twelve through the existing consolidated `TestProviderRegistry.withRegisteredProvider` rather than hand-editing each `defer`.
