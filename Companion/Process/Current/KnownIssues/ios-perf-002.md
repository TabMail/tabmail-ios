## Full detail

**The mechanism.** `PriorityGate` has two `write` overloads. The `async` one enters `DatabaseWriteQueue` at the caller's tier; the synchronous one is documented in `PriorityGate.swift` as *"Sync write — can't `await`, so it can't enter the queue; passes through."* **A pass-through write has no tier at all** — it goes straight to GRDB's writer and holds SQLite's single writer for the duration, *ahead of every `.priority` write already queued behind `DatabaseWriteQueue`*, which is the exact contention the tiering exists to prevent. **The census, by the shared dependency rather than by one symbol (`MIS-006`):** `rg -n 'dbPool\.write' TabMail/Services/Sync/SyncEngineMaintenance.swift` → **five synchronous sites across four functions** — `runPruneIfOverBudget` (**two** sites), `runEvictStaleBodies`, `refreshAICacheTTLAndPurge`, `runPurgeExpiredAICache` — plus a **fifth function**, `runEvictChatSessions`, which reaches the same overload *indirectly* through `ChatStore.evictInboxSessionsSync` / `evictMessageDetailSessionsSync` / `evictComposeSessionsSync`. A grep for `dbPool.write` alone finds four functions and misses the fifth; the state, not the call text, is what defines the class.

**Basis in this codebase.** All five are **byte-identical to shipped `07a4bb703`** — this is not a v3 regression, and the tree has run this way in every shipped release. They are also **batched**: each write is one bounded batch inside a loop with a `batchEmpty` terminator, so a single hold is bounded by the batch size, not by the table. That is the material difference from `runRefreshPlannerStatisticsIfStale`, which was converted to `async` because it was **one unbounded ~8.5 s `ANALYZE`** — a single hold long enough to stall the UI outright. A bounded batch is a different risk class from an unbounded one.

**Relationship to the round-6 `runWALMaintenance` tier fix, stated because the two look like the same bug.** That fix corrected the *pool* handed to `SyncEngine.runWALMaintenance` (`SyncScheduler` now passes `AppDatabase.backgroundPool`, not `AppDatabase.dbPool`). It changes behaviour **only for writes that ENTER the queue** — i.e. the `async` overload, which reads `effectivePriority`. For these five the pool's tier is **never consulted**, because the pass-through overload ignores it entirely. So the two are complementary, not duplicates: one makes the tier correct where a tier is read, this row records the sites where no tier is read at all. Handing these functions a `.background` pool does **not** fix them.

**Accepted cost.** A foreground `.priority` write can wait behind one maintenance batch's writer hold. **Recoverability.** Total: every write still completes, in order, with the same result; nothing is dropped, nothing is misattributed, no user intention is at risk. The cost is *latency only*, it is bounded per batch, and maintenance runs on the background pass rather than the launch path — so per THE MANTRA this is registered, not mechanised. **The non-recovering case, named per `MIS-IOS-008`:** it stops being recoverable if a batch loses its bound. If any of these five is ever changed to write the whole candidate set in one transaction — or if `SyncConfig`'s batch sizes are raised far enough that one hold spans seconds — the argument above collapses, because the accepted cost is bounded *by the batch*, not by the pass-through being harmless. Anyone widening a batch here must convert the function to `async` and await the queued overload first, exactly as `runRefreshPlannerStatisticsIfStale` did.

⚠️ **Stated negatively (`MIS-019`):** this row does **not** say the synchronous overload is fine in general. It says these five are bounded, shipped, and latency-only. A *new* pass-through write, an unbounded one, or one on the launch path gets no cover from this row.

## Amendment 2026-11-23 (#1354): the evict step's batch was bounded in rows, not in work

**What broke this row's argument.** `runEvictStaleBodies` was "bounded per batch" only in the rows it EVICTED or KEPT per write. Each page was `messageBody WHERE fetchedAt < cutoff LIMIT chunk OFFSET skipCount`, run INSIDE the write, and `skipCount` grew by every body the rules kept (inbox, recent per folder, undo-protected, protected orphans). `messageBody` had no index on `fetchedAt`, and `fetchedAt` is stored after `htmlContent` and `attachmentsJSON`, so every page walked the table from its start, reading the overflow pages of every kept body, while holding SQLite's single writer. On a 1.11.6 device log (2026-11-23) a page held the writer 14-16 s; Send's `.priority` writes (the draft save, the queued send, the outbox claim) and the unread recount waited behind it (`DBwrite EXEC[priority] sched=` 13,936 to 16,017 ms, body 1 to 9 ms). The evict step's median went from about 2 s (logs of 2026-11-06/07) to 35 s as the kept stale bodies grew. This is the case the clause above names ("check both the batch size and the plan of every statement executed inside it"): the plan of the page query was a scan that grew with the offset. Beyond the hold, every run read the whole table (the `fetchCount` it ran first, then each page), however few bodies were stale: disk reads, and so battery, on every maintenance pass.

**Fix (#1354).** The stale set is found through a purpose-built index, `messageBody_staleEvict` on `messageBody(fetchedAt)` (ADR-IOS-029 rule 1). Each write's page is a keyset seek on it: the next `pruneChunkSize` bodies older than the cutoff after a `(fetchedAt, rowid)` cursor, in index order (`SyncEngine.staleBodyPageSQL`; `EXPLAIN QUERY PLAN`: `SEARCH messageBody USING INDEX messageBody_staleEvict ((fetchedAt,rowid)>(?,?) AND fetchedAt<?)`, no scan, no sort; before it, `SCAN messageBody`). A write reads the B-tree descent to its page, at most one page of index entries and those rows' leading `id` (never a kept body's HTML), the rules' per-row lookups, and the pages it frees for the bodies it deletes. So one write's hold is independent of the number of kept stale bodies and of the table's size, and a run reads only the stale bodies. The whole-table `fetchCount` is gone. The rules, the orphan fail-safe and the undo protection are unchanged. The write stays the synchronous pass-through overload, which this row's accepted cost covers again now that its batch is bounded in work.

**The index is deferred, and the step is gated on it.** The index joins `SyncEngine.deferredIndexes` (built by the background maintenance pass, IOS-PERF-005), not a migration. Building it reads every body once, seconds on a large cache, and ADR-IOS-029's 2026-08-05 amendment keeps such work off the launch path. Its absence changes no query's result, and nothing names it in an `INDEXED BY`; while it is missing the step does not run (below), so stale bodies stay cached a pass longer. Without it the keyset page would scan and sort the whole table inside each write, a worse hold than the one fixed. So `runWALMaintenance` reaches the step only through `runEvictStaleBodiesIfIndexed`, which skips the step while the index is missing. A pass that finds the index missing skips eviction and builds it later in the same pass; the next pass evicts (a pass that runs after another caller built it evicts at once). **Accepted one-time cost:** the build is one background-tier write that holds the writer for as long as it reads every body, once per install, in the first maintenance pass after the upgrade to complete it. `runWALMaintenance` has two callers, each foreground poll (`SyncEngine.scheduleMaintenanceInBackground`, scheduled after the poll's read stage and before it drains actions, the outbox and the calendar) and the `.full` BGProcessing drain, and the notification extension runs neither, so that pass is whichever of the two comes first. A Send in that window waits behind it once. The alternative, a migration, puts the same read before first paint on that launch.

**Proof the index is needed (a new index needs proof that no existing field or index can carry it).** Before this change `messageBody` had exactly one index, the primary-key autoindex on `id`; no index covered `fetchedAt`, and no other table records when a body was cached.

the rules still evict exactly the archive bodies past the newest `bodyCacheRecentPerFolder`); `StaleBodyEvictWriterHoldTests.oneWriteDoesNotGrowWithTheKeptBodiesWidth` (the same, with the kept bodies' HTML 64 times wider); `SyncEngineMaintenanceTests.evictStepNeedsOnlyItsOwnIndex` (the step runs once its own index exists, with every other deferred index missing); `SyncEngineMaintenanceTests.evictStepWaitsWhenItsIndexCannotBeChecked` (a catalog that cannot be read keeps the step from running); `SyncEngineMaintenanceTests.evictStepIsReachedOnlyThroughItsGate` (production calls the step only through the gate). `StaleBodyEvictRunTests` checks which bodies a run leaves: a `fetchedAt` shared across three pages, stored as text and as a number (every victim evicted, every keeper kept);
