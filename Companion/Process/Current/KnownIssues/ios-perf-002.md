## Full detail

**The mechanism.** `PriorityGate` has two `write` overloads. The `async` one enters `DatabaseWriteQueue` at the caller's tier; the synchronous one is documented in `PriorityGate.swift` as *"Sync write — can't `await`, so it can't enter the queue; passes through."* **A pass-through write has no tier at all** — it goes straight to GRDB's writer and holds SQLite's single writer for the duration, *ahead of every `.priority` write already queued behind `DatabaseWriteQueue`*, which is the exact contention the tiering exists to prevent. **The census, by the shared dependency rather than by one symbol (`MIS-006`):** `rg -n 'dbPool\.write' TabMail/Services/Sync/SyncEngineMaintenance.swift` → **five synchronous sites across four functions** — `runPruneIfOverBudget` (**two** sites), `runEvictStaleBodies`, `refreshAICacheTTLAndPurge`, `runPurgeExpiredAICache` — plus a **fifth function**, `runEvictChatSessions`, which reaches the same overload *indirectly* through `ChatStore.evictInboxSessionsSync` / `evictMessageDetailSessionsSync` / `evictComposeSessionsSync`. A grep for `dbPool.write` alone finds four functions and misses the fifth; the state, not the call text, is what defines the class.

**Basis in this codebase.** All five are **byte-identical to shipped `07a4bb703`** — this is not a v3 regression, and the tree has run this way in every shipped release. They are also **batched**: each write is one bounded batch inside a loop with a `batchEmpty` terminator, so a single hold is bounded by the batch size, not by the table. That is the material difference from `runRefreshPlannerStatisticsIfStale`, which was converted to `async` because it was **one unbounded ~8.5 s `ANALYZE`** — a single hold long enough to stall the UI outright. A bounded batch is a different risk class from an unbounded one.

**Relationship to the round-6 `runWALMaintenance` tier fix, stated because the two look like the same bug.** That fix corrected the *pool* handed to `SyncEngine.runWALMaintenance` (`SyncScheduler` now passes `AppDatabase.backgroundPool`, not `AppDatabase.dbPool`). It changes behaviour **only for writes that ENTER the queue** — i.e. the `async` overload, which reads `effectivePriority`. For these five the pool's tier is **never consulted**, because the pass-through overload ignores it entirely. So the two are complementary, not duplicates: one makes the tier correct where a tier is read, this row records the sites where no tier is read at all. Handing these functions a `.background` pool does **not** fix them.

**Accepted cost.** A foreground `.priority` write can wait behind one maintenance batch's writer hold. **Recoverability.** Total: every write still completes, in order, with the same result; nothing is dropped, nothing is misattributed, no user intention is at risk. The cost is *latency only*, it is bounded per batch, and maintenance runs on the background pass rather than the launch path — so per THE MANTRA this is registered, not mechanised. **The non-recovering case, named per `MIS-IOS-008`:** it stops being recoverable if a batch loses its bound. If any of these five is ever changed to write the whole candidate set in one transaction — or if `SyncConfig`'s batch sizes are raised far enough that one hold spans seconds — the argument above collapses, because the accepted cost is bounded *by the batch*, not by the pass-through being harmless. Anyone widening a batch here must convert the function to `async` and await the queued overload first, exactly as `runRefreshPlannerStatisticsIfStale` did.

⚠️ **Stated negatively (`MIS-019`):** this row does **not** say the synchronous overload is fine in general. It says these five are bounded, shipped, and latency-only. A *new* pass-through write, an unbounded one, or one on the launch path gets no cover from this row.

⚑ **ONE OF THE FIVE STOPPED BEING "byte-identical to shipped `07a4bb703`" IN THE INTERIOR, AND THIS ROW'S BOUND IS ABOUT ROWS, NOT ABOUT WORK PER ROW (round-13 U11).** The fifth function — `runEvictChatSessions` → `ChatStore.evictMessageDetailSessionsImpl` — loops every `msg:%` session inside `dbPool.write` and calls `isMessageInInbox`, which falls through to `ChatStore.findByStableId` exactly when the primary-key lookup fails (i.e. for the sessions the sweep is targeting). A per-row regression inside a bounded batch multiplies the hold by the same factor and this row's cell would not notice. When re-deriving the accepted cost, check both the batch size **and** the plan of every statement executed inside it.
