## Full detail

`CopyUID(nio:)` is constructed inside the tagged-OK handler, so a malformed COPYUID makes `move` **throw after the server already committed the move**. Upstream signals this as `IMAPError.commandFailed("COPYUID …")` while a genuine failure is `IMAPError.commandFailed("Move failed: …")` — the same case, separated only by a message prefix — so discriminating "possibly succeeded" from "failed" is string-based today. v3 therefore **fails toward "possibly succeeded"**: it does not retry the destructive half and drops the op for sync to reconcile. That is the safe direction; a wrongly-assumed failure would re-issue a move that already happened. A dedicated upstream error case would remove the string dependency.

✅ **CLOSED AS A DECISION (2026-08-04) — fail toward "possibly succeeded", and do NOT add a local string matcher.** The decision: when `CopyUID(nio:)` throws inside the tagged-OK handler after the server has already committed, v3 does not retry the destructive half and lets sync reconcile. **Why that direction:** a wrongly-assumed FAILURE re-issues a move that already happened; a wrongly-assumed SUCCESS costs a reconciliation. **Why no fix in this repo:** the premise is a property of the **pinned SwiftMail fork**, not of TabMail — `IMAPError.commandFailed("COPYUID …")` versus `IMAPError.commandFailed("Move failed: …")` is one enum case separated by a message prefix — so the only real fix is a dedicated upstream error case, which is a SwiftMail change and the owner's PR per `feedback_swiftmail_pr_upstream`. Adding a LOCAL matcher on that prefix would be a fallback routine keyed on text the fork can change at any release, forbidden by global rule 4 and fragile in exactly the way this register complains about elsewhere. **The point that makes it a decision rather than a deferral: failing toward "possibly succeeded" needs no discrimination at all**, so the string dependency is never load-bearing for correctness — it would only ever buy a better log line. **Accepted cost:** a move that may or may not have landed, until sync reconciles both folders. **Recoverability:** reconciliation needs both folders sync-reachable. A custom non-favourite folder is excluded from `syncableFolders`, but `IOS-EPOCH-001`'s round-8 correction establishes that on-demand navigation reaches ANY folder (`InboxView.onAppear` → `InboxViewModel.startSync()` → `AccountManager.syncFolders(_:)`, filtering on `!folder.path.isEmpty` alone), so reconciliation is at worst deferred until the user opens the folder — one ordinary gesture. **No permanent non-recovery state found.**

🚨 **CORRECTED AND FIXED 2026-08-05. THE DECISION ABOVE IS KEPT; ITS RATIONALE IS REPLACED, because two of the premises it rested on are falsified at the resolved fork revision `078a09b8`.** Per `MIS-019`, a false justification is worse than none — it invites reversal of a correct instruction — so both are named rather than quietly overwritten. **FALSIFIED PREMISE (a): "v3 does not retry the destructive half and drops the op for sync to reconcile."** The code did the OPPOSITE. `let copyEvidence = try await server.copy(messages:to:)` had **no `catch`**, so the throw propagated out of `IMAPProvider.move` to the generic arm of `AccountManagerQueue.executeSingleOp`, which sets `status = queued`, increments `retryCount`, adds the account to `failedAccounts` and returns `.haltLane`. Nothing was dropped and nothing was left to sync: the throw happens BEFORE the `STORE \Deleted`, so the source is untouched, the next drain re-runs A1/A2/A3 and issues **another `UID COPY`** — one more duplicate at the destination per drain, forever, while the op never retires and the lane stays halted. Durable actions retry without a cap. **FALSIFIED PREMISE (b): "genuine and malformed failures share `IMAPError.commandFailed`, separated only by a message prefix."** Not at `078a09b8`. `CopyHandler` **overrides** `handleTaggedErrorResponse` to fail with `IMAPError.copyFailed`, so a genuine tagged NO/BAD is `.copyFailed`; a timeout is `.timeout`; a dropped connection is `.connectionFailed`. The malformed case is `.commandFailed`, raised by `CopyUID.init(nio:)`'s three throw sites (cardinality mismatch, invalid UID range, >1,000,000-UID expansion). **They are different enum cases, so the discrimination this row said could only be string-based is available BY TYPE** — which is what makes the fix admissible under the standing no-string-matcher rule rather than a violation of it. **THE FIX:** catch `IMAPError.commandFailed` **only** around the `server.copy(...)` call and map it to `copyEvidence = nil`, routing it into the already-designed, already-audited no-evidence path — the same path a server that withholds `COPYUID` entirely takes. That path authorizes at most the REVERSIBLE `\Deleted` STORE (tagged OK ANDed with `liveSourceUIDs`) and makes the irreversible `UID EXPUNGE` **structurally unreachable**, because `copyProvenUIDs` is empty ⇒ `purgeAuthorizedUIDs` is empty. No new durable state, no new terminal exit, no new exit from the queue, no destination `SEARCH` (banned — ADR-IOS-068/D4, `IOS-IMAP-002`). ⚠️ **THE CATCH IS DELIBERATELY NARROW AND MUST NOT BE WIDENED (`MIS-005` mirror image):** catching bare `IMAPError` or a bare `catch` would swallow `.copyFailed` / `.timeout` / `.connectionFailed` and convert a copy that provably did NOT happen into "it may have landed", soft-deleting sources for copies that never occurred. **Pinned by** `NeverDropExitClosureTests.anUnparseableCopyUidMoveIsNeverReCopied`, which asserts the count of `UID COPY` commands on the WIRE across two drains (1, not 2) via a new `FakeIMAPServer.reportCopyUIDWithCardinalityMismatch()` seam — never on a flag or an error type. ⚠️ **ONE PREMISE OF THE FIX IS ITSELF NARROWER THAN THE CODE, and it is recorded rather than assumed:** it is NOT true that `COPYUID` parsing is the only producer of `.commandFailed` inside `server.copy`. `CapabilityHandler.handleTaggedErrorResponse` also raises `.commandFailed` and is reachable through `IMAPServer.executeCommand`'s lazy re-auth and `IMAPConnection.executeCommandBody`'s reconnect, both of which call `refreshCapabilities` → `CAPABILITY`. It needs a server that answers `CAPABILITY` with tagged NO/BAD **and** omits `[CAPABILITY]` from both greeting and LOGIN OK, inside the window between two adjacent `await`s. The disposition is the same either way — no evidence, no expunge reachable, at most a reversible `\Deleted` — so the fix is correct, but **the structural fix belongs upstream in SwiftMail's `CopyHandler`**, which has the tagged response in hand and should distinguish "tagged OK + unparseable COPYUID" from every other `.commandFailed` (owner's PR, per `feedback_swiftmail_pr_upstream`). **`v1.6.38` did not have this defect** — it probed the destination by RFC 822 Message-ID first and took the cleanup-only branch on finding the landed copy — so this was a v3 REGRESSION, introduced when that banned `SEARCH` probe was removed without a replacement for the committed-but-unparseable case. ➡️ **The residual precondition breadth described in the paragraph above now has its own row — `IOS-IMAP-009`** — where the structural bound, the accepted cost, the trigger conjunction and the upstream remedy are recorded. This row is FIXED; that one is an ACCEPTED LIMITATION of the fix, and they are deliberately separate so closing one does not read as closing the other.
