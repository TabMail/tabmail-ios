**CURRENT REACHABILITY NARROWING (2026-08-08, `dd51c74ff`).** When `MOVE` is advertised, TabMail now emits one atomic-only `UID MOVE`; that route never performs the app-owned `STORE \\Deleted` or expunge tail. A source row left `\\Deleted`-but-present by TabMail's move implementation is therefore reachable only on the no-`MOVE` owned route: deliberately on no-`MOVE`/no-UIDPLUS servers, or through an already-registered cleanup failure after the owned route's `STORE \\Deleted` and before its UID-scoped expunge succeeds. The standing fail-closed decision and every unrelated closure in this row remain unchanged.

**HISTORICAL RECORD (retained).** A server without UIDPLUS cannot target an EXPUNGE safely. Archive/move therefore copies the intended message and marks only its source UID `\\Deleted`; destination-exact recovery likewise soft-deletes only the source. The source can remain or relist until the server or another client safely expunges it. Do not restore mailbox-wide EXPUNGE or add provider-wide `\\Deleted` filtering: incomplete visible cleanup is safer than permanently deleting an unrelated pre-deleted message. **v3 re-baseline:** the mailbox-wide `EXPUNGE` that `v1.6.38` still reached — both directly and *through* SwiftMail's `move` fallback, which falls through to a bare, mailbox-wide `expunge()` whenever the UID branch lacks UIDPLUS — is gone. `IMAPProvider.move` no longer calls `server.move` (`3843940cb`) and `saveDraft`'s two former bare expunges now route through the scoped `expungeScopedToTargets`. No production call site issues an argument-less `EXPUNGE`; C3-I5 is enforced unconditionally. **Open decision D3:** nobody has verified whether a `\Deleted` source copy is even rendered today. Hiding `\Deleted` rows at the local merge layer is option (b) and destroys nothing server-side; a server-side mailbox-wide purge is FORBIDDEN. **⚠ AUDIT ROUND 3 — THIS ROW WAS BRIEFLY NOT WHAT THE CODE DID, AND THE CODE IS BACK.** Between `4e08ff720` and round 3, `IMAPProvider.move` opened with `guard await server.supportsUIDPlus else { throw … }`, so on this class of server the move did not "copy and soft-delete" — it **refused before any wire mutation, on every attempt, forever**, and because that refusal's drain arm returns `.haltLane` it also starved every later gesture naming the same message on every future drain. Neither the queued move nor the starved sibling had any user-visible resolution path. Round 3 deleted the guard. What authorizes the source cleanup on a non-UIDPLUS server is now the COPY's own **tagged OK**: RFC 3501 §6.4.7 requires that an unsuccessful COPY MUST restore the destination mailbox, so a tagged OK is a positive statement that the whole named set copied, and SwiftMail surfaces any tagged `NO`/`BAD` as a thrown `IMAPError.copyFailed` (`CommandHandler.processResponse` → `CopyHandler.handleTaggedErrorResponse`). A UIDPLUS server is still held to per-member `COPYUID` and still refuses without it. **The accepted cost is exactly the one this row already stated** — the source copy stays, `\Deleted`, and may remain visible or relist — and it is preferred over BOTH alternatives: over the permanent queue wedge, and over a folder-wide EXPUNGE that irreversibly destroys unrelated pre-deleted mail. This row, not a fresh judgement, is the governing decision for that choice.
