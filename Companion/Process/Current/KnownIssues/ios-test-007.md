## Full detail

**The epoch-stamp oracle is structurally blind to RFC-less rows — and that is a coverage note, not a gap in the app.** `FakeIMAPServer.epochStampViolations(mailbox:localRfc822ByUID:)` compares, per UID, the server's normalized RFC 822 Message-ID against the local one the caller supplies, and reports a violation on disagreement. Its **local** side comes from `EpochVerifiedBootstrapTests.localRfc822ByUID(pool:folderId:)`, whose loop is `guard let uid = Int(header.messageId), let rfc = header.rfc822MessageId, !rfc.isEmpty else { continue }` — **so a row with no RFC 822 Message-ID is skipped and never enters the map at all.** An RFC-less survivor is therefore structurally invisible to `EpochVerifiedBootstrapTests.aStampedFolderNeverHoldsAForeignHeader`, which is the test that oracle backs. 🚨 **STATED WITH ITS QUALIFIER, because without it this reads as a C3 hole and it is not one:** actual **mutations** are covered by a different and stronger oracle — `FakeIMAPServer.recordOracleCheck(command:mailbox:uids:state:)` runs from inside the already-held state lock at **every** mutating command (`EXPUNGE`, `UID STORE`, `UID MOVE`, `UID EXPUNGE`, `UID COPY`), **BEFORE** the mutation is applied. So no wrong-message mutation can slip past on an RFC-less row; what this oracle cannot see is a *stamped-folder-holds-a-foreign-header* condition on rows that carry no RFC id. Since an RFC-less row has no content witness by construction, there is nothing for an RFC-keyed oracle to compare — **the blindness is a property of the evidence, not an omission in the harness.** **Registered as an OPTIONAL harness note, not as a defect and not as work anyone owes.** If it is ever taken, the shape is a second, non-RFC witness keyed on something an RFC-less row does carry; anyone proposing that must first say what wrong outcome it would catch that `recordOracleCheck` does not, because "more oracle" is not by itself a reason.
