## Full detail

**What the range broke, and what was fixed.** Adding `id ASC` to the keyset `ORDER BY` (correct, and it stays — it is what makes the SQL order total, `IOS-SCROLL-004`) made SQLite abandon `messageHeader_triage_display` **entirely** and take `messageHeader_inbox_display` plus a sort of the whole folder. An index SWITCH, not an extra sort term, which is why it costs an order of magnitude rather than a few percent: at 100k rows in one folder, **18.28 ms → 1.91 ms** with the hint (Mac, SQLite 3.51.0, median of 7; device 2–4×), reproducing in EVERY statistics regime including a schema-only empty database, so `ANALYZE` fixes neither half. `InboxListReader.fetchSync` is `@MainActor` with a blocking `dbPool.read`, its loop runs ONCE PER DISPLAYED FOLDER, and it is on first paint and on every scroll page — a unified inbox multiplies it. Fixed by naming the index the planner used to choose, with no migration and no new index.

**THE RESIDUAL THIS ROW IS ACTUALLY ABOUT — the hint is withheld under `filterUnread`, and that is the fix's mirror image rather than an omission.** With the unread filter on, the planner picks `messageHeader_folderId_isRead`, whose selectivity is the entire point of that mode. Measured on the same 100k folder with **three** unread rows — the state triage exists to drive users toward — forcing the triage index costs **18.891 ms vs 0.022 ms**, 860× the wrong way. It is not one-sided: at 33k unread the hint WINS, 1.44 ms to 14.29 ms. The crossover is a per-folder unread ratio, and `ANALYZE` records table- and index-level statistics, not the live unread fraction of one folder, so a static hint is provably wrong for one of the two populations. **Where there is no dominating answer, the planner keeps the decision.**

**The accepted cost, stated as the population that pays it.** A user with a large folder AND a large unread count in triage mode pays the un-hinted plan (~14 ms Mac ⇒ ~28–56 ms device at 33k unread of 100k) where the hint would have been faster. That is latency only: the same rows in the same order, later. It is the same accounting as `IOS-PERF-003` — an opt-in mode, bounded, recoverable by completing.

**Pinned two-sided, so "completing" the fix fails.** `DatabaseIndexTests.unreadFilteredTriagePageIsNotForcedOntoTheTriageIndex` asserts the production statement carries **no** `INDEXED BY` under `filterUnread` and that its plan seeks `isRead=?`. Applying the hint uniformly turns it red. `triageFirstPageDoesNotSortTheWholeFolder` is the other side, and is two-sided in its own right: it plans the un-hinted statement in the same test and asserts the regression is STILL there, so a green result cannot come from a planner that never sorts.

**⚠️ A TRAP THE NEXT READER WILL WALK INTO, recorded because it silently disarms the control above.** The `LIMIT` in `durableQuerySQL` is a **literal**, not a bound parameter, and that is load-bearing: SQLite folds a literal `LIMIT` into its cost model and cannot fold a bound one, so the two forms PLAN DIFFERENTLY. On the `v83` schema with an EMPTY `messageHeader`, `LIMIT ?` makes the un-hinted triage query pick `messageHeader_triage_display` anyway while `LIMIT 50` picks `messageHeader_inbox_display` and sorts everything. GRDB emitted the literal, so the rewrite changed only the hint — but parameterising it "for cleanliness" would make the pre-fix half of the control stop reproducing the defect it exists to demonstrate, and the test would pass while proving nothing.

**Why the query is raw SQL at all.** GRDB's query interface cannot express `INDEXED BY` (no `indexedBy`/`notIndexed` anywhere in `GRDB/QueryInterface`). Both hinted statements are NAMED — `InboxListReader.durableQuerySQL` and `ChatStore.findByStableIdSQL` — following `MessageContentStore.ownersSQL`, so the plan invariants are asserted against what production executes rather than against a copy that drifts. Both fail SAFE: a migration renaming or dropping either index makes the statement **throw**, which the inbox turns into an empty list until the next reload and the chat resolve turns into "unresolved" — loud, never a wrong row. `InboxListReaderStatementTests` is the drift guard for the rewrite itself: 24 shapes (2 modes × unread on/off × 0/1/2 labels × cursor/no cursor) run both the new statement and the pre-rewrite query-interface form and compare row-id sequences, with a non-vacuity assertion that all 24 ran and none was empty, plus a control reproducing a swapped keyset argument.

**Recoverability, with the NON-RECOVERING case named (`MIS-IOS-008`).** None — the residual is spent latency on an opt-in filter; nothing is wrong afterwards and no state needs repair. **What would re-open this row:** the unread filter becoming non-opt-in (a default chip, a restored filter on launch, a filter set by a shortcut or intent); `messageHeader_folderId_isRead` being dropped or reshaped; or evidence that the unread-heavy population is the common one rather than the tail, which would flip which side of the crossover deserves the static hint.
