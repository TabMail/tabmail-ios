## Full detail

**`userLabel`'s primary key is the label id ALONE (`t.primaryKey("id", .text)`), but a label id is only unique WITHIN an account — so two accounts that share a label name share one row.** The id is provider-supplied and not namespaced: the Gmail arm of `SyncEngineFullSync` sets `labelId = info.path`, and the IMAP/keyword arms in `SyncEngineFullSync`, `SyncEngineBackfillDeep` and `SyncEngineDeltaSync` all set `UserLabel(id: labelId, accountId:, name: labelId, isSystem: false)` from the raw keyword. Two Gmail accounts each having a `Receipts` label, or two IMAP accounts each using a `work` keyword, therefore collide on the PK. **Three consequences, all verified at the tip.** **(1) The row's owner flaps.** The Gmail arm writes with `.save(db)` (an upsert, and its own comment says `// upsert`), so whichever account syncs last overwrites `accountId`, `name` and `isSystem` on the shared row. The IMAP arms write with `.insert(db, onConflict: .ignore)`, so there the FIRST writer wins permanently and later accounts silently bind to a row that names someone else's `accountId`. **(2) A cascade crosses the account boundary.** The Gmail stale sweep deletes with `staleLabelIds.contains(Column("id")) && Column("accountId") == account.id` — the FILTER is account-scoped, but the ROW it deletes is global, and `messageUserLabel.userLabelId` references `userLabel` with `onDelete: .cascade`. So account A removing a label server-side drops the shared row and, with it, **every association row for account B's messages**. **(3) The read path that the plan's `labels(ids:accountId:in:)` = 0 hits actually names.** `UserLabelStore.loadLabels(for messageIds:in:)` and `UserLabelStore.labelsForMessage(_:in:)` join `messageUserLabel → userLabel` by id **with no `accountId` predicate at all** — they are the two readers that are not scoped, and they are the ones that render a message's label chips. A message in account B is therefore displayed with whatever `name`/`isSystem` the shared row currently carries, which after (1) may be account A's. **Concrete reachability:** any user with two accounts on the same provider who uses the same label or keyword name in both — an ordinary configuration, not an exotic one. **Why REGISTRABLE and not BLOCKING:** no message is mutated, misattributed, or destroyed; no wire operation is issued; no queued intention is dropped or wedged. Consequence (3) is local display only, and consequence (2) is recovered by the next sync of the affected messages, because `SyncEngineDeltaSync` and `SyncEngineBackfillDeep` re-insert each association from the server's own `info.userLabelIds` — the server, not the local row, is the source of truth for which labels a message carries. It fails toward showing the wrong label NAME, never toward acting on the wrong message. **Why it is nonetheless owner-gated rather than shrugged off:** the fix is a data-model change, which is exactly what D10 is for. Making the identity account-unique means either a composite primary key `(accountId, id)` or a derived surrogate id, and **either choice must also rewrite every existing `messageUserLabel.userLabelId` value**, so it needs a real migration (next free number is `v82`; the shipped `v1.6.38` line ends at `v67`, and `v68`–`v81` are post-release). Scoping the two unscoped readers WITHOUT changing the key would not fix it — with one shared row there is nothing for an `accountId` predicate to disambiguate, and adding the predicate alone would make account B's chips vanish instead of showing the wrong name. **That ordering is the reason this row exists:** the smaller-looking change is not a partial fix, it is a different bug.

✅ **FIXED by `168b7a665`, "Scope userLabel identity to its account and keep the wire value bare" — and the ordering this row insisted on is exactly the ordering the fix took.** **The invariant that now holds:** a label's identity is unique per account, so two accounts sharing a label name no longer share a row — the owner cannot flap, a stale sweep in one account cannot cascade away another account's associations, and the display path cannot render account A's name on account B's message. `UserLabel` carries a surrogate primary key `"<accountId>:<providerLabelId>"` plus a new `providerLabelId` column holding the provider's own value; `accountId` is a colon-free UUID string, so the concatenation is **injective** and `(accountId, providerLabelId)` uniqueness follows from the primary key with no second index. The memberwise initialiser is suppressed by a single deterministic `init(accountId:providerLabelId:name:isSystem:)` — mirroring `Folder.init` — so **every unrouted construction site is a compile error rather than a silent bare-id row.** ⚠️ **THE VALUE ON THE WIRE STAYS BARE, and this is the load-bearing half:** `PendingOperation.userLabelId` is a RAW PROVIDER ARGUMENT — the drain hands it to Gmail as `addLabelIds:` and to IMAP as `STORE +FLAGS (<keyword>)` — so all three construction sites pass `providerLabelId`, never `id`. Putting the surrogate there would be **worse than a loud failure**: on IMAP it writes a bogus keyword onto the user's real message, and on Gmail the API answers `"Invalid label"`, which `GmailProvider.isAuthoritativeActionRejection` classifies as a provider-authoritative no-op — so the operation would leave the queue **as if it had succeeded**, silently discarding the user's intention. **Migration `v82_accountScopedUserLabelIdentity` REBUILDS both tables rather than rewriting keys in place** (precedent: `v2_dropMessageHeaderFolderFK`): an in-place `UPDATE` of the primary key can collide TRANSIENTLY with a not-yet-rewritten sibling — a provider keyword literally named `<accountId>:x` — which would abort the migration and **brick launch**; and `providerLabelId TEXT NOT NULL` cannot be added in place without a bogus default. Associations are re-pointed through `messageHeader.accountId`, the only evidence of who a legacy association belonged to; labels created but never applied survive via a second insert keyed off the legacy row's own `accountId`; associations whose owning message is already gone are deleted first, because they carry no account and cannot be re-pointed. A fresh install (`v33` then `v82`) and an upgraded database converge on the same schema, **asserted behaviourally by a test** rather than by inspection. **The tests assert the SYSTEM PROPERTY, not the mechanism** — which rows survive, which name renders, what reached the wire — and none asserts that the id contains a colon, which would stay green on a system whose accounts still collide. **ACCEPTED LIMITATION, stated by that commit:** a legacy row reachable only through associations is reconstructed with `COALESCE(l.name, p.labelId)`, so in the rare case where the hijacked row's name belonged to the other account, that account's label is renamed to its provider id until the next sync overwrites it. **No association and no row is lost.**
