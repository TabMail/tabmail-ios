## Full detail

**A row whose captured RFC 822 Message-ID is absent, empty, or unusable (a bare `<>`) is still authenticated by ADDRESS ALONE, exactly as before this class was closed.** `ExpectedMessageIdentity.init?` is failable and `.map` therefore omits such rows, so `partition` returns them unrefused — "no witness ⇒ no refusal" is structural, not a branch someone can forget. Consequence: for those rows a UIDVALIDITY turnover during the window (the unbounded AI confirmation wait, the life of an undo entry, the gap between the search-result proof and the detail view's own resolve) can still let an action land on a different physical message. **Why this is accepted rather than fixed:** rows with no usable RFC witness genuinely exist, and refusing every action on them would drop user intention wholesale — a large behaviour regression taken to close a rare edge, which is the opposite of the trade THE MANTRA asks for. Refusing the witnessed case costs nothing (the witness is read off headers the caller already holds — zero extra I/O) and refusing the witness-less case costs the user their archive, delete, undo or read-on-open every time. **Banned substitutes, stated so nobody re-derives one:** `date` alone (authored and REMOVED as unsound in `v2final`'s own `ExpectedMessageIdentity`, ADR-IOS-061 item E) and the `(fromAddress, subject, date)` triple (`94fac3e79` reverted `3bd9f0bac`). A witness that can be forged by an ordinary duplicate is worse than none, because it converts a known gap into a false proof. **Recoverability:** the mis-targeted action is a move to Trash/Archive or a read flag — no permanent delete is reachable from any of the four members — and sync plus one ordinary user gesture restores the state. **Pinned by:** `UndoDestructiveActionTests.undoWithoutAWitnessKeepsTodaysBehaviour` and `SearchLocalResultIdentityTests.witnessLessRowStillOpensAndStillMarksRead` (the gap is preserved on purpose — a "fix" that closes it by refusing everything fails both loudly), against `undoRefusesWhenTheRowAtTheAddressIsADifferentMessage`, `reseatedAddressIsRefusedAtPreResolve`, `reseatedAddressIsRefusedInsideTheQueuedClosure` and `reseatAfterTheProofMarksNothingRead` for the witnessed half.

**THE NON-RECOVERING CASE, NAMED (2026-08-05, `MIS-IOS-008`) — and it lands in the C3 bucket, which this row states rather than papers over.** The recovery above is the user's own corrective gesture, so it does not fire in the state where the user never learns a mutation happened, and that state is concrete per member rather than hypothetical. **(i) The read-flag members.** `MessageDetailViewModel.markReadOnOpenIfNeeded` and the open carrying `SearchView.OpenTarget` mutate a read flag on a row the user is not looking at: no animation, no toast, no undo entry, and read state is durable and pushed to the server rather than re-derived from it, so no sync pass restores it — the message simply stays read and drops out of any unread-filtered view. **(ii) The move members.** `EmailArchiveTool` and `EmailDeleteTool` reach `performCoordinatedRoleMove` with `role: .archive` / `role: .trash`, so the wrong message is *moved*, never destroyed — but restoring it requires the user to notice and to find it at the destination, and the `.trash` destination is the **account's** Trash folder, whose retention belongs to the provider and not to this app. A mis-targeted delete that is not noticed before that folder is emptied — by the server's own policy, by another client, or by the user — is not restorable by any path TabMail owns. **Why this stays accepted rather than being escalated as a defect.** **A1: `ExpectedMessageIdentity` has ZERO occurrences at shipped `07a4bb703`** (`git grep -l 'ExpectedMessageIdentity' 07a4bb703` returns nothing), so shipped authenticated **every** one of these members by address alone, for **100 % of rows**. v3's remainder is the witness-less subset of a population shipped never refused at all — a net narrowing with a stated remainder, not a regression, and shipped is the floor. The other direction is also inside the non-recoverable set: refusing every action on witness-less rows drops user intention wholesale. So the choice is between two members of that set, and this row records which one the owner took. **This paragraph authorises nothing.** The banned substitutes stay banned, and `undoWithoutAWitnessKeepsTodaysBehaviour` / `witnessLessRowStillOpensAndStillMarksRead` must keep failing loudly if anyone "closes" the gap by refusing everything.
