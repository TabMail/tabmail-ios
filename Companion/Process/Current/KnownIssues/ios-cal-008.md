## Full detail

**The census, with its predicate and its membership (`MIS-007` — the property is about the WRITE, not about the terminal arms R17-2 already fixed).** Property: *every arm of `drainCalendarQueue` that treats a durable bookkeeping write as having succeeded without checking it.* Re-derive with two predicates this row cannot satisfy (`MIS-033`), deliberately spelled WITHOUT alternation so no literal pipe lands in a table cell: `rg -c --pcre2 '^(?!\s*/).*retryWrite\(' TabMail/Services/Account/AccountManagerCalendarQueue.swift` → **3**, and `rg -c --pcre2 '^(?!\s*/).*dbPool\.write' TabMail/Services/Account/AccountManagerCalendarQueue.swift` → **3**; **6** durable writes at R17b, cited by SYMBOL because line numbers go stale: (1) `retireCalendarOperation` — CHECKED, returns `Bool`, and `retireAndAnnounce` gates the announcement on it (R17-2's fix); (2) `queueCalendarOperation`'s enqueue — not in the drain, `throws` to the caller, which is never-drop rule 1; (3) the drain's **mark-in-flight** — CHECKED, `catch` → `continue`, the op is left `queued` and retried; (4) the drain's **success delete** — the subject of this row; (5) the drain's **transient requeue** — was `try? await` and is now `do`/`catch` with a recorded failure, disposition deliberately unchanged; (6) `reconcileCalendarQueue`'s `inFlight` → `queued` reset — CHECKED, `catch` logs, and a failed reset simply leaves the rows for the next launch. So beyond R17-2's six terminal arms there are three durable writes in the drain, two of which were unchecked, and exactly one of those two can change what the server sees.

**Reachability.** `executeCalendarOperation` returns normally (the provider write COMPLETED), then the delete fails through every `retryWrite` attempt — a persistent write failure such as GRDB suspension under `0xdead10cc` during a background drain (`IOS-DB-001` family), or a kill between the provider's ACK and the commit. The row is still `inFlight`, so the rest of that session skips it (`status == queued` is the drain's filter); at next launch `reconcileCalendarQueue` returns it to `queued` and the drain re-issues it.

**Why the asserted harm does not reproduce — discharged per operation type, in the tree.** `PendingCalendarOperation.eventId` is documented *"for create, pre-generated for idempotency"* (`generateGoogleEventId`), and all three providers consume it: **Google** posts it as the resource `id`, so a replay returns 409 and `GoogleCalendarProvider.isDuplicateIdConflict` reads that positively as "already created"; **Exchange** sends it as Graph's `transactionId` (`createEventJSON`, ≤256 chars — that is `IOS-CAL-004`, fixed in round 12 for exactly this reason); **CalDAV** PUTs the `.ics` at a filename derived from it under `If-None-Match: *`, and the 412 is read as success (`IOS-CALDAV-001`). `.delete` replays into a 404, which `isCalendarNotFoundError` claims and the drain retires terminally. `.edit` with scope `all` or `this_only` re-applies the SAME `argumentsJSON` field values, so the end state is byte-identical, and `resolveAttendeeDelta` resolves `add_attendees`/`remove_attendees` against the CURRENT attendee list — re-adding a present attendee and re-removing an absent one are both no-ops. `.edit` with scope `this_and_following` is the one that creates a new resource, and its successor id is **deterministic** on all three providers (`GoogleCalendarProvider.deterministicSplitEventId(masterId:recurrenceId:)`, used as Google's `newSeriesId`, Exchange's `transactionId` and CalDAV's `newUid`), while the master's RRULE cap is recomputed from the master's own rule and is therefore idempotent. Re-derive the provider half: `rg -n --pcre2 '^(?!\s*/).*deterministicSplitEventId' TabMail/Providers/` → **4** (one definition, three consumers).

**The residual, stated narrowly because the brief's version was too wide.** A replayed `.edit` re-writes the same values under `sendUpdates: "all"`, so **attendees may receive a duplicate "event updated" notification**. That is outward-facing and not undoable, but it is a duplicate NOTIFICATION, not a duplicate event and not a duplicate invitation set. Plus one extra wire round trip per replayed op.

**Why no completion marker was built, against the brief's suggestion.** `OutboxMessage` stamps `sentAt` before deleting and `reconcileOutbox` reads it — but `sentAt` is a COLUMN, and `PendingCalendarOperation` has no equivalent. Adding one is a schema change, and the brief forbids inventing a migration for these items; the alternative (a new `PendingStatus` case) needs new arms in `reconcileCalendarQueue` **and** in `runReclaimRetiredCalendarOps`, whose filter is `status = PendingStatus.failed.rawValue` only. Neither closes the window — it moves from "delete did not commit" to "marker did not commit", which is the two-generals problem restated. The Outbox carries the identical residual, which is why Outbox rule 4 says *"prefer double-send over drop"* rather than claiming the firewall is total. Here the idempotency keys already give the calendar queue what `sentAt` gives the outbox, one layer down: the SERVER, not the local row, is what recognises the replay.

🚨 **The mirror image, explicitly not built (`MIS-005`, `MIS-026`).** Making the success arm terminal-on-failure — retire the op because the LOCAL delete failed — trades a recoverable duplicate for a dropped intention whose remote half MAY NOT have happened (a `deleteOne` can fail before OR after `executeCalendarOperation`'s effects are known to have landed at all, e.g. a lost ACK). A dropped intention is in the non-recoverable set; a duplicate calendar event is one user gesture. When the two directions conflict this codebase states the preference for sends and it holds here.

**Recoverability under THE MANTRA.** Fail-closed and self-healing: the op is not lost, the server's own idempotency recognises the replay, and the user's calendar reaches the intended state without any gesture at all.

**What would re-open this row:** a new `CalendarOperationType` that is NOT idempotent under a pre-generated id (the predicate to check is `deterministicSplitEventId` + `eventId` consumption per provider, above); a provider dropping its duplicate-id semantics; `sendUpdates` being tightened such that a replayed no-op edit stops re-notifying; or a durable `sentAt`-equivalent arriving on `PendingCalendarOperation` for some other reason, at which point the delete should be gated on it.
