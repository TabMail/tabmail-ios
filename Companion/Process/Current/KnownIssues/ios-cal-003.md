## Full detail

**What was wrong.** `GoogleCalendarProvider.request` and `ExchangeCalendarProvider.request` convert a 401/403 to a typed `.missingScope` **only on the FIRST response**. After a 401 forces a token refresh, the retry's status is rethrown RAW as `httpError(retry.statusCode, nil)`. ⚠️ **The brief for this item asserted that every 403 is converted to a typed error; that is FALSE of the code and the code wins** — so a post-refresh 401 *or* 403 matched no classifier, took the drain's transient arm, and requeued forever. That is the **wedge corollary** of never-drop: an op that starves forever never recovers via sync, which puts it in the non-recoverable set rather than in THE MANTRA's accepted-edge set.

**What now holds.** `isCalendarMissingScopeError` additionally claims raw `httpError(403, _)` from both providers and `isCalendarAuthError` additionally claims raw `httpError(401, _)`; both, plus `isCalendarUnsupportedError` and `isCalendarNotFoundError`, are now `static` so the classification roster is callable from a test without an actor instance. A new `isCalDAVAuthError` splits the auth arm: **only** a CalDAV `authFailed` runs `UPDATE caldavConfig SET needsReauth = 1`, because that column is CalDAV's own and setting it for a Google or Exchange failure would prompt the user to re-enter a password that does not exist. Every arm signals `.permanentFailure(reason:)` with a provider-appropriate reason instead of retrying.

**Counterfactual discharged.** The alternative — keep requeueing so a transient network 401 eventually succeeds — is what produced the wedge. A permanent failure here is fail-closed and recoverable by one ordinary gesture (re-grant the calendar scope, then re-issue the action); the wedge is not recoverable at all.

**Verification.** `CalendarBadRequestClassificationTests.postRefreshAuthFailuresAreTerminal()` (red pre-fix: four `claimedByATerminalArm(...)` expectation failures across Google/Exchange × 401/403) and `transientFailuresAreStillRetryable()` as the negative case — a genuine transient must NOT be claimed.

**Accepted residual.** A provider that returns 403 for a reason other than a missing scope (quota, org policy) is now classified as a scope failure and retired rather than retried. That is deliberate: the reason string is surfaced, and re-issuing the action is one gesture.

⚠️ **CORRECTED 2026-08-06 (round-14 F4) — THE FIX WAS RIGHT AND ITS CENSUS WAS THE WRONG SHAPE, WHICH LEFT A SECOND WEDGE OF THE SAME CLASS STANDING (`MIS-007`).** This row's *"the classifiers now claim the raw post-refresh status"* is true and is the whole of what round 12 covered — because round 12 enumerated calendar OAuth failure **by HTTP status**, statuses being what was on screen. **A token that is never MINTED carries no status.** `GoogleCalendarProvider.request` opens with `try await accessToken(false)` and its 401 branch calls `accessToken(true)`, **both uncaught**, and that closure (`AccountManager.makeOAuthAccessor` → `OAuthRefreshCoordinator.refresh` → `refreshGoogleToken`/`refreshMicrosoftToken`) raises `ProviderError.authenticationFailed` and `OAuthError.tokenExchangeFailed(<code>)`. `ExchangeCalendarProvider.request` has the identical shape. Neither type matched any arm, so a revoked Google/Exchange grant took the transient arm and head-of-line-blocked the account's calendar lane on every subsequent drain — the same wedge this row was opened for, reached by a spelling the status-shaped census could not see. ⚠️ **And `rg -c authFailedAccounts AccountManagerCalendarQueue.swift` returned ZERO**: the round-12 split that correctly stopped arming CalDAV's `needsReauth` for OAuth accounts left OAuth accounts with **no persistent user-visible signal at all**, so the user was never told to sign in again.

**What now holds (`271d13334`+).** `isCalendarAuthError` additionally claims `OAuthError.tokenExchangeFailed(reason)` when `isGrantLevelOAuthFailure(reason)` — an exact match against `invalid_grant`, `invalid_client`, `unauthorized_client`, positively parsed from the token endpoint's own body, never a bare failure. A new `isCalendarOAuthReauthRequired` raises `markAuthFailed(accountId)` — the `authFailedAccounts` signal `RootView`, `SettingsView` and `AccountDetailView` all render — **before any disposition is chosen**, for an INCOMPARABLE set — not a nested one — because the SIGNAL is about the account and the DISPOSITION is about the op. ⚠️ **This row said *"for a strictly larger set than the terminal arm claims"* until R17-7, and that was false in BOTH directions.** R16-10 corrected the identical sentence in `isCalendarOAuthReauthRequired`'s own doc block and left this copy — the row that OWNS this class — plus a test display name asserting it. Provable from the two arm lists: signal ∖ terminal = `ProviderError.authenticationFailed` (signalled, deliberately never terminal); terminal ∖ signal = `CalDAVError.authFailed` (retired by the auth arm, but signalled through `caldavConfig.needsReauth` instead of `authFailedAccounts`). Neither set contains the other. `calendarAuthFailureReason` replaces a two-way ternary whose OAuth branch asserted *"refused again after a token refresh"*, false of a token that was never minted (`MIS-031`).

**Counterfactual discharged, and one clause of the fix brief was REFUTED in the tree.** The mirror image is blanket-terminalizing `tokenExchangeFailed`: both endpoints raise the same case for `temporarily_unavailable`, `server_error` and the `"unknown"` fallback (a body with no `error` key at all), which is exactly never-drop clause 2's *"we could not determine the answer"*. **`ProviderError.authenticationFailed` is signalled but deliberately NOT terminal**, against the brief's claim that it *"is unambiguous and can be claimed directly*": `OAuthRefreshCoordinator.refresh` raises it from `guard let refreshToken = KeychainHelper.loadString(…)`, and `KeychainHelper.load` returns nil for **any** `SecItemCopyMatching` failure — an absence of evidence. Its other raise site (`guard !invalidated`, account removed) cannot wedge anything, because `pendingCalendarOperation.accountId` is one of the 10 live `ON DELETE CASCADE` foreign keys and those rows are already gone. Terminalizing it would trade a wedge that ONE ordinary user gesture clears — re-authenticate, now prompted — for a permanently dropped intention, which nothing recovers.

⚠️ **CORRECTED 2026-08-07 (round-18, item B) — THE `needsReauth` HALF OF THIS ROW WAS A WEDGE, NOT A SIGNAL, AND IT HAS BEEN REMOVED.** Four sentences in this row describe `caldavConfig.needsReauth` as CalDAV's re-authentication *prompt*. They are quoted here verbatim rather than deleted, because the reasoning they carried is what a future reader needs to not repeat: (1) the status cell's *"only CalDAV arms the `needsReauth` re-authentication prompt"*; (2) *"A new `isCalDAVAuthError` splits the auth arm: **only** a CalDAV `authFailed` runs `UPDATE caldavConfig SET needsReauth = 1`, because that column is CalDAV's own and setting it for a Google or Exchange failure would prompt the user to re-enter a password that does not exist"*; (3) *"the round-12 split that correctly stopped arming CalDAV's `needsReauth` for OAuth accounts left OAuth accounts with **no persistent user-visible signal at all**"* — which reads as though CalDAV accounts had one; (4) *"terminal ∖ signal = `CalDAVError.authFailed` (retired by the auth arm, but signalled through `caldavConfig.needsReauth` instead of `authFailedAccounts`)"*. **The set memberships every one of these states are still correct; only the word "signalled" was wrong.**

**What was actually true.** The column had exactly ONE writer (`retireCalendarOperation`'s rider), exactly ONE reader (`AccountManager.createCalDAVProvider`'s `if config.needsReauth { return nil }`), and **nothing that ever cleared it** — the only other write is `CalDAVConfig.init`'s `false`, reached only when the CalDAV setup path creates a NEW config row. No UI read it: `ToolSettingsView`'s `needsReauth` is a DIFFERENT symbol, a local `CalendarPickerModel.AccountEntry` field written from a LIVE `listCalendars()` probe's catch arms. Two unrelated symbols with the same spelling, one of which has real UI behind it (`MIS-008`).

**The harm, which is the wedge corollary and therefore in the non-recoverable set.** Once set, `createCalDAVProvider` returned nil ⇒ the account was absent from `AccountManager.calendarProviders` ⇒ `drainCalendarQueue`'s `guard let calProvider = calendarProviders[currentOp.accountId] else { continue }` skipped every op queued on that account on every subsequent drain, forever — not executed, not retired, no user signal. **And the same absence removed the account from the calendar picker**, because `CalendarPickerModel.loadData` enumerates `CalendarProviderDispatch.resolveAll()`, which iterates that dictionary — so the one working affordance ("Calendar Access Required" + "Grant Access", driven by the live probe) could never render for the wedged account. The durable column *defeated* the working signal.

**What now holds.** `createCalDAVProvider` no longer reads the column and `retireCalendarOperation` no longer writes it; the `caldavReauthAccountId` parameter is gone from `retireCalendarOperation` / `retireAndAnnounce`. A CalDAV auth failure now retires the offending op exactly as every other terminal calendar failure does, the account keeps its provider, later ops keep reaching the drain, and the live probe renders the prompt the next time the calendar picker opens. **The column stays in the schema, unread and unwritten** — migrations are immutable, and a future credential re-entry flow is the thing that would consume it.

**Why this does not create a hammering loop.** `drainCalendarQueue` declares a LOCAL `var failedAccounts = Set<String>()` per drain, tests it *before* the provider lookup, and the CalDAV auth arm inserts into it — so an account with dead credentials makes at most ONE wire attempt per drain pass.

**The counterfactual, not taken (`MIS-026`).** The other repair is to wire `ToolSettingsView.grantCalendarAccess` for `.caldav` — it currently `break`s for that case. That needs a credential re-entry UI, i.e. product work; and it does not fix the wedge, because a wedged account never reaches the picker to be re-authenticated in the first place. **Residual, stated because it is real:** the "Grant Access" button rendered for a CalDAV account is inert — the *information* reaches the user, the one-tap remedy does not; re-entering the password goes through the CalDAV/iCloud setup flow. That residual is recoverable by ordinary gestures and is registered here rather than built.
