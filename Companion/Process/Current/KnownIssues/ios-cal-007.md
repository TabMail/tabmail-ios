## Full detail

**What this row registers.** `retireCalendarOperation` writes `failureReason` onto the durable `pendingCalendarOperation` row (`v84`'s column), and **nothing in production reads it.** Census, stated by its noun so a future reader can re-derive it rather than trust it: `rg -n 'failureReason' TabMail/ Shared/ TabMailNotificationService/` — the only **durable-column** sites are the write in `retireCalendarOperation` and the model's own declaration/initialiser in `PendingCalendarOperation.swift`; **every other hit is the unrelated in-memory `ConfirmationCardState.failureReason`** that `AgentChatSheet` renders on a live confirmation card. Two different `failureReason`s with the same spelling is exactly why this looked covered. The only path from a terminal arm to the user is `signalCalendarOpOutcome(.permanentFailure(reason:))` → `awaitCalendarOpOutcome`, which is an **in-process continuation with a timeout**.

**Reachability — when there is no awaiter.** Three ways, all ordinary: (1) `awaitCalendarOpOutcome` timed out and the chat turn already resolved; (2) the op was enqueued in one app session and drained in another, or after the sheet was dismissed; (3) the drain was started by something other than the tool call — `NetworkMonitor` on connectivity restore, `SyncScheduler`'s periodic and background passes, or `reconcileCalendarQueue` at launch recovery. In all three the op is correctly retired with a reason, the reason is correctly persisted, and **no UI ever reads it.**

**What IS already covered, and by what.** The most common cause — a revoked or expired grant — raises `markAuthFailed(accountId)` into `authFailedAccounts` **before any disposition is chosen**, and `RootView`, `SettingsView` and `AccountDetailView` all render that persistently. **That is true of the OAUTH half only.**

⚠️ **WIDENED 2026-08-07 (round-18, item B) — THIS ROW SAID *"the CalDAV half raises `caldavConfig.needsReauth` in the same write as the retirement. So the auth family already has a durable user-visible signal that survives the awaiter."* THAT SENTENCE WAS FALSE, AND IT WAS LOAD-BEARING:** it is what carved the CalDAV auth class OUT of this ACCEPTED LIMITATION. The `needsReauth` write was never a signal — nothing ever cleared the column, no UI ever read it (`ToolSettingsView`'s `needsReauth` is a different, in-memory symbol fed by a live `listCalendars()` probe), and its one reader made `AccountManager.createCalDAVProvider` return nil permanently, which starved the account's calendar lane AND removed it from the calendar picker. Round 18 removed the write and the gate (see `IOS-CAL-003`'s round-18 correction for the full chain). **So the CalDAV auth class is IN this row, not outside it:** a CalDAV auth failure retires the op with a durable `failureReason` that nothing reads, exactly like the classes below. What partially covers it — and what the removed gate was defeating — is `ToolSettingsView`'s live probe, which renders "Calendar Access Required" the next time the user opens the calendar picker. That is real but not persistent-and-unprompted, and its "Grant Access" button is inert for `.caldav` (`grantCalendarAccess` `break`s for that case); the remedy is re-entering the password through the CalDAV/iCloud setup flow.

**What is NOT covered — SIX terminal classes. ⚠️ This said "five terminal classes, one more than the fix brief listed" until round 18 added the sixth.** `isCalendarNotFoundError` (the event is gone), `isCalendarUnsupportedError` (this provider cannot do it), `CalDAVError.inconsistentState` (a half-landed `this_and_following` split whose rollback also failed), `isCalendarBadRequestError` (a structurally malformed request), **`isCalendarMissingScopeError`** — the brief's list omitted the scope arm, and it belongs here: `CalendarBadRequestClassificationTests` asserts `ExchangeCalendarError.missingScope` must **not** raise the OAuth re-auth prompt, so a missing calendar scope is terminal with **no** persistent signal at all — **and (round 18) `CalDAVError.authFailed`**, which `isCalendarAuthError` retires and which `isCalendarOAuthReauthRequired` deliberately does not claim, so it too is terminal with no persistent signal.

**Why this is an ACCEPTED LIMITATION rather than a defect.** Nothing is wrong; a capability is absent. Shipped `v1.6.38` **deleted** the row on a terminal arm and made the identical in-memory-only delivery, so the notification gap is pre-existing and R16-1's retirement change strictly improved it — it added the durable record that did not exist before. Building a persistent calendar-failure surface (a badge, an inbox card, a notification) is a **feature**, and this is the end of an audit train.

**Recoverability under THE MANTRA — one ordinary gesture.** The op is fail-closed: it does not execute, does not retry, and cannot wedge the lane (it is neither `queued` nor `inFlight`). The user re-issues the calendar action in chat, which enqueues a fresh op with a **live** awaiter, and the failure is then reported in-turn as it always was. No sync pass is required and nothing is silently wrong on the server.

**And the durable row is what a future surface would read.** This is the reason the column stays despite having no reader today: `retireCalendarOperation` now leaves `status = 'failed'` + `failureReason` + `retryCount`, retained for `SyncConfig.retiredCalendarOpRetentionDays` (30) before `runReclaimRetiredCalendarOps` reclaims it. Anything built later queries that row; it does not need a new column or a migration. **Do not delete the column as unused** — it is deliberately written ahead of its reader, and this row is the record of that intent.

**What would re-open this row:** evidence of a real user hitting a non-auth terminal failure and not understanding why nothing happened, a terminal class that is **not** recoverable by re-issuing the action, or a drain path that retires ops with no chat turn ever involved (e.g. a scheduled or rule-driven calendar write).

✅ **AMENDED 2026-08-07 (round 18c, item F1) — the inert `Grant Access` button is FIXED; the ACCEPTED LIMITATION this row registers is UNCHANGED.** `CalendarPickerView`'s `needsReauth` section (in `TabMail/Views/Settings/ToolSettingsView.swift`) rendered a `Grant Access` button for **every** provider, but `grantCalendarAccess` `break`s for `.imap`, `.icloud` and `.caldav` — so on a password / app-specific-password account the button was **inert**: it changed nothing, reported nothing, and left the user pressing it. That is an honesty defect that exists independently of the durable-surface limitation above, and it is the one thing here that is fixable without building product. The view now branches on a new `CalendarPickerView.canReauthInPlace(_:)` (the owning TYPE — `ToolSettingsView.swift` is the FILE and there is no type of that name in it; the inert button and the `break` both live on `CalendarPickerView`) (`.gmail` / `.outlook` ⇒ true; `.imap` / `.icloud` / `.caldav` ⇒ false; the switch is exhaustive over `AccountProvider` so a new provider cannot silently inherit the wrong arm): OAuth accounts keep *“Re-sign in to grant calendar access.”* plus the button, password accounts get *“This account signs in with an app-specific password, which TabMail can't renew for you. Add the calendar account again with a new password to restore access.”* plus a `NavigationLink` to the existing `CalendarSetupView`. `grantCalendarAccess`'s `.imap, .icloud, .caldav` arm keeps its `break` for exhaustiveness, with a comment recording that it is now unreachable **from this view**. **Deliberately NOT built:** an in-place CalDAV credential re-entry flow — that is product work, out of scope for an audit round; the link reuses the setup screen that already exists rather than inventing a second credential surface.
