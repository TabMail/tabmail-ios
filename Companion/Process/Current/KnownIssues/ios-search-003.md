## Full detail

The REMOTE arm of the search tap travelled **unwitnessed**, so a durable mark-read on a remote result could land on a re-seated address — the same C3 misattribution `IOS-SEARCH-001` closed for the LOCAL arm, one branch over. `presentableRemoteResults` built every remote `SearchResult` without `capturedRfc822MessageId` even though `MessageHeaderInfo.rfc822MessageId` (the struct's second field, set by the one true producer `IMAPProvider.mapMessageInfo`) was already in the value being mapped, and `tapOutcome` then hard-forced `provenRfc822MessageId: isRemote ? nil : …`, discarding it a second time. **Silent in both directions:** `SearchResult.capturedRfc822MessageId` is nil-DEFAULTED so the omission compiled clean, and `MessageDetailViewModel.markReadPermitted` is `guard let openIdentity else { return true }` — FAIL OPEN. Nothing reported it.

🚨 **THE MORE DANGEROUS HALF WAS THE COMMENT, and it is the reason this row exists.** The code was accompanied by *"A remote result carries NO content witness (there was no local row to capture one from) … a false proof is worse than none."* The **second** clause is sound and the **first** is FACTUALLY FALSE — a witness needs no local row; the provider supplied one — so the sound conclusion was drawn from a false premise and protected the defect from review. A wrong rationale outlives wrong code, because nothing compiles it and no test fails on it (same failure shape as the retraction in `faf4d133f`, same file range). The comment is corrected in place at `tapOutcome`, and the test that blessed it (`aResolvableRemoteResultOpensWithoutAnUnprovenWitness`) is rewritten — note it would have stayed **GREEN** through the fix, since its fixture minted a witness-less result, so no gate could have found it.

**The invariant that now holds:** a remote search result carries the provider's own Message-ID for the record it rendered, and that witness reaches `MessageDetailViewModel`, where it can only **REFUSE** the open's durable mark-read — never select, widen or nominate a target (**not** an ADR-IOS-068 / D4 violation; the target is still chosen by the durable composite address). Rendering is deliberately NOT gated: a re-seated address still opens, because refusing to render is a regression with no C3 payoff. **Severity, adjudicated:** REGISTRABLE-HIGH rather than blocking — every pre-range path carried NO witness on ANY tap (`b1ae6e262` authored the mechanism, `afa7889ee` authored this remote path, both in range), so the range is a strict improvement, and the window is one live on-screen search session, not unbounded.

⚠️ **ACCEPTED RESIDUAL — a NEW fail-closed population, named because the fix's absolute is otherwise unfalsifiable (`MIS-019`).** A live local row whose own `rfc822MessageId` is absent or differs while the server reports one now loses **only** its mark-read-on-open. The message still opens and renders; it stays unread. **Recoverable by one ordinary gesture** (mark read by hand, or the row's own next sync-driven update) and therefore acceptable per THE MANTRA. **The non-recovering case, named per `MIS-IOS-008`:** none — nothing is deleted, refused or queued, and no durable state records the refusal, so the next tap re-evaluates from scratch. The opposite population (provider supplies no Message-ID at all) keeps today's **fail-open** behaviour with **no new branch**, because `ExpectedMessageIdentity.init?(capturedRfc822MessageId:)` already rejects an absent or unnormalizable value; the mirror-image "refuse when no witness" over-correction (`MIS-005`) is pinned red by `SearchRemoteResultIdentityTests.remoteResultWithNoProviderWitnessStillOpensAndMarksRead`. **A1:** neither shipped `07a4bb703` nor `v2final` `e28dd4edb` contains `capturedRfc822MessageId`, `OpenTarget`, `tapOutcome` or any content witness on any tap path — both push a bare address into `MessageDetailView(messageId:)`, which has no expected-identity parameter. The shipped architecture is **NONEXISTENT** (A1 step 3); there is no shipped property to restore and none to inherit.
