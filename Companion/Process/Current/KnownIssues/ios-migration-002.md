## Full detail

**The lever, verbatim:** *"if migrations take long, we should even consider just dropping things instead and rely on delta sync, ie, the fail closed strategy."* **It does not apply, on three independent grounds.** **(1) The only re-derivable mass is already dropped.** `messageBody` is a re-fetchable cache of rendered HTML, and `v70_dropMessageBodyHeaderFK` drops the whole table outright — the lever's single valid target is already pulled. **(2) `messageUserLabel` is NOT re-derivable, and the census is broader than a sync-path search finds.** Predicate: `rg -n 'MessageUserLabel\(' TabMail` → **14** construction sites. Seven are sync-side header-INSERT paths (`SyncEngineFullSync` ×4, `SyncEngineDeltaSync` ×2, `SyncEngineBackfillDeep` ×1); five are `PreviewMocks` (not production data). **The two that settle it are neither:** `UserLabelMenuView` writes the junction row for a label the **user applied by hand** (optimistic local write paired with a queued `PendingOperation`), and `NSEDataBridge` re-inserts it on the NSE re-key path. `MessageHeaderRekey.apply` states the property outright and is built around it — `messageReference` is **REBUILT** from the header's own `References`/`In-Reply-To`, while `messageUserLabel` has **NO rebuild source** and is therefore **CAPTURED before the delete and re-inserted under the new id**. Dropping the table loses user-visible labels with no recovery path, which is a dropped user intention, not a fail-closed edge. **(3) The cost was never in CARRYING rows — it was in VALIDATING them.** Measured over the whole `v68…v83` chain at profile H: 61.8–87.4 s total, of which combined migration BODY time is 19.2–22.2 s and **42.5–65.0 s (69–74%) is `PRAGMA foreign_key_check`**, run over the entire database once inside *each* of the 16 migrations by GRDB's `.deferred` default. `v68_addFolderUidValidityResetPending` is one `ALTER TABLE … ADD COLUMN` with a **0.3 ms** body and an **8,750–10,661 ms** FK check. Declaring `foreignKeyChecks: .immediate` on the 14 migrations whose bodies cannot create a violation removes that cost **without dropping anything** — **independently re-measured by the implementing agent on a quiet machine, shipped chain vs patched chain back to back: profile H 56.0–84.6 s → 28.0–28.3 s, profile L 12.7–13.0 s → 3.7–4.8 s, profile M75 (75k headers / 628 MB) 2.45–2.47 s → 1.30–1.31 s, profile M25 (25k / 209 MB) 0.78–0.80 s → 0.40 s, profile S (5k / 28 MB) 0.147–0.149 s → 0.078–0.080 s.** `PRAGMA foreign_key_check` returned zero violations after every run. (The earlier measurement pass reported 87.3–89.4 s → 31.3–31.4 s at H; the re-run's absolute numbers move with machine load, the ratio does not.) ⚠️ **What the fix does NOT buy, because past ~200k headers the residual is BODY work, not validation:** at 200k the patched chain is still 3.7–4.8 s on a Mac (7–19 s device-adjusted at the ×2–4 correction) and at 500k it is 28 s (56 s–1.9 min device-adjusted), dominated by `v82`'s label rewrite, `v70`'s super-linear `DROP TABLE` and `v83`'s index build. **The "a few seconds on device" boundary lands at roughly 70k headers at ×4 and 140k at ×2.** No further foreign-key-mode tuning moves that line; only deferral or laziness would, and neither was implemented. ⚠️ **SUPERSEDED 2026-08-06 — this row used to read "`v71` deliberately keeps `.deferred`, so a PRE-EXISTING orphan is still caught".** `v71` now runs `.immediate`.
