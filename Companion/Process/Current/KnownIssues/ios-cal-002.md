## Full detail

**The class, by symbol.** Every calendar UPDATE-path write in this tree lands without a precondition that names WHICH version it is replacing, so a concurrent edit by another client or device is silently overwritten (last-writer-wins, no error, no user signal). Three independently verified members:

**(1) CalDAV `.unconditional` PUT.** Round-9 S1 introduced `enum CalDAVPutPrecondition { case ifMatch(String); case ifNoneMatchAny; case unconditional }` in `CalDAVClient`; `.unconditional` sets NEITHER `If-Match` nor `If-None-Match`. FOUR write sites reach it through `etag.map(CalDAVPutPrecondition.ifMatch) ?? .unconditional`: `CalDAVProvider.updateEvent`, `updateOccurrence`, `splitSeries`' capped-master PUT, and `revertMasterCap`. On a server that returns no ETag on PUT — RFC 4791 §5.3.4 says SHOULD, not MUST — all four are blind overwrites.

**(2) `revertMasterCap` / `mergeExistingEventWithPatch`.** `revertMasterCap`'s own doc claimed the `.ifMatch(capETag)` property of the path rather than of one branch of it; corrected in place 2026-08-06 (round-11 R11-H). `GoogleCalendarProvider.mergeExistingEventWithPatch` is the read-modify-write helper both Google (`updateEvent`, `updateOccurrence`) and Exchange (`updateEvent`, `updateOccurrence`) drive: it GETs the existing event, merges the patch over it, and PUTs/PATCHes the result back with nothing asserting that the GET's version is still current.

**(3) Exchange and Google `splitSeries` rollback writes.** THREE `splitSeries` implementations exist — `CalDAVProvider.splitSeries`, `GoogleCalendarProvider.splitSeries`, `ExchangeCalendarProvider.splitSeries` — and only the CalDAV one carries any conditional-header machinery at all: `rg -ic 'if-match|odata\.etag|etag'` over `GoogleCalendarProvider.swift` and `ExchangeCalendarProvider.swift` exits **1** (zero matches), so their cap-then-create-successor sequences and their rollbacks are unconditional at every step.

**THE TRADE, STATED IN BOTH DIRECTIONS — this is the whole point of the row (`feedback_absolutes_need_the_negative_case`).** Reverting to shipped `07a4bb703`'s mapping is **NOT** a safe default. Shipped `CalDAVClient.put(url:body:etag:)` did `if let etag { If-Match } else { If-None-Match: * }`, i.e. it turned "I have no ETag" into an ASSERTION OF ABSENCE. Against a resource that already exists, RFC 4918 §10.4.2 requires a conforming server to answer **412 always** — so on an ETag-less server every calendar edit, every occurrence override, every series split and every rollback would fail **forever**. That is a permanently broken feature, not a recoverable fail-closed edge, and it is the round-9 bug `CalDAVPutPrecondition` was introduced to kill. Round 9 relaxed it deliberately and **three anchor tests pin the relaxed behaviour** with `FakeCalDAVStore(servesETags: false)` (search that symbol in `TabMailTests/Providers/CalDAVSplitHelpersTests.swift`). **Accepted cost:** a lost update when two clients edit the same event concurrently. **Rejected cost:** a calendar feature that cannot work at all on a conforming-but-ETag-less server. The accepted side is recoverable — the user re-applies the edit, and the next sync shows them the current state — while the rejected side is not recoverable by any gesture.

**Why NOT fixed now.** Building ETag capture, storage and conditional-header plumbing across two further providers at the end of an audit train is exactly the risk `IOS-CALDAV-001` declined for the same family, and for the same reasons: it needs a durable witness (Google/Graph have no ETag plumbing at all today), a new failure classification for 412, and that classification is the *provider-authoritative stale* versus *could-not-determine* distinction `CLAUDE.md` names as this codebase's single most repeated defect. Landing it unrehearsed and late trades a rare lost update for a broad never-drop violation.

**RELATIONSHIP TO `IOS-CALDAV-001` — read both, they partition the same family.** That row owns the **DELETE** path: a bare `DELETE` on an href with no `If-Match`, i.e. no witness that the resource at the href is still the event the user chose. **This row owns the UPDATE/PUT path.** They are disjoint by HTTP method and joint by cause (no durable ETag witness anywhere in the calendar queue). `IOS-CALDAV-001` already records the REMEDY SHAPE and a future implementer should inherit it rather than re-derive it: capture an ETag at enqueue, add the column in a **NEW `v84`** and never by editing `v83` (data-integrity rule 5 — `v83` has already run on every dev database), reuse the existing `CalDAVPutPrecondition` enum rather than inventing another nil-means-something sentinel, and add the 412 arm as **fail closed, still queued, visible and retryable** — never a retirement through a success path.

**Recoverability, with the NON-RECOVERING case named (`MIS-IOS-008`).** The ordinary outcome recovers: an overwritten edit is visible to its author on the next sync and can be re-applied in one gesture, and no event is destroyed — this is UPDATE, not DELETE, so the resource still exists and still holds a valid event. **The non-recovering case is the CONTENT of the overwritten edit** when its author is a different person or a different device that never re-reads: those keystrokes are gone, nothing signalled the loss, and no sync pass reconstructs them. It is accepted on frequency — it requires two clients editing the SAME event inside the same window — and on the alternative being strictly worse. **What would re-open this row:** any provider gaining durable ETag/`@odata.etag` storage (the plumbing cost is then already paid), calendar writes moving to a deferred or offline-first queue (which widens the window from a round-trip to a drain delay), evidence of a real occurrence, or a shared-calendar feature that makes concurrent editing the common case rather than the rare one.
