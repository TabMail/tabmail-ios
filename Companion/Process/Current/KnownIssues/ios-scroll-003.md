## Full detail

Both `InboxViewModel.error` write sites are wrapped in `if !SyncEngine.isConnectionError(error)`. At the **`performSync`** catch that carve-out is covered by a second surface: `AccountManagerState.shared.lastSyncFailed = true` is set **unconditionally** in the same catch and drives the sync-status subtitle, so a connection failure is still reported. At the **infinite-scroll** catch there is **no such fallback** — no `lastSyncFailed`, no other surface — so a *connection* failure during pagination stays completely silent even now that the banner renders in production: the list stops growing and nothing says why. This is exactly the case companion topic 105's 2026-08-04 correction predicted (*"the guard suppresses that surface for connection errors, which is exactly when infinite scroll fails"*). **(b) Reachability and FREQUENCY — stated first, because the mantra requires the frequency question BEFORE the recoverability test and "an edge that is actually the common path is not an edge".** Phase 2 (`manager.fetchOlderMessages`) runs only once the phase-1 local GRDB page comes back empty — i.e. for any user who scrolls past their cached window, which is routine, not exotic. `SyncEngine.isConnectionError` then covers **every** `URLError` (airplane mode, DNS failure, "connection appears to be offline"), both raw NIO domains (`NIOCore.ChannelError`, `NIOCore.IOError`) and a substring list including `"timed out"` — so the suppressed case is ordinary offline / flaky-network paging. **This row therefore does NOT claim the case is rare; it claims it is recoverable and non-destructive, which is the operative test.** **(b2) No third surface — census with its predicate.** `grep -rn 'lastSyncFailed *=' TabMail/ Shared/` returns **SEVEN lines**, of which exactly **FOUR are assignment sites** — `InboxViewModel.performSync` (both polarities) plus `SyncScheduler`'s delta-sync completion and its foreground `poll()` (`result.failed`). ⚠️ **The other three are not writers and the earlier wording of this row wrongly implied the raw grep returned four** (`MIS-007`/`MIS-008` — a count is a claim about what the PATTERN can match, and `lastSyncFailed *=` matches the text, not the assignment): they are the property DECLARATION `var lastSyncFailed = false {` in `AccountManagerState.swift` and **two string-literal mentions** inside that property's `didSet` — a `print("[SyncPhaseMut] lastSyncFailed = …")` and a `BootProfiler.mark("'Last updated' subtitle: lastSyncFailed = …")`. The load-bearing claim is about **writers**, so re-derive it as *assignment sites outside the declaration*, not as a line count. **None of the four is on the pagination path.** The only durable channel that path has at all is `BackgroundSyncLogger.logError(…, source: "infiniteScroll")` inside `SyncEngine.fetchOlderMessages` — and it sits on the `isSelectFailedError` arm, which `continue`s to the next folder and never rethrows, so it is not reached by the errors that arrive at *this* catch; it is a developer channel (`error.log`, exported by `DebugLogView`'s "Error Logs") rather than a user surface in any case. **(c) Attribution — PRE-EXISTING; A1 verdict NONEXISTENT.** `git show 07a4bb703:TabMail/ViewModels/InboxViewModel.swift` and `git show e28dd4edb:…` both carry this catch verbatim — same `print`, same guard, same absent `lastSyncFailed` — beside a `performSync` that *does* have the unconditional write. **The shipped release never surfaced a pagination connection failure, so there is no behaviour to RESTORE and any fix would be authored work** (A1 corollary 3 — the release is a floor, not a ceiling; but it is also empirical evidence that this particular silence was tolerable to real users across the whole `v1.6.38` line). What `3573574ed` changed is the *other* half: before it, `InboxViewModel.error` had no production render site at all, so BOTH catches were silent for EVERY error; now non-connection failures at both sites render. The connection half is exactly the shipped baseline. **(d) Recovery — proved from the state, not asserted.** `hasMoreMessages = pull.mayHaveMore` is the last statement of the `do` block, and the appends to `loadedMessages` / `loadedIds` / `targetWindowSize` live inside the `pull.inserted > 0` branch, so a throw skips all of them; `isLoadingOlder` is cleared by `defer`. **The view-model state after a failed page is identical to the state before it — the failure leaves ZERO residue**, which is exactly what separates this row from `IOS-SCROLL-001` / `IOS-SCROLL-002`, where `hasMoreMessages` is written FALSE and the scroller genuinely stops. The sentinel therefore stays armed: `InboxView` renders `if viewModel.hasMoreMessages { … Color.clear.frame(height: 1).onAppear { viewModel.loadMoreMessages() } }`, so any scroll that brings that 1-pt row back into view re-attempts the page; independently, both list paths carry `.refreshable { await viewModel.refreshSync() }` → `performSync` → `reloadMessages()`, which recomputes `hasMoreMessages` from a fresh query. ⚠️ **Stated negatively (`MIS-019`):** this row does NOT assert that the `isLoadingOlder`→`false` rebuild *alone* re-fires `onAppear` — that is a SwiftUI structural-identity question nothing here proves, and the recovery claim deliberately rests only on the ordinary gesture, which is checkable. **(e) Accepted cost, and why the obvious fix is not obviously correct.** Recoverable ⇒ fail closed and let it be. The mantra's non-recoverable set is closed and exhaustive — C3 wrong-message mutation or misattribution, a dropped user intention including the wedge corollary, a brick, secret exposure — and this is a READ path that queues, mutates, sends and deletes nothing, so the not-rare frequency finding above does not promote it into that set. **Neither one-line fix is right.** Mirroring `performSync` (`lastSyncFailed = true` here) re-labels a *pagination* failure as a *sync* failure in `SyncStatusSubtitle` ("Last updated" vs "Updated") — a field whose three other writers are all whole-pass sync outcomes — and nothing on this path ever clears it, so it would stay set until the next successful sync or poll. Deleting the guard puts raw transport text (`NIOCore.ChannelError`, `"timed out"`) in front of the user on every connectivity blip, which is precisely what the carve-out exists to keep off-screen. A correct fix needs a THIRD signal, and authoring one at the close of the refactor is exactly the mechanism the mantra says not to build. **If it is ever revisited**, consider a scroll-local, non-sticky indicator owned by the sentinel row — which already knows a page was attempted and did not arrive — rather than a new write to a global sync flag. **No test blesses the current behaviour** (`MIS-014`): every `loadMoreMessages` test in `TabMailTests` exercises phase-1 local paging, dedup, `excludeIds` ordering or the diff rebuild, and none asserts the catch's suppression.

**THE NON-RECOVERING CASE, NAMED (2026-08-05, `MIS-IOS-008`) — and it is a different question from the `MIS-019` clause in (d), which says what this row does not ASSERT rather than where recovery does not FIRE.** The recovery here is a retry of the same page, so it does not fire while its own cause persists: the suppressed class is exactly `SyncEngine.isConnectionError`, and for as long as the device stays offline every re-arming of the sentinel and every pull-to-refresh fails identically and just as silently. **That state cannot become a defect, for a reason this row already proves:** the failure leaves **zero residue** — `hasMoreMessages = pull.mayHaveMore` is the last statement of the `do` block and the appends to `loadedMessages` / `loadedIds` / `targetWindowSize` live inside the `pull.inserted > 0` branch — so no local state is wrong to be repaired, and what is unreachable (older mail still on the server) is unreachable by construction rather than by anything we recorded. The limiting case is a device that never regains connectivity, where there is nothing to recover *to*. **What WOULD move this row out of the registrable set is a residue** — any future change that writes state at this catch — which is exactly why both one-line fixes are rejected in (e), and `lastSyncFailed` in particular, since nothing on this path ever clears it. **A1 re-derived at the tag rather than inherited from (c):** `git show 07a4bb703:TabMail/ViewModels/InboxViewModel.swift` carries `print("[InfiniteScroll] Error: \(error)")` followed by `if !SyncEngine.isConnectionError(error) { self.error = … }` verbatim.
