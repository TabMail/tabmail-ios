## Status

## Subsystem and search terms

## Full detail

**CURRENT v1.7.5 MECHANISM (`35e0eefe1`).** `refetchBody` now snapshots the current in-memory or durable `MessageBody`, asks `AccountManager.fetchBody(..., replaceExistingBody: true)` for a replacement, and keeps the prior body visible on provider or database failure. `BodyFetchProcessor.persistDisplayableBody` swaps only after a displayable replacement exists, and `bodyReloadToken` forces the WKWebView to reload even when the replacement HTML bytes are identical. The mid-move address gate deliberately remains before the fetch: an already-open view still carries the stale source UID under the destination folder, so refresh is refused without deleting or changing anything. The user-visible residual is now only that the requested refresh does not occur until the user returns to the list and reopens the message against its current address. No body, queue row, or server message is lost.

**HISTORICAL PRE-v1.7.5 MECHANISM (retained; the delete-first implementation described below was removed by `35e0eefe1`).** `refetchBody` deletes the durable `MessageBody` and resets `bodyComplete` / `bodyEmptyConfirmed` / `emptyFetchCount` FIRST, then fetches. With the gate in place that fetch is refused, so the destructive half would land and the restorative half would not — the user would lose a body they could previously read. `refetchBody` therefore checks the address BEFORE the delete and returns early, preserving the existing body. The cost is that the user's explicit "retry from scratch" gesture is not performed: for a legitimately confirmed-empty message the reset that would give the empty-fetch chain a fresh start does not happen, and the replacement `startBodyPoll` exits on its first two-second tick because a body already exists (it skips the pre-loop adoption block when `messageBody` is non-nil, sleeps once, then returns at the loop-top guard — "immediately" was the same timing overclaim this file removed from `IOS-BODY-004`, one row over).

**THE COUNTERFACTUAL, STATED BECAUSE BOTH ALTERNATIVES ARE WORSE.** Performing the refresh means deleting a good body to then be refused — a self-inflicted blank message. ⚠️ **And the sentence that used to end here, "with no path back until an unrelated sync or queue drain", was wrong in the way this row's own recoverability paragraph now explains.** The DURABLE body does come back that way: the delete leaves `bodyComplete = 0`, so once the address settles the body queues re-fetch and re-write it. The VIEW does not — it is still polling the stale key (the stale-open-view closure on `BodyAddressGate`), so the user sits in front of a blank message they could read a moment ago until they back out and reopen. A row whose counterfactual promises a recovery its own mechanism section denies is the exact failure this train has now spent three rounds on, so it is spelled out rather than trimmed. Skipping only the delete while still fetching means fetching against a UID that names another message, which is the defect this whole change exists to close.

**RECOVERABILITY — THE RECOVERING EVENT, NAMED, AND IT IS REOPEN RATHER THAN A SECOND PULL.** ⚠️ **This row said "a second pull-to-refresh after the move settles performs the refresh in full" until an audit round showed that is false in the view the user is actually looking at.** `refetchBody` re-tests the address against the same in-memory `message` the view was constructed with, and `AccountManagerQueue.publishRekeys` does not push the re-keyed row into an already-open `MessageDetailViewModel` — so a second pull in an UNCHANGED open view re-submits the same stale (destination folder, source UID) pair and stays declined even after the database has settled. That is the same stale-open-view condition as `IOS-BODY-004` and `IOS-BODY-005`, and this row contradicted its own neighbours for a day. **Going back to the message list and opening the message again** rebuilds the view model against the current row, after which pull-to-refresh performs the reset in full. Moves drain in seconds on the happy path (`finishMove` re-keys on COPYUID proof), so the window is short, and nothing is lost meanwhile: the body the user had is still on screen. One ordinary gesture, which is THE MANTRA's fail-closed-and-let-it-be case.

**WHAT WOULD RE-OPEN THIS ROW:** the decline becoming silent-and-permanent (e.g. if moves commonly parked undrained), or a deferred-refresh mechanism landing that replays the gesture once the address settles.
