## Status

✅ **CLOSED AS A DECISION (2026-08-05, round-9 S2)** — a durable calendar delete addresses its target by **href alone**, with no ETag witness, so a same-href substitution inside the drain window destroys an event the user never chose, on the one wire operation for which WebDAV defines no undelete. Registered rather than mechanised: the remedy is a new migration plus a new durable-queue failure classification, and the fail-closed half of that classification is the exact distinction (exit 2 vs exit 4) that has produced the most repeated defects in this codebase

## Full detail

**The mechanism, by symbol.** `CalendarEventDeleteTool` → `AccountManager.queueCalendarOperation` writes a `PendingCalendarOperation` whose entire address for the event is `eventId` (plus `calendarId`); the durable row's columns are `id`, `operationType`, `accountId`, `eventId`, `calendarId`, `argumentsJSON`, `status`, `createdAt`, `retryCount` — **there is no ETag column**. Later, `drainCalendarQueue` → `executeCalendarOperation` calls `CalDAVProvider.deleteEvent`, which resolves the href with `resolveEventURL` and calls `CalDAVClient.delete(url:)`. That method sets `httpMethod = "DELETE"` and the auth header and **nothing else**. So the durable operation asserts *"delete whatever is at this href now"*, never *"delete the event I showed the user"*.

**And the witness that does exist is volatile and unread here.** `CalDAVProvider.etagCache` is a private in-memory `[String: String]` populated by the list and get paths; `deleteEvent` only **removes** from it (`etagCache.removeValue(forKey: eventId)`) and never reads it. It does not survive a process restart and is not bound to the durable row, so it cannot serve as the op's identity witness even today.

**Why this is worse than an ordinary stale-address bug.** WebDAV `DELETE` on the event's `.ics` is **irreversible wire operation #5** (`CLAUDE.md` § THE MANTRA; `Companion/Memory/Current/102-there-are-four-irreversible-wire-operations-not-one.md`): RFC 4918 and RFC 4791 define **no** trash, undelete or restore for it. iCloud's whole-calendar snapshot rollback is a per-calendar operation, not a per-item recovery, and does not exempt it. For mail, `.delete` is a move to Trash and a wrong one is walked back; here there is nothing to move back.

**The accepted cost, stated as an exposure window rather than as "rare".** The window is exactly enqueue→drain for **one href**, and the loss additionally requires a *different* event to occupy that href inside it. A CalDAV href derives from the event UID, so this is not the ordinary "somebody edited it meanwhile" case — an edit leaves the same event at the same UID and deleting it is precisely what the user asked for. It needs a genuine identity substitution at the same UID by another client or device inside the drain delay. The cost accepted is that when that happens, one event the user did not choose is destroyed with no undo.

**The remedy shape, recorded so a future implementer does not re-derive it.** **(1)** Capture an ETag at enqueue time (the delete path does not GET, so this means either persisting the value the read path already saw or adding a conditional pre-read). **(2)** Add an `etag` column to `pendingCalendarOperation` in a **NEW** `v84` — never by appending to `v83`, which has already run on every dev database (`CLAUDE.md` data-integrity rule 5). **(3)** Thread it into `CalDAVClient.delete` as `If-Match`, mirroring the `CalDAVPutPrecondition` enum the round-9 S1 fix introduced for `put`: the enum shape exists and should be reused, not re-invented, so `delete` gains the same three explicit modes rather than another nil-means-something sentinel. **(4)** Add the 412 arm — a precondition failure means the href now holds a different resource, so the op must **fail closed and remain queued, visible and retryable**, never retire through a success path. Step (4) is the expensive one: it is a new failure classification on a durable queue, and getting it wrong trades a rare wrong-delete for a common dropped intention, which is strictly the worse defect.

**Why not now — three grounds, each sufficient alone.** **(a)** A schema migration and a new durable-queue failure arm are the two highest-risk edit classes in this codebase, and this is the end of an audit train. **(b)** The exposure is one href over the drain delay, and requires a same-UID substitution inside it. **(c)** The classification step (4) needs is exactly the *"provider-authoritative stale result"* versus *"we could not determine the answer"* distinction that `CLAUDE.md` names as the single most repeated defect here; landing it unrehearsed, late, is how a narrow wrong-delete becomes a broad never-drop violation.

**Recoverability, with the NON-RECOVERING case named explicitly (`MIS-IOS-008`).** The ordinary outcomes all recover: a delete that reaches the intended event is the user's own instruction; a delete whose resource is already gone returns 404 and the op retires as provably done; a transient failure leaves the op queued and it drains later. **The non-recovering case is the one this row exists for, and nothing repairs it:** a same-href substitution inside the drain window destroys the substituted event, WebDAV offers no undelete, and the next sync propagates that deletion to every other client rather than restoring it. No gesture, sync pass or retry brings it back — this is a C3-class wrong-target mutation that is accepted, deliberately, on a narrow window, rather than a latency or state edge that self-heals. **What would re-open this row:** the drain delay growing (a longer queue, an offline-first calendar mode, deferred or scheduled execution), `deleteEvent` acquiring a caller that reaches it without a fresh read, a provider whose hrefs are recycled rather than UID-derived, or any evidence of a real occurrence.

**⚑ COUNTERPART ADDED 2026-08-06 (round-11 R11-F): `IOS-CAL-002` owns the UPDATE/PUT half of this same family.** This row is the **DELETE** path (a bare `DELETE` on an href with no `If-Match`); that row is every calendar **UPDATE-path** write that carries no precondition naming the version it replaces — CalDAV's four `.unconditional` PUT sites plus the Google and Exchange `splitSeries`/`mergeExistingEventWithPatch` writes, which have no ETag plumbing at all. They are disjoint by HTTP method and joint by cause: there is no durable ETag witness anywhere in the calendar queue. **The remedy shape recorded above (steps 1–4) is the shared one** — capture at enqueue, a NEW `v84`, reuse `CalDAVPutPrecondition`, and a fail-closed 412 arm — which is why `IOS-CAL-002` points back here for it rather than restating it. Read both before touching either; fixing one alone leaves the other's window open and pays the migration cost twice.

**⚑ EXPOSURE NARROWED, NOT CLOSED — 2026-08-06 (round-12 T2).** This row's bound used to be *"the window is exactly enqueue→drain for one href"* while the producing tool would happily enqueue a delete for an event it had never successfully read. `CalendarEventDeleteTool` fetched the event only to populate the confirmation card and, on a failed fetch, rendered the placeholder title `(Event)` with `Date()` for both ends — the user confirmed **that** — and then persisted the delete anyway. `CalendarEventEditTool` already refused the same shape, so the two tools disagreed and **the destructive one was the permissive one**. The delete tool now mirrors the edit tool's refusal: an event that cannot be dereferenced yields a structured error naming `calendar_event_read` / `calendar_search`, and **no `PendingCalendarOperation` row is written**.

⚠️ **That is not a dropped intention** — the refusal happens BEFORE `queueCalendarOperation`, so nothing was persisted and nothing was acknowledged; never-drop governs intentions that were one or the other. ⚠️ **And it does not close this row.** The read that now gates the enqueue happens at CONFIRMATION time, not at DRAIN time, so the enqueue→drain substitution window this row exists for is untouched; what changed is that the window can no longer be entered from an unread starting state. **Verification:** `CalendarDeleteIdentityProofTests.unreadableEventIsRefusedAndNeverQueued()` (red pre-fix: the wire mock recorded the delete AND the tool told the agent *Calendar event deleted successfully.*), with `readableEventIsStillDeleted()` as the fixture anchor (`MIS-030`) proving the refusal is not vacuous.
