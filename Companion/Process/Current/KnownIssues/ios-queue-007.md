## Full detail

**A provider mutation that exceeds its deadline is abandoned, not joined, and the queue immediately releases ownership of it.** `withTimeout`'s own doc says so: *"The cancelled operation task is abandoned — it will clean up when it eventually finishes or when the process exits."* `executeSingleOp` wraps every `executeOperation` in it, receives `TimeoutError`, and requeues the row. `IMAPProvider.mutateAdmittedUIDs` contains **no** cancellation checkpoint around `server.store(...)` — it is `withActionConnectionSelection { requireUidValidity; selectMailboxTracked; requireUidValidity; store }` — and SwiftMail's NIO continuations are the non-cooperative case `withTimeout` was written for. **Two reachable outcomes.** (1) *Ordering:* a timed-out `UID STORE +\Seen` on M can land AFTER the retry and after the user's newer `markUnread(M)`, leaving the message read against the newer intention. (2) *Duplication:* a `move` whose `UID COPY` completed just before the deadline is retried, producing a second destination copy. **Why REGISTRABLE.** Both land on the **correct** message — the abandoned task carries the UID and epoch it already admitted, and the source expunge stays `COPYUID`-gated — so C3 is not reached; no queued intention is dropped (the op is requeued, and its retry is idempotent); and the wrong end state is visible and correctable by one ordinary gesture, with the duplicate removable by an ordinary move-to-Trash. **The mechanism the reference used and this tree does NOT have, named so nobody assumes it:** searches for `onAbandon`, `zombieActive` and zombie registration return **zero** production implementations here; the v2final line added synchronous zombie registration, an account-wide fence and a reaper for exactly this race. **Do not port that as a first move** — it is a large compensating mechanism (A3) for a rare edge, and the cheaper direction is a cancellation checkpoint immediately before the wire command plus an account-wide in-flight fence keyed on `(account, folder, uid)`. ⚠️ **Interacts with `IOS-QUEUE-003` item 4:** any fix that keeps a timed-out op claimed must not turn a permanently slow server into a permanent lane wedge.

**THE NON-RECOVERING CASE, NAMED (2026-08-05, `MIS-IOS-008`).** The recovery in both outcomes is the user's own gesture, and it is available because nothing is destroyed — outcome (1) leaves a read flag to re-clear, outcome (2) leaves a duplicate to move to Trash. It does not fire *cleanly* while the abandoned task is still in flight: nothing joins it, so a corrective `markUnread` issued before the abandoned `UID STORE` finally lands is itself overwritten and the user must repeat. The gesture stays available and eventually wins, so that is a repeat, not a loss. **The shape that would NOT recover is an abandoned task that never returns at all**, because it still holds the action connection's `actionInUse` mark and every later action on that account queues on `actionWaiters` behind it — the wedge corollary, which is defect-class rather than registrable. **Nothing in the current code produces it, and this is the property any fix must preserve:** `IMAPProvider.withActionConnectionSelection` releases on BOTH legs — `releaseActionConnection(healthy: true)` after `body` returns, `releaseActionConnectionAfterFailure` in its `catch` — and the abandoned work is a NIO command on a socket, so it unwinds when the command completes or the connection errors rather than holding the mark for the life of the process. That is the same property the `IOS-QUEUE-003` warning above is about, stated from the other side. **A1 — pre-existing, verbatim:** `git show 07a4bb703:TabMail/Helpers/AsyncTimeout.swift` carries the same *"The cancelled operation task is abandoned"* contract and the same `operationTask.cancel()`, and shipped's `AccountManagerQueue` already wrapped `executeOperation` in `withTimeout(seconds: SyncConfig.pendingOperationTimeoutSeconds)`. There is no shipped behaviour to restore.
