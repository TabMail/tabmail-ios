## Full detail

**The staging key is `"\(accountId):\(messageId)"` — no folder, no epoch, no generation — and the three writers that use it disagree about what that key means.** `stageHeader`'s UPSERT overwrites IDENTITY (`rfc822MessageId`, `observedUidValidity`, `subject`, `date`, …) and **deliberately RETAINS the body/AI payload**; its own comment says so: *"The columns this UPSERT deliberately RETAINS are the body/AI payload; keeping a PREVIOUS run's epoch beside a re-read UID is precisely what would misattribute the row."* The comment identifies the hazard for the **epoch** and then leaves the **payload** retained on the same reasoning it just rejected. `stageBody` and `stageSummary` compound it: both are bare `UPDATE … WHERE id = ?` with **no** epoch, RFC, folder or run-generation compare-and-swap, so a run that returns from its AI await after a successor has re-headed the row writes its summary onto the successor. The merge then consumes it — `NSEDataBridge` writes `summaryBlurb`/`summaryTodos` durably from a staged row with `aiCompleted = 0`, which is precisely the window `stageSummary` targets. **Retention is CORRECT for the case it was written for** (a re-push of the SAME message, where recomputing the body and summary is pure waste); the defect is that "same id" is taken as "same message" when the row already carries the `rfc822MessageId` that would settle it. **Why this was FIRST graded REGISTRABLE — three of the four defenses named here DO hold, and are restated because a later reader must not re-open the paths they close.** IMAP staging only ever SELECTs INBOX (`NSEIMAPConnection`, `folderPath: String = "INBOX"`), so there is no cross-folder UID collision; the key can only collide after a **UIDVALIDITY turnover recycles the UID**. And on a settled folder the collision fails closed: `uidValidityStagingRowStatus`' `isOldEpoch` is a positive inequality between the staged and stored epochs, so the re-headed row (fresh epoch, stale stored epoch) is **skipped AND deleted**; while the folder is quarantined ARM 2 keeps it unmerged; and reaching a settled NEW epoch requires the reaction, whose step-3 purge deletes the predecessor row before step 5 stamps. **The one path that stays open is the nil-folder-epoch population** — `uidValidityStagingRowStatus` fails open on both signals when either epoch is nil, no reaction (and therefore no purge) ever fires for a folder that never earned an epoch, and `insertNewHeaderFromStaging` does not consult `nseMergeIdentityConfirmed`. That is the same `IOS-AI-003` / `IOS-EPOCH-001` population `IOS-ROUND3-D6`'s sync-merge closure accepted, **but `IOS-NSE-002`'s residual is stated as needing "an RFC-less message", and this does not**: the row's identity is the successor's and is entirely correct — only its body and summary belong to the predecessor. **⛔ THE FOURTH DEFENSE WAS FALSE — RETRACTED IN PLACE THE SAME DAY. The retracted basis is kept verbatim so a later reader can see what was believed and why it was wrong:** *"Bounded, and the bound is a verified fact rather than an estimate: the same merge pass reaps `populated = 1, aiCompleted = 0` rows older than `staleStagingWindowSeconds` (60 s), and `processedAt` is not on `stageHeader`'s `ON CONFLICT` SET list, so a re-headed row keeps its PREDECESSOR's staging instant and ages out on the original clock. A turnover, a push at the recycled UID and a merge must therefore all fall inside one 60-second window."* **What is actually true:** `mergeNSEStagingData`'s step-1 read is `SELECT * FROM nse_processed_message WHERE populated = 1` with **no `processedAt` predicate at all**; `abandonedCutoff` (`now − staleStagingWindowSeconds`) appears only at the **post-commit deletion** decision (`if msg.aiCompleted || msg.processedAt < abandonedCutoff { localMergedIds.append(msg.id) }`, and the analogous `.filter` before its `DELETE`), and the separate orphan reap targets `populated = 0` only. **`abandonedCutoff` is a DELETION predicate, not an ADMISSION predicate** — the row is merged into durable GRDB *first* and reaped *after*. It guarantees the row is not merged **twice**; it does not stop it being merged **once**. (`MIS-024` instance 3: a defense cited from a mechanism that is real and correct but whose call site is **downstream of the damage**.) The clause was doubly void: `aiCompleted` is not on the `ON CONFLICT` SET list either, so a row that reached terminal in run 1 and is then re-headed carries `aiCompleted = 1` and is deleted on **that** arm irrespective of age. **The three surviving defenses were then re-tested against HEAD and none of them closes the path.** (i) `isOldEpoch` needs BOTH epochs present — `guard let observed = msg.observedUidValidity, let stored = entry.lastKnownUidValidity, observed != stored` — so it is inert, not protective, on a nil-epoch folder. (ii) The reaction's step-4 `NSEDataBridge.purgeStagedStateForFolder` genuinely does precede the step-5 stamp and genuinely does abort the reaction on failure — but the reaction only runs once a turnover has been **detected**, and on a nil-epoch folder the sole detector is `verifyAndBootstrapPrePopulatedFolderEpoch`, whose `.unobservable` legs (no header carries an rfc822; the SELECT reports no UIDVALIDITY; the sample read or sample FETCH throws) leave the epoch nil — permanently, for the first two. (iii) INBOX-only staging kills the cross-folder UID collision and nothing else; it says nothing about a turnover recycling a UID inside INBOX. **THE PATH, END TO END (every step verified against HEAD, not inferred):** ① NSE run 1 completes for message X at INBOX UID 42 under epoch E1 — `persistProcessedMessage` (INSERT OR REPLACE) leaves `aiCompleted = 1`, X's body, X's summary/todos/reminder, X's `actionTag`. ② The app is backgrounded, so no merge consumes the row. ③ The server's UIDVALIDITY turns over E1→E2 and reissues UID 42 to a different message Y. ④ NSE run 2 for Y: `NotificationService.swift:549` calls `stageHeader`, whose `ON CONFLICT(id) DO UPDATE SET` list overwrites `rfc822MessageId`, `observedUidValidity`, `subject`, `senderName`, `date`, … and **retains** `htmlContent`/`textContent`/`summaryBlurb`/`summaryTodos`/`actionTag`/`aiCompleted`/`processedAt`. ⑤ **`NotificationService.swift:652` — the aggravator, and it makes step ⑥'s precondition deterministic rather than accidental:** `NSEStagingDB.getCachedResult(db:accountId:messageId:)` selects `WHERE id = ? AND aiCompleted = 1` with **no RFC and no epoch term**, hits X's retained payload, logs *"STAGING cache HIT — skipping AI calls"*, fills the notification for Y with **X's `summaryBlurb`, `actionTag`, `reminderContent`, `reminderDate`, `reminderTime`**, delivers, and returns — so run 2 never reaches its own terminal `persistProcessedMessage` and the spliced row is left exactly as step ④ made it. The user is shown X's AI summary under Y's sender and subject **before any merge runs at all**, and this stage needs no nil epoch. ⑥ Next foreground: the merge. ARM 1 is inert (nil folder epoch), the folder is not quarantined, and there is no durable row at `acc:INBOX:42` (X was never merged and never synced), so `DurableIdentityLookup.find` returns nil and the **new-header arm** is taken — `insertNewHeaderFromStaging` (3457), which by direct grep does **not** call `nseMergeIdentityConfirmed` (its only two production call sites are 1639 and 1978, both existing-durable-row arms), and `persistRenderedBodyFromStaging` (2968), whose only guard is `guard htmlContent != nil || textContent != nil`. **THE END STATE — durable, and this is why it is not merely a display splice:** Y's `messageHeader` row is written with Y's correct identity and **X's `summaryBlurb`/`summaryTodos`/`reminderDate`/`reminderTime`/`reminderContent`/`actionTag`**; a `MessageBody` keyed `ContentKey(rawValue: headerId)` holds **X's body**; the post-commit `flushNSEBatchToFTS` indexes **X's text** under Y's header id and runs `UPDATE messageHeader SET bodyComplete = 1 WHERE id IN (…)`; a `messageAICache` row is upserted under `MessageIdentity.aiCacheKey(accountId:folderPath:rfc822MessageId:)` — i.e. keyed on **Y's RFC id**, so the poisoning survives any later UID re-key; and `queueSetTagPendingOp` inserts a `setTag` `PendingOperation` that will write **X's action tag as an IMAP keyword on Y**. **WHY IT IS NON-RECOVERABLE (the mantra's test, applied rather than asserted):** sync finds nothing to repair — Y's header genuinely IS UID 42 under E2; the body queue selects `headerComplete = 1 AND bodyComplete = 0` and this row is `bodyComplete = 1`, so it never re-fetches; and even if it did, `BodyFetchProcessor` inserts with `onConflict: .ignore`, which preserves the wrong body. The AI cache is an RFC-keyed **HIT** for every later recompute — the hazard `NSEDataBridge`'s own phase-2 ARM comment already names (*"that row's own later summary job then reads the poisoned value as a cache HIT"*), here reached through the arm that has no identity door. No sync pass and no single ordinary user gesture restores it: the user opens what the list calls Y and reads X. That is C3 misattribution, which the mantra places in the non-recoverable set outright. **REACHABILITY, stated honestly:** the durable half needs an IMAP INBOX whose `Folder.lastKnownUidValidity` is nil at merge time — the `IOS-EPOCH-001` / `IOS-AI-003` population, which is narrow but **durable** rather than a window (a folder no row of which carries an rfc822, and a server that reports no UIDVALIDITY, never leave it), plus a genuine turnover that recycles a UID onto a pushed message. Frequency is not the test here: the mantra's rare-edge dispensation is available only for the recoverable set, and this is not in it. 📋 **IMPLEMENTATION BRIEF — do not implement from this row; hand it to a fresh implementation agent.** **File/symbol to change: `TabMailNotificationService/NSEStagingDB.swift`, `stageHeader` — and only it.** **The invariant to encode:** a staged row's retained body/AI payload may only survive a re-`stageHeader` when the incoming identity is **not positively different** from the identity already on the row; on positive disagreement the payload columns (`htmlContent`, `textContent`, `attachmentsJSON`, `icsText`, `hasUnresolvedCIDs`, `summaryBlurb`, `summaryTodos`, `actionTag`, `reminderDate`, `reminderTime`, `reminderContent`, `aiCompleted`, `notified`, `processedAt`) must be cleared in the SAME write transaction that rewrites the identity. Read-then-branch inside the existing `db.write` (delete the row, then plain INSERT) is acceptable and simpler than a `CASE WHEN` per column. **Positive disagreement means exactly what `NSEDataBridge.nseMergeIdentityConfirmed` already means by it, and MUST reuse that shape rather than invent a second one:** (a) both `rfc822MessageId`s present and unequal after the tree's identity-comparison normalizer, **or** (b) both `observedUidValidity`s present and unequal. Door (a) is the load-bearing one **and it is available precisely where door (b) is not**: the IMAP NSE resolves its push by Message-ID (`fetchIMAPMessage(rfc822MessageId: headId)` → `searchMessageId` → UID), so both sides carry an RFC even on the nil-epoch folder that defeats the epoch door. A test that merely asserts "the clear-arm ran" is a mechanism test and will stay green on a wrong spec.

The doors are `NSEDataBridge.nseMergeIdentityConfirmed`'s, same precedence: **(a) RFC first and unconditional** (both `MessageIdentity.comparableRfc822Identity` present and unequal), **(b) epoch only when (a) could not adjudicate**.
