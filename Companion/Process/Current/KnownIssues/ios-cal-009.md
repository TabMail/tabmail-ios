## Full detail

**Byte-identity to shipped, verified independently and not inherited from the report.** `git show 07a4bb703:TabMail/Services/AI/Tools/CalendarToolHelpers.swift` and `…:TabMail/Providers/GoogleCalendarProvider.swift`, extracting each function body and comparing: `formatDetailedEvent` **3787 bytes, identical**; `resolveInstanceId` **2807 bytes, identical**. Every clause below is SHIPPED behaviour, not a v3 regression. That changes the framing and not whether it is a defect (A1: shipped is a floor, not a ceiling).

**Clause 1 — the formatter emitted a self-contradictory timezone pair. REPRODUCES. ✅ FIXED in this round.** `formatDetailedEvent` formatted `start_iso`/`end_iso` with `toNaiveISO(…, timeZone: tz)` — the resolved DISPLAY zone — and then emitted `timezone: \(storedTz.isEmpty ? tz.identifier : storedTz)`, i.e. the PROVIDER'S stored zone whenever one existed. A Vancouver device reading a Tokyo event produced `start_iso: 2026-05-20T17:00:00` beside `timezone: Asia/Tokyo`, which names an instant **16 hours** from the real one. The old comment (*"Either way the agent gets an unambiguous IANA id"*) was true of the id and false of the PAIR. **The other three emitters of this key already meant the display zone** — `formatGroupedSummary`'s `timezone: \(tz.identifier)` and both `CalendarEventCreateTool` / `CalendarEventEditTool` echoes' `timezone: \(resolvedTz.identifier)` — so this was the odd one out, not the convention. Now: `timezone:` always names the zone the ISO values are expressed in, and the stored zone moves to its own `event_timezone:` key rather than being dropped (it is genuinely needed for provider-local wall times and DST). **`start_iso` itself is unchanged**, so this fix does not perturb which `recurrence_id` the agent sends and therefore cannot move the resolver's answer. Pinned by `FormatDetailedEventTests.timezoneNamesTheZoneTheIsoValuesAreIn` (red pre-fix, 2 issues) plus its negative case `noStoredZoneEmitsNoEventTimezoneLine`.

**Clause 2 — `recurrence_id` is documented as "the `start_iso` of the target occurrence". REPRODUCES**, verbatim, in `CalendarEventEditTool`'s own error string. **And the three providers do not agree on what that string means.** `CalDAVProvider` states and implements *"The naive recurrence_id is the occurrence's wall-clock time IN THE MASTER'S ZONE — parse it there, not in the device zone, so the absolute instant is correct even when they differ"*; `GoogleCalendarProvider.resolveInstanceId` and `ExchangeCalendarProvider.resolveInstanceId` both set `fmt.timeZone = .current` and parse it in the DEVICE zone. One naive string, two incompatible readings, no schema sentence that picks one. CalDAV's reading is the one that yields the correct instant.

**Clause 3 — the day-prefix match can select the PRECEDING occurrence. REPRODUCES, and remains reachable after clause 1 is fixed.** Google's resolver takes `dayPrefix = String(recurrenceId.prefix(10))` and matches it against `ev.start?.dateTime ?? ev.start?.date`, which Google renders **in the event's own timezone**, while the window centre was parsed in the DEVICE timezone. For a Tokyo daily series read on a Vancouver device, the agent's `start_iso`-derived `recurrence_id` carries the Vancouver date `2026-05-20`; the ±25 h window contains both `2026-05-21T09:00:00+09:00` (the intended occurrence) and `2026-05-20T09:00:00+09:00` (the previous day's, 24 h earlier); `.first(where:)` returns the **previous** one, and `updateOccurrence` then `PATCH`es it with `sendUpdates: "all"`. That is a **C3-shaped wrong-target mutation with outward-facing invitations we cannot recall.** Exchange's resolver is the same shape. A sub-daily series is a second, timezone-independent route to the same defect: several instances share one day prefix and `.first` takes the earliest.

**Why clause 3 is not fixed here.** The honest fix is to stop matching on a rendered day prefix and resolve the occurrence by its `originalStartTime` in the master's timezone — the witness Google and Graph both expose and that `CalDAVProvider` already uses. That is a resolver redesign across three providers plus a schema sentence pinning `recurrence_id`'s zone, i.e. a design change with its own review surface. Reported to the coordinator for its own round rather than attempted at the end of an audit train.

**Clause 4 — a locally-generated resolution failure is classified as provider-authoritative. REPRODUCES, and is WIDER than reported.** `AccountManager.isCalendarNotFoundError` claims `GoogleCalendarError.eventNotFound` and `ExchangeCalendarError.eventNotFound`, and the drain's arm for it retires the durable op with the reason *"event not found on server"*. But the census of THROW sites (`rg -n '\.eventNotFound' TabMail/ Shared/ TabMailNotificationService/`) shows those two cases have **exactly two production throw sites each, all four inside `resolveInstanceId`** — an unparseable `recurrence_id`, or a window in which nothing day-matched. **Neither is the server saying anything.** A genuine server 404 arrives as `httpError(404, _)`, which the same predicate claims separately and correctly; `CalDAVError.notFound` comes from `CalDAVClient`'s HTTP 404 and `DemoError.eventNotFound` from the demo store's own authoritative read, so both of those stay correct. So *"we could not determine which occurrence you meant"* is being laundered into never-drop exit 2, which clause 2 of the invariant forbids by name. The report named Google; Exchange has the identical defect, which makes this a class and not an instance (A7). `GoogleCalendarProvider.splitSeries` already carries a comment naming this exact hazard for its proof-GET.

🚨 **Why the prescribed remedy was NOT applied — it is this defect's own mirror image (`MIS-005`, `MIS-026`).** The brief said to make the local failure *stay retryable*. An error that no terminal arm claims falls to `drainCalendarQueue`'s transient arm, which requeues it **and** inserts the account into `failedAccounts`. Because the queue is FIFO by `createdAt`, a `recurrence_id` that can never resolve then sits at the head of that account's calendar lane and head-of-line-blocks every later calendar op on it, on every drain, forever. **This file's own `isCalendarUnsupportedError` doc says so in as many words**: *"an error no arm claims falls through to the transient arm, which requeues it and inserts the account into `failedAccounts`, head-of-line-blocking every later op on that account on every subsequent drain. That starvation is a wedge, and the wedge corollary sits in the same non-recoverable set as a dropped intention."* So the two candidate dispositions — terminal-as-not-found and retryable — are inverses of each other and **neither is the fix**; MIS-005's round-15 recurrence records exactly this shape and its lesson (*"when the two candidate fixes are inverses of each other, neither is the fix"*). The third thing — splitting the malformed-`recurrence_id` case (terminal, honestly a bad request) from the could-not-resolve case (which needs clause 3's `originalStart` witness to stop being reachable at all) — is part of the same design round as clause 3, and reclassifying the arm without it would only change which false reason string the user is shown.

**Recoverability under THE MANTRA, and the accepted cost.** For clause 4 the op fails closed: it does not execute, cannot wedge the lane, and is durably retired with `status = 'failed'` + a reason. A calendar edit is chat-initiated and `queueCalendarOperation` drains immediately, so an awaiter is normally live and the agent reports the failure in-turn; the user re-issues the edit — one ordinary gesture. The accepted cost is that the reason string says "event not found on server" when the server said nothing, which misleads about the CAUSE while being correct that the edit did not happen.

**THE NON-RECOVERING CASE, NAMED (`MIS-IOS-008`).** Clause 3 is not recoverable and is not claimed to be: if the resolver patches the wrong occurrence, the wrong occurrence has been changed and `sendUpdates: "all"` has already notified its attendees. Nothing in this row makes that acceptable — it makes it **reported and registered rather than silently carried**, and it is the reason clause 3 is escalated to the coordinator rather than closed. Its reachability is bounded: a RECURRING event, edited with `this_only` or `this_and_following`, on Google or Exchange, where the device date and the event-timezone date of the target occurrence differ (or the series is sub-daily).

**What would re-open this row:** clause 3's resolver redesign landing (at which point this row becomes FIXED for that clause and clause 4's split becomes safe); a report of a user's recurring event being edited on the wrong day; a fourth provider adopting the day-prefix match; or `drainCalendarQueue`'s transient arm acquiring a per-op retry cap or a per-op (rather than per-account) block, which would remove the wedge that currently makes clause 4's obvious fix unsafe.

✅ **AMENDED 2026-08-07 (round 18c) — CLAUSES 2, 3 AND 4 ARE NOW FIXED. THE FIX WAS THE ADDRESS, NOT THE DISPOSITION.** Root cause, stated once: **a recurring occurrence was addressed by a naive wall-clock string carrying no timezone, and every consumer re-interpreted that string in a different frame.** That is the calendar instance of THE ADDRESS PROBLEM — an address minted in one frame, carried as something weaker than the frame it needs, re-resolved later on weaker evidence. Clauses 2, 3 and 4 are three symptoms of that one absence, which is why fixing the address closes all three and why fixing the *disposition* closed none.

**(a) The address now carries its frame.** `CalendarProvider.updateOccurrence` and `CalendarProvider.splitSeries` both take a required `recurrenceIdZone: TimeZone` — **no default value on either**, deliberately (`MIS-018`): the two methods take the SAME `recurrence_id` string off the SAME durable operation, so honouring the declared frame in only one of them would make one argument mean two different instants depending on `edit_scope`. `AccountManagerCalendarQueue`'s `.edit` case stamps it once from `CalendarToolHelpers.resolveTimeZone(resolvedArgs)` — **the same resolver that produced the `start_iso` the agent copied into `recurrence_id`** — and threads it into both calls, so the string and the frame that gives it meaning travel together.

**(b) Resolution is by INSTANT, in one frame, and never guesses.** New shared `RecurrenceOccurrenceResolver` (declared in `GoogleCalendarProvider.swift`, used by all three providers) maps `[OccurrenceCandidate]` × `recurrenceId` × `zone` to an `OccurrenceMatch` of `.resolved(id)` / `.absent` / `.ambiguous(n)` / `.malformed`. Rules: a timed address matches an exact instant; a date-only address matches the day **rendered in the declared zone**; an all-day candidate is matched by its literal DATE; and **exactly one** match resolves — two or zero are distinct outcomes, not a `.first(where:)` winner. The `items.count == 1` “only one instance came back, it must be the one” **guess is DELETED** from both Google and Exchange; it was the mechanism that turned a failed match into a confident wrong-target PATCH.

**(c) CalDAV converts once, and both writers agree.** `CalDAVProvider.recurrenceIdInMasterFrame(_:declaredZone:kind:)` renders the declared-frame naive string into the master `DTSTART`'s frame (`.allDay` and `.floating` pass through unchanged — a DATE has no zone and a floating master has no target frame; `.utc` and `.zoned(tzid)` convert; an unrecognised TZID returns nil and the edit **fails closed**). The converted value now feeds **both** `buildOverrideVEvent` and `spliceOrReplaceOverride`, which is load-bearing: if they disagree the splice does not replace the override, it **appends a second VEVENT sharing the same UID and RECURRENCE-ID**. `deterministicSplitEventId` still hashes the RAW `recurrenceId` so a retry of the same durable op stays idempotent. **The refutation this encodes:** the pre-fix comment claimed the input was already in the master's zone. It never was — `formatDetailedEvent` renders `start_iso` in `timezone ?? .current`, so the string the agent copies is in the DISPLAY frame.

**(d) Clause 4's classifier is UNCHANGED, and that is the outcome rather than an omission (`MIS-026`, counterfactual stated).** `AccountManager.isCalendarNotFoundError` still claims `eventNotFound`, because after (a)–(c) `eventNotFound` is thrown **only after a full enumeration proved the occurrence absent** — which is a genuine exit 2, provider-authoritative. The three failures that previously shared one error are now three: **absent** ⇒ `eventNotFound` (retire, authoritative); **ambiguous** ⇒ `CalendarProviderError.notSupported("… matched N occurrences … refusing to guess…")`; **malformed** ⇒ `notSupported("Invalid recurrence_id …")`. Both `notSupported` arms are terminal-and-reported and neither wedges the lane. What breaks if this goes the other way: widening `isCalendarNotFoundError` to cover the `notSupported` arms would re-create the exact laundering this round removed — “we could not determine the answer” silently becoming “the provider says it is gone.”

⛔ **THE REFUTED REMEDY, RECORDED SO IT IS NOT RE-DERIVED (`MIS-005`).** The obvious fix for clause 4 — make the locally-generated failure **retryable** — is wrong: retryable routes it to `drainCalendarQueue`'s transient arm, which requeues the op **and** does `failedAccounts.insert(accountId)`, head-of-line-blocking every later calendar op on that account forever. That is the **wedge corollary**, in the same non-recoverable set as a dropped intention. So both available dispositions were wrong — and *that* is the proof that the disposition was never the bug. When the two candidate fixes are inverses of each other, neither is the fix; go up a level and fix what made the choice necessary.

⚠️ **PREMISE CORRECTION — clause 3's sentence “Exchange's resolver is the same shape” is true of the SHAPE and false of the EXPOSURE.** `ExchangeCalendarProvider.request` sends `Prefer: outlook.timezone="<device IANA id>"` on **every** Graph request, so Graph renders occurrence starts in the **device** zone — which is the same frame the pre-fix day-prefix comparison parsed in. Exchange's comparison was therefore frame-CONSISTENT, and **the cross-date-boundary C3 mechanism in clause 3 is GOOGLE-ONLY.** Exchange's residual defects were real but different and are all now removed: the `timezone` argument was ignored outright, matching was day-granular (so a sub-daily series still collided), and the `count == 1` guess was present. Exchange additionally **fails closed** on an occurrence whose `start.timeZone` string does not resolve to a real `TimeZone`, rather than defaulting it.

**Alternatives rejected, with the reason each was rejected** (recorded because each is the first thing a future reader will propose): **(1) Google's server-side `originalStart` filter** — a mis-formatted or mis-framed filter returns an **empty** list, which is indistinguishable from genuine absence; that is precisely the laundering this round exists to remove, and it is unverifiable except against a fake. Client-side enumeration lets absence, ambiguity and malformation stay three different answers. **(2) Normalising the address into the device zone at the queue boundary** — destroys the DATE vs DATETIME distinction, so an all-day occurrence's DATE gets offset-shifted onto the **adjacent** occurrence: a C3 in the fix. **(3) Multi-frame fallback matching / “accept any plausible offset”** — the mirror image of the bug (`MIS-005`); it makes a wrong-occurrence match *more* likely, not less. **(4) Matching `originalStartTime` as a second key** — that is the master's own start, not the addressed occurrence's.

**Accepted residuals, all recoverable by one ordinary gesture (THE MANTRA), and all strictly better than a non-recoverable C3.** (i) Reading with `timezone: X` and then editing **without** it makes the two frames differ, so the edit **refuses** rather than guessing — recovered by re-issuing the edit naming the zone. (ii) A DST-fold wall clock is ambiguous in **any** zone-based naive representation; it resolves to one of the two instants, which is a property of the representation, not of this resolver. (iii) Instant matching is **stricter** than day matching, so an occurrence that has already been moved and is then addressed by its ORIGINAL start now refuses instead of patching — the deliberate direction.

**Compatibility: none needed, verified rather than assumed.** v3 has never shipped to any device (`v2final` is a sibling of `v1.6.38`, never released), so no durable `PendingCalendarOperation` row anywhere carries the old-format `recurrence_id`. **No migration and no compatibility shim** — the next free migration number is untouched by this round.

**Pinned by** `TabMailTests/Providers/RecurrenceOccurrenceAddressTests.swift` — four suites (`Recurring occurrence address — selection`, `… Google wire`, `… CalDAV override frame`, `… the declared frame reaches the provider`) whose fixtures name every zone explicitly and never touch `.current`. The wire suite asserts the **system property**, not the mechanism: the PATCH that reaches the network names `occ-named` and not `occ-preceding`; a lone non-matching instance produces **no PATCH at all** and its absence IS `isCalendarNotFoundError` (the held side of the two-sided invariant, per `MIS-030`); and an unusable address is neither not-found nor transient.
