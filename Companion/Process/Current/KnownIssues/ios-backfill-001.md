## Full detail

**A SELECT that never reported UIDNEXT permanently marked the folder fully crawled.** SwiftMail's `Mailbox.Selection.uidNext` is non-optional with a `UID(0)` default (`SwiftMail/IMAP/Models/Mailbox.swift`) and `SelectHandler` assigns it only when the wire carried `* OK [UIDNEXT n]`, so "the server did not say" arrived at `SyncEngineBackfillWalk`'s `.fresh` branch as the **number 0**. `initialCursor = uidNext - 1` was then `-1`, which took the `initialCursor < 1` early-out — a branch written for UIDNEXT **1**, the one value that PROVES the mailbox never held a message (RFC 3501 §2.3.1.1 assigns UIDs strictly increasing from 1) — and wrote `backfillComplete = true`. Completion removes the folder from `remaining` on every later pass, so **nothing ever revisited it and the whole mailbox stayed outside automatic backfill**. This is `MIS-IOS-004`'s class — *"could not determine"* treated as an authoritative answer — and the **tell was already in the file**: the epoch beside it WAS normalised for the zero case (`observed != 0 ? observed : nil`) and the UIDNEXT was not. **The fix:** `getUidNextWithEpoch` returns `uidNext: Int?`, normalising 0 → nil at the same site and for the same reason as the epoch, so absence of evidence is unrepresentable as a number at the decision point; the `.fresh` construction declines the folder (`epochDeclinedFolderIds`, `continue`) instead of computing a cursor from it. The row is left EXACTLY as the pass found it — `backfillComplete` still false, no cursor, no stamp — so the next call meets the same preconditions and retries. **The `initialCursor < 1` completion path is unchanged and still fires for UIDNEXT 1**, together with its NB3 epoch bootstrap in the same transaction, so a genuinely empty folder still settles and is still gestureable; both directions are pinned (`aFolderWithNoReportedUidNextIsNeverMarkedFullyCrawled`, `aGenuinelyEmptyMailboxStillSettles`). **Accepted residual, with its bound:** a server that omits UIDNEXT on *every* SELECT is now never deep-crawled at all — one SELECT per `runBackfill` call, declined, forever. That is a deliberate trade of a bounded, self-correcting refusal for a silent permanent mis-completion, and it is a nonconforming server (RFC 3501 §6.3.1 lists UIDNEXT among SELECT's REQUIRED OK untagged responses), which is why the case is not reachable by ordinary sync. **Recoverability, with the caller named:** the folder stays in `remaining`, so the first SELECT that does report a UIDNEXT crawls it with no user gesture — `runBackfill` is invoked by `SyncEngine.startBackfill` after every sync and by `SyncScheduler`'s BGProcessing pass. Meanwhile its recent window still arrives on navigation (`InboxView.onAppear` → `InboxViewModel.startSync()` → `AccountManager.syncFolders(_:)` → `SyncEngine.syncFolderMessages` → `runSyncMessages`), the same path `IOS-EPOCH-001`'s round-8 correction relies on.
