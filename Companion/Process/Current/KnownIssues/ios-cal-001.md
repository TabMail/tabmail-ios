## Full detail

Done as prescribed: one helper (`GoogleCalendarProvider.encodedPathSegment`), all **11** sites (not 12), `?? id` deleted everywhere — the fallback was the wrong-resource arm. The refusal throws `GoogleCalendarError.invalidPathSegment`, claimed by `AccountManager.isCalendarBadRequestError` so a permanently-unencodable stored id terminalizes instead of wedging the account's calendar lane. `GraphAPI.encodedGraphPathSegment` was deliberately NOT reused: it allows only RFC 3986 unreserved, which would newly encode the `@` in every secondary-calendar id (`x@group.calendar.google.com`), and `%40` is not formally equivalent to `@` in a path segment (RFC 3986 §6.2.2.2) — a silent wire change to a working path in the name of a hazard only `/` and dot-segments create. Pinned by `CalendarPathContainmentTests`, which asserts the encoded BYTES for an ordinary secondary-calendar id are unchanged.
