## Full detail

**`6b689890d`'s refusal is permanent, not deferred, in one narrow state — and the retry loop around it costs paid LLM calls without a ceiling.** This is the mirror-image cost of that fix, found by both reviewers rather than cleared silently. The state: an IMAP/iCloud row with **no** `rfc822MessageId` (so arm 6 cannot carry it) in a folder whose `lastKnownUidValidity` is nil and **can never become non-nil** — because blind bootstrap (`bootstrapFolderUidValidity`'s `NOT EXISTS (messageHeader WHERE folderId)` term) refuses a folder that already holds rows, while the verified door `verifyAndBootstrapPrePopulatedFolderEpoch` excludes RFC-less rows from its sample and returns `.unobservable` on an all-RFC-less population. Reachable via the orphan re-adoption chain the fix's own doc comment describes, and on a server that never reports UIDVALIDITY. **The consumer makes it expensive rather than merely inert:** `readJobOutcome` returns `.needsRetry`, `jobCompleted` retries with `maxRetries: .max` and a backoff capped at 30 s, and `repopulateOnDrain` re-enqueues every drain — so summary, action and reply each re-run the LLM indefinitely, with no `MessageAICache` short-circuit because that cache keys by `rfc822MessageId` and these rows have none. Only an unrelated future RFC-bearing message in the same folder unlocks verification. **Why REGISTRABLE and not blocking:** it is a refusal, never a wrong write, so not C3; an AI summary is recomputable derived content explicitly outside the never-drop set; and it is **not** the wedge corollary — the job yields its slot each cycle and starves no other intention, least of all a durable `PendingOperation`. `readJobOutcome`'s `!message.isInInbox ⇒ .scopeExited` bounds the loop to inbox-resident rows. **It materially extends `IOS-AI-002`'s billing/battery loop** to newly-synchronized, positively-stamped headers, and the arm-8 doc comment already names this exact hazard (*"a paid API call repeated forever for a summary that could never land"*). ⚠️ **`6b689890d`'s commit body claims the refusal is recoverable. That is true in general and FALSE in this sub-case** — recorded here rather than by amending the commit, because history is not rewritten.

✅ **FIXED by `403496b21`, "Stop paying for AI jobs whose write-back can never be attributed" — jointly with `IOS-AI-002`, which is the same defect reached from a different direction.** **The invariant that now holds:** an AI job whose guarded write-back is **structurally** refused issues at most one classification and no paid model call — it is retired via `JobOutcome.writeRefused` → `abandonWithoutCompletion` (the arm `.scopeExited` already takes, so nothing claims completion) and memoized in `unattributableJobs` so `repopulateOnDrain` cannot re-enqueue it into a spin. `ActiveAIQueue.writeAdmission(_:target:)` classifies inside the read that already captures the `AIWriteTarget`, and a structural refusal returns before the FTS body read, the NSE lease claim and the LLM call — so summary, action and reply stop re-running indefinitely for a population whose results were always thrown away. ⚠️ **THE PERMANENCE THIS ROW IDENTIFIED IS NOT DENIED — IT IS CLASSIFIED.** The refusal is unchanged and arm 7 is untouched; what changed is that a permanent refusal is now recognised as permanent instead of being treated as a transient failure. **The terminal condition, stated precisely by that commit and worth keeping:** because the target is re-captured at the top of every attempt, arms 1–3 cannot fire and arm 6 admits on the row's own non-empty RFC id, so the condition reduces exactly to arms 7 and 8 — an epoch-addressed row with **no** RFC 822 Message-ID whose folder's numbering is absent or unknown, or whose own `observedUidValidity` is unset or disagrees. **Proof it was not over-broadened, two-sided:** a folder mid UIDVALIDITY reset holding the same RFC-less unstamped row classifies `transientlyRefused`, is NOT retired, and lands once the reaction finishes; 📝 **NOTE (final audit train round 3, Claude reviewer) — the classification's THIRD shape, recorded so it is not re-raised: an ABSENT `Folder` row classifies STRUCTURAL, not transient.** `ActiveAIQueue.writeAdmission(_:target:)` returns `.transientlyRefused` only when `Folder.fetchOne` **succeeds** *and* that row's `uidValidityResetPendingAt != nil`; a folder row that is **absent altogether** falls through to `.structurallyRefused`, so that message's AI jobs are retired for the process lifetime. The two-sided proof above covers a **present** folder mid-reset and is silent about an absent one, which is why this is written down rather than left to be rediscovered. **Not a defect, and no mechanism is owed.** The recovery path, by symbol: `ActiveAIQueue.rearmUnattributableJobs()`, called from `repopulateFromDatabase()` (launch / foreground / AI re-enable) and `cancelAllInFlight()` (suspension recovery), clears the memo wholesale — so the retirement lasts one process lifetime, not forever.
