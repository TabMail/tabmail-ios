## Full detail

**A Graph `400` can never be classified, because the body that would classify it is dropped before it reaches the classifier — so an op naming a malformed id retries forever instead of retiring.** Four verified citations, each checked in-tree at HEAD rather than taken on report: (1) **the body-preserving transport exists and names Graph as an intended consumer** — `Shared/HTTP/AuthedHTTP.swift`, `requestPreservingBadRequestBody`, whose doc says it is *"a narrow opt-in for the handful of action-path call sites (Gmail label modify/lookup, **Graph move**) that must structurally classify a `400` error payload rather than guess from the status code alone"*; (2) **only Gmail actually consumes it** — `GmailProvider.swift:1256` (the private wrapper) and `:1462` (the label-lookup site); `ExchangeProvider.patchMessage` (`:1223`) and `ExchangeProvider.moveMessage` (`:1244`) both still call the body-dropping `request`, so every Graph mutation's 400 arrives as a bodyless `HTTPError.networkError(statusCode: 400)`; (3) **the classifier has no Graph arm at all** — `AccountManagerQueue.isPermanentlyInvalidError` is the single expression `GmailProvider.isAuthoritativeActionRejection(error)`, so a Graph 400 is `false` by construction; (4) **`isGraphInvalidIdMalformed` does not exist as code** — the only occurrences in the tree are a comment in `GmailProvider.swift:1333` naming it as *"the reference"* implementation and a line in `PLAN_IOS_REFACTOR_V3/PLAN_V3_S4_tier3.md`. **Consequence:** a Graph mutation rejected with a genuinely permanent `ErrorInvalidIdMalformed` falls through to the generic arm and is retried without a cap, forever, for as long as the address stays malformed.

**WHY REGISTRABLE AND NOT BLOCKING — the failure is a stall, not a discard, and it is scoped to one message.** Nothing leaves the queue, so no exit is taken and Never Drop User Intention is not violated; the `PendingOperation` stays durable and visible, and the op's own address is repaired by the very sync that re-materialises the message under its current Graph id. **The blast radius is bounded by the lane grouping, and that is the load-bearing fact:** `AccountManagerQueue.buildLanes` forms connected components of `accountId:folderPath:messageId` and `drainPendingQueue` launches **one Task per lane**, each draining its own lane **sequentially** while different lanes run concurrently (`AccountManagerQueue.swift:519`). A permanently-400ing op therefore halts the op chain **for its own message only** — it cannot starve the account, the folder, or any other message's gestures. That is the `IOS-QUEUE-006` shape (the user can see it and re-act), not the `IOS-GRAPH-002` shape (a silent destruction behind a UI that showed success). By the mantra's test, Q1 answers **YES** — a sync pass re-addresses the row and one ordinary gesture completes the work — so this fails closed and is registered rather than mechanised.

**WHY THE SHIPPED BEHAVIOUR WAS WORSE — HEAD is strictly safer on this axis and must not be reverted toward it.** `v1.6.38`'s `isPermanentlyInvalidError` (`AccountManagerQueue.swift:812` at that tag) returned `true` for `HTTPError.networkError(statusCode: 400)` and for `NSError(domain: "Gmail"|"Exchange", code: 400)` — i.e. it retired the user's intention on **every** 400, including every transient and unexplained one. That is a never-drop violation and it is exactly the *"a bare status code is not a classification"* defect the current doc comment at `AccountManagerQueue.swift:1500-1524` was written to close. **The cost of the honest classification is a retrying row rather than a silently discarded gesture, and that trade was made deliberately** — `v2final` had a demote lane (`ProviderError.persistentActionFailure`) to park such a chain at the queue tail; v3 has none, so the retry is the price. **Do not restore the status-code arm, and do not add a Graph-specific retry cap — a cap is a discard on a timer.**

**SHAPE OF A FUTURE FIX, if one is ever wanted.** Route the Graph mutation call sites (`patchMessage`, `moveMessage`, and any sibling action-path request) through `AuthedHTTP.requestPreservingBadRequestBody` so the 400 body survives as `HTTPError.networkErrorWithBody`, then add a Graph arm to `isPermanentlyInvalidError` that mirrors `GmailProvider.isAuthoritativeActionRejection` **in its narrowness**: parse Graph's documented `{ "error": { "code": … } }` object and accept **only** a parsed `ErrorInvalidIdMalformed` (or a comparably deterministic documented rejection) as authoritative. **Everything else — an unparseable body, an empty body, an unrecognised code, any non-400 — stays retryable.** 🚨 **The trap, named because it has already been taken once in this subsystem:** reclassifying a Graph 400 as terminal **without** the body-parse is MIRROR-IMAGE TRAP 1 from `IOS-GRAPH-002` in reverse — there, converting a drop into a retry without re-keying makes a wedge; here, converting a retry into a drop without a parsed reason re-creates the `v1.6.38` never-drop violation. The parse is what makes the retirement *authoritative*, exactly as the re-key is what makes the retry *terminate*. **Attribution: pre-existing, not candidate-introduced** — the body-dropping call sites and the Gmail-only classifier both predate this candidate; what is new is only that the gap has now been enumerated.

**THE NON-RECOVERING CASE, NAMED (2026-08-05, `MIS-IOS-008`) — with its precondition established as REACHABLE and the mechanism that bounds it named, rather than left as a hypothetical.** The op itself never retires; what recovers is the **message**, once a sync pass re-materialises it under a provider-minted id, after which a fresh gesture forms a different `accountId:folderPath:messageId` lane key and drains independently of the halted one. So the state where recovery does not fire is one in which the malformed id is **never replaced**. In that state the lane stays halted, every later gesture on that message joins it by construction, and `SyncEngineDeltaSync`'s orphan-reclaim arm additionally **skips** the row for as long as a destructive op is pending (*"the user's optimistic folderPath is authoritative … sync will converge when the op drains"*), so the UI keeps showing the move as done and nothing ever contradicts it. That is the wedge corollary and it would be defect-class, not registrable. **The one in-tree producer of a permanently malformed provider id is named, and it IS bounded:** `insertOptimisticSentHeader`'s synthetic `sent-<UUID>` placeholder, whose own migration comment says so outright — *"the queue then forwards the synthetic `sent-<UUID>` id to the provider — Gmail/Graph reject it with HTTP 400 'Invalid id value'"* (`v57_repairOptimisticSentBodyComplete`, `AppDatabase.swift`). Delta sync replaces that placeholder with the real message under its real provider id, which is precisely the re-materialisation the recovery depends on. **A producer with NO such replacement path would move this row out of the registrable set**, so enumerating one is the check any future change to id minting owes — state it beside the change, not here. **A1 — verified at the tag, and shipped must not be restored:** `git show 07a4bb703:TabMail/Services/Account/AccountManagerQueue.swift`'s `isPermanentlyInvalidError` returns `true` for `HTTPError.networkError(statusCode: 400)` and for `NSError(domain: "Gmail"|"Exchange", code: 400)` — it retired the user's intention on **every** 400, transient ones included, which is a never-drop violation. A retrying row is the price of the honest classification and is strictly the safer side of that trade.
