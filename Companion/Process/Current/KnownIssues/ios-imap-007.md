## Full detail

**STATE THE CLOSURE, NOT ONE INSTANCE: undo of an already-drained move is a whole-command closed no-op unless EVERY member's row ends the drain carrying BOTH the destination address `COPYUID` proved AND an epoch stamp equal to the destination folder's `Folder.lastKnownUidValidity`.** The drain finishes a move locally by adopting the destination address the server itself reported (`MessageHeaderRekey.finishMove`), and `AccountManager.undoMove` then reverses it as an ordinary forward move admitted through `admittedOrdinaryActionTargets`, which requires `message.observedUidValidity == liveEpoch` and a parseable positive UID. The refusal is deliberately **WHOLE-COMMAND** — `undoMove` guards on `admission.messages.count == currentRows.count` and returns an empty result otherwise, so a partly-admissible bundle is refused entirely with zero local and zero durable mutation (*"a partly-reversed move is a worse outcome than an unreversed one, because the user cannot see which half moved"*). **THREE ARMS reach that state, all verified at the tip:** **(1) G4 — no `COPYUID` for that member, PER MEMBER.** State the condition correctly: it is *"no `COPYUID` for that member"*, **NOT** *"no UIDPLUS"*. RFC 4315 §3 makes the response code a SHOULD *"with limited exceptions"*, and those exceptions are properties of the MAILBOX, not of the server or of the attempt: a mailbox the client may COPY to but not SELECT/EXAMINE (*"SHOULD NOT send"*), and a `UIDNOTSTICKY` mail store (*"MAY omit"*). A fully UIDPLUS-advertising server therefore returns no `COPYUID` for such a mailbox. `finishMove` decides per member and never per operation, so a partly-named batch is partly re-keyed — while undo of that batch is still refused whole. **(2) G1 — the whole `COPYUID` response refused for pairing, BATCH-WIDE, which is strictly wider than (1).** `IMAPProvider.copyProvenDestinations` returns an EMPTY array — no member re-keyed at all — unless BOTH expanded lists are strictly ascending (`IMAPProvider.isStrictlyAscending`, equal neighbours rejected). `CopyUID.init(nio:)` in the pinned SwiftMail fork builds its mapping as a POSITIONAL `zip` and validates cardinality but not ordering, so promoting the destination half to a mutation address makes a mis-pairing C3-critical; refusing the response whole is the fail-closed answer. The same function also yields nothing for a wholly absent `CopyUID` or a zero destination UIDVALIDITY (batch-wide), and skips a member with a zero destination UID or a source UID this call never requested (per member). **(3) G2 — re-keyed, but the epoch stamp withheld.** `finishMove` writes `observedUidValidity` only when the server-reported destination epoch EQUALS the destination folder's `Folder.lastKnownUidValidity`, and otherwise re-keys the row with a NIL stamp — deliberately, because `AccountManagerActions.roleMoveRejectDispositions` treats a POSITIVE disagreement as its only terminal arm, so stamping optimistically would TERMINALLY DROP the user's next gesture (the mirror image of the bug the re-key fixes). A nil stamp is refused by `admittedOrdinaryActionTargets` too, so such a member has a correct address and is still un-undoable. **Reachability:** any move into a `UIDNOTSTICKY` or COPY-but-not-SELECT mailbox, plus any server that simply omits the code for some or all of a set (arm 1); a nonconforming server whose `COPYUID` lists are not both ascending (arm 2); a destination folder whose stored epoch has not caught up with the epoch the server stamped on this copy (arm 3). Modelled in tests by `FakeIMAPServer.withholdCopyUID(forSourceUIDs:)` and `FakeIMAPServer.reportCopyUIDDestinationsDescending()`. **Why REGISTRABLE and not BLOCKING:** nothing is lost and nothing is misattributed. The copy is in the destination, the source copy is left `\Deleted`-but-present (the purge stays gated on per-member `COPYUID` — `IOS-IMAP-004`), no queued operation is dropped or wedged, and the row is repaired by a later sync of the destination folder — `finishMove`'s G2 note states the nil-stamp case is *"recoverable by the next sync of that folder"* — after which an ordinary gesture on the message works normally again. The user-visible cost is that one undo does nothing until then. ⚠ **The refused undo entry is not itself revived by that repair:** `undoMove` authenticates each member by the `originalHeaderId` it captured, and the only production caller of `UndoService.applyRekeys` is the drain (`AccountManagerQueue.executeSingleOp`), so a re-key applied by any other path leaves the stacked member naming an id that no longer exists — another whole-command refusal. What recovers is the message's actionability, not that particular undo. **Deliberately not "fixed":** the only ways to name the message without `COPYUID` are an RFC 822 Message-ID `SEARCH` (banned by ADR-IOS-068/D4 and registered as `IOS-IMAP-002` — it returned every copy sharing the Message-ID and mutated all of them) or a durable receipt/alias object, which this change exists to avoid. Failing closed is the correct outcome. **Pinned by a red-first invariant test:** `FinishTheMoveLocallyTests.undoDoesNothingForAMemberCopyUidNeverNamed()` (suite type `FinishTheMoveLocallyTests`, display name *"Finish the move locally"*, file `TabMailTests/Services/FinishTheMoveLocallyTests.swift`) — it places an unrelated BYSTANDER at the stale source UID in the destination folder, so the naive alternative (queue the inverse naming the source UIDs) is a C3 wrong-message mutation, caught by the `FakeIMAPServer` wire oracle. ⚠️ **SCOPE CORRECTED AT APPLY TIME, recorded rather than silently applied.** The drafted row stated arm 1 only — *"when the server does not name a member in `COPYUID`, that member is not re-keyed"* — and would therefore have described a narrower condition than the code enforces, missing the batch-wide G1 pairing refusal and the G2 nil-stamp arm entirely. The closure above was re-derived from `copyProvenDestinations`, `finishMove` and `admittedOrdinaryActionTargets` at the tip before pasting. The draft's *"an ordinary gesture and an ordinary undo both work again"* was also narrowed to what the code supports, per the ⚠ note above.

✅ **CLOSED AS A DECISION (2026-08-04) — the closure stated at the head of this row IS the decision, and there is no third option to look for.** **The decision:** undo of an already-drained move stays a whole-command closed no-op in the three arms enumerated, and the whole-command shape is deliberate — *"a partly-reversed move is a worse outcome than an unreversed one, because the user cannot see which half moved."* **The alternatives are both banned and both already enumerated in this row:** an RFC 822 Message-ID `SEARCH` (ADR-IOS-068/D4, registered as `IOS-IMAP-002` — it returned every copy sharing the Message-ID and mutated all of them), or a durable receipt/alias object, which `59423bb7d`/`f7c3354c5` exist precisely to avoid. `FinishTheMoveLocallyTests.undoDoesNothingForAMemberCopyUidNeverNamed()` already pins the C3 hazard of the naive alternative by placing a BYSTANDER at the stale source UID, so the "obvious" fix is not merely unavailable — it is proven wrong by a red-first test. **Accepted cost:** one undo silently does nothing. **Recoverability, stated WITH its named exception rather than as a bare "recoverable":** the message's ACTIONABILITY recovers at the next sync of the destination folder (`finishMove`'s G2 note). What does **NOT** recover is that particular undo ENTRY — `AccountManagerActions.undoMove` authenticates each member by the `originalHeaderId` it captured, and the only production caller of `UndoService.applyRekeys` is the drain, so a re-key applied by any other path leaves the stacked member naming an id that no longer exists, which is another whole-command refusal. **That is a real, named, non-recovering thing**, and it is bounded to *"one undo does nothing"* — no loss, no misattribution, no dropped or wedged op. **Editorial note for a future reader, so nobody re-measures it:** arm (3)'s reachability shrinks materially now that `IOS-NSE-001` has landed (`ce6fb384c`), because the destination folder's `Folder.lastKnownUidValidity` is current more often.
