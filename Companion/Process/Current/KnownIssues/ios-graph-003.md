## Full detail

**A 404 also deletes the local header — but only where the op's `folderPath` matches the folder segment already baked into the row's primary key, which the post-move path does NOT satisfy.** `isConfirmedGoneError` matches `ProviderError.messageNotFound` and `HTTPError.networkError(statusCode: 404 | 410)` structurally; `deleteConfirmedGoneHeader` then fetches `MessageHeader` **by primary key** and, if the row exists, deletes it and calls `MessageContentStore.releaseUnowned(… stores: [.searchIndex, .body] …)`, with the `messageUserLabel` and `messageReference` FK cascades taking the children. **The two paths where the key DOES match, enumerated rather than asserted:** (1) **a retry of the move op itself after its wire call already landed** — `IOS-QUEUE-007`'s abandoned-`withTimeout` task, a crash between the Graph `200` and the op's deletion, or the `"CRITICAL: Failed to delete completed PendingOperation"` arm; the retry carries the op's SOURCE `folderPath`, which is exactly the segment in the PK, so the header, its body and its FTS row are destroyed; (2) **a message whose Graph id churned because something ELSE moved it** — Outlook desktop, OWA, or a server-side rule — where the local row is still at its original address and the user's first gesture 404s. A third, longer path exists on our own churn: move S→D, then D→S (each dropped), then a gesture from S, at which point the op's `folderPath` and the PK segment coincide again.

**Why REGISTRABLE.** Nothing is destroyed on the server, no wire operation is issued, and no message is mis-addressed — C3 is not reached. Everything deleted is **re-derivable server state**: the header, the `MessageBody` (re-fetched by the ordinary body pipeline), the FTS row (re-indexed), and `messageUserLabel`, which for Exchange is a Graph **category** and is re-ingested by `SyncEngineFullSync` / `SyncEngineDeltaSync` / `SyncEngineBackfillDeep` from `info.userLabelIds` on insert. No user-authored content is touched — drafts, Outbox sends and attachments are outside this arm entirely. **The four-exit lattice does not govern this limb at all**: a header is cached server state, not a queued intention, so limb B is judged against the mantra and the Data Integrity rules, not against exits 1–4. Only the op deletion in `IOS-GRAPH-002` is a never-drop question.

**Recovery, with the mechanism, its caller, and its POSITION named (`MIS-024` instance 5).** *Mechanism:* the ordinary per-folder sync of the folder the message is actually in re-inserts it under its current Graph id — `SyncEngine.syncFolderMessages` → `runSyncMessages`, plus `exchangeDeltaSync`'s `messagesAdded` → `fetchMessageDetails` for the Inbox-scoped delta. *Caller:* `SyncScheduler`'s periodic pass, foreground refresh, pull-to-refresh, and the post-drain `foldersToSync` loop — note the 404 arm itself does **not** insert into `foldersToSync`, so no targeted sync is scheduled by the failure. *Position:* **strictly AFTER the delete.** It is a repair, not a guard; it does not prevent the loss, it only ends it. **The state where it does not fire is the same date window `IOS-GRAPH-002` names**: `selectStaleHeaders`' `.date` arm and Graph's `receivedDateTime` ordering mean a message older than the destination folder's newest-N window is not re-fetched, so a deleted header for old mail can stay absent until a crawl or a full re-sync reaches its date range. **If this is fixed later, fix `IOS-GRAPH-002` first** — a re-key removes the precondition for path (1) entirely. For path (2) the honest narrowing is that a `404` proves *"no message at this address"*, which on a folder-scoped-id provider is weaker than *"this message is gone"*; gating the header delete on the same evidence class the op retirement uses keeps the two consistent. **Do not close this by deleting the header more eagerly, and do not widen `isConfirmedGoneError` to the string-matching branch** — its own doc says why: *"IMAP error descriptions can be noisy and we never want a false positive to permanently delete user data."*
