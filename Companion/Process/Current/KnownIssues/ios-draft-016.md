## Full detail

**What the fix changed, and why.** `DraftStore.performStageA` durably commits `serverPushStatus = "pushing"` in its own transaction **before** the provider call, and `pushDraftToServer`'s entry guard admits only `nil` or `"dirty"`. Every *in-process* failure arm already clears it (`applyPushCompletion` → `nil`/`"pushed"`, `restorePushableAfterProviderThrow` → `"dirty"`), but a **crash** in the network window — jetsam, force-quit, a `0xdead10cc` suspension kill — leaves no process alive to run them. The next drain then read `.notApplied`, which is a **normal return**, so `AccountManagerQueue.executeOperation`'s `.saveDraft` arm fell through to `.allMembers` and `executeSingleOp` deleted the `PendingOperation` — the durable Save producer retired by **none of the four exits**: the guard tests a *local row state*, and an interrupted attempt is an **unknown**, which clause 2 makes retryable. The census was one writer, three readers that require the state, and **zero sweeps**; both sibling queues sweep their own in-flight state (`PendingOperation.inFlight` → `reconcilePendingOperations`; `OutboxMessage.sending` → `performOutboxReconciliation`). It was also a **regression from shipped** — `07a4bb703`'s `pushDraftToServer` wrote nothing before the provider call, so a kill left the row admissible and the op retried normally. The fix adds `DraftStore.resetOrphanedPushingDrafts` into the **existing** launch crash-recovery transaction in `AccountManager.reconcilePendingOperations`, beside the `inFlight` → `queued` reset.

**Why launch-only, and why that is not a shortcut.** `reconcilePendingOperations` is launch-only (`RootView`), so nothing has drained yet **in this process** and any `"pushing"` row is orphaned **by definition** — which is what lets this sweep carry no drain latch. That side-steps the live-vs-residue ambiguity recorded at length on `AccountManagerOutbox.reconcileOutbox`, where a reset landed on a row whose send was already on the wire (`IOS-OUTBOX-006`). A **foreground** sweep is deliberately NOT added: a foreground return within the same process cannot produce `"pushing"` residue, because the in-process arms above clear it, so such a sweep could only ever hit a LIVE attempt.

**THE ACCEPTED RESIDUAL.** A `"pushing"` row whose Stage-B *reset write* itself fails transiently inside a **live** process stays stuck **until the next launch**. Only the SERVER copy is stale; the local `Draft` content — the user's authored text — is intact and fully editable throughout.

**Why it is accepted rather than mechanised.** Two independent recoveries reach it, and both are ordinary: the next app launch runs this same sweep, and an authored edit re-admits the row through `DraftStore.applySave`'s existing `"pushing"`/`"pushed"` remap. THE MANTRA's test is recoverability, and this edge recovers by a plain relaunch — mechanising it would need a foreground sweep whose safety argument this row has just refuted, or a retry ladder around a write that is already inside `retryWrite`. **The non-recovering case, named per `MIS-IOS-008`:** none is known — the sweep is predicate-only (`serverPushStatus == "pushing"`), it holds no latch that a refusal could strand, and it re-runs unconditionally on every launch, so there is no state from which the recovery path is itself blocked. If a future change gates the sweep on anything, that gate becomes the non-recovering case and this sentence must be re-derived.

**Re-push duplicate risk, stated rather than hidden.** If the APPEND landed server-side before the crash, the retry can create a duplicate server draft, because the retry still carries the pre-attempt `previousIdentity`. That is exactly shipped `07a4bb703`'s behaviour and the same accounting `IOS-DRAFT-011` and `IOS-DRAFT-015` already accept: strays are ordinary Drafts-folder messages, synced with real server UIDs, deletable by the ordinary path. It is the correct direction under this repo's stated ranking (`IOS-IMAP-006`, Outbox Reliability Rule 4) — **a duplicate draft is recoverable, a dropped Save producer is not.**

**The mirror image, refused explicitly.** Making `.notApplied` throw instead would requeue the four genuinely-stale cases forever (`instanceEpoch` mismatch, `"pushed"`, a lost Stage-A CAS, a lost Stage-B CAS) — a permanent lane wedge, which is in the **non-recoverable** set.

**THE FIX (2026-08-06), and why each half of that refusal was wrong.**
▸ **Premise (a) was wrong about the BLAST RADIUS, and it was checkable.** `DrainContext.failedAccounts` is a per-drain `var` declared inside `AccountManagerQueue`'s `DrainContext` and documented at its consult site as *"prevents hammering within a single drain"*; `drainPendingQueue` constructs a fresh `DrainContext` on every call. Its lifetime is ONE DRAIN, not the session. A throw therefore requeues the op with `retryCount += 1` and skips the account for the remainder of that pass only — bounded and recoverable, the fail-closed side of THE MANTRA, not the wedge corollary. (The refusal's own premise *"the row only clears at launch"* was itself an artefact of not re-admitting; it is no longer true.)
▸ **Premise (b) was right about the HAZARD and wrong to treat it as a blocker.** The reentrancy question is real — `pushDraftToServer` is an `actor` method that `await`s across the provider call, so a second entry during the suspension is NOT excluded by isolation — and it is reachable in production, because `executeSingleOp` wraps `executeOperation` in `withTimeout`, whose own doc comment says the operation task is **abandoned**. But it does not have to be *proved absent*; it can be *made observable*. `DraftStore.pushesInFlight` is a `Mutex<Set<String>>` (Resilience Rules; same claim/release shape as `ComposeAgentSendFence`) that `pushDraftToServer` claims BEFORE Stage A's durable `"pushing"` write and releases in a `defer` on the far side of the provider call. Absence from that set is then a POSITIVE witness of orphanhood — the launch sweep's "nothing is in flight ⇒ orphaned" reasoning with a live witness instead of the process-boundary proxy. A refused claim is an unknown, so it THROWS (`DraftStore.PushClaimError.alreadyInFlight`) into the generic transient arm rather than returning a disposition.
▸ **And the status quo was the thing being compared against.** Today's behaviour DROPPED the intention, which is non-recoverable; both candidate remedies were recoverable. Either beat it.

**THE RESIDUE CENSUS, corrected — there are THREE in-process producers, not one.** The original cell named only the failing Stage-B *reset* write. Enumerated by "which `"pushing"`-clearing write can itself throw": (1) `restorePushableAfterProviderThrow`'s `try draft.update(db)` on the provider-throw path; (2) `applyPushCompletion`'s `try draft.update(db)` on the SUCCESS path (worse — the server copy exists, so the retry costs one `IOS-DRAFT-015` stray); (3) a `withTimeout`-abandoned attempt that is still LIVE, which is not orphaned at all and is exactly what the claim refuses. All three are handled by the same admission-site change rather than three site-specific patches (`MIS-006` — a confirmed site is a lead, not a scope).

**ACCEPTED RESIDUAL, unchanged in kind.** A re-admitted attempt whose predecessor had actually committed on the server leaves ONE stray Drafts-folder message, because the retry still carries the pre-attempt `previousIdentity`. That is `IOS-DRAFT-015`/`IOS-DRAFT-011`'s existing accounting verbatim — ordinary messages with real synced UIDs, deletable by the ordinary path — and the standing ranking settles it: *a duplicate draft is recoverable, a dropped Save producer is not*. **The non-recovering case, named (`MIS-IOS-008`):** a claim that is never released would refuse every later push for that draft for the process's lifetime. It cannot arise from a return or a throw (the `defer` covers both) and is pinned two-sided by the release leg of the mirror-image test; it WOULD arise if a future change moved the release out of the `defer` or added an early `return` between the claim and it.

**`resetOrphanedPushingDrafts` is NOT superseded** and stays launch-only: it normalises rows no `.saveDraft` producer will ever visit again (one already retired by the pre-fix behaviour), which `MailNavigationView`'s server-draft open path — filtered on `["pushed", "dirty"]` — would otherwise skip forever. The objection to a BLIND foreground sweep still stands; the remedy is per-draft and claim-authorised precisely because a blind predicate sweep cannot tell residue from a live attempt.

**Pinned by** `NeverDropExitClosureTests.inProcessPushingResidueNeverRetiresItsSaveProducer` — the drain-level invariant, asserted through `IntentionLedger` (the never-drop law itself: settle `.executed` or be reported) plus the wire, so "did not drop" cannot be satisfied by "did nothing"; and `DraftGenerationSafetyTests.aLivePushBlocksASecondPushForTheSameDraft` — the mirror image, which drives a genuine reentrant second push from inside the provider call and asserts zero duplicate `saveDraft` on the wire, a THROW rather than a disposition, and release-restores-admission. `AccountManagerQueueDrainTests.launchReconciliationReAdmitsAnOrphanedDraftPush` still pins the launch sweep, asserted through the production admission decision (`performStageA` admits a fresh attempt) rather than the column value, and is two-sided on one fixture: the pre-sweep half proves the Stage-A CAS really does refuse a `"pushing"` row.
