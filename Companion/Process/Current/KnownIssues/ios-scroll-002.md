## Full detail

`InboxViewModel` writes `hasMoreMessages` at **three** sites and all three still compare `loadedMessages.count` — the COMPOSED row count — against a page size (`resetMessages` and `reloadMessages`' `applyDiff` against `targetWindowSize`; `loadMoreMessages` phase 1 against `SyncConfig.inboxPageSize`). The fourth site, `loadMoreMessages` phase 2's `hasMoreMessages = pull.mayHaveMore`, is already server-coverage-sourced and is the shape the other three are measured against. **What was fixed:** the label filter, the only PERSISTENT narrowing `InboxListComposer.compose` applied after `InboxListReader.gather`'s per-folder SQL `LIMIT`, now runs INSIDE that query, so the `LIMIT` bounds MATCHING rows and both the count and the pagination cursor (`loadedMessages.last?.date`) become honest. **What remains, enumerated rather than summarised:** compose still narrows D after the `LIMIT` via (1) the overlay folder-drop in `applyOverlay` — a swiped-away row is dropped in memory while its durable row is still in the folder; (2) `excludeIds` (step 2.5), which drops already-loaded rows AFTER the SQL `LIMIT` chose them, reachable in **triage mode only**, where the sort is not date-monotonic so an already-loaded row can legitimately re-enter a later page's window; (3) the staged-row `filterUnread` re-filter and the P/S `beforeDate` cut, which touch only P and S; and (4) the `isSystem`/`shouldExcludeLabel` corner of compose's step-6 belt, which no filter reachable from `LabelFilterPickerView` can produce. **Why registered rather than fixed:** every one of them can only make the count SMALLER, so they fail closed — the scroller stops early, no mail is deleted, mis-addressed or dropped — and every one is transient. **Recoverability, with the caller named:** `reloadMessages` recomputes `hasMoreMessages` from a fresh D query, so the moment the overlay drains (or the user's triage window moves) the flag is re-armed with no user gesture; it is invoked by `InboxViewModel.runReloadCoalesced` from the `.inboxDataDidChange` observer registered in `init`, and by `listDidAppear`. **Why the fix is not a coverage signal plumbed out of the reader:** it would have to fail OPEN to be useful, and `InboxView`'s infinite-scroll sentinel is `if viewModel.hasMoreMessages { Color.clear.onAppear { viewModel.loadMoreMessages() } }` — a `hasMoreMessages` that stays true while the composed page is EMPTY re-arms that sentinel on every render while the cursor `loadedMessages.last?.date` cannot advance, which is an unattended network pull of the whole mailbox. That is the mirror image of the bug (`MIS-005`), so the ordering was fixed instead of the signal compensated (`CLAUDE.md` A3). **If it is ever revisited, fix the ordering again, not the comparison** — move the remaining narrowings ahead of the `LIMIT` rather than teaching the three sites to read a coverage flag.

**THE NON-RECOVERING CASE, NAMED (2026-08-05, `MIS-IOS-008`).** `reloadMessages` is a **reaction**, not a re-derivation on render: it runs from `runReloadCoalesced` on `.inboxDataDidChange`, from `listDidAppear`, and from pull-to-refresh — and its own full-range query passes `excludeIds: []` (`InboxViewModel.fetchFullRange`), so the recomputation is not narrowed by the paging exclusion that produced the short count in the first place. Two consequences, and only one is a live state. **(i) The understated flag outlives its cause.** In the quiescent case the transient narrowing clears, nothing further changes, and `hasMoreMessages` stays false until the next data change, the next list appearance, or a pull-to-refresh — one ordinary gesture, so it stays inside the mantra. **(ii) Recovery would genuinely not fire only if one of the four narrowings were DURABLE rather than transient**, because `reloadMessages` re-applies all of them to its own fresh query. The overlay narrowing cannot be that one: `releaseOverlayEntry` runs at the end of the gesture's **queued write closure** on every exit path, so it is bounded by the local GRDB write and never by the network drain. The only state that holds an overlay entry open indefinitely is a wedged write lane, which is `IOS-QUEUE-003`'s subject and is not producible by anything this row enumerates. **A1:** `git show 07a4bb703:TabMail/ViewModels/InboxViewModel.swift` carries the same three composed-count sites verbatim; shipped's phase-2 site was `freshPage.count >= SyncConfig.inboxPageSize` plus a bare `hasMoreMessages = false`, i.e. materialisation-count-sourced, which v3 replaced with server-coverage `pull.mayHaveMore`. Shipped is the floor and the fourth site already stands above it.
