## Full detail

**The end-to-end gap, stated whole because each half alone is misleading.** For a parent the app cannot positively address — the `IOS-EPOCH-001` fail-closed window — the UI can still show "replied" while the server's `\Answered` is never set. There are **two producers** of that local flag and only one of them is gated. `AccountManagerOutbox.persistQueuedSend` writes `UPDATE messageHeader SET isReplied = 1` (and the `isForwarded` sibling) **optimistically at queue time with no admission gate at all**; `AccountManagerOutbox.deleteCompletedSendAtomic` writes it again at completion, and audit round 2 moved *that* write inside its `if let flagAdmission` guard so the local flag and the durable op now share one fate **at the completion producer**. The queue-time write is unchanged: it is verbatim in `07a4bb703`, it is correct optimistic-UI behaviour per ADR-IOS-001, and changing when a reply shows as replied is a product decision rather than a bug fix. **Consequence to hold onto:** the completion path no longer re-asserts a server-side claim it did not queue, but the queue-time claim still outlives an unaddressable parent, so the invariant *"local reply state never claims a server-side flag that was never queued"* does **not** hold end-to-end. Sync restores truth on the next pass that can address the folder.

✅ **CLOSED AS A DECISION (2026-08-04) — the queue-time write stays optimistic and ungated, and that is a product decision the owner has already made by shipping it.** **The decision:** `AccountManagerOutbox.persistQueuedSend` continues to write `isReplied`/`isForwarded` at queue time with no admission gate. Three grounds, in order of weight. **(1)** It is **verbatim in `07a4bb703`** and is correct ADR-IOS-001 optimistic-UI behaviour; changing WHEN a reply shows as replied is a product change, not a bug fix. **(2)** Gating it would mean the user replies and the "replied" indicator does not appear, on an account whose folder epoch has not settled — a visible regression traded for an invariant no user can observe. **(3)** The invariant this row wanted — *"local reply state never claims a server-side flag that was never queued"* — is the **wrong invariant for an optimistic-UI field**. The right one is *"the completion path never re-asserts a server-side claim it did not queue"*, which round 2 established and which **holds**: `deleteCompletedSendAtomic` writes both flags inside its `if let flagAdmission` guard, so the completion producer and the durable op share one fate. **Accepted cost:** the "Consequence to hold onto" sentence above, which survives this closure verbatim and is the honest statement of the residual. **Recoverability:** a sync pass — `SyncEngineDeltaSync`/`SyncEngineFullSync` assign `header.isReplied = info.isReplied` from server flags, so the next pass that can address the folder restores truth. **The state where that does not fire** is a folder whose epoch is never established (the `IOS-AI-003` population) — but note that in that state the flag itself was never queued either, so the divergence is *"UI optimistically ahead of a server the app cannot address"*, which is precisely what optimistic UI means. **There is no state in which the local flag contradicts a KNOWN server truth.**

⚠️ **SUPERSEDED 2026-11-25 (#1468; fix in #1476 and #1477): the queue-time write is gone, and the end-to-end invariant now holds.** `AccountManagerOutbox.persistQueuedSend` no longer touches the original message. Its replied or forwarded mark and the cleared Reply tag are written only by `deleteCompletedSendAtomic` when the send goes out, the two marks inside its `if let flagAdmission` guard as before, so *"local reply state never claims a server-side flag that was never queued"* now holds on the whole queue, send and complete path, not only at the completion producer. The "Consequence to hold onto" above describes the code before this change.

**Why the decision above was reversed.** Its recoverability ground was false: sync does not assign `header.isReplied = info.isReplied`. The flag merges are set-only (`SyncEngineFullSync` ORs the stored value into an existing row and assigns only on insert; `SyncEngineChangesApply` likewise), so a local mark the server never received is never cleared by a pass. A measurement on the code before this change showed it: after a reply or forward was queued and then undone (or a failed send discarded), the original kept `isReplied` (or `isForwarded`) and lost its Reply tag on Gmail, Outlook and IMAP, through a change pass, a full pass and a re-read of the message, IMAP server keywords included. Undo and the discard of a failed send are ordinary gestures, so the state was everyday and permanent, not an optimistic indicator briefly ahead of the server.

**Cost accepted instead (ground 2 above):** the replied or forwarded indicator now appears when the send completes, after the undo window, not when it is queued. The completion posts `.messageDataDidChange` for the original whenever it changed the row, so an open email screen re-reads it then.

**Approved 2026-11-25.** The owner approved marking the original only when the send completes, the offline case included: until the reply actually leaves the device, the original keeps its Reply tag, shows no replied arrow, keeps its reminder and reads as not replied to the AI. The owner's words: *"I think I like the behavioral change, and I think it makes more sense that shows up when the email is already finally sent."*

**Residual, pinned as today's behaviour.** An original archived (moved) while the reply is held is re-keyed to its new address, and the queued row still names the old one, so the completion writes no mark and queues no server mark; the Reply tag stays. When the Sent copy is synced, `ReplyParentResolver` finds the moved original by its Message-ID, marks it replied and clears its Reply tag. The server's `\Answered` stays unset.

**Tests:** `SendReplyMarksTests` (Gmail, Outlook and IMAP worlds: queue then Undo, queue then discard after a failure, and queue then completion, each followed by change, full and re-read passes, with the original's row byte-identical and no operation queued after the queue, the Undo and the discard; queuing alone; the refresh of the open original for a reply, a reply-all, a forward and a tag-only clear, and none when nothing changed; a Reply tag the AI writes during the hold; the original archived before the send goes out), `OutboxCompletionMarksOriginalTests`, `OutboxDoubleSendTests`, `ComposeSendReplyTargetTests`.

⚠️ **REVERSED AGAIN 2026-11-25 (#1490, a product decision for 1.11.7): Send marks the original at once, and a send that never goes out takes its own mark back.** The paragraphs above describe 1.11.6, where the replied or forwarded arrow appeared only when the send completed, after the undo window, and an offline reply showed none until it left the device. 1.11.7 shows it at Send again, and closes the defect that made 1.11.6 move it (#1468) with a record instead of a delay.

- **At Send** (`AccountManager.persistQueuedSend` → `markOriginalAtQueue`, inside the queuing write): the original is resolved as the completion resolves it. `isReplied` (a forward: `isForwarded`) is set only when `admittedOrdinaryActionTargets` admits the original, the same admission the completion's server op needs, so the local mark never claims a server flag that cannot be queued. A reply's `reply` action tag goes to none, stamped with the outbox row's `createdAt`; the tag is local-only (ADR-IOS-036), so it is cleared whatever the admission. The row records exactly what changed in `outboxMessage.originalChangesAtQueue` (migration `v117_addOutboxOriginalChangesAtQueue`; `setMark`, `clearedReplyTag`). No server op is queued at Send. A deduplicated second tap changes nothing.
- **An unsent removal** (`cancelHeldOutboxRow`, which Undo, Undo to Drafts and the Outbox discard all run, → `revertQueuedOriginalChanges`): undoes only its own row's record. The mark goes back to unset; the tag goes back to Reply only while it is still none with that row's stamp, and the restored Reply is queued to the server (`setTag(reply)`), after any clear a full pass queued during the hold. A tag set after Send (the user's, or the server's Reply a pass wrote back) is a newer intention and stays. No other outbox row is read: each removal undoes exactly its own record.
- **The completion** (`deleteCompletedSendAtomic`): as in 1.11.6, plus the server's tag clear (`setTag(none)`) when Send's clear still stands; the server learns it only once the reply has gone out.
- **Rows queued before v117** have no record (NULL): their removal changes nothing and their completion marks the original, exactly as in 1.11.6.

The invariant *"local reply state never claims a server-side flag that was never queued"* now reads: the local mark is written only where the server's mark can be queued, the completion queues it, and every path on which it will never be queued (the three unsent removals) takes it back. During the hold the mark is ahead of the server by design.

**Registered costs:** `IOS-OUTBOX-010`, a change pass during the hold writes the server's Reply tag back until the completion clears it again; `IOS-OUTBOX-011`, with two pending replies to one original, undoing the first leaves no reply arrow until the second is sent. **Fixed in the same release by #1479:** an original archived while the reply is held keeps Send's marks on its moved row, and until #1479 neither the completion nor an Undo finds it (pinned in `SendReplyMarksTests` as the behaviour #1490 ships with).
