## Full detail

**Folder-qualifying the lane key is right for IMAP and splits same-resource ordering for the stable-id providers.** `buildLanes` unions on `"\(op.accountId):\(op.folderPath):\(id)"`. On IMAP that IS the address (UID is mailbox-local) and the change closed a never-drop wedge-with-bystander. On Gmail and Graph the id is **folder-independent**: `admittedOrdinaryActionTargets`' non-IMAP arm returns `admitted.map(\.messageId)` — the provider resource id — with a `nil` epoch, and `optimisticMoveToFolder` writes the header's `folderPath` to the destination in the same transaction that inserts the op. So a second move on the same message enqueues with `folderPath = B` while the first still carries `folderPath = A`, the two land in **different connected components**, and `drainPendingQueue` launches **one Task per lane concurrently**. Offline A→B then B→C can reach Gmail as B→C first: final labels `{B, C}` — the message is in two places and both ops retire as provider successes, so sync imports the wrong state rather than repairing it. **Exchange sibling:** `stripLegacyCategories` and `setUserLabel` each GET-then-replace the whole Graph category array, so a concurrent pair is a lost update. **Why the IMAP guard does not also cover this:** the second gesture on a just-moved IMAP row is refused by `admittedOrdinaryActionTargets` (the optimistic move set `observedUidValidity = nil`), so IMAP cannot produce the two-row precondition at all — the non-IMAP arm has no such gate. **Why REGISTRABLE.** Every op acts on the correct provider resource (no C3), nothing is deleted (Gmail move is a label change; Graph ids churn on move — see the severity note at the end of this cell, which CORRECTS "stale no-op"), no queued row is dropped, and the wrong end state is visible and fixed by one ordinary gesture. **If it is fixed later, fix the KEY's provenance, not its shape:** the lane key should be the op's ADDRESS SPACE — folder-qualified where the provider's ids are folder-local, account-qualified where they are stable — decided from `Account.provider` the same way `admittedOrdinaryActionTargets` and `stickyDurableMember` already decide it. 🚨 **Reverting to `accountId:messageId` re-opens `IOS-QUEUE-001`, which was a never-drop violation with a bystander.** 📌 **SEVERITY NOTE (2026-08-04) — Exchange/Graph id churn, settled from the code; it does NOT change this row's classification, and it surfaces an ADJACENT question this adjudication did not have the remit to judge.** ⚠️ **PARTLY STALE — read the dated closure at the END of this note first.** Three of this note's statements were true of the tree on 2026-08-04 and are FALSE at HEAD. The Exchange sibling has the same shape one level down — a lost-update category becomes visible only once that message's categories are re-imported and the user actually looks at its labels.
