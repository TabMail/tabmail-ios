## Full detail

`Draft.resolveReplyToHeader(...)`'s Strategy-2 cardinality guard is in tension with its own stated Gmail multi-label premise: the premise says one message legitimately appears under several labels, while the guard treats multiplicity as ambiguity. Recorded because the two disagree, not because either is unsafe — **both directions fail closed**, so the user sees a missing reply-parent link, never a wrong one. **⚠ ROUND 2 REPLACED THIS GUARD; ROUND 3 PUT IT BACK, AND THE CARDINALITY GUARD IS WHAT THE CODE DOES TODAY.** Strategy 2 fetches under `.limit(2)` and refuses on `candidates.count != 1`; `Draft.swift`'s executable code was byte-identical to the round-3 base `cec7450e1` as of `3bd9f0bac` (its only diff against that base was comment prose); a round-4 cleanup has since deleted that file's dead non-`db` `resolveReplyToHeader` overload, so it is no longer byte-identical — but Strategy 2 and its cardinality guard are untouched and still are. *What round 2 (`94fac3e79`) did — kept on the record, not deleted:* it argued the predicate should not be cardinality at all, because every candidate already shares `(accountId, rfc822MessageId)` by construction, so `count == 1` measures how many FOLDERS hold the message rather than how many MESSAGES are in play; it replaced the guard with agreement on an identity witness (sender address, subject, timestamp), resolving when copies AGREE and refusing when they DISAGREE as a Message-ID collision, and replaced `.limit(2)` with a fixed cap fetched with one extra row so truncation was observable and also refused. *Why round 3 reverted it:* **agreement between rows is not identity.** The witness is wrong in BOTH directions, which is what makes it the wrong predicate rather than one short a field. It is **too weak to prove sameness** — it omits everything this resolver actually consumes (the body, the attachments, `replyTo`), so two genuinely DIFFERENT messages that collide on a Message-ID while sharing sender, subject and timestamp both satisfy it, and content the user never selected is quoted into a reply or carried into a forward (**C3**: no action may ever mutate the wrong message; failing closed is always acceptable). And it is **too strong to admit real copies** — its timestamp is INTERNALDATE, which RFC 3501 §6.4.7 makes a SHOULD-not-MUST to preserve across a COPY, so legitimate copies of one message can disagree on it. The unverified Gmail multi-label premise is therefore still unsettled, which is why this row stays open rather than closing. **The accepted cost, stated rather than hidden:** when a message is legitimately present in several folders/labels, Strategy 2 refuses and the reply or forward ships WITHOUT its quoted body and attribution. The user's authored text is untouched. ⚠ **The words "and the send still works" stood here and are RETRACTED — see the round-4 correction at the end of this cell; the sentence that follows describes the guard's history, not the accepted cost.** Shipped `07a4bb703` was WORSE here — its Strategy 2 was a bare `.filter(accountId && rfc822MessageId).fetchOne(db)`, i.e. an arbitrary row — so the restored guard is not a regression against the release; it is the round-2 improvement being given up as unproven. Pinned by three tests in suite `ReplyQuoteIdentityTests` (file `TabMailTests/Models/DraftResolveReplyTests.swift`, which is a FILE name and not a type — an earlier revision of this row cited it as a type qualifier): `severalCopiesOfOneMessageFailTheReplyTargetClosed` (several copies of one message refuse — the round-2 blessing test, INVERTED in round 3, red proof against the witness resolver recorded in its doc comment), `ambiguousRfcIdentityResolvesToNothing` (a genuine Message-ID collision refuses) and `witnessAgreeingRowsWithDifferentBodiesResolveToNothing` (rows agreeing on every field of the round-2 witness but carrying different bodies must still resolve to nothing — the test that pins the revert's reason).

🚨 **ROUND-4 CORRECTION — THE CONSEQUENCE WAS UNDERSTATED, AND THE ACCEPTED COST IS REVERSED ON NEW INFORMATION.** Every statement of this row's cost above — and the matching prose in `Draft.resolveReplyToHeader`'s "THE ACCEPTED COST" comment and in `ReplyQuoteIdentityTests.severalCopiesOfOneMessageFailTheReplyTargetClosed`'s doc block — said a refusal costs *the quoted body and the attribution*, and that *the send still works*. That described `Draft.resolveReplyToHeader` in isolation. It was **false of the system**, and the earlier adjudication ("both directions fail closed, so the user sees a missing reply-parent link, never a wrong one") was made on that understated premise. **What a refusal actually cost, before this change:** `ComposeView.loadDraftOrPrepopulate` computed the refusal and only LOGGED it, then `ComposeView.send` derived the outgoing parent from its own `replyTo` PARAMETER — so (i) `ThreadUtils.outgoingThreadHeaders(replyTo: nil)` returned `.none`, and the reply left with **no `In-Reply-To` and no `References`**, i.e. as a brand-new message in every client that threads; (ii) `AccountManagerOutbox.persistQueuedSend`'s `guard let originalId = replyToHeaderId` short-circuited, so the parent got **no `isReplied`/`isForwarded` write and no Reply action-tag clear** — the user's reply state silently did not exist; (iii) the send was **permitted**, compose **dismissed**, and `AccountManagerOutbox.finalizeOutboxMessage` then made the local draft **deletable on delivery**, so the last local record of what the draft replied to went with it. The user was never told any of this: the quote was restored from the draft row, so the compose *looked* correct. **Worse, the same loss occurred with no refusal at all** on the Undo-Send reopen path — `UndoReopenCompose.composeView(for:)` builds `ComposeView(account:prefillDraftId:retainedDraftAuthority:)` and passes **no `replyTo`** while the row still carries `replyToId`, so *every* undo-then-resend of a reply sent unthreaded. The `ADR-IOS-043` memory topic's claim that `ComposeView.send` is "the ONE callsite" for outgoing thread headers is what kept this invisible; it does not enumerate the Undo reopen. **What is now guaranteed:** the SEND's parent is the persisted draft row's own GUARDED resolution (`ComposeDraftGuards.sendReplyTarget` / `persistedReplyTargetClaim`); the `replyTo` parameter is authority only when no persisted row exists. A row that CLAIMS a parent which resolves to nothing **blocks the send** (Send `.disabled` plus a `guard` in `send()`) with an explanation, and blocks **nothing else** — the draft stays openable, editable, savable and discardable, so the authored text is never trapped. A row whose claim resolves now threads correctly, including on the Undo reopen, which previously always sent unthreaded. **So the cost of a Strategy-2 refusal is no longer "quote only, send proceeds"; it is "no quote, and no send from this draft until the user starts the reply again from the original message".** That is a deliberate trade: shipping a reply with the wrong parent bookkeeping, or with none, is a wrong-message hazard (C3) and a silent one; refusing is loud and recoverable. Message-ID" using the fields available.** The identity witness is unsound in BOTH directions, which is what makes it the wrong predicate rather than one field short: too weak (it omits the body, the attachments and `replyTo` — everything this resolver consumes — so a Message-ID collision satisfies it and foreign content reaches the user's outgoing mail, **C3**) and too strong (its timestamp is
