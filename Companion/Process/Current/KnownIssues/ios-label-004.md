After round 18 they are preserved whenever the guard does NOT fire and lost exactly when it does — **never worse, sometimes better**. So the judgement holds, and it holds for the reason that matters: the guard-firing branch reproduces the OLD behaviour rather than introducing a new loss. **Reachability, derived rather than asserted (`MIS-IOS-008` — the question is which states block the recovery path, not whether a recovery path exists).** The lossy state needs BOTH (a) an optimistic row matching on `(folderId, rfc822MessageId, messageId != header.messageId)`, so the carry runs and its sources are destroyed, AND (b) a row already occupying `header.id` inside the same write transaction. The ordinary duplicate — the same message appearing twice in one delta batch — is **not** lossy: the first iteration consumes the optimistic row and inserts, so the second finds no optimistic match, carries nothing, and its `continue` discards nothing. Reaching (a) AND (b) together requires **two** optimistic Sent rows sharing one RFC 822 Message-ID in one folder (an outbox retry that reuses the id) **and** the same provider message appearing twice in one batch. **Recoverability:** the surviving header exists and is the server's own row, so the body is re-fetchable by the ordinary body-fetch pass (`hasBody == 0` ⇒ re-fetch — no user gesture needed), and the label is restored by the next delta once the user's `.addUserLabel` op drains and the provider becomes authoritative for it. **Nothing is mutated on the wire, nothing is misattributed, and no queued intention is dropped or wedged** — the guard's alternative is a thrown `UNIQUE` constraint that aborts the whole delta transaction for every folder in the pass, which is strictly worse. **Not mechanised** (THE MANTRA): closing the residual would mean re-attaching the carry onto the pre-existing row inside the `continue` branch, which is new logic on the rarest path in the file, guarded by evidence no stronger than the carry it already rests on.
