## Full detail

**The mechanism.** `InboxListReader.gather` adds **one correlated `EXISTS` subquery per selected label** to the inbox query, evaluated **before** the `LIMIT`. On a date-DESC walk with sparse matches the engine must walk deep into the index before it can fill a page, so cost grows with folder size rather than with page size.

**The measured curve** — real index shapes, worst case for a date-DESC walk (50 sparse matches placed at the OLDEST rows) — is in the **`IOS-PERF-003` latency table** immediately below this register table; it is kept out of the cell because a markdown table cannot nest, and out of a bare integer because **the number is the argument**. Summary: **linear, no cliff**, ~0.9 ms warm at 12k rising to ~53.8 ms at 500k on the Mac, i.e. ~2–4 ms to ~108–215 ms on device at the standard 2–4x. ⚠️ **The honest band is wider than the harness says, and the row states it rather than quoting its best number:** the fixture's `messageHeader` carries **6** columns against the real **~48**, and the plan needs a table fetch per candidate row to read `id`, so real page I/O is higher. Codex measured **0.164 s** at 500k independently; that is the conservative end of the same line, not a contradiction. **Honest band at 500k: ~54–164 ms Mac ⇒ ~0.1–0.66 s device.** A separate measurement at 12k (14 ms) cleared it; both are right, and the disagreement was a scale disagreement, which is why the curve is recorded instead of a verdict.

**FIVE independent reasons to register rather than fix — each sufficient alone.** **(1) Not a regression, and the shipped behaviour was FASTER AND WRONG.** `v1.6.38` filtered labels **after** the `LIMIT`, which is cheap precisely because it discards rows the page already paid for — and that is the mechanism behind `IOS-SCROLL-002`'s false pagination exhaustion (a full page of non-matching rows filters to empty, and the list concludes there is nothing more). Pre-`LIMIT` filtering is the **fix** for that; its cost is the price of correctness. **(2) Latency only, fully recoverable** — no wrong state, no data loss, no dropped intention; the query returns the right rows, later. **(3) Bounded at realistic sizes on an OPT-IN gesture** — under ~43 ms on device through 100k headers, and `filterLabelIds` **defaults to `[]`**: the correlated `EXISTS` terms are not in the query at all until the user taps a chip in `FilterChipBar`. Nobody pays this by existing. **(4) The cheap fix is foreclosed and the clever one INVERTS.** Filtering post-`LIMIT` is exactly the shipped defect (1). Driving the query from the label side instead — walk `messageLabel`, join back — is faster for a **sparse** label and dramatically **slower** for a dense one (a label on most of the folder degenerates into the same walk plus a join), and the crossover depends on per-label selectivity that SQLite cannot know: `ANALYZE` records table- and index-level statistics, not per-value selectivity for an arbitrary label id, so **the planner provably cannot choose between the two shapes**. Any fix therefore has to pick one shape and be wrong for the other population, or carry a hand-maintained selectivity estimate — a mechanism, for a latency edge, which is what THE MANTRA exists to refuse. **(5) Scope** — this is a query-shape optimisation in an audited release candidate, coupled to nothing else in the range.

**The NON-RECOVERING case, per `MIS-IOS-008` — because "it is only latency" is exactly the claim that clause exists to interrogate.** A user with a >200k-message folder who taps a filter chip waits **~0.1–0.5 s on the main actor**. There is **no state to recover** — nothing is wrong afterwards, and no sync pass or gesture makes that particular wait not have happened. It is a spent half-second, accepted deliberately: it is opt-in, it is proportional to a folder size a small minority reach, and every alternative shape trades it for a different population's regression per (4). **What would re-open this row:** the filter ever becoming non-opt-in (a default chip, a restored filter state on launch, a filter applied by a shortcut or intent), or the walk moving off an opt-in gesture onto a boot or sync path.
