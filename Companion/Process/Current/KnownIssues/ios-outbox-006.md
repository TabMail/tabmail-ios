## Full detail

**A message whose SMTP transaction was already on the wire could be returned to `.queued`, become discardable, and be discarded — while still being delivered, and while never reaching Sent.** `reconcileOutbox` resets `.sending`/`sentAt == nil` rows to `.queued` because that is what a process killed mid-send leaves behind, and durable state cannot distinguish that residue from a row a LIVE drain has just claimed: `sentAt` is stamped only after `provider.send()` RETURNS, so an in-flight send is byte-identical to residue. `isDrainingOutbox` is the ONLY thing that separates them, which makes it the latch that AUTHORISES the reset — and it was **read** rather than **acquired**. `AccountManager` is an actor; `reconcileOutbox`'s first statement is `await dbPool.read`; `PrioritizedDatabase.read`'s async overload runs a full NSE staging merge before it reads (measured 7.6 s cold-boot, and staging is pending precisely on foreground return). The actor was therefore released for a long, reachable window, a drain starting in it claimed a row and put the SMTP on the wire, and reconciliation resumed with that row in a snapshot taken AFTER the claim and reset it. **The consequence, stated whole:** `discardOutboxMessageConfirmed` refuses only `outboxStatus == .sending` and `sentAt != nil`; a row reset to `.queued` satisfies neither, so the Discard gesture was accepted, the row and its attachment directory were deleted, `stampSentAt`'s `UPDATE … WHERE id = ?` matched zero rows and returned false, and `sendSingleOutboxMessage` returned at that guard — no optimistic Sent header, no Sent APPEND, no finalize. **The recipient receives a message the user was told was discarded, and the sender has no record of it.** Outbox Reliability Rule 3 and Rule 10 both forbid that. **THE CENSUS — the class has exactly TWO production entries and they differ in what protected them.** (1) **LAUNCH**: `AccountManagerQueue.reconcilePendingOperations` → `reconcileOutbox()`, awaited by `RootView`'s startup task, with **no ownership check at all**. Launch does not gate first paint, so a held row's deadline can expire, `drainOutbox` can claim it, and launch reconciliation is still running — this entry is PRE-EXISTING and is byte-identical in `v2final` and `v1.6.38`. (2) **FOREGROUND**: `reconcileOutboxOnForeground()`, wired to `RootView`'s `scenePhase → .active` by `792048ebd`; it checked the latch and then awaited. A fix at the foreground wrapper would have closed one entry of two. **The invariant that now holds:** the latch that authorises the `.sending → .queued` reset is ACQUIRED in the same synchronous run as its check and HELD across the reset. `reconcileOutbox` takes it, holds it across the extracted `performOutboxReconciliation()`, and releases it before its trailing `drainOutbox()`; `reconcileOutboxOnForeground` is now a pure delegate with no logic of its own, so both entries are governed by one piece of code. **A1 — authored, not restored, and the reason is checkable:** neither `v2final` nor `07a4bb703` has a foreground reconciliation trigger at all, so there is no shipped sequencing to restore. `v2final` DOES do its classification and reset in ONE write transaction, which is a better shape — but it does **not** close this: reconciliation and `atomicClaim` are already serialised by the single GRDB writer, so a one-transaction reconcile still cannot tell a row claimed a millisecond earlier from residue. Only the in-memory latch carries that. **ACCEPTED, fail-closed, both directions recoverable:** a drain trigger firing during reconciliation is skipped and subsumed by reconciliation's own trailing `drainOutbox()`; a reconciliation finding a drain in flight returns without reconciling and is re-driven by the next foreground return or launch — the in-session recoverability `IOS-OUTBOX-001` established — and the orphan-attachment sweep it also skips is pure byte reclamation, idempotent next pass. **No second latch was added**: `drainPendingQueue`'s `isDraining`/`needsRedrain` and `ComposeView.isSending` were audited, are CLEAN (each sets its flag in the same synchronous run as its check), and are untouched. **Verification — red-first, recorded:** `OutboxReconcileInFlightSendTests` pins the SYSTEM property (*a message whose SMTP is on the wire is never observable as `.queued` and can never be discarded*) using a new `MockEmailProvider.sendHook` in-flight seam. Pre-fix, the LAUNCH case failed four expectations: `(during?.outboxStatus → .queued) != .queued`, `(discardAccepted → true) == false`, `survives`, and `await provider.appendedToSent.count == 1`. ⚠️ **What could NOT be proven red, stated rather than hidden:** the FOREGROUND entry's own scheduling window. Reconciliation snapshots at its first await, which in a test completes in microseconds, so the drain never wins the race — the production window exists only because that read runs a seconds-long staging merge, and the harness has no honest way to reproduce that. The interleaving sweep is therefore a regression guard, and says so in its own doc comment; what carries the proof to the second entry is structural. **No schema change, no migration, no wire behaviour change.**
