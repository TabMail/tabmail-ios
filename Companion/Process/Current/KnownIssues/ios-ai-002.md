## Full detail

An RFC-less IMAP/iCloud row that is also unstamped can have its AI result refused and then recomputed without bound, so the same paid LLM call is issued again on every open. **The mechanics, each verified against the code rather than inherited from the audit brief:** migration `v77_addMessageHeaderObservedUidValidity` adds the column with **no backfill** (its own comment: *"Nullable, with no default and no backfill: existing rows remain unproven rather than adopting the Folder's current epoch by assertion"*); `SyncConfig.syncMessageLimit == 50`, so ordinary sync only re-observes the newest 50 per folder; and deep backfill **skips rows that already exist**. Therefore a pre-`v77` RFC-less IMAP row outside the newest-50 window is permanently unstamped — neither path will ever stamp it. `ActiveAIQueue` then calls `storage.jobCompleted(job, shouldRetry: true, maxRetries: .max)`, so there is no retry ceiling to stop the loop. **Population bound:** RFC-less IMAP/iCloud rows only. Gmail and Graph bypass epoch admission entirely via stable provider ids, and an RFC-BEARING row is admitted by the Message-ID baseline. **Not fixed here** because the cost is money and battery, not a wrong-message mutation or a lost intention, and any fix touches the same admission surface round 3 is deliberately not re-opening.

✅ **FIXED by `403496b21`, "Stop paying for AI jobs whose write-back can never be attributed" — jointly with `IOS-AI-003`, because they are one defect at two reachabilities.** **The invariant that now holds:** an AI job whose guarded write-back is refused for a **structural** reason is classified BEFORE anything is spent, and is retired instead of retried — so the same unattributable `(headerId, jobType)` cannot issue repeated paid model calls. `ActiveAIQueue.writeAdmission(_:target:)` runs inside the read that already captures the job's `AIWriteTarget` (zero extra round trips) and answers `admissible` / `transientlyRefused` / `structurallyRefused`; a structurally refused job returns `ExecutorReport.unattributable` **before** the FTS body read, the NSE lease claim and the LLM call, and `jobCompleted` maps it to the new `JobOutcome.writeRefused`, which takes `abandonWithoutCompletion` — the same arm `.scopeExited` already takes, so **nothing claims the work completed** — and records the job in an in-memory `unattributableJobs` memo so `repopulateOnDrain` cannot turn the backoff into an unthrottled spin. ⚠️ **THE REFUSAL ITSELF IS UNCHANGED — this classifies the refusal's COST, it does not relax the refusal.** Arm 7 is untouched; the alternative to refusing is the C3 misattribution `6b689890d` closed. No row gains an AI field it would not have gained before, because everything skipped here was already being discarded at `aiGuardedHeaderWrite`. **And `maxRetries: .max` is UNTOUCHED everywhere** — the shipped unbounded ladder is proven adequate for the transient case and was restored verbatim rather than weakened; what was added is the one outcome the shipped design never needed, *"the write was refused for a structural reason"*. **Nothing about the refusal is durable:** no column, no flag, no migration, no database write at all. The memo is process-lifetime and `rearmUnattributableJobs()` clears it wholesale from `repopulateFromDatabase()` (launch / foreground / AI re-enable) and `cancelAllInFlight()` (suspension recovery) — the exact moments a sync may have stamped the folder or the row — so a row that later becomes attributable gets its result, on the right row. **A1:** `07a4bb703` carries the identical retry ladder, but there `.needsRetry` could only mean "the model call failed" (`observedUidValidity` does not exist at that tag), so the shipped architecture has no answer to this problem because the problem did not exist in it — authored under A1's "nonexistent" branch.
