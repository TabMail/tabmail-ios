## Full detail

**(a) Defect. 80 ungated diagnostic `print` sites across the SIX files of the calendar family, with ZERO `DebugModeManager` occurrences and ZERO `#if DEBUG` in any of them** at `3e63335b2`: `AccountManagerCalendarQueue.swift` **40**, `ExchangeCalendarProvider.swift` **21**, `CalDAVProvider.swift` **7**, `GoogleCalendarProvider.swift` **7**, `CalDAVClient.swift` **3**, `CalDAVDiscovery.swift` **2**. **The predicate is the word-boundary `print(` form stated in prose above `IOS-LOG-001`** — re-run that, not a bare `print\(`. ⚠️ **This corpus is the one case where the gate-chain ambiguity that predicate warns about cannot arise**: `rg -c DebugModeManager` over all six files returns **zero**, so there is no hoisted gate local and no enclosing `if` chain to miss — every match is unambiguously ungated, with no false positives. **The worst single site is `CalDAVClient.put`**, which logs `body.prefix(4000)` of the outgoing ICS: that is user-authored calendar content — `SUMMARY`, `DESCRIPTION`, `LOCATION` — together with every `ATTENDEE` `mailto:` address, i.e. third parties' email addresses the user never typed into a log. `CalDAVProvider.deleteEvent` logs the deleted event id; `AccountManagerCalendarQueue` logs account ids, op ids, event ids and raw error payloads.

**(b) Reachability — identical to `IOS-LOG-001`, and it is the whole reason this is registrable.** A `print` on iOS writes to `stdout`, which on a device is **discarded** unless a debugger or Console.app is attached; nothing in this tree redirects it. The app persists none of it — no file, no server, no crash payload — so **ADR-004 zero-retention is NOT violated**. The exposure is exactly: an attached Xcode/Console session, or a `sysdiagnose` the user deliberately captures and hands to someone.

**(c) Attribution — PRE-EXISTING, zero range attribution.** `git diff 07a4bb703..HEAD --` over `TabMail/Providers/CalDAV/`, `GoogleCalendarProvider.swift`, `ExchangeCalendarProvider.swift` and `AccountManagerCalendarQueue.swift` is **EMPTY**: all six files are byte-identical to shipped `v1.6.38`. Global rule 12 binds **new** diagnostics; none of these is new.

**(d) Recovery.** Nothing degrades while this stays open. Any individual site is a one-line gate with zero coupling to schema, migration, protocol or ordering.

**(e) The NON-RECOVERING case, named because the row is worthless without it (`MIS-IOS-008`).** If a user captures a `sysdiagnose` while a CalDAV `PUT` is in flight and hands it to support or to a forum thread, the ICS body in it **cannot be un-disclosed**. That is a disclosure, not a state, and no sync pass or gesture recovers it. It is the same non-recovering case `IOS-LOG-001` carries, with a **wider payload** — a whole ICS document including other people's addresses, rather than one interpolated field. It is accepted on frequency: the capture must be deliberate, concurrent with a calendar write, and handed on.

**Why REGISTERED and not swept, stated so the next round does not re-open it as a task.** Gating 80 sites across six shipped-identical files is ~80 lines of churn inside an audited release candidate for zero behavioural benefit, against the standing minimal-diffs rule, and it is **not** behaviour-neutral in the sense that would make it free: gating changes what an attached support session can see, on the one subsystem (`CalDAV`, iCloud) whose failures are opaque `403`/`412` codes with no body — which is the stated reason `CalDAVClient.put` logs the ICS at all. `IOS-LOG-001`'s `af98d92c7` **range-not-corpus** precedent governs: the range's own added diagnostics are censused and gated; a pre-existing corpus is registered.
