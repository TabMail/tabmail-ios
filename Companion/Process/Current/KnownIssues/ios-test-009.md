## Full detail

**A test closes a fake URLSession while an unstructured drain the production code itself started is still in flight, and the whole test process dies.** `InboxViewModel.delete` → `AccountManagerActions.queueDraftDelete` fires `Task { await drainPendingQueue() }` — unstructured, so it outlives the test body. `InboxGestureActionTests`' two Gmail draft tests (`staleGenerationDraftsPlaceholderDeletesNothingAndStaysRetryable`, `realGmailDraftsRowIsDeletedByItsOwnProviderAddress`) build a `FakeHTTP.Scenario()` and `defer { http.close() }`. When the escaped drain reaches `GmailProvider.deleteDraft` → `trashContainedDraftMessage` → `performHTTPRequest` after that `close()`, `URLSession.data(for:)` raises `NSGenericException` *'Task created in a session that has been invalidated'*, which is an **uncaught ObjC exception**: `libc++abi` terminates the process, xcodebuild logs *"Restarting after unexpected exit, crash, or test timeout"*, and the run is reported as `** TEST EXECUTE FAILED **` with `NeverDropExitClosureTests.batchSplitChildrenRemainExecutable()` named — **the test that happened to be running next, not the test at fault.** That misattribution is the reason this is registered rather than left to be rediscovered. **ATTRIBUTION, established by controlled comparison rather than asserted:** the same crash, same exception, same next-test attribution appears on the INVERTED build — i.e. with the pre-`57f10a76b` un-awaited `defer { Task { … } }` teardown restored — so it is pre-existing. `57f10a76b` in fact **narrows** the window, because the provider unregister now completes BEFORE `defer { http.close() }` runs, where previously it was merely enqueued. **Why it is not a product defect:** nothing here is app behaviour. The escaped drain is real production code doing the right thing (a queued intention is drained promptly); what is wrong is a TEST tearing down a network seam the drain is still using. **Why it is nonetheless worth fixing:** an uncaught ObjC exception kills the whole test process, so every test not yet run in that launch is silently dropped and the summary is stitched together from two launches — the same evidence-destroying shape as `IOS-TEST-006`, one layer down. **The fix shape, for whoever takes it:** make the two tests deterministic about the work they started — drain to quiescence before the scope ends (the bounded-loop idiom `BackfillOnlyFolderEpochTests` already uses), or keep the `FakeHTTP.Scenario` alive past it — rather than widening any production guard. ⚠️ **Do NOT "fix" it by making `queueDraftDelete` stop kicking a drain**: that is a user-intention-latency change made to satisfy a test, and the never-drop contract owns that decision, not this row.

🟢 **FIXED by `87c805784`, "Fix IOS-TEST-009: test scopes tore down transport a drain still needed" — 2 files, `TabMailTests` only, ZERO production code.** **WHAT IT WAS.** `AccountManagerActions.queueDraftDelete` ends its success path with an unstructured `Task { await drainPendingQueue() }`, which outlives the test body that started it. The test's `defer { http.close() }` then called `URLSession.invalidateAndCancel()` on the very session the escaped drain was about to use, so `GmailProvider.deleteDraft` → `trashContainedDraftMessage` → `performHTTPRequest` raised the Objective-C `NSGenericException` *'Task created in a session that has been invalidated'* on its next `dataTask` creation. That exception is **uncatchable in Swift**, so `libc++abi` terminated the whole test process.

🚨 **WHY THIS MATTERED FAR MORE THAN A FLAKY TEST — this is the half that must survive.** The crash **silently dropped every test not yet run in that launch**, and xcodebuild blamed the **wrong** test. The observed pre-fix evidence, recorded verbatim rather than paraphrased: the faulty test `realGmailDraftsRowIsDeletedByItsOwnProviderAddress()` itself **PASSED**; `NeverDropExitClosureTests.batchSplitChildrenRemainExecutable()` recorded **two spurious expectation failures**; then `libc++abi` killed the process; then *"Restarting after unexpected exit, crash, or test timeout"*; then the relaunch reported **`Executed 0 tests`**; and the run ended `** TEST EXECUTE FAILED **` naming `NeverDropExitClosureTests.batchSplitChildrenRemainExecutable()` — the test that happened to be next, not the test at fault. **A truncated run reports a plausible pass count that is simply cut short**, which is why this made the full-suite gate untrustworthy and why a pre-existing, non-candidate-attributable defect was worth fixing inside this push at all.

**THE FIX.** New file `TabMailTests/Infrastructure/EscapedDrainTransportScope.swift`. `EscapedDrainTransport.withProviderAndTransport` composes provider registration and transport lifetime into **ONE** scope so the ordering cannot be skipped, and awaits drain settlement before `transport.close()`. **Composition is NECESSARY, not tidiness:** the drain's claim loop skips operations whose account has no registered provider, so unregistering the provider before awaiting settlement would make the operation **permanently unclaimable** — `everAttempted` would never flip and the barrier would wait out its whole bound. Two scopes could be written in the wrong order; one cannot.

**WHY A NEW BARRIER RATHER THAN AN EXISTING ONE — and NO EXISTING BARRIER'S BOUND WAS WIDENED.** *"Never widen a barrier's bound"* is a standing rule here (the recorded quiescence-flake lesson), so state the compliance explicitly: **not one existing barrier was touched.** They could not be reused for two independent reasons. (1) Every existing barrier waits for queue **EMPTINESS**, which is unreachable in this scenario — the drain's Gmail call has no matcher on some paths, so the operation requeues forever and emptiness never arrives. (2) Every existing barrier **ASKS FOR** a drain, and `drainPendingQueue`'s first statement is `guard !isDraining else { needsRedrain = true; return }`, so asking re-arms `needsRedrain` and cannot express *"the drain this gesture already started has finished"*. ⚠️ **THE COUNT IS FIVE EXISTING BARRIERS, NOT FOUR — corrected here because `87c805784`'s own commit body says "four".** Censused by symbol against the tree: `FinishTheMoveLocallyTests.drainToQuiescence`, `ProviderIdQueueFuzzTests.drainProviderQueue`, `IdResetDispositionMatrixTests.drainProviderQueue`, `PostSendServerDraftCleanupTests.drainUntilSettled` and `DraftDeleteEpochBoundaryTests.drainUntilSettled` — **five**, and all five wait on emptiness and all five call `drainPendingQueue()`, so the substantive argument holds unchanged and is in fact one instance stronger. **The new barrier `EscapedDrainTransport.awaitPendingQueueSettled` never calls `drainPendingQueue()` at all** (verified: zero call sites in the file, comments aside) and adds **exactly one** signal — the **durable** `PendingOperation.everAttempted` witness, read back through `pool.read` — which closes the start race a bare `pendingQueueIsQuiescentForTesting()` poll leaves open, namely that the escaped drain task may not have started when the poll runs. On bound expiry it records a `Testing` issue naming the observed state rather than hanging or passing silently.
