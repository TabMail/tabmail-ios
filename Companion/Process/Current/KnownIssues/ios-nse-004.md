## Full detail

**The notification extension is a materialisation path the `isDeletedOnServer` census structurally could not see, and it drops the flag.** `rg -i deleted TabMailNotificationService/NSEIMAPConnection.swift TabMailNotificationService/NSEMessageMetadata.swift` returns **zero** matches, and `isDeletedOnServer` has zero occurrences anywhere under `TabMailNotificationService/`, in `StagedInboxRow` or in `NSEDataBridge`. `performFetch` receives a `MessageInfo` that carries `.deleted`; `mapInfoToMetadata` does not preserve it; the row is published to the ADR-IOS-049 in-memory read model before its durable write and can then be inserted by `insertNewHeaderFromStaging` as an ordinary Inbox header. Reachable when another client flags the message between the push and the extension's one-shot FETCH — `SEARCH` still returns the UID. **This is the same census-shape limitation as the FIFTH presentation path** (`SearchView.searchAccount`): the noun enumerated was `MessageHeader(` construction inside `TabMail/`, and the NSE builds through `NSEMessageMetadata` in a different target. **Why REGISTRABLE.** One IMAP provider only (Gmail and Graph have no `\Deleted` notion). Nothing is deleted or mis-addressed; the harm is a visible interval in which a message the server has flagged for removal appears as ordinary new mail, plus a notification for it. **Recoverability:** the next main-app top-window sync covers the just-arrived (highest) UID by construction, so `selectStaleHeaders`' `remoteIds` — which excludes `\Deleted` records — removes the row on the first pass; that is the same channel `IOS-IMAP-008` above cannot reach only because its UID is *below* the floor, which a just-pushed message never is. **If it is fixed, carry the flag through `NSEMessageMetadata` and refuse the STAGE, not the notification** — suppressing the alert while still staging the row would leave the row and lose the only signal.

**THE NON-RECOVERING CASE, NAMED (2026-08-05, `MIS-IOS-008`).** The stated recovery rests on the staged UID still being **inside** the merge window when the main app next syncs that folder, and `SyncEngineFullSync.selectStaleHeaders` makes that condition explicit rather than implicit: in `.uid` mode it takes `floorUID = fetched.compactMap { Int64($0.messageId) }.min()` and keeps only candidates with `uid >= floorUID`, so a row below the floor is never stale-checked at all. **The state where recovery does not fire is therefore a device that stays in the NSE-only regime long enough** — the app is not foregrounded, and more than one top-window page of further mail arrives in that folder — after which the soft-deleted row's UID has dropped below `floorUID` and no later pass revisits it. The row then stays listed indefinitely. That is exactly the `IOS-IMAP-008` blind spot this row contrasts itself with, and the contrast is narrower than it reads: the just-arrived UID is on the safe side of the floor **at stage time**, not permanently. Nothing is deleted or mis-addressed in that state, so it stays registered. **A1 — pre-existing, and the flag never existed in this subtree:** `git show 07a4bb703:TabMailNotificationService/NSEIMAPConnection.swift | rg -c 'deleted'` → **0**. Shipped's NSE dropped the flag identically, so there is no shipped behaviour to restore.
