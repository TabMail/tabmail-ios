## Full detail

**A notification's `messageId` is an ADDRESS, and the tap can happen days after delivery.** The push `userInfo` carries `messageId`/`provider`/`accountId`/`accountEmail` and **no** `rfc822MessageId`, so nothing in the notification records WHICH physical message it was about. Two intervals follow, and only one is closable on-device. **Interval 2 (tap → execution) is now CLOSED:** the router resolves a real `MessageHeader` before dispatching, so `ExpectedMessageIdentity.map([header])` is free, and both of `performCoordinatedRoleMove`'s refusals run strictly later than that capture — pass 1 after its own re-resolve, pass 2 after the FIFO write queue has taken an unbounded amount of other work, which is exactly the window a turnover can purge the row and re-seat a different message under the same composite id. **Interval 1 (push delivery → tap) stays OPEN:** by tap time the resolve already returns whatever now occupies the UID, so a witness captured then is captured FROM the impostor and cannot refuse it. **The epoch gate cannot substitute, and this is the whole reason the witness type exists:** checkpoint A (`AccountManagerQueue`) compares the op's stamped `observedUidValidity` against the folder's `lastKnownUidValidity`, but a post-turnover resync writes the impostor row with the NEW epoch and the folder carries the NEW epoch, so `stamped == live`, the guard AGREES and admits. `ExpectedMessageIdentity`'s own header states it outright — *"an epoch guard proves the row is addressable in the CURRENT epoch; it cannot prove the row is the message the producer pointed at, because after a turnover the impostor's epoch is fresh too."* **What bounds interval 1, with the caller named and its position established (`MIS-024`):** `AccountManager.clearDeliveredNotificationsForPurgedMessages` removes the delivered notifications for exactly the message ids the purge transaction captured. Its one production caller is `runUidValidityResetReaction`, which invokes it in step 4 — **after** the step-3 purge commits and **before** the step-5 fresh-epoch stamp, and therefore before any resync can seat an impostor at the vacated UID. It is a genuine ordering guarantee rather than an after-the-fact cleanup. **Negative case, stated because this is the half a reader would over-credit (`MIS-019`):** it clears only ids the purge CAPTURED, it is best-effort (`UNUserNotificationCenter.removeDeliveredNotifications` promises no completion), and it runs only when a turnover is actually DETECTED — though an undetected turnover also means nothing purged or re-inserted locally, so no impostor row exists under that id either. A notification whose message was never local is not in the captured set — the **staging-only** case, which is ordinary rather than exotic: the NSE stages and delivers in its own process and the main app merges later, and `uidValidityResetPurgeTxn` sources its id list solely from `MessageHeader.filter(Column("folderId") == folderId)` while `NSEDataBridge.purgeStagedStateForFolder` returns `Bool` only, so staged rows cannot feed `clearDeliveredNotificationsForPurgedMessages` at all. ⚠️ **CORRECTED 2026-08-05 — the previous wording of this sentence said such a tap *"resolves `.absent` and takes the cold-op path, not this one"*, and BOTH halves are wrong.** (i) After the resync that follows the turnover, the tap does **not** resolve `.absent`: `resolveAfterMerge` returns `.found(Y)` for whatever now occupies the UID, and `NotificationActionRouter.execute`'s ARCHIVE/DELETE arms then build `ExpectedMessageIdentity.map([header])` **from Y itself**, so the witness agrees with the impostor and cannot refuse it — this tap lands squarely on interval 1, exactly as the row's *"a witness captured then is captured FROM the impostor"* sentence already says. (ii) The cold path is not a safe fallback either, so it bounds nothing: `queueColdPendingOperation` stamps `observedUidValidity: AccountManager.admissionEpochForNewGesture(…)` — the **NEW** epoch, read in the admitting transaction — onto a **bare UID**, which is precisely the shape an address-reuse can misresolve. It is the right stamp for the gesture it was written for (a genuinely cold push whose message has not synced yet) and is not a bound on this scenario. Neither correction changes the row's disposition: this is interval 1, still OPEN, still accepted, for the reason stated below. **Why the push payload is NOT being extended:** adding `rfc822MessageId` would mean changing the NSE and the push worker (a separate repo and deploy) to close a residual that a live, correctly-ordered mechanism already bounds — the widening THE MANTRA asks us not to do for a rare edge. **Attribution:** shared with the reference line in shape; `v2final:AccountManager.recordRoleMove` took `headers: [MessageHeader]` and derived the witness itself, so it had no omittable seam — v3's id-plus-optional-map signature is where the guard could be, and was, dropped (`MIS-018`, half-port drops the guard).

**RECOVERABILITY — WRITTEN OUT 2026-08-05, BECAUSE THIS ROW CARRIED NONE.** The paragraph above states what *bounds* interval 1; it never said what the user is left with when interval 1 actually lands, and a bound is not a recovery. Both arms of `NotificationActionRouter.execute` call `AccountManager.performCoordinatedRoleMove` with `role: .archive` and `role: .trash` — **moves**, not destructions; no permanent-delete path is reachable from a notification button. So a mis-targeted action leaves the impostor at Archive or Trash and the intended message untouched, and the correct state is one ordinary gesture away in each direction: move the impostor back, then repeat the gesture on the message the user meant. **Sync does not repair it** — a move is a legitimate provider success, so nothing re-derives the previous folder — which means the recovery is the user's gesture and nothing else. **THE NON-RECOVERING CASE, NAMED (`MIS-IOS-008`):** the tap happens outside the app and produces **no in-app confirmation**, so the only signal available is that a message the user never chose has left its folder; a user who does not notice issues neither gesture. For the `.trash` arm the window in which the corrective gesture remains available is bounded by the provider's Trash retention rather than by anything this app owns, so "unnoticed" can become permanent. That case is inside the mantra's C3 bucket — the same already-adjudicated exposure `IOS-IDENTITY-001` carries — not a new finding. **A1 — shipped is the floor and v3 is strictly above it:** `git show 07a4bb703:TabMail/App/AppDelegate.swift` calls `performCoordinatedRoleMove(ids: [header.id], role: .archive)` and `role: .trash` with **no `expectedIdentities` argument at all**, so shipped left BOTH intervals open for every notification. Interval 1 is a subset of what shipped carried, which is why extending the push payload is not owed here.
