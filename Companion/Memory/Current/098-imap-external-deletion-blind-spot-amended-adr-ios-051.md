## IMAP external-deletion blind spot — old server-deleted messages linger forever (audit 2026-07-02)

**STATUS: FIXED 2026-07-03 — ADR-IOS-051 (Phases 1+2 of `PLAN_IMAP_DELETION_RECONCILE.md`).** `SyncEngineDeletionReconcile.swift`: IDLE `.vanished` UIDs now drive targeted deletes (`SyncScheduler` → `handleVanishedUIDs`); a `localHeaderCount > STATUS messageCount` predicate (evaluated in `imapDeltaSync` per changed folder + at the end of `fullSync` per IMAP folder) triggers a chunked explicit-set `UID SEARCH` walk (`IMAPProvider.searchExistingUIDs(folder:uids:)`, chunks of `SyncConfig.deletionReconcileChunkSize`=500) that deletes local-not-on-server UIDs via the SAME stale-deletion protections + FTS-removal channel. UIDVALIDITY guard via new `folder.lastKnownUidValidity` (migration v63) — mismatch/unreported aborts the walk. Failed SEARCH chunk = delete nothing from it. Phase 3 (QRESYNC, O(changes)) remains documented-only. Audit findings below kept for reference. **Known caveat (post-implementation review 2026-07-03):** the UIDVALIDITY guard only protects walks AFTER the bootstrap — the folder's FIRST-ever walk pins whatever validity the server currently reports, so if UIDVALIDITY had reset at some earlier point, old-epoch rows below the sync window read as ghosts and get deleted. Those rows are already permanent zombies today (their UIDs are dead — unopenable, unfetchable), so removal is arguably cleanup, but sub-window history is NOT re-fetched by a completed backfill. Rare (Gmail effectively never resets; the walk only fires on count evidence); proper fix = capture UIDVALIDITY during normal sync SELECTs too, not just the walk. **Open UX follow-up (2026-07-03):** opening a message that was just deleted externally (before delta/reconcile removes the header) surfaces a generic "network error" from the body-fetch failure. Proper handling: map provider "gone" (Gmail API 404 / IMAP UID-vanished on a SUCCESSFUL lookup) to verified-permanently-gone -> show "message was deleted on the server" + remove header/FTS (the Data Integrity rule 1 404/410 exception applies). Generic network failures must NOT trigger this. **Hardening added 2026-07-03: deletion circuit breaker** — walk deletions are capped at the trigger's expected mismatch + `SyncConfig.deletionReconcileCapSlack`; a falsely-empty SEARCH response (the one single-source seam no unit test can cover) now aborts the walk before the offending chunk instead of wiping the folder. VANISHED (Phase 1) stays uncapped — server-named UIDs.

Code-verified audit (triggered by the TB FTS drift investigation, see `../tabmail-thunderbird/PROJECT_MEMORY.md` 2026-07-01/02). **Gmail/Exchange are SAFE; raw IMAP/iCloud is NOT.**

- **Gmail/Exchange:** provider deltas catch deletions of ANY age — Gmail `history.list` `messagesDeleted` (`SyncEngineDeltaSync.swift:89,106-134`), Graph `$delta` (`:444,458-483`); expired cursor → full sync fallback. No blind spot.
- **IMAP/iCloud blind spot (CONFIRMED):** stale detection (`SyncEngine.selectStaleHeaders`, in `SyncEngineFullSync.swift`) only covers the newest-`syncMessageLimit=50`-UID window per folder (full sync AND STATUS-gated delta both funnel into `runSyncMessages` limit=50). Backfill is insert-only (never deletes); `selfHealRecentMessages` is add-only + 90-day-bounded (`SyncEngineSelfHeal.swift:61,125-169`); the complete-knowledge branch only fires for folders <50 server msgs & ≤2000 local rows. So an old, already-bodied message deleted externally below the UID floor persists in GRDB+FTS indefinitely.
- **The drift evidence is captured and then DESTROYED:** `SyncEngine.imapDeltaSync` sees `status.messageCount != folder.totalCount`, triggers only the windowed 50-msg sync, then OVERWRITES `folder.totalCount` with the server count (`Column("totalCount").set(to: status.messageCount)`, same function) — consuming the count-mismatch signal while the stale row survives. Change-detector, not reconciler.
- **IDLE `VANISHED` is CONSUMED; only `EXPUNGE` still degrades to a poll** (corrected 2026-07-31 — the previous "both DISCARDED" claim was falsified by ADR-IOS-051 Phase 1). `SyncScheduler`'s IDLE `.vanished(UIDSet)` case decodes the UID set and calls `SyncEngine.handleVanishedUIDs` for targeted deletes before polling. `.expunge` carries a SEQUENCE number rather than a UID, so it still falls through to a generic `backgroundPoll`.
- **SwiftMail fork already supports CONDSTORE/QRESYNC/HIGHESTMODSEQ/VANISHED** (STATUS `highestModificationSequence` when `.condStore`; `IdleHandler`'s IDLE untagged-response decode; `SearchCriteria.modSeq`) — the app uses HIGHESTMODSEQ **only as a coarse folder-level change/skip gate**, never for O(changes) content sync. ⚠ **CORRECTED 2026-07-31: `IMAPProvider.folderStatus` does NOT discard modseq** — it propagates it verbatim (`highestModSeq: status.highestModSequence`). **Re-corrected 2026-07-31 (same-day):** the first correction got the WIRING wrong, so state it exactly. There are TWO independent modseq propagation sites in `IMAPProvider`, feeding two different consumers — do not conflate them: (a) **`folderStatus`**, whose single production call site is in `SyncEngine.imapDeltaSync`, feeds `SyncEngine.modSeqIndicatesChange`, which gates the DELTA fetch; (b) **`fetchFolders`**'s `FolderInfo.highestModSeq` feeds `SyncEngine.shouldSkipFolderFetch`, which skips a whole FULL-SYNC folder fetch. ⚠ **Re-re-corrected 2026-07-31 (third restatement): the previous "`shouldSkipFolderFetch` never sees a `folderStatus` value" was FALSE — distinguish the two SIDES of the comparison, not merely the two producers.** `shouldSkipFolderFetch(role:freshModSeq:cachedModSeq:isDeepSync:)` compares a FRESH value against a CACHED one. Its **FRESH side never comes from `folderStatus`** — it is always `fetchFolders`'s `FolderInfo.highestModSeq`, passed as `freshModSeq: info.highestModSeq`. Its **CACHED side is the shared `Folder.lastKnownHighestModSeq` column** (`cachedModSeq: existing.lastKnownHighestModSeq`), and **BOTH paths write that column** — delta's changed branch does `Column("lastKnownHighestModSeq").set(to: modseq)` where `modseq = status.highestModSeq` and `status` is `provider.folderStatus(path:)`'s return value. **So after a changed delta iteration that supplies a modseq the cached side of the skip comparison routinely IS a `folderStatus`-derived value.** (Quantifier corrected 2026-07-31: this previously read "after any delta cycle", which is too strong — a QUIET delta iteration hits `continue` BEFORE the cursor write, so the cached value may still be `fetchFolders`-derived, or nil. Only the quantifier was wrong; the fresh/cached distinction, the UPDATE/INSERT asymmetry, the `continue`-not-`return` point and the three-OR'd-terms point below are all verified correct and must not be rewritten again.) The two producers stay distinct; the one durable column they share is where they meet. Cursor persistence is nonetheless ASYMMETRIC, not "both paths, same way": full sync writes the column for EVERY EXISTING folder row it UPDATES, changed or quiet — the write sits after the skip decision (which only adds the path to `skippable`) and is gated solely on the server having supplied a value (`if let modseq = info.highestModSeq`) — whereas delta writes it ONLY on the changed branch, so a quiet folder hits `continue` (it is a `for folder in syncableFolders` loop iteration, NOT a `return` — the remaining folders are still processed) before the cursor write and keeps its old value. **The full-sync asymmetry claim is scoped to the UPDATE branch only:** the sibling `else` branch that INSERTS a first-seen folder row sets `totalCount`, `lastKnownUidNext` and `lastKnownUidValidity` and **never** `lastKnownHighestModSeq`, so a brand-new row starts with a nil cursor and `shouldSkipFolderFetch`'s `guard let cachedModSeq` makes its first pass unskippable by construction. Note also that `modSeqChanged` is one of THREE OR'd change terms in delta (`if !uidNextChanged && !countChanged && !modSeqChanged { … continue }`), so it can only ever FORCE a fetch, never PREVENT one — "gate" is defensible for that reason but only in that direction; the skip-capable gate is full sync's `shouldSkipFolderFetch`, where an equal pair really does suppress the fetch. (Both helpers are `nonisolated static` members of `extension SyncEngine`; there is no `SyncEngineDeltaSync` or `SyncEngineFullSync` TYPE — those are file names only, and naming them as types is a citation that cannot be grepped.) What is genuinely absent is the O(changes) machinery: no `CHANGEDSINCE` FETCH modifier, no QRESYNC `SELECT` parameters, no `VANISHED (EARLIER)`, no `SearchCriteria.modSeq` use — and `IMAPProvider.fetchHistory` returns nil, so IMAP always falls back to a windowed sync. `HistoryDelta.cursor`'s "IMAP MODSEQ" doc comment is aspirational. (Symbol-cited: line citations into `IMAPProvider.swift` are abolished **in Swift sources**; ~180 stale ones still survive in `PLAN_*.md` and `analysis/v3-recon/*.md` and are NOT covered by that convention.)
- **FTS wiring is correct on every deletion path** (staleIds → `SearchIndex.removeMessages`, delta deletes, confirmed-gone, budget prune) — fixing GRDB reconciliation automatically fixes search.
- **Fix directions (mirrors TB's evidence-triggered design, not yet implemented):** (1) use the IDLE `.vanished` UIDSet for targeted deletes (free, library already delivers it); (2) treat the STATUS count mismatch that the windowed sync CAN'T explain as reconcile evidence → chunked full-folder UID SEARCH walk (backfill already has the chunked-UID-SEARCH primitive) diffed against local UIDs — integer set diff, bounded memory; (3) CONDSTORE `CHANGEDSINCE`/QRESYNC where advertised → O(changes). NEVER a date window (ADR-IOS-042).
