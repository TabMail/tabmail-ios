
### Progressive Backfill & Storage Budget (ADR-IOS-005, ADR-IOS-006)
- **No age cutoff** — backfill always walks to completion: IMAP walks UID range from UIDNEXT-1 to UID 1, Gmail/Exchange exhausts all page tokens. Storage budget is the only gate.
- `StorageEstimator.budgetMB` (UserDefaults, default 2048) — global storage soft cap across all accounts
- **Storage limit vs the catch-up re-arm (2026-11-11, ADR-IOS-107 decision 8).** `SyncEngine.runCatchUp` snapshots `StorageEstimator.budgetMB != Int.max` into `CatchUpContext.storageLimitInForce` (the code's default budget is `Int.max`, unlimited, despite the line above). While it holds, `applyCatchUpTransaction` declines every re-arm and a Gmail listing goes no lower than the folder's oldest local row, so the prune's deletions are not reloaded weekly (prune orders by `date`, ranges by `providerDate`, so pruned ids sit between kept rows too). Trade-off: under a limit, old mail moved into a folder is not loaded. Tests: `GmailCatchUpTests.storageLimitStopsTheReload`, `productionSnapshotTakesTheStorageLimit`.
- After initial sync, `SyncEngine.startBackfill()` fetches older messages in background
- **Backfills ALL folders** (not just primary/secondary) — sorted by priority: inbox → favorites → secondary → custom
- IMAP backfill uses UID range walking (no SEARCH, avoids NIO 8KB buffer limit)
- Gmail/Exchange uses page-token cursor walk from newest to oldest
- **Page walk bounds (Gmail/Exchange, `SyncEngineBackfillWalk.swift`); the per-call ones in memory, the page hold bound saved on the folder.** The always-running backfill worker (`startBackfill`) calls `runBackfill` with NO deadline, so a folder the walk could not move past used to be re-picked at network rate for as long as the app stayed in the foreground, starving the folders behind it. The rules: (1) a page-list request carrying the saved token that fails with `400` is TREATED as a refused token (neither provider documents a stale-token answer, and a `400` for another reason lands here too): the token is dropped and the folder restarts from the top, once per folder per call (`pageTokenRestartedFolderIds`); the drop is a compare-and-set on the token it listed with, so a token another writer saved meanwhile (and its hold time) is kept; a second one skips the folder for the call. (2) Any other page-list failure skips the folder for the rest of the call (`pageWalkSkippedFolderIds`), keeping the saved token, except cancellation (ends the call) and a connection error (keeps the outer exponential backoff and lists the same page again in the call). A refused or failed sign-in reaches these providers as `AuthError.refreshFailed`, never `ProviderError.authenticationFailed` (`AccountAuthSource` wraps every token-getter error), so it skips unless its text reads as a connection error. (3) After a page's missing messages are fetched, the strictest failure on the page decides its saved token, by TWO kinds only (`backfillFetchFailureKind`): PER-MESSAGE is an explicit list (a 4xx other than 401/403/429, 404 and 410 included; `DecodingError`; no header and no error, i.e. an answer the provider could not read as a message), and the walk moves past it at once; everything else HOLDS (no answer/`URLError`, 5xx, 429, 403, 401, `AuthError`, cancellation, anything unclassified). One `hold` holds the page whatever else failed on it and in whatever order. A held page stays held while less than `SyncConfig.backfillPageHoldMinutes` (60) has passed since its FIRST hold, then those messages are passed over like a per-message failure. The first hold is saved as `Folder.backfillPageHeldSince` (migration `v99_addFolderBackfillPageHeldSince`), set only while NULL and only while the saved token is still the one the page was listed with, so the bound survives calls and relaunches; every write that moves or clears `backfillPageToken` clears it in the same write (the walk's advance, completion and restart writes, `resetCrawlState`, the UIDVALIDITY purge, both `StartupMigrations` resets, the Settings nuke and the account reset SQL), so a page held after its token moved starts a fresh bound. 403: Gmail's HTTP policy retries it as a rate limit before the walk sees it; Graph's does not retry a 403. A held page skips its folder for the call, and the walk never advances the saved token past it inside the bound; a later call re-lists only that page. The guarantee is about the saved token, not the held messages: on Exchange the token is an offset (`$skip`), so a held message that newer removals shift out of the page is passed over like any message the listing no longer returns. The bound is wall-clock time from the page's first hold, including time when no attempt was possible (app suspended, device offline, sign-in refused), and it is per page, not per message: once a page is past it, a message on it is passed over on its first failure. (4) A `startBackfill` cycle whose `runBackfill` did no work (a re-held page with nothing new is one) waits `profile.interCycleIdleDelay`, not `interCycleActiveDelay` (`SyncEngine.backfillInterCycleDelay`). Exchange's real nextLink pages with `$skip=<integer>` (a non-integer `$skip` answers `400`), so a saved Exchange link cannot expire; the fake's `$skiptoken` rejection is modelled. Tests: `BackfillPageWalkTokenTests`, `BackfillPageWalkFailureTests`, `BackfillPageWalkHoldBoundTests` (fakes: `servePagedListings`, `failListings` incl. `transport:`, `injectGetFailure` on both fakes, `failTokenRefresh`, `onRejectedPageToken`; DEBUG clock seam `backfillPageHoldNowForTesting`).
- **Backfill inserts via GRDB**: `insertBackfillBatch` uses `dbPool.write { }` — GRDB's `DatabasePool` is thread-safe, no background DispatchQueue or ModelContext needed.
- **Strictly incremental backfill** (no large object materialization): Two-step approach — (1) provider SEARCH/LIST returns lightweight IDs, (2) batch `fetchSet` existence checks via GRDB (never materializes objects), (3) FETCH only missing IDs. `insertBackfillBatch` uses a batch `fetchSet` for final dedup (one query, not per-row). Returns `(inserted, ftsRecords)` — FTS indexing coalesced per window by caller.
- `Folder.backfillComplete` / `Folder.oldestSyncedDate` track per-folder progress
- Backfill pauses for user activity via `signalUserActivity()` → `waitForIdle()` at folder, window, deep-crawl, BodyFTS, and SnippetFill boundaries. Inner loops also check `isUserActive` per-iteration for near-immediate yield. Views signal activity via `.onScrollPhaseChange` → `AccountManager.signalViewActivity()`
- **IMAP pool priority checkout**: `pool.checkout(priority: true)` inserts at FRONT of waiter queue — used by all user-initiated IMAP methods (fetchMessage, markRead, archive, delete, move, search, fetchAttachment, fetchOlderMessages). Background backfill batches use `priority: false` (FIFO). Ensures user ops never wait behind multiple background batches.
- **fullSync**: GRDB writes are immediate and don't trigger SwiftUI re-renders directly — `NavigationStore` handles UI refresh.
- **No age-based eviction** — fetched messages are never deleted based on age
- **Storage pruning**: `pruneIfOverBudget()` runs after sync — deletes bodies first (re-fetchable), then headers, oldest-first across ALL accounts, but keeps ≥50 messages per folder
- **StorageEstimator**: measures actual file sizes (GRDB `tabmail.sqlite` + FTS `fts.db` + WAL/SHM files) across Application Support
- **MessageBody**: only stores `htmlContent` (no `textContent`). Plain-text-only emails converted via `plainTextToHTML` on ingest using RFC 3676 format=flowed: trailing space before line break = soft wrap (join with next line), no trailing space = hard break (preserve). `white-space: pre-wrap` on container preserves multiple spaces. FTS holds stripped plain text for search.
- **Infinite scroll**: `fetchOlderMessages()` in SyncEngine/AccountManager, triggered by sentinel view at bottom of inbox list. IMAP uses bounded SEARCH windows to avoid buffer overflow.
- **Power-aware backfill (BackfillProfile)**: Two profiles — `normal` (default) and `aggressive` (on power + user idle 30s+ + not low-power + not thermally throttled). Aggressive mode uses larger chunks (1000 vs 500), higher batch sizes, and much shorter delays (0.1s vs 0.5s between batches, 0.5s vs 3s between cycles). `UIDevice.current.isBatteryMonitoringEnabled = true` set in TabMailApp.init. Profile checked dynamically at each decision point via `SyncEngine.backfillProfile`. **Battery gate**: backfill pauses entirely when battery < 20% and not charging (`shouldPauseBackfill`). **Cellular gate**: on metered connections (`NetworkMonitor.isExpensive`), only inbox-role folders are backfilled.
- **Per-batch pool checkout**: `fetchMessageHeaders` checks out a pool connection per batch (100/200 UIDs) instead of holding one for the entire call. Each batch gets a fresh connection, re-SELECTs the folder, and returns it. Other operations can use the pool between batches.
- **Connection failure backoff**: After 3 consecutive connection failures within a backfill cycle, the cycle aborts. Next sync poll restarts backfill with a fresh connection.
