## Ordinary sign-out releases the device push registration and ends the auth session — worker first, BOTH legs, pinned to the subject that was signed in, `scope=local`, one bounded window (2026-09-03)

**The invariant.** `TabMailAuthService.signOut()` performs a best-effort, time-bounded release handshake while its bearer is still valid, and then clears the local session on EVERY path regardless of how that handshake went. The handshake is: (1) `PushNotificationService.unregisterDeviceForSignOut()` — `DELETE /register-device` on the push worker for this install's device id; (2) `POST {auth base}/auth/v1/logout?scope=local` with the same bearer and the `apikey` header the refresh path uses. Both legs run inside one window bounded by `PushConfig.signOutHandshakeTimeoutSeconds`; there are no retries, no bookkeeping and no persistence. The docblock promise of `signOut()` — never fails, never waits past the bound — still holds (push-worker issue #42, owner ruling 2026-09-03).

**Identity follows the WORK, at ONE chokepoint.** `signOut()` reads `subject = getSession()?.userId` before any await and passes it to `releasePushRegistrationAndEndAuthSession(subject:transport:)`. That function makes exactly ONE comparison, immediately after `TabMailTokenCoordinator.shared.validToken()` succeeds: `guard getSession()?.userId == subject`. A sign-in that lands during the bounded cleanup flush, or while the bearer is being resolved, therefore makes the handshake REFUSE outright — no release, no logout — because the ambient session slot now belongs to somebody else, and acting on it would delete the NEW user's device route and end the NEW user's freshly created session. This is the same rule, and the same shape, as the pinned-identity guard in `drainPendingRemovedAccountCleanupsOnce` (`PushCleanupIdentity.pinnedAuthToken`); do not add a second check elsewhere in the handshake, and do not re-derive the subject from ambient state. The Keychain clear proceeds exactly as on every other path — a refusal never keeps the local session alive.

**Why this order, and why BOTH legs.** The worker's own release check needs a live session for the subject, so the registration is released first. The logout then runs whether or not the release threw. ⚠️ **The earlier "logout only after a successful release" coupling is RETIRED and must not be reinstated** (round-1 review, 2026-09-03): gating the auth leg on the worker's status code protected nothing while leaving this device with a live server-side session after every worker outage. ⚠️ **Round 1 justified that retirement with a server-side staleness sweep that is NOT DEPLOYED yet — do not repeat the claim in the present tense.** On the currently deployed push worker the only server-side nets that retire a registration whose session ended before the release landed are the next-owner eviction (the next account to claim the same APNs token displaces the older registration) and APNs feedback once the app is uninstalled. The general staleness sweep lands with the push worker's half of issue #42; **once deployed** it becomes the standing backstop. The retirement does not depend on it either way: the coupling's cost — a live server-side session after every worker outage — is certain, while its benefit was never established, so both legs run regardless of what the server can retire on its own. The one thing that still stops the logout is the bound: `guard !Task.isCancelled` sits between the legs, so a release that completes only after `signOut()` has given up does not walk on into a logout. `scope=local` is load-bearing: GoTrue's default scope is `global`, which would end the user's sessions on every other device and, with them, the registrations those devices hold.

**Failure model.** Every outcome is tolerated silently (at most an `AuthDiagnostics.log` line): a thrown release, a non-2xx logout, a transport error, the bound expiring. The release-failure line logs `\(error)` and not `localizedDescription`, because the worker's failures are `PushError.workerRequestFailed(statusCode:errorCode:)` and the localized description drops both values. The handshake `Task` itself is cancelled BEFORE `completeSession(mode: .deactivate)`, for the same reason the removed-account flush is (`TabMailTokenCoordinator.performRefresh` can write a refreshed session back to the Keychain and resurrect what sign-out is about to clear), and the release runs AFTER that flush because a flush may re-register the device for the surviving accounts.

**Scope: this is the ordinary user-initiated path ONLY.** `AccountDashboardView`'s "Sign Out of TabMail" button is the sole production caller of `signOut()`. The account-deletion flow (`AccountDeletionView`) and RootView's "account no longer available" path do **not** reach it — they call `TabMailAuthService.completeSession(mode: .deactivate)` directly and are deliberately outside the handshake, because they act on a subject the server has already invalidated. `AppDataWiper.wipeAll` has its own reset variant and does not come here either. (An earlier revision of this note claimed those two paths run the handshake and "both legs answer 401"; that was never true of the code and is withdrawn.) The Sign Out button's disabled window now covers both bounds — `signOutCleanupFlushTimeoutSeconds + signOutHandshakeTimeoutSeconds`.

**Why a sibling and not `unregisterDeviceForReset()`.** The reset variant also removes `PushConfig.lastDeviceTokenKey` — the cached APNs token that `registerDeviceWithWorker` reads on the next sign-in, which APNs only re-delivers at launch — so reusing it would break a sign-out → sign-in in one process. `unregisterDeviceForSignOut()` keeps that token and goes through the `removedAccountCleanupClient` / `removedAccountCleanupDefaults` seams so tests observe and fault it.

**Cache honesty on every exit.** The other three effects — removing `PushConfig.registeredEmailsKey`, and resetting the in-memory `lastRegistrationTime` / `lastRegisteredStateHash` — live in a `defer`, so they run on the throwing exit too. A release that timed out client-side but completed server-side would otherwise leave a `SyncConfig.deviceRegistrationCacheTTLSeconds` "already registered" cache behind, and the next sign-in would trust it and skip registration: dead push that no user gesture repairs. A redundant re-registration is an idempotent upsert; a stale cache is not recoverable.

**Re-registration on sign-in is EXPLICIT, not implicit.** `TabMailAuthService.restorePushRegistrationAfterSignIn()` calls the existing foreground primitive `PushNotificationService.shared.subscribeAllAccounts()`, and RootView's `.tabMailDidSignIn` receiver — the single funnel every sign-in completion posts through — invokes it. Without it a sign-out → sign-in inside one process has no registration at all until the next scene-phase transition reaches `SyncScheduler.startForegroundPolling`, which never happens if the user simply stays in the app. Note there is no service-side poster of `.tabMailDidSignIn`: the three posters are `RootView`, `MailNavigationView` and `TabMailSignInPrompt`, and RootView is the sole receiver.

**Test seams and suite.** `TabMailAuthService._setSignOutLogoutTransportForTesting` (DEBUG-only; production default is `sharedEphemeralSession.data(for:)`), `PushNotificationService._setRemovedAccountCleanupDependenciesForTesting`, and `PushNotificationService._deviceRegistrationCacheForTesting` / `_setDeviceRegistrationCacheForTesting` (DEBUG-only; the in-memory registration cache is invisible to UserDefaults assertions). `SignOutHandshakeTests` pins: worker release before logout with the registered device id and the PINNED bearer; the logout runs after a FAILED release too; `scope=local`; session cleared on all four outcome paths; the handshake task cancelled while the session still exists; a 401 from either leg is silent with exactly one attempt; sign-out returns while the release is stuck; a release that succeeds only AFTER the bound does not still send the logout; and the durable effects both ways — `lastDeviceTokenKey` survives, `registeredEmailsKey` and the in-memory cache do not, on the success and the failed-release paths alike. `RemovedAccountPushCleanupTests` pins the cross-subject and ordering halves: a sign-in landing mid-flush makes the handshake refuse; the release runs after the flush's device re-registration and nothing re-registers behind it; and a completed sign-in restores the registration the sign-out released. Its `withHarness` answers the logout leg locally with a 401 and records it on the mock, so the flush suite never reaches the live auth host.
