## Ordinary sign-out releases the device push registration and ends the auth session — worker first, logout only after a successful release, `scope=local`, one bounded window (2026-09-03)

**The invariant.** `TabMailAuthService.signOut()` performs a best-effort, time-bounded release handshake while its bearer is still valid, and then clears the local session on EVERY path regardless of how that handshake went. The handshake is: (1) `PushNotificationService.unregisterDeviceForSignOut()` — `DELETE /register-device` on the push worker for this install's device id; (2) ONLY if (1) succeeded, `POST {auth base}/auth/v1/logout?scope=local` with the same bearer and the `apikey` header the refresh path uses. Both legs run inside one window bounded by `PushConfig.signOutHandshakeTimeoutSeconds`; there are no retries, no bookkeeping and no persistence. The docblock promise of `signOut()` — never fails, never waits past the bound — still holds (push-worker issue #42, owner ruling 2026-09-03).

**Why this order.** The worker's own release check needs a live session for the subject, so the registration is released first. A registration the worker still holds must keep its session alive so the worker's staleness sweep can still recognise it — which is exactly why a FAILED release skips the logout on purpose rather than "cleaning up anyway". `scope=local` is load-bearing: GoTrue's default scope is `global`, which would end the user's sessions on every other device and, with them, the registrations those devices hold.

**Failure model.** Every outcome is tolerated silently (at most an `AuthDiagnostics.log` line): a thrown release, a non-2xx logout, a transport error, the bound expiring. The account-deletion flow and RootView's "account no longer available" path sign out against a subject the server has already invalidated; there both legs answer 401 and that is the expected, silent case. The handshake `Task` itself is cancelled BEFORE `completeSession(mode: .deactivate)`, for the same reason the removed-account flush is (`TabMailTokenCoordinator.performRefresh` can write a refreshed session back to the Keychain and resurrect what sign-out is about to clear), and the release runs AFTER that flush because a flush may re-register the device for the surviving accounts.

**Why a sibling and not `unregisterDeviceForReset()`.** The reset variant also removes `PushConfig.lastDeviceTokenKey` — the cached APNs token that `registerDeviceWithWorker` reads on the next sign-in, which APNs only re-delivers at launch — so reusing it would break a sign-out → sign-in in one process. `unregisterDeviceForSignOut()` keeps that token, clears `registeredEmailsKey` and resets the in-memory registration cache (`lastRegistrationTime` / `lastRegisteredStateHash`, whose TTL would otherwise skip the re-registration the next sign-in needs), and goes through the `removedAccountCleanupClient` / `removedAccountCleanupDefaults` seams so tests observe and fault it.

**Test seams and suite.** `TabMailAuthService._setSignOutLogoutTransportForTesting` (DEBUG-only; production default is `sharedEphemeralSession.data(for:)`) and `PushNotificationService._setRemovedAccountCleanupDependenciesForTesting`. `SignOutHandshakeTests` pins: worker release before logout with the registered device id; logout skipped after a failed release; `scope=local`; session cleared on all four outcome paths; the handshake task cancelled while the session still exists; a 401 from either leg is silent with exactly one attempt; sign-out returns while the release is stuck. Every test also asserts the handshake was ATTEMPTED, so "session gone" alone cannot bless its absence. `RemovedAccountPushCleanupTests.withHarness` answers the logout leg locally with a 401 so the flush suite never reaches the live auth host.

**Supersedes** IOS-PUSH-001 §3 ("Ordinary sign-out policy remains intentionally small"), which is kept as history. `AppDataWiper.wipeAll` and its reset variant are unchanged.
