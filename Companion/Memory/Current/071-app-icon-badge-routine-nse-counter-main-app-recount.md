
### App Icon Badge Routine (NSE counter + main-app recount)

- **Two mechanisms**: (1) NSE best-effort incremental counter in App Group key `nse.unreadBadge` (`NSEBadge.badgeCountKey`), attached as an *absolute* value via `c.badge` on each delivered push; (2) main app's `UnreadCountManager.updateBadge()` — authoritative `SUM(folder.unreadCount) WHERE role=inbox`, calls `setBadgeCount` and **overwrites the mirror**. The counter only has to stay reasonable between main-app wakes; every recount self-heals drift.
- **All per-delivery badge values MUST go through `NSEBadge.badgeForDelivery`** (`Shared/Persistence/NSEBadge.swift`, compiled into app + NSE) — never raw increments. Gates:
  - **Dedup key = `NSEBadge.countedId` (rfc822-preferred), NOT the provider `messageId`.** The composite is `"\(accountId):rfc:\(normalizedRfc822)"` when an rfc822 Message-ID exists, else `"\(accountId):\(messageId)"`. **Why this matters (fixed 2026-06-15):** the NSE keys IMAP off the RFC 5322 Message-ID carried in the push payload, while main-app IMAP sync may store the *UID* as `messageId` (see the `WHERE accountId=? AND messageId=?` lookup in `mergeNSEStagingData`). A `messageId`-only key therefore silently NEVER matched for IMAP/iCloud — so the main-app-overlap dedup below would no-op for those accounts. rfc822 matches across both processes for all providers. All 3 NSE `badgeForDelivery` call sites pass `msg.rfc822MessageId`. Normalize with `EmailFilter.normalizeMessageId` on both sides.
  - **Gate 1 (duplicate pushes)**: per-`countedId` idempotency arbitrated by atomic `INSERT OR IGNORE` into `nse_badge_counted` in the shared staging DB. Deliberately a separate table (NOT a column on `nse_processed_message` — those rows get `INSERT OR REPLACE`d by re-runs and deleted by the merge). Created lazily by `NSEBadge`; 7-day retention pruned opportunistically.
  - **Gate 2 (main-app overlap, AI lease)**: when the main app holds a *fresh* `AIOwnershipLease` on the message (looked up by provider `messageId` — the lease key is unchanged), the NSE delivers the current counter without bumping. Narrow — only catches the case where AI is actively processing that exact message.
  - **Main-app authoritative recording (the real overlap fix, 2026-06-15)**: `UnreadCountManager.updateBadge()` → `recordRecentUnreadForNSE()` writes the recent unread inbox messages' `countedId`s into `nse_badge_counted` via `NSEBadge.markCounted`. So a message the awake main app already counted → row exists → NSE's Gate 1 doesn't bump → **no "+2 for one email"**, regardless of AI-lease state. Order-independent (whoever counts first wins the `INSERT OR IGNORE`). Bounded to `SyncConfig.nseBadgeDedupRecentLimit` (200) most-recent-by-date — only recently-arrived mail can race a concurrent NSE delivery. This generalizes Gate 2 WITHOUT a liveness heartbeat (which would risk a persistent under-count if the app backgrounds right after its heartbeat). **`recordRecentUnreadForNSE` is gated on `UIApplication.shared.applicationState == .active`** (ADR-IOS-041, fixed 2026-06-15): the overlap only happens in foreground, and opening a fresh `openStagingDB()` connection + writing from the background-detached badge Task while suspended aborts (or worse — a fresh connection that misses the suspend notification writes-while-suspended → 0xdead10cc). See the "GRDB database-suspension abort handling" note below.
  - **`db == nil` fallback**: no staging DB → dedup via an App Group map (`nse.badgeCountedIds`, `[countedId: epoch]`, retention-pruned) so a duplicate delivery still doesn't double-bump (previously this path unconditionally incremented).
- `NSEState.incrementBadgeCount`/`decrementBadgeCount` remain ONLY for the legacy Gmail history.list delta-adjust path (payload has no `messageId`). `markedUnreadCount` now **excludes `addedSet`** (`GmailNSEClient.fetchNewMessageIds`, fixed 2026-06-15): a brand-new message is badge-counted on delivery (head via `badgeForDelivery`) or by main-app sync (tail) — counting it again as a `labelsAdded(UNREAD)` delta double-bumped. The delta path now only moves the badge for messages ALREADY in the inbox that got re-marked unread on another client.
- **`updateBadge()` only SUMs `folder.unreadCount`; it does NOT recompute it.** So any path that inserts/deletes inbox `messageHeader` rows must FIRST update `folder.unreadCount` (optimistic delta in the same tx, like `markRead`) OR call `UnreadCountManager.requestRecount(folderIds:)` (authoritative COUNT recompute) — only THEN is `updateBadge` correct. Every sync path does this (`SyncEngineFullSync` requestRecount per folder after commit; delta `requestUnreadRecount`; backfill; actions). **Badge-desync bug fixed 2026-06-15:** `NSEDataBridge.mergeNSEStagingData` inserted NSE-delivered headers + did sleep-time removals but called `updateBadge()` (sum-only), so the badge/sidebar undercounted new mail until the next full sync (worse once "fast read" made the inbox UI update instantly, exposing the lag). Fix: `mergeNSEStagingData` calls `UnreadCountManager.recountInboxFolders()` (blanket authoritative recompute of ALL inbox-role folders) whenever the merge mutated. No per-message folder tracking — the merge only ever touches inbox folders (new arrivals are `isInInbox`; removals delete from inbox folders; the existing-header branch only updates AI fields, never `isRead`), so recounting all inbox folders is sufficient and self-healing. Sync paths still call `requestRecount(folderIds:)` with their specific changed folders (the thin `SyncEngine.requestUnreadRecount` wrapper was removed as redundant — call `UnreadCountManager.shared.requestRecount` directly).
- **Foreground is safe by construction**: `NotificationDelegate.willPresent` returns `[]` for email pushes (badge never applied) and triggers merge + sync recount.
- Push-worker sets **no `apns-collapse-id`** — a true APNs duplicate shows two banners; badge dedup is entirely client-side via Gate 1.
