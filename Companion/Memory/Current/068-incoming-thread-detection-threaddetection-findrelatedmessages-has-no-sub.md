
### Incoming Thread Detection — `ThreadDetection.findRelatedMessages` has NO subject-based fallback (by design)
- **Deliberate, documented in the file's own header comment**: relatedness is a pure union of real signals only — `rfc822MessageId`/`inReplyTo`/`References` chains (BFS-expanded) plus native Gmail/Exchange `threadId`. A synthetic `"subj:"`-prefixed `threadId` (the IMAP fallback used elsewhere for display grouping) is explicitly EXCLUDED from the native-threadId lookup (`!threadId.hasPrefix("subj:")`) — subject matching was rejected as a relatedness signal because it would pull in every unrelated message sharing a generic subject (false-positive groupings).
- **Diagnosed 2026-07-08 (`logmain.log`, `[ThreadDebug]`)**: a message showed `inReplyTo=nil references=[]` and 0 related messages found, despite its BODY visibly containing an embedded prior reply chain (a `----- Original Message -----` quote). This is NOT a TabMail bug — the received email genuinely lacks `In-Reply-To`/`References` headers (the sender's webmail system composed the "reply" as new text + manually-embedded quote rather than a proper RFC5322 threaded reply; same email had a non-standard `[re]re:` subject prefix). Since ALL client-side thread detection (TB included — confirmed failing on the same message) depends on those headers, no local fix is possible without reintroducing subject-based matching, which was already rejected for good reason. Recognize this pattern quickly next time: `inReplyTo=nil` + `references=[]` in a `[ThreadDebug]` log on a message that visibly quotes prior correspondence = broken/non-standard sender, not a detection bug.
