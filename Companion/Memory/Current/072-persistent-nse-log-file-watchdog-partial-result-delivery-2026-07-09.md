
### Persistent NSE log file + watchdog partial-result delivery (2026-07-09)

- **Problem:** the NSE logged only via `os_log(.error, ...)` (subsystem `ai.tabmail.nse`) — field-invisible (no Console.app access on a user's device). AND the 27s graceful-exit watchdog / `serviceExtensionTimeWillExpire` always delivered the bare "New Email" fallback, even when step 6a had already computed a summary (staged to `nse_processed_message` via `stageSummary`) — the summary was a local var inside static `process()`, invisible to the exit paths.
- **Persistent log:** `Shared/Notifications/NSELogStore.swift` (compiled into BOTH targets — the NSE writes, the main app reads) is a SYNCHRONOUS append-only file (`nse.log`, App Group container, alongside `nse_staging.sqlite`) — deliberately not async like `BackgroundSyncLogger`, since the NSE can be hard-killed at any instant and an async queue would lose exactly the line that explains why. Gated on App Group key `nse.debugLoggingEnabled` (mirrored by `NSEDataBridge.mirrorDebugLogging()` on launch AND immediately from `DebugModeManager.isUnlocked`'s `didSet`, since `SharedNSEData`/Keychain-session checks aren't reachable from the NSE process). Trims to `keepBytes` (1.5MB) once per NSE process when it opens over `maxBytes` (3MB) — never via an atomic external replace (`BackgroundSyncLogger.trimTail`'s approach), which would silently orphan a cached `FileHandle` onto a deleted inode; instead `truncate(atOffset:)` + rewrite on the SAME handle. Debug menu: "NSE Logs" in `DebugLogView` (`LogShareButton`, mirrors the "Boot Profile Logs" pattern).
- **`NSELog.step(_:)`** (`TabMailNotificationService/NSELog.swift`) is now the dual-channel logger: fires `os_log(.error, ...)` (unchanged field-visibility trick) AND appends `[wall-clock ISO8601ms] [+totalms Δdeltams] message` to `NSELogStore` (BootProfiler-style timing, own process-start/last-step statics). NOTE: iOS may REUSE one NSE process for several pushes — `+total` is since process start (not push start) and the first Δ of a run measures the idle gap since the prior run's last line; the `NSE ━━━ STARTED ━━━` marker + wall-clock delimit runs. Same caveat for the `nse.debugLoggingEnabled` gate cache: a mid-life toggle takes effect on the NEXT NSE process launch. **All ~65 `os_log(.error, log: log, "NSE ...")` call sites across the NSE target were converted to `NSELog.step(...)`** (`NotificationService.swift`, `GmailNSEClient.swift`, `OutlookNSEClient.swift`, `NSEIMAPConnection.swift`, `NSETokenManager.swift`, `NSEAICacheProbe.swift`, one `.error` site in `NSEAuthSource.swift` — its lone `.info` site + `OSLog`/`import os` were left alone, still needed). The `NSE stepN` / `NSE ━━━` message prefixes are a stable grep contract — preserved byte-for-byte.
- **Watchdog partial delivery:** `PartialSignalHolder` (mirrors the existing `LeaseHolder`/`CancellableTaskHolder` class-wrapped-`Mutex` pattern in `NotificationService.swift`) carries the best-known `EmailNotificationBuilder.Signal` from static `process()` back to the instance. Set twice: right after step 4 (header-only — sender/subject, no summary) and again after step 6a's `stageSummary` call (summary/reminder fields added, `actionTag` stays nil — the vote hasn't returned). The watchdog closure and `serviceExtensionTimeWillExpire` both call the shared `NotificationService.applyPartialOrBareFallback` helper: delivers the partial via `EmailNotificationBuilder.fill` if one exists, else the original bare fallback — either way FORCING `.passive`/no sound (the action vote is unknown at exit time, so never ring for a guess, regardless of what `fill` would otherwise decide).
- Tests: `TabMailTests/NSE/NSELogStoreTests.swift` (append/read/clear/gate/trim, all via `fileURLOverride`/`enabledOverride`/`maxBytesOverride`/`keepBytesOverride` test seams + `_resetForTesting()` — mirrors `BodyAssetStore._setTestEnvironment`/`_resetForTesting()`), `TabMailTests/Notifications/EmailNotificationBuilderTests.swift` (new file — no prior coverage existed for `fill`/`isImportant`).

#### Field evidence + two follow-up fixes (2026-07-09, same day)

- **DEFECT 1 root cause — idle timer vs SSE:** `BackendNSEClient.sendCompletions` set `request.timeoutInterval = timeout` (12s nominal) believing it was a wall-clock cap. It's an IDLE timer — it resets on every received byte — and `/completions/chat` streams SSE frames, so a trickling response keeps the connection alive far past 12s. Production nse.log proved it: a summary call ran **26.4s**, missing the delivery window by **9ms** against the 27s watchdog (watchdog fired first, delivered a summary-less banner, and the real summary landed 9ms later — wasted work). Action calls were separately observed at 16.8s/17.4s/19s+.
- **Fix 1 — true wall-clock deadline + remaining-time budgeting:** `BackendNSEClient.performRequestWithDeadline` now races `URLSession.shared.data(for:)` against `Task.sleep(for:)` via `withTaskGroup` (first finisher wins, `group.cancelAll()` — `data(for:)` is cancellation-aware and aborts the HTTP request); `request.timeoutInterval` is kept as the underlying connection-level layer. On deadline: logs `NSE LLM call DEADLINE (...) — abandoning`, returns nil. Each call's timeout is no longer the flat nominal constant — `NSEProviderSupport.llmCallBudget(nominal:elapsed:watchdog:finishMargin:minCall:)` (pure, `Shared/Notifications/NSEProviderSupport.swift`, unit-tested in `TabMailTests/NSE/NSELLMBudgetTests.swift`) returns `min(nominal, watchdog - elapsed - finishMargin)` or nil (skip — not enough time to bother) below `minCall`. `process()` now takes a `runStart: CFAbsoluteTime` param (the same `t0` `didReceive` already captured) and computes the budget fresh before step 6a and again before step 6b. New `NSEConfig` constants: `llmFinishMarginSeconds = 2.5` (reserved for step 7/8 after the last LLM call — staging writes measure 1-20ms in production), `llmMinCallSeconds = 2`. The watchdog (`NSEConfig.watchdogSeconds = 27`) is now a true backstop — a healthy-but-slow run finishes or gives up on its own with margin to spare; the watchdog should only fire on a genuinely stuck non-LLM step.
- **DEFECT 2 — zombie resume:** when the watchdog delivers and iOS later REUSES the suspended NSE process for a new push, the OLD `process(...)` Task can resume — its in-flight LLM call returns (usually nil), and step 7's `persistProcessedMessage` (INSERT OR REPLACE) would run minutes later WITHOUT holding the AI lease (already released by the watchdog), potentially clobbering a row the main app has since claimed/merged. Observed twice in the field: `"NSE step6b: action=nil"` minutes after `"NSE ⏱️ WATCHDOG"`, interleaved with the next push's run, plus a `"NSE deliver: already fired (race)"` line.
- **Fix 2 — zombie abandon checks keyed on the `delivered` OneShotFlag:** `OneShotFlag` gained a non-consuming `hasFired()` (same lock as `tryFire()`). `didReceive`'s existing `deliverGuard` (the `delivered` flag) is now also passed into `process(...)` as `deliveredFlag`. Three checks, each `if deliveredFlag.hasFired() { NSELog.step("NSE zombie: exit path already delivered — abandoning without persist"); return }`: immediately after the step-6a summary call returns (before `stageSummary`), immediately after the step-6b action call returns, and immediately before the step-7 `persistProcessedMessage`. The top-of-function `defer` (watchdog cancel / heartbeat stop / lease release) still runs on this early return — it's idempotent, so no double-release. These checks cannot false-positive on the natural path: `deliverOnce` only fires after step 8, past all three checkpoints. Initially NOT added to `task_alarm` / `imap_reconnect` / peer-cache-hit / staging-cache-hit paths on a "those deliver quickly" rationale — **that rationale was WRONG for the two network-awaiting, staging-writing branches** (peer-cache probe + task_alarm; corrected in audit round 4 below, checkpoints 8-9). `staging-cache-hit` remains legitimately exempt (synchronous local read, no await to zombie-resume from); `imap_reconnect` writes nothing to staging (its delivery no-ops on the fired flag; the `PushHealthStore` stamp is a benign health signal any real push also records).
- **Follow-up (2026-07-09, post-073c98d) — action-requires-summary parity gate + summary retry loop.** Field trigger: the first production run of the deadline fix logged `NSE LLM call DEADLINE (12s wall-clock)` on the summary, then ran the action WITHOUT summary context (budget=10.4s) and classified "reply" — but the main app's `ActiveAIQueue.executeActionJob` (~line 957) guards `guard let blurb = msg.summaryBlurb, !blurb.isEmpty else { skip("Action skipped (no summary yet)") }`; the NSE was violating AI-parity (ADR-IOS-008). Two changes: (1) **parity gate** — step 6b only runs when `summaryBlurb?.isEmpty == false`, else `NSE step6b: SKIP — no summary (action requires summary context; main-app AI will complete on next wake)`; step 7/8 already handled nil actionTag. (2) **summary retries within its budget** — `NSEConfig.summaryTimeoutSeconds` raised 12 → 15 and is now a per-ATTEMPT nominal; step 6a is a retry loop that recomputes `llmCallBudget` each iteration (TWO terminators: nil budget — a DEADLINE attempt drained the window — and `NSEConfig.summaryMaxAttempts = 3`, added in review because a FAST-failing attempt (offline / connection refused) returns in ms and would otherwise spin the loop for the whole ~24.5s window, spamming nse.log + the backend), logs the attempt number on each failure (deadline or nil response), keeps the zombie check INSIDE the loop right after each call returns (before any staging write), and runs the success path (parseSummary → stageSummary → partialHolder upgrade) once, then breaks. Net effect: a summary failing its first 15s attempt gets a second ~7-8s attempt; the action then runs only on summary success with whatever budget remains. A pre-loop `authToken == nil` short-circuit (`while authToken != nil`) prevents a futile tight-spin — `sendCompletions` returns nil instantly without a token, which would otherwise loop thousands of times appending to nse.log.
