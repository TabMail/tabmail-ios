> **Current routing note (2026-11-08, tabmail-ios #429 and #444): Gmail history pagination and the delta work bound; a delta detail fetch skips only a gone message; the full sync runs every `SyncEngine.fullSyncInterval` (900 s), not "every 10 min" as written below, and only when it is due: a failed or refused delta does not "fall through to full sync automatically" as the bullet below says, it clears or keeps its cursor and the full sync runs at its next due time.**
>
> - **Gmail `history.list` is paginated, and every page is read before the cursor moves (tabmail-ios #429).** A page holds at most 500 records (default 100), and Gmail says "If you receive no `nextPageToken` in the response, there are no updates to retrieve". Until #429, `GmailAPI.historyList` read one page and the delta's cursor was that response's `historyId` (the mailbox's CURRENT id), so once more than one page of changes had built up (a bulk archive on the web, a long background gap), every later record was skipped for good and only the full sync's recent window healed it. `GmailAPI.historyList` now follows `nextPageToken` (`maxResults` = `GmailAPI.historyPageSize`, 500) and returns one delta for all pages, with the FIRST page's `historyId` as the cursor (a record newer than that is re-read next time, which delta sync treats as harmless). The delta is bounded by the WORK it commits to, not only by round trips: `gmailDeltaSync` fetches each changed message with its own GET (one at a time until #449, now `GmailAPI.maxConcurrentRequests` at a time) under the per-account sync deadline (`SyncConfig.perAccountSyncTimeoutSeconds`, 60 s), and saves those messages and moves the cursor only after the GETs (deletes are applied before them, which is idempotent), so a 20,000-record delta timed out before its cursor moved, starved the due full sync and failed the same way on every poll (found in review of #429 and reproduced). So history holding more than `GmailAPI.historyMaxChanges` (100, Gmail's default page, the delta the app took on before it read further pages) records, or naming more than that many distinct messages to fetch (added or relabelled; one record can name every message of a conversation, so records alone do not bound the GETs), or running past `GmailAPI.historyMaxPages` (40) pages, returns nil exactly like the 404 expiry: `gmailDeltaSync` clears `lastHistoryId` before any detail GET, later deltas skip with `noHistoryId`, and the ADR-IOS-009 full sync takes over when `SyncEngine.fullSyncInterval` (900 s) is next due. Reading stops at the page that crosses a bound. It never advances past unread records, and a long history is never a throw (a throw would fail identically on every retry); transport, status and decoding errors still throw and keep the cursor. An unencodable page token throws `HTTPError.invalidURL` rather than being sent raw. The NSE shares `historyList`; on nil its own cursor stays where it was, the same as on a 404. A page without `history` (Gmail's answer when nothing changed) is an empty delta that moves the cursor. Logs say "expired or too long" for both nil causes. Tests: `GmailHistoryPaginationTests` (end to end through `performDeltaSync`: every page applied, later-page error status, transport failure and 404, the page limit, the record budget alone, the message budget per record kind and across pages, the quiet page).
>
> - **A delta skips a changed message only when its fetch answers that it is gone (404/410), and a Gmail full sync finishes past one message it cannot read (tabmail-ios #444).** `GmailProvider.fetchMessageDetails` and `ExchangeProvider.fetchMessageDetails` used to catch every error and skip the message as "deleted", so a transient failure (a 5xx, a 429 past the retry budget, a dropped connection, cancellation, an unreadable body, a record the parser refuses for want of a date) dropped that change while the delta still moved its cursor. Now they skip only what `isHttpGoneStatus` matches; every other failure throws, so the delta fails without moving its cursor (the Gmail history id, the Outlook delta link) and a later pass fetches the same change again. A failure that never clears is bounded by the full sync's `captureSyncCursors` (Gmail history id moved forward, Outlook delta link recaptured). For that bound to hold on Gmail, `GmailProvider.fetchMessagesWithObservedEpoch` no longer aborts the folder when one message's metadata GET answers an error status (other than 401) or does not decode: that id is reported in `FetchCoverage.unmaterialisedIds` (row kept) and the folder still syncs; a dropped connection or cancellation still fails the folder. **Limit:** when the full sync runs in the same pass as a failed delta (or a failure never clears), the capture moves the cursor past the whole failed batch, and a change in it that no full-sync window covers is not recovered; this is the same exposure as any other delta failure under the two-tier design, and a missed state change on an existing row outside every window is not recovered by any path (tracked in tabmail-ios #464). Background syncs (Gmail and Outlook) run no full sync, so there the bound is the next foreground full sync. Tests: `DeltaDetailFetchFailureTests`.
> - **Every Outlook full sync takes a new Inbox delta link, walked in coarse pages; only Graph refusing the link discards it; an Inbox move in Settings launches a full sync (tabmail-ios #427).** Graph's initial delta round returns every message in the folder, so `ExchangeProvider.getCurrentDeltaLink` walks the whole Inbox; it asks for ids only, with `Prefer: odata.maxpagesize=SyncConfig.graphDeltaCursorWalkPageSize` (100) on every page instead of `$top=1`. The walk runs inside the foreground pass, which `AccountManager.foregroundSyncOne` cuts at `SyncConfig.perAccountSyncTimeoutSeconds`; a large Inbox's walk can take longer, so the provider keeps where an unfinished walk stopped (`deltaWalkContinuation`: the folder and the next page's `@odata.nextLink`, recorded after every page, in memory only) and the next walk of that folder resumes there; a kept link Graph refuses restarts the walk at page 1 in the same call, and another folder starts at its own page 1. Without this, every poll re-ran the full sync and restarted the walk at page 1, so the link was never refreshed (the MIS-IOS-022 shape: work cut by a deadline and redone from the start). The full sync always takes a link (owner 2026-11-09: the full sync is the universal healer; an earlier ruling that a failed delta page costs no walk was withdrawn). `ExchangeProvider.fetchHistory` returns nil (link discarded, the next full sync takes one) only when Graph refuses the round on any page: a 4xx other than 401, 403, 408 and 429 (`syncStateNotFound`, `410 Gone`). A 401/403 after the token refresh, 408, 429, 5xx, a dropped connection or cancellation throws and keeps the link for the next pass. Every folder-role write goes through `FolderRoleEdit` (`FolderRoleWriterFenceTests`); an edit that changes which folder is the Inbox marks the account's full sync due (`lastFullSyncAt = NULL`, provider-blind) and Settings starts `AccountManager.syncAccount` with the account read back, so that pass runs the full sync and takes the new Inbox's link. The 15 s recent-sync check still applies; when it skips the kick, the next foreground pass runs the due full sync. Until then the delta follows the old folder's link, which is harmless (delta rows are filed by `parentFolderId`). One sync pass at a time per account (ADR-IOS-104) means no cursor write needs to guard against another pass. Tests: `ExchangeDeltaCursorTests`.
>
> - **A Gmail delta fetches its changed messages a request gate's width at a time (tabmail-ios #449).** One GET at a time made a background delta of a few dozen messages miss its 10 s per-account deadline (`SyncConfig.backgroundPerAccountTimeoutSeconds`), save nothing and repeat on every silent push. `GmailProvider.fetchMessageDetails` now keeps a sliding window of `GmailAPI.maxConcurrentRequests` gets in flight (a task group seeded with that many ids, one more started per answer, a gone answer included), so a later request on the account, such as a user's action, waits behind at most one window at the FIFO request gate rather than the whole delta. The outcome is unchanged: a gone (404/410) message is skipped, any other failure throws and no partial list is returned, and results come back in completion order (the delta passes its ids in set order and keys every write by message id). The foreground poll's delta-first path calls the same function, so it is concurrent too. The Outlook delta (`ExchangeProvider.fetchMessageDetails`) still fetches one at a time. Tests: `DeltaDetailFetchFailureTests` (width in flight, room for another request, one failure in a large batch, gone messages filling the window).

### Two-Tier Sync (ADR-IOS-009)
- **Delta sync** (every 60s): lightweight check for changes since last sync
  - Gmail: `history.list` API with `lastHistoryId` cursor → returns adds/deletes/label changes
  - IMAP: `STATUS` command per folder → compares `uidNext` + `messageCount` with cached values
- **Full sync** (every 10 min): safety net, self-healing — runs `fullSync()` as before
- Delta sync skips unchanged folders entirely (IMAP) or processes only affected messages (Gmail)
- If delta fails (e.g., Gmail 404 expired cursor), falls through to full sync automatically
- `Account.lastFullSyncAt` tracks when last full sync ran (delta syncs don't update it)
- `Folder.lastKnownUidNext` caches IMAP uidNext for change detection
- `GmailProvider.fetchMessageDetails(ids:)` returns headers + labelIds for folder assignment during delta sync
- `IMAPProvider.folderStatus(path:)` returns quick STATUS without SELECT
