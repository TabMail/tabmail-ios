### HTML Email Render Pipeline (AutoSizingHTMLView) — MUST stay idempotent (ADR-IOS-039)
- The render is a measure→mutate→re-measure pipeline with **two feedback-loop arms**, both now closed. Do not reopen either:
  - **Height arm** (closed earlier): `html,body{height:auto;min-height:0;max-height:none}` in `EmailHTMLWrapper` stops `scrollHeight` inheriting the layout-viewport floor; `monitorHeightJS` reads `window.__tmLayoutVp` (not `innerWidth`, WebKit bug 170595).
  - **Width arm** (closed 2026-06): `fitViewportJS` has an **idempotency guard** — bails if `window.__tmLayoutVp` is already set. Without it, every re-entry (esp. the `didBecomeActive` foreground re-fit) re-measured a widened document against an unreliable `innerWidth` and re-mutated it → fonts shrank on every background→foreground cycle.
- `fit()` stamps `window.__tmDeviceWidth` from `webView.bounds.width` before running the script — **never trust `window.innerWidth`** anywhere in this pipeline (bug 170595). `monitorHeightJS` vp fallback chain: `__tmLayoutVp || __tmDeviceWidth || innerWidth`.
- Re-fit after a REAL width change (rotation/sheet resize) goes through `viewportResetJS(deviceWidth:)` which clears `__tmLayoutVp` + restores `width=device-width` BEFORE `fit()` — required or the guard bails and heights scale against the stale viewport.
- **ScrollFreezeGate** (in AutoSizingHTMLView.swift; Mutex-based, NOT @MainActor — the Coordinator is nonisolated): while the detail List scroll phase is non-idle, Coordinators buffer changed heights in `pendingHeight` and flush on `.scrollFreezeReleased`. Prevents row resize mid-pan → List self-sizing repositioning rows under the finger → overlapping cards. Driver: `MessageDetailView` `.onScrollPhaseChange`; `end()` also called in `onDisappear` (a stuck gate freezes height application process-wide). Exception: `height <= 1` (never-sized row) applies immediately.
- Key invariant making this work: `handleHeightMessage` only writes `height` when the value CHANGED — so idempotent re-measurement is free, and only genuine changes (late image loads) ever hit the freeze buffer.
- **HeightSeedCache** (in-memory, NOT disk — ADR-004): List dismantles far-offscreen rows and **`@State height` does NOT survive** recreation (log-proven 2026-06-09: same message reloaded 5×/session with `frameH=1` at onload — row collapsed to 1pt and re-inflated mid-scroll = the residual overlap). `AutoSizingHTMLView.init` seeds `@State` from the cache (keyed by `headerId`); Coordinator writes on every applied height. Seeded row re-enters at its real height; the idempotent re-measure returns the identical value → `!=` guard drops it → row never moves. Seeding is only sound BECAUSE the fit is idempotent — never add a seed/persist layer to a non-convergent measurement pipeline.
- **`img { height: auto }` MUST be scoped to `img[width]`, NOT applied to every image** (`EmailHTMLWrapper.swift` ~line 131). The wrapper's responsive-image reset was `img { max-width: 100%; height: auto; }`. `height:auto` (author CSS, specificity 0,0,0,1) OVERRIDES an email's `height="29"` presentational attribute (specificity 0). For a logo sized ONLY by `height="29"` with no `width` attr (the Apple Support survey header), stripping the height removed its only size cap → the image rendered at its full natural size capped to the container width (a ~29px logo **ballooned to ~420px wide+tall**), overflowing the 288pt device viewport. That cascaded: `fitViewportJS` saw a 420px culprit → widened the layout viewport to 440 → whole email scaled down and the **right edge clipped** (screenshots 2026-06-16: giant black Apple logo + "…how satisfied were you[r]" / "Apple Suppor[t]" cut off). Apple Mail / Thunderbird render the logo small because they honor the `height` attr. **Fix:** `img { max-width: 100%; }` for all images + `img[width] { height: auto; }` only for images carrying an explicit width attr (where capping width via max-width must scale height to avoid distortion). A width-less image keeps height:auto behavior implicitly (height defaults to auto when only width or neither is set), so honoring its explicit `height` is safe. Test: `EmailRenderPipelineTests.imgHeightAutoScopedToWidthAttr`. **Misdiagnosis log (don't repeat):** first attributed it to fitViewportJS measuring a *not-yet-loaded* image (added a skip-loading-images guard) — WRONG; `logmain.log` showed `skipped 0`, the image was fully loaded and genuinely 420px because of the `height:auto` balloon. Guard reverted.
- **`fitViewportJS` widen is ITERATIVE (re-measure after reflow), not measure-once** (`measureMaxRight()` helper + `MAX_PASSES=4` loop). After the logo fix the Apple survey still clipped "a bit on the right": `table#main` (`width="100%"`) has a 420px min-content while its parents are 288, so we widen to 420 — but 288→420 crosses the email's OWN `@media (max-width:415px)` query, flipping it out of the mobile layout into a wider one (desktop voting buttons `width:442px` etc.) that overflows the 420 we set. A single measure-then-widen undershoots → right clip. Fix: after each `meta width=` set, force a synchronous reflow (`void documentElement.offsetHeight`) and RE-measure `maxRight`; widen again to the revealed width. Bounded: the loop only GROWS `targetWidth`, stops when a pass asks for no more than already set (so `width:100%` tables that track the viewport can't loop), pass-capped at 4, ceiling 1200. All passes run in ONE JS execution (synchronous reflows, no paint between) so the user sees only the final widen — no flicker. `window.__tmLayoutVp` is set to the FINAL `targetWidth` after the loop. This email's mobile min-width (420) exceeds its own mobile breakpoint (415), so there is NO width where its mobile layout both fits and is active — widening to the stable desktop width + scaling is the only clip-free outcome (matches mainstream clients). Test: `EmailRenderPipelineTests.fitViewportIterativeWiden`. The loop is hard-bounded (can't recreate the ADR-IOS-039 width/height runaways): synchronous `for` with (1) `pass < MAX_PASSES`, (2) monotonic non-decreasing `targetWidth` + no-progress break (`want <= targetWidth`), (3) 1200 ceiling + explicit break; never calls `fit()` (no re-entry), no paint between passes, and sets `__tmLayoutVp` so the idempotency guard blocks future re-entry. Test: `fitViewportWidenTerminates`.
- **`fitViewportJS` RUNAWAY GUARD — abort the widen on a FLUID culprit instead of shrinking to a tiny scale (2026-06-29, Scholar Inbox digest).** Symptom: the whole email rendered at "desktop size" — i.e. **shrunk to a sub-0.5× scale** (tiny text, whole newsletter crammed in), while Apple Mail renders the same email at device width with large readable text. `logmain.log 2026-06-29`: the culprit was the header logo `<a><img width="160" height="auto" style="max-height:40px;width:auto;…"></a>`, and it was **deferred** (our `data-tmsrc` first-paint optimization strips the `src`). An unloaded `width:auto` image is NOT clamped by `img{max-width:100%}`, so it overflowed device width by only 43px at `vw=288` — but because it's *fluid* (`max-width:100%`), it GREW with every widen: the loop ran `288→400→499→648→873`, never converging, and committed `873px → 0.33× scale`. The idempotency guard then locked that scale even after the image loaded and would have fit. **The widen loop's old termination assumption ("a width:100% element fills whatever viewport we set, so its remeasure is within slop → immediate break") is FALSE for an unloaded/`width:auto` image** — it overflows the viewport you give it, so the loop chases it to the cap. **Fix:** a `converged` flag (set only on the no-progress `want <= targetWidth+OVERFLOW_SLOP` break) + a post-loop guard: `if (!converged && targetWidth < 1200 && maxRight > targetWidth + OVERFLOW_SLOP)` → **revert the meta to `width=device-width, initial-scale=1`, leave `__tmLayoutVp` unset, report height at 1.0×, reveal** (Apple-Mail-like). Discriminator rationale: genuinely fixed-width content CONVERGES (once viewport ≥ its intrinsic width it fits → `maxRight <= targetWidth`); fluid content never does. The `targetWidth < 1200` gate preserves scale-to-fit for genuinely-wider-than-cap FIXED emails (clipping those would lose real content; fluid ones don't lose content — `html{overflow-x:clip}` hides the transient overflow and the loaded image's `max-width:100%` snaps it inside the device-width container). Only changes behavior for the runaway case (which always produced an unreadable sub-0.5× scale). Test: `EmailRenderPipelineTests.fitViewportRunawayGuard`. NB: this is the *width-arm* sibling of the `height:auto` logo-balloon fix (line above) — both are "a not-fully-constrained header image perturbs `fitViewportJS`", but that one was a loaded image ballooned by `height:auto`, this one a *deferred/unloaded* image ballooned by `width:auto`.
- **`measureMaxRight()` excludes not-yet-loaded images from the overflow scan — the UPSTREAM fix for the above runaway (2026-06-29, layer 2; the runaway guard is the downstream backstop, layer 1).** Root of the phantom overflow: `fitViewportJS` runs at first-layout/`didFinish`, BEFORE deferred images load (`deferredImageLoadJS` swaps `data-tmsrc`→`src` only AFTER first paint). An unloaded `width:auto` `<img>` has no reliable intrinsic size and balloons past its container, so `measureMaxRight` saw a 43px phantom overflow and widened. **Fix:** in `measureMaxRight`, before the rightmost-edge scan, hide (`display:none !important`) every `<img>` matching `hasAttribute('data-tmsrc') || hasAttribute('data-tmsrcset') || !complete`, scan, then RESTORE each image's original inline `display` value **and priority** (`getPropertyValue`/`getPropertyPriority` — so an `enforceMediaDisplayJS`-set `!important` survives). Hiding (not skipping the `<img>` node) is REQUIRED so the inline `<a>` wrapper collapses too — the culprit `getBoundingClientRect().right` is the `<a>`'s, driven by the img. **Scope discipline (do NOT loosen):** key on `data-tmsrc`/`!complete`, NEVER `naturalWidth===0` — deferred imgs report `complete===true` (no src) so `data-tmsrc` is the load-bearing check (the reverted-2026-06-16 `!complete`-only guard "skipped 0"), and `naturalWidth===0` would also hide a LOADED intrinsic-size-less SVG and wrongly drop its real width. Does NOT regress the `height:auto` logo case (that img is LOADED → not hidden) nor genuine desktop-width emails (their width comes from tables/fixed elements, not from unloaded imgs; loaded wide imgs are clamped by `img{max-width:100%}` so they never drive a widen). Height-change was NOT the cause — `logmain.log id=6HS8GR` shows `contentH=1658` STABLE the whole time while the `TABLE` body-child's `getBoundingClientRect().top` slid `0 → −13 → −1` with `body.rectTop` pinned at `0` (= an internal scroll offset on `body`, not the page/UIScrollView). **Root cause A (the slide): `overflow-x: hidden` on `html`/`body` in `EmailHTMLWrapper`.** Per CSS Overflow L3, when one axis is a scrolling value (hidden/scroll/auto) and the other is `visible`, the visible axis computes to **`auto`** — so `overflow-x: hidden` silently made html/body **Y-scroll containers**, and the late `deferredImageLoadJS` swap reflow left a stray `body.scrollTop` that WebKit doesn't re-clamp (oscillates `13 → 1` toward the `scrollHeight−clientHeight=1` clamp). **WebKit implements NO scroll anchoring / `overflow-anchor`** (bug 171099, still open) so that property is a no-op here — removing the scroll container is the only fix. **Fix A: `overflow-x: clip`** (NOT a scrolling value → no promotion → html/body never become scroll containers → the stray offset is structurally impossible). Belt-and-suspenders: `monitorHeightJS.pinBodyScroll()` resets ONLY `document.body.scrollTop` on image load (NEVER `documentElement`/`scrollingElement` — those mirror the native UIScrollView = pinch-zoom pan; `<!DOCTYPE html>` standards mode makes documentElement the viewport scroller, so body.scrollTop is always a safe inner reset). **Root cause B (the 1px double-scroll): the native WKWebView `UIScrollView` held ~1px of scrollable range** — `body.scrollHeight=1659` vs `clientHeight=1658` (a `SPAN` overflowing body by `+1px`), while the frame is `ceil(rect)=1658`, so the inner scroll view ate 1px before the gesture reached the parent SwiftUI ScrollView. **Fix B: zoom-aware inner-scroll lock** — `webView.scrollView.isScrollEnabled = false` (locks inner scroll at 1:1 so vertical drags pass straight to the parent) + a KVO on `scrollView.zoomScale` that re-enables it only while pinch-zoomed (`> 1.001`) so the user can pan magnified content. **`isScrollEnabled = false` does NOT disable pinch-zoom** (separate gesture recognizer — WebKit bug 234584); and **do NOT replace `scrollView.delegate`** to detect zoom (breaks WebKit's internal `viewForZooming` → kills zoom) — observe `zoomScale` via KVO instead.
