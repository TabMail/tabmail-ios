
### Email image aspect-ratio distortion — gated post-load correction (2026-06-26)
- **Symptom:** full-width images in rendered emails render too tall (vertical stretch). **Root cause:** the responsive-image CSS (`EmailHTMLWrapper.swift:230-231`) is `img { max-width: 100% }` + `img[width] { height: auto }` — `height:auto` is scoped to images that carry a `width` *attribute*. A sender that pins a fixed `height` (height attr or inline `height`) with fluid/capped width and NO `width` attr gets its width capped by `max-width:100%` on a phone while the height stays fixed → distortion. It is **fundamentally not CSS-fixable**: a `height="29"` logo (keep small) and a `height="300"` + `width:100%` hero (must scale) are *syntactically identical* — the only disambiguator is the true intrinsic aspect ratio, which (per the HTML spec's width/height→`aspect-ratio: auto w/h` mapping) the browser itself only knows after the image loads.
- **Fix = gated post-load JS correction** (`fixImgAspectFnJS` / `fixImageAspectRatioJS` in `AutoSizingHTMLView.swift`, registered after `heightMonitor`; `tmFixImgAspect(img)`). On each image's `load`, if `|renderedRatio − naturalRatio| / naturalRatio > 0.02` it sets **`height:auto !important` and NOTHING ELSE**. Two invariants make it safe and are the whole point:
  1. **Only ever touches `height`, never width** → the document's horizontal extent is unchanged, so `fitViewportJS`'s horizontal-overflow widen decision (the thing the logo-balloon regression feeds) can't be perturbed.
  2. **Gated on rendered-vs-natural ratio divergence** → a proportional logo (rendered ratio ≈ intrinsic) is left untouched and can never balloon to full container width (the exact regression the scoped CSS guarded against). `naturalWidth/Height` are EXIF-orientation-corrected by WebKit, so rotated photos compare correctly.
- **Why post-load and not render-time stamping:** remote images are deferred (`src`→`data-tmsrc`, loaded after first paint) and never downloaded in Swift, so their dimensions are unknowable until load — and the user's distorted full-width heroes are almost always remote CDN images. Render-time stamping in `BodyRenderer` would only help inline `cid:` images AND adds real surface (manual EXIF handling, NSE 24MB budget, regex img-tag matching) — deferred as a non-fix for the reported case. Post-load is the spec mechanism (browser switches to intrinsic ratio on load), not a band-aid.
- **Wiring caveat:** `monitorHeightJS`'s image listeners do `if (img.complete) continue` — a deferred remote `<img>` is `complete` (no src) at documentEnd, so it's skipped there. The aspect-fix script attaches its OWN non-`{once}` load listeners + re-scans (rAF + 1600ms, after `deferredImageLoadJS`'s 1500ms failsafe swap) so the swapped-in remote load is caught. It calls `window.__tmReportHeight()` after a correction so the webview frame resizes; idempotent via `img.__tmAspectFixed`.
- **Tests:** `ImageAspectRatioFixTests` (JSContext, mock `img`, same zero-drift pattern as `walkUpToWrapStart`) — distorted→corrected, logo/proportional/unloaded/zero-box→untouched, idempotent, + string-level guards that the production script never touches width. The pinned CSS test (`EmailRenderPipelineTests:imgHeightAutoScopedToWidthAttr`) is UNCHANGED — this fix is purely additive JS, the `img[width]` CSS stays.
- **Debug logging:** `tmFixImgAspect(img, log)` takes an optional `log` callback (no-op in prod/tests, same pattern as `walkUpToWrapStart`'s `logFn`); the production script injects a `DebugModeManager`-gated `[ImgAspect]` logger (mirrors `fitViewportJS`'s `log`, lands on the `consoleLog` handler). `fixImageAspectRatioJS` is therefore a computed `var` (not a `let`). Each line: `FIX|skip(reason) nat=WxH(ratio) render=WxH(ratio) div=N% attrW= attrH= <src-tail>`.
- **Validated on a real newsletter (2026-06-26, `logmain.log`):** the distorted images (div 15–23%) **carried BOTH `width` and `height` attributes** yet still rendered at their pinned height — i.e. `img[width]{height:auto}` (a non-`!important` stylesheet rule, spec 0,1,1) was being beaten by the sender's **inline `style="…height…"`** (spec 1,0,0,0). So the CSS rule was silently INEFFECTIVE for this whole class; the JS works only because it writes inline `height:auto !important`, the one thing that outranks an authored inline height. First scan logged all imgs `skip(unloaded nat=0x0)` (deferred remote not yet loaded → no premature fix), later scans fixed the distorted ones and `skip(already-fixed)` the rest (idempotency + load-listener wiring confirmed). Distortion (15–23%, +one 2.5%) vs proportional (0–1.2%) separated cleanly around the 2% gate — well-calibrated. NOTE: the `img[width]{height:auto}` CSS rule is doing less than its comment implies whenever inline height styles are present — the JS is the real fix.
