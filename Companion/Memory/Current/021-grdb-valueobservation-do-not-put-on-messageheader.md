
### GRDB ValueObservation — DO NOT put on `messageHeader`
- **NEVER** use `ValueObservation` to drive the inbox list off the `messageHeader` table. `messageHeader` is written on every sync commit, every AI field update (`actionTag`, `summary`), every unread recount, every backfill batch. A row-level observation would re-emit on every one of those writes, causing full list re-fetch + diff + @Observable invalidation + SwiftUI re-render many times per second during sync bursts. This is strictly worse than the current design.
- **Current design is load-bearing and correct:** explicit `.inboxDataDidChange` notifications fire at deliberate checkpoints; the observer has a 500ms throttle + dirty-bit coalescer; AI updates route through `.messageDataDidChange` into `flushAIBatch` (per-row in-place snapshot replacement, no full reload).
- **`ValueObservation` IS appropriate for `folder` table** — small set (5–50 rows), rarely changes (only at startup classification and folder add/remove), cheap per emission. `InboxViewModel.startFolderObservation()` uses it to drive `VM.folders` authoritatively; dedup on `(id, role)` keeps `unreadCount` churn from reaching the sink.
- `NavigationStore.outboxMessages` correctly uses `ValueObservation` on the outbox table — small set, user-driven writes only.
- Rule of thumb: `ValueObservation` is only OK on tables where write frequency is low (user-initiated, not sync-driven) AND the tracked set is small.
- **The `messageHeader` exception (2026-11-15): the shown chat's summaries** (`ChatSummaryState.changes`, ADR-IOS-114 decision 9). It observes only the members of the one chat on screen, by primary key, and selects only `bodyComplete`, `summaryBlurb` and `summaryTextMessage`, with `removeDuplicates`. GRDB still re-runs the small fetch on a reader after every commit that writes those columns anywhere in the table, but only a real change of that chat's rows reaches the main actor, and the observation runs only while a chat is shown. It does not drive a list: a change only asks the AI queue for that row's summary. Do not widen it to the inbox list or to more columns.
- **REMOVED 2026-11-27: the Sending bubble no longer reads `messageHeader`.** `ChatUnsentReply.changes` observes the outbox (and the AI cache for the summary) only. The `filed` count below is gone: a send's bubble now follows its email by the filing's posted move (`MailPointerMove.sent`, `.mailPointersMoved`) and stays, "Sent", until the chat shows the copy (`ChatSendBubbles`, ADR-IOS-114 decision 10, 2026-11-27 amendment). The count also raced the move: the reload it triggered could draw the copy beside a bubble that did not point at it yet, so the words showed twice. Do not bring a `messageHeader` read back into this observation. The earlier text, kept as history:
- *(Superseded 2026-11-27.)* **A second, short-lived `messageHeader` read: the chat's Sending bubble** (`ChatUnsentReply.changes`, ADR-IOS-114 decision 10). It observes the outbox; only while a sent row waits for its Sent copy does each fetch also count, by account and Message-ID, the headers that carry the row's `sentMessageId` (`filed`). While that lasts, GRDB re-runs the small fetch after every commit to `messageHeader`; the read is one indexed count per waiting row, `removeDuplicates` keeps unchanged results off the main actor, and the count stops being read once the Sent copy joins the chat, normally seconds after the send. Removing `filed` would bring back the moment when neither the bubble nor the Sent copy shows. Do not add more `messageHeader` reads to this observation.
- **A third, short-lived `messageHeader` read: a new email's send follow** (`ChatNewEmailSend.changes`, ADR-IOS-114 decision 24). After a new email's chat sends, it observes that send's outbox row and reads the email's Sent copy by folder and Message-ID (`messageHeader_rfc822MessageId`, one indexed row), with `removeDuplicates`, so GRDB re-runs it after every commit to `messageHeader` while it lasts. It lasts only until the chat becomes the sent email's thread: the view's `.task(id:)` is keyed to the send only while `threadId` is nil, so either swap to the thread cancels the task and the observation with it (`ChatNewThreadScreenTests.threadEndsTheSendFollow` counts the read before and after). Do not key it to the send alone, and do not add more `messageHeader` reads to it.
