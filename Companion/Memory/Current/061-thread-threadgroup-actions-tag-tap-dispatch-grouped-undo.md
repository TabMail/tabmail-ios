
### Thread (ThreadGroup) Actions — tag-tap dispatch & grouped undo
- A collapsed thread row's badge shows `group.threadTag` = the **highest-priority** tag across all members (`reply`＞`none`＞`archive`＞`delete` by `ActionTag.sortOrder`, computed in `ThreadGroupBuilder.buildDisplayGroups`). This can differ from the representative/head message's own `actionTag`.
- **`InboxView.executeTaggedAction` MUST act on `group.threadTag` for a collapsed thread, NOT `snapshot.actionTag`.** The `snapshot` arg is `group.representative` (the most-recent/head message); using its tag was a bug — tapping a surfaced "reply" badge archived the whole thread when the head happened to be tagged archive. Single messages and expanded-thread child rows still use `snapshot.actionTag`. The `.reply` case targets `snapshot.id` (the head = most recent), which is the intended reply target.
- **A thread can span ACCOUNTS (2026-11-22, #1274).** The unified inbox groups one conversation that reached several of the user's accounts, so a thread gesture never takes a destination from one member's account. `archiveThread`/`deleteThread` resolve each member's OWN account's role folder (`InboxViewModel.roleFolderMoves`) and record each account's read-then-move as its own calls (`markRead` and `move` write every account they are given in ONE transaction, so a shared call would let one account's refused insert roll back another's; two accounts can both call the folder "Archive"); `moveThread` takes the picker's `accountId` and reports members of other accounts skipped (a message cannot move between accounts), and also a member already in the chosen folder (`move` drops it as a no-op; in the Undo it would get a same-folder reverse move). The one undo entry is built with `UndoableAction(moves:timestamp:)`, which makes one `UndoAccountCommand` per account, destination and source folder, because `AccountManager.undoMove` refuses a command whose members differ in any of those. `undoMove` restores or refuses each command whole, so `UndoService` decides the notice after the LAST command: "Nothing was moved back." when none came back, "Some messages were not moved back." when others did. Before this, an Outlook member of a thread whose first member was on Gmail was queued to Gmail's `__GMAIL_ALL_MAIL__`, a path Outlook has no folder for, and Undo refused the whole thread. ADR-IOS-058 had fixed the same defect on the journal; the v3 undo rewrite (`UndoAccountCommand`, single command) brought it back. Tests: `InboxThreadAcrossAccountsTests`.
- **All multi-message thread actions push ONE grouped `UndoableAction`** carrying every member, so the whole thread restores in a single undo: `archiveThread` / `deleteThread` / `moveThread` in `InboxViewModel`. `UndoService.undo` runs one `AccountManager.undoMove` per `UndoAccountCommand` of the entry (one per account, destination and source folder; see the bullet above), each admitted on its own: a never-attempted forward is cancelled, an attempted one gets one reverse move. (Before the v3 undo rewrite this was one write txn + one move-back op through `undoDestructiveAction`.) When adding a new whole-thread action, mirror this pattern — never loop a per-message action (that yields N undo entries). Move was the last gap; fixed via `moveThread` + `moveThreadGroup` sheet state (collapsed-thread Move swipe). Expanded-thread child actions stay per-message by design.
- **`InboxView.body` is at the SwiftUI type-checker limit.** Adding another `.sheet`/`.fullScreenCover` modifier triggers "unable to type-check this expression in reasonable time" (error points at an *unrelated* existing modifier). Fold new sheet content into the existing sheet via a `@ViewBuilder` computed property (e.g. `moveSheetContent`) and extract closures into private methods — don't append more top-level modifiers to `body`.
- **`expandedThreads` is pruned in `rebuildDisplayGroups()` (2026-06-09).** Only the head-row swipe/chip paths call `evictAndRebuild` (which removes the group id); every OTHER removal pathway (expanded-child swipe/chip, detail-view archive/delete via `.messageDismissedFromDetail`, agent tools, sync from another device) shrinks the thread without touching `expandedThreads`. A stale id on a group that dropped to `memberCount == 1` permanently painted `Color(.tertiarySystemFill)` listRowBackground (reads as a stuck selection highlight) + hidden separators on the remaining row, with no chevron to clear it (`MessageRowView` renders the toggle only for `isThread`). The prune intersects `expandedThreads` with the rebuilt multi-member group ids — the rebuild choke point covers all pathways. Rule: any UI state keyed by ThreadGroup id must be pruned/validated in `rebuildDisplayGroups`, not at individual call sites. Tests: `InboxViewModelThreadEvictTests` (`childRemovalPrunesExpandedThreads`, `threadRemovalPrunesExpandedThreads`, `survivingThreadKeepsExpansion`).
