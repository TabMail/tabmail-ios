
### Swift Gotchas
- `ActionTag.none` must be fully qualified in `ActionTag?` contexts — bare `.none` resolves to `Optional.none` (nil)
- **`\u{XXXX}` is NOT a valid escape in an ICU regex pattern — use `\x{XXXX}` (or a literal char).** A Swift *raw* string `#"...\u{2014}..."#` passes the literal bytes `\u{2014}` to `String.replacingOccurrences(of:options:.regularExpression)` (ICU); ICU's only code-point escapes are `\uHHHH` (exactly 4 hex, no braces), `\x{H...}`, `\UHHHHHHHH`. So `\u{...}` matches nothing and the replace is a **silent no-op** — no error, just doesn't fire. This is why `AIService.normalizeUnicode` (AIHelpers.swift) had **never** normalized dashes, smart quotes, or special spaces (only NFKC + the plain-string `\u{3010}`/`\u{2026}` replaces worked; no test asserted the regex passes, so it went unnoticed). Fixed 2026-06-28 by switching all three character classes to `\x{...}`; verified with standalone `swift`. If you write a regex character class of code points, use `\x{...}` and add an assertion that the substitution actually changes the input.
- **Dash normalization is line-start-only (parity with TB `normalizeUnicode`).** `normalizeUnicode` converts dashes (en/em/figure/horizontal-bar/minus) to ASCII `-` **only** at the start of a line — regex `(^|\n)([ \t]*)[\x{2010}…\x{2212}]` → `$1$2-` (indentation preserved). Reason: LLMs emit en/em-dash list bullets (`– item`) that the summary/action/KB parsers need as `- item`; an **inline** em-dash (prose punctuation, ranges like `10–20`) is deliberately preserved so real typography survives. Mirrors `tabmail-thunderbird/agent/modules/utils.js`. **Compose/reply text is intentionally NOT run through `normalizeUnicode` on iOS** (see `AIReply`): unlike TB there is no inline-autocomplete diff to keep ASCII-clean, and email is sent as HTML, so the model's real typography should reach the recipient.
