
### GRDB Persistence
- All persistence via GRDB `DatabasePool` (`AppDatabase.swift`) — thread-safe concurrent readers, serialized writers via WAL journal mode
- `dbPool.write { db in ... }` for mutations, `dbPool.read { db in ... }` for queries
- **`read`/`write` overload selection depends on the closure's return type being `Sendable`.** `try await dbPool.read { ... }` only picks the *async* (non-blocking) overload when the closure returns a `Sendable` value. Returning a non-`Sendable` type — most commonly `[Row]` (GRDB `Row` is not `Sendable`) — silently falls back to the *synchronous, thread-blocking* overload, which surfaces as the compiler warning `no 'async' operations occur within 'await' expression` AND violates the never-block rule. **Fix: map to a `Sendable` type inside the closure** (e.g. `try Row.fetchAll(db, sql: …).map { $0["id"] as String }` → `[String]`) so the async overload is chosen. Do NOT "fix" the warning by deleting `await` — that keeps the blocking overload. (Cleared 4 such sites 2026-06-12.)
- No background `DispatchQueue` needed — GRDB handles thread safety internally
- **`journal_size_limit` is ALREADY 32768 (32 KB) on a WAL `DatabasePool` — do NOT add a `PRAGMA journal_size_limit` "cap" thinking the residual WAL is unbounded.** SQLite's *raw* default is `-1` (unbounded), but Apple's system libsqlite3 (what GRDB uses on iOS; GRDB's own source sets it nowhere) defaults it to 32768 for WAL. So after every passive checkpoint the WAL is already truncated to 32 KB — there is no "unbounded residual WAL" problem to fix. Raising it (e.g. to 16 MB) makes the post-checkpoint residual *larger*, and `journal_size_limit` never bounds growth *during* checkpoint starvation (long-lived readers) anyway — only the residual after a successful reset. Verified empirically 2026-06-13 (a WAL pool with no custom config reads back `PRAGMA journal_size_limit = 32768`). This killed a proposed PLAN_HANG_FIX follow-up; the warm-foreground hang is addressed by the async-read work, not by WAL-size knobs.
- Stale detection runs for **all folders including inbox** — `MessageAICache` preserves AI state for re-inserted messages
- `NavigationStore` provides reactive UI updates (replaces SwiftUI `@Query`)
- **Startup gating is two-phase + migration-splash is conditional (`AppStartup`, PLAN_HANG_FIX).** DB build runs OFF `TabMailApp.init` because the O(mailbox-size) thread-repair migrations (v9/v27/v47/v53/v54) + one-time destructive resets can take minutes after a multi-version jump (the "hang on boot"). `AppStartup.runIfNeeded` runs: **Phase 1** `AppDatabase.makePool()` (opens the pool, NO migrations) → `AppDatabase.hasPendingMigrationWork(_:)` (cheap, read-only: migrator's applied set + `StartupMigrations.allResetsComplete`); **Phase 2** `AppDatabase(pool:runStartupResets:true)` (runs migrations + resets) then the DB-dependent launch steps, then `isReady`. The `SplashView(mode: .migrating)` "Updating…" screen shows **only** when `hasPendingMigrationWork && dbExisted` (the file pre-existed the launch) — i.e. real, possibly-slow work on an existing mailbox. The common path (already-migrated DB) and fresh installs (empty DB migrates instantly) stay on a **blank `Color(.systemBackground)` screen matching the empty `UILaunchScreen`** until `isReady` flips straight to the inbox — no per-launch "Updating…" flash. `dbExisted` MUST be sampled before `makePool()` (which creates the file). `AppDatabase()` no-arg init was removed; production builds via `makePool()` + the designated `init(pool:runStartupResets:)`; the test/preview `init(dbPool:)` is now a convenience → `runStartupResets:false` (never touches global UserDefaults flags / FTS dir). `StartupMigrations.resetFlagKeys` is the single source of truth for the 4 reset flags (pinned by a test).
- **The DB build MUST be triggered from a path that runs on EVERY launch — NOT only `body.task`.** A cold BACKGROUND launch of a terminated app (silent push / BGTask / background notification action) does NOT run the SwiftUI `WindowGroup` body / `.task` / `.onAppear` until foregrounded (documented lifecycle) — so a `body.task`-only trigger left `AppDatabase.shared` nil on those launches → BGTask handlers crashed on the `AppDatabase.dbPool` force-unwrap, and push/notification-action handlers hung on `awaitReady()` (dropping the user's action). Fix: `ensureDatabaseReady()` is navigationStore-free and kicked off from `AppDelegate.didFinishLaunchingWithOptions` (always runs) AND `body.task` (foreground, which adds the sidebar load + `isReady`); `awaitReady()` self-bootstraps it. `dbReady` (DB usable) is the gate background paths await; `isReady` (DB + sidebar) is the UI-only gate and is never set on a pure background launch. **EVERY background entry point that touches `AppDatabase.dbPool` MUST `await AppStartup.shared.awaitReady()` first** — both `SyncScheduler` BGTask handlers (`handleBackgroundSync`/`handleBackgroundAIProcessing`) and the AppDelegate push/notification handlers do. Pre-gating this was free because the DB was built in `TabMailApp.init` (always runs); don't reintroduce a view-lifecycle-only trigger.
  - **2026-06-15: the APNs device-TOKEN path was a GAP (boot crash).** `AppDelegate.didRegisterForRemoteNotificationsWithDeviceToken` → `PushNotificationService.didReceiveDeviceToken` → `registerDeviceWithWorker` touched `dbPool` (line ~141) with NO readiness gate. After an app update (migrations delay the DB build), APNs delivered the token before the pool existed → `AppDatabase.dbPool` force-unwrap (`shared.withLock { $0!.dbPool }`) → `EXC_BREAKPOINT` crash on the first boot(s), then it stopped once migrations finished (and a debugger's timing hid it). Fixed by `await AppStartup.shared.awaitReady()` inside `registerDeviceWithWorker`, after the no-session/no-token early returns and before the first `dbPool` access. Lesson: the "push/notification handlers gate" claim covered the *received-notification* callbacks, NOT the *device-token registration* callback — audit every APNs/AppDelegate entry independently.
