
### FTS↔GRDB id drift (folder baked into the key) — "indexed but unfindable" / wrong-subject class
- **The FTS `headerId` IS the GRDB `MessageHeader.id` = `"accountId:folderPath:messageId"` — it embeds the folder.** So ANY folder move re-keys the GRDB header and the FTS entry MUST be re-keyed in lockstep or it drifts: search/AI/embedding re-hydration does `MessageHeader.fetchOne(key: ftsHeaderId)` and **silently drops** the hit on a miss (`compactMap` → nil). Confirmed real: Gmail archive (INBOX→`__GMAIL_ALL_MAIL__`) and trash (→`TRASH`) left stale `:INBOX:` FTS entries.
- **Drift SOURCE fixed (`SyncEngineDeltaSync` Gmail delta, ~line 168):** the label-removed branch did `existing.delete(db)` (header left a folder) WITHOUT `removeHeadersFromFTS` — unlike the messages-deleted path. Now threads `removedIds` out of the write and calls `removeHeadersFromFTS`. Other delete-and-reinsert edges still leak (Gmail/Exchange optimistic-sent dedup, `DraftStore` placeholder→real migration) — catch via reconciliation.
- **Drift HEAL on access (`ftsResultsToSearchResults`):** exact `fetchOne(key:)` miss → recover by `(accountId, messageId)` and `SearchIndex.rekeyHeaders` the stale entry to the current id (+ `updateFolderIds`). Repairs the INDEX so the fix propagates to ALL consumers, not just search. Gated to **Gmail/Graph** (move-stable, globally-unique messageId); IMAP UID is unsafe to recover by (changes on move, repeats across folders) → owned by sync-side re-key + source fix. Log: `healedDrift=N`.
- Proper-but-deferred fix = key GRDB+FTS on a move-stable id (`stableId`/rfc822) so folder is a plain mutable column (big 253k-row migration). Recommended central heal = make `pruneFTSOrphans` RE-KEY (not just delete) and run recurring (currently one-shot via `ftsReconcileDoneKey`). Distinct from the EXISTING `staleCorrections` path, which only fixes `meta.folderId` for the orphan-reclaim case where the id still resolves.
- **Search-all fan-out**: Gmail/Outlook accounts get ONE account-wide search (`folder: ""` — Gmail omits labelIds, Graph hits `/me/messages`; both exclude spam/trash by default). Per-folder fan-out is IMAP-only (no account-wide IMAP SEARCH). Per-folder Graph fan-out trips the MailboxConcurrency throttle (429) — don't reintroduce it.
- The per-folder remote fan-out runs as child tasks whose cancellation is propagated manually from `searchTask` (the Swift 6 region-isolation checker rejects `group.addTask` closures capturing a SwiftUI view). Cancelled/failed/timed-out folder searches resolve as empty results; whatever completed is merged.
- `triggerRemoteSearch` bumps `searchGeneration` so a re-submit of the same query invalidates the previous wave (otherwise stale children corrupt the `pendingAccounts` counter).
