
### IMAP Folder Role Detection & Dedup (iCloud "Trash" + "Deleted Messages")
- `IMAPProvider.mapRole(attributes:name:)` returns a single role per folder via SPECIAL-USE first, then a name-based fallback. Both "Trash" and "Deleted Messages" match the trash heuristic — without dedup, iCloud accounts ended up with two `.trash` folders (and a confusing/empty unified Trash view).
- `IMAPProvider.dedupRoles(_:)` runs at the end of `fetchFolders()` and demotes losers to `.custom`. Tiebreak: SPECIAL-USE flag first, then `canonicalNameRank` (the position in the canonical-name list — lower wins), then shorter name.
- `fullSync` deliberately does NOT update `role` on existing folders (it only refreshes `name`/`totalCount`/`uidNext`). This protects user manual reassignments — but it also means existing duplicate state needs a one-shot migration.
- Migration `v48_dedupFolderRoles` in `AppDatabase.swift` mirrors the same canonical-name preference (no SPECIAL-USE info on disk) and runs once to heal pre-fix accounts.
- **The name fallback matches a folder directly under INBOX or the personal-namespace prefix (tabmail-ios #533, 2026-11-12).** `mapRole(attributes:name:delimiter:namespacePrefix:)` and `canonicalNameRank(_:role:delimiter:namespacePrefix:)` compare `IMAPProvider.roleMatchName`: the name with a leading `INBOX`+delimiter (case-insensitive) or the NAMESPACE personal prefix removed, otherwise the WHOLE name. So `INBOX.Sent` / `INBOX/Sent Items` on a server with no attributes is Sent, while a role name under a user folder (`Clients/Sent`, `Projects/Trash`, `Work/Archive`) is always `.custom`, even with no top-level folder for that role and even against a less canonical top-level alias (`Sent Messages`, `Deleted Items`). INBOX matches only as the whole name (`Old/INBOX` is custom). A special-use attribute still decides wherever the folder sits. (History: commit 1 of #533 matched the LAST segment; review round 1 found nested user folders taking roles, e.g. `Clients/Sent` beating `Sent Messages`, and it was narrowed to this rule, which keeps the pre-#533 whole-name behaviour for every non-INBOX nesting.)
- **One source of server-side roles: `IMAPProvider.discoveredRoles(_:namespacePrefix:)`.** Selectable mailboxes → `mapRole` → `dedupRoles(_:namespacePrefix:)` → `[path: FolderRole]`. `fetchFolders` and `sentFolderPathCreatingIfNone` both call it, so the folder sync and the pre-CREATE check cannot disagree about which folder is Sent.
- **Special-use attributes come from `LIST ... RETURN (SPECIAL-USE)` when advertised (#533).** A plain LIST may omit them (RFC 6154 §2 "MAY"). `IMAPProvider.listMailboxesWithSpecialUse` runs the plain listing, then `CAPABILITY`, then — only if BOTH `SPECIAL-USE` and `LIST-EXTENDED` are advertised — the fork's `listSpecialUseMailboxes()`, merging attributes by name. The RETURN option belongs to the extended LIST (RFC 5258) and RFC 6154 never says `SPECIAL-USE` implies it (erratum 5581); a server that answered it BAD would fail every folder sync (a real precedent: Gmail answered `BAD Could not parse command`, though it did not advertise SPECIAL-USE then). Without both, the plain listing is used as is, and the fork keeps any special-use attributes the server puts on a plain LIST reply (one attribute converter for every LIST, `Mailbox.Info.Attributes.init(from:)`). Never call that fork method on a server without `SPECIAL-USE`: it falls back to substring guesses ("Consent Forms" would become Sent). Test: `IMAPFolderRoleDiscoveryTests.specialUseWithoutListExtendedUsesPlainList` (the fake answers a RETURN option BAD without `LIST-EXTENDED`).
- **No Sent folder at all ⇒ IMAP creates "Sent" (owner ruling, #533).** When the account has no local `.sent` row, `AccountManagerOutbox.attemptSentAppend` passes `sentFolderPath: nil` to `EmailProvider.appendToSentFolder`. `IMAPProvider.sentFolderPathCreatingIfNone` then ASKS THE SERVER first (`listMailboxesWithSpecialUse` + `discoveredRoles`), because local rows can be stale: `fullSync` never rewrites a stored role, so an existing account's real Sent folder (`INBOX.Sent Items`, a RETURN-only `\Sent`) may still be `.custom`, and the first send can precede the first folder sync. A Sent folder found there takes the copy, with no CREATE. Only when the server has none (no special-use `\Sent`, no Sent name) does it CREATE `IMAPProvider.createdSentFolderName` ("Sent"), unresolved; the fork's `createMailbox`/SELECT/APPEND resolve it into the personal namespace (`INBOX.Sent` under an `INBOX.` prefix), and appends there. A refused CREATE is ignored (usually the folder already exists); the APPEND's SELECT is the authority, and on failure the copy stays owed (`appendedToSent == false`) and is retried by the next drain. The old "no Sent folder ⇒ mark appended without a copy" arm is gone. Gmail/Exchange ignore the nil path (their APIs save the copy). The next folder sync gives the new folder the Sent role by name. Tests: `OutboxSentFolderCreationTests` (FakeIMAPServer `requireExistingMailboxes()` + CREATE).
- UI: `AccountDetailView`'s "Folder Roles" section shows ALL folders for a role (joined) plus a `exclamationmark.triangle` warning icon when >1 — surfaces edge cases the migration didn't catch.
