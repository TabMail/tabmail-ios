
### IMAP Folder Role Detection & Dedup (iCloud "Trash" + "Deleted Messages")
- `IMAPProvider.mapRole(attributes:name:)` returns a single role per folder via SPECIAL-USE first, then a name-based fallback. Both "Trash" and "Deleted Messages" match the trash heuristic — without dedup, iCloud accounts ended up with two `.trash` folders (and a confusing/empty unified Trash view).
- `IMAPProvider.dedupRoles(_:)` runs at the end of `fetchFolders()` and demotes losers to `.custom`. Tiebreak: SPECIAL-USE flag first, then `canonicalNameRank` (the position in the canonical-name list — lower wins), then shorter name.
- `fullSync` deliberately does NOT update `role` on existing folders (it only refreshes `name`/`totalCount`/`uidNext`). This protects user manual reassignments — but it also means existing duplicate state needs a one-shot migration.
- Migration `v48_dedupFolderRoles` in `AppDatabase.swift` mirrors the same canonical-name preference (no SPECIAL-USE info on disk) and runs once to heal pre-fix accounts.
- **The name fallback matches the LEAF, not the full path (tabmail-ios #533, 2026-11-11).** `mapRole(attributes:name:delimiter:)` and `canonicalNameRank(_:role:delimiter:)` compare the last segment after the server's hierarchy delimiter, so `INBOX.Sent` on a server with no attributes is Sent. INBOX matches only as the whole name (`Old/INBOX` is custom). A nested `Clients/Sent` next to a top-level `Sent` loses dedup on the shorter-name tiebreak; with NO top-level folder for a role, a nested folder whose leaf is a role name now gets the role.
- **Special-use attributes come from `LIST ... RETURN (SPECIAL-USE)` when advertised (#533).** A plain LIST may omit them (RFC 6154 §2 "MAY"). `IMAPProvider.listMailboxesWithSpecialUse` runs the plain listing, then `CAPABILITY`, then — only if `SPECIAL-USE` is advertised — the fork's `listSpecialUseMailboxes()`, merging attributes by name. Never call that fork method on a server without the capability: it falls back to substring guesses ("Consent Forms" would become Sent).
- **No Sent folder at all ⇒ IMAP creates "Sent" (owner ruling, #533).** When no folder gets the Sent role (no SPECIAL-USE `\Sent`, no English name), `AccountManagerOutbox.attemptSentAppend` passes `sentFolderPath: nil` to `EmailProvider.appendToSentFolder`; `IMAPProvider.sentFolderPathCreatingIfNone` CREATEs `IMAPProvider.createdSentFolderName` ("Sent") in the personal namespace (`INBOX.Sent` under an `INBOX.` prefix) and appends there. A refused CREATE is ignored (usually the folder already exists); the APPEND's SELECT is the authority, and on failure the copy stays owed (`appendedToSent == false`) and is retried by the next drain. The old "no Sent folder ⇒ mark appended without a copy" arm is gone. Gmail/Exchange ignore the nil path (their APIs save the copy). The next folder sync gives the new folder the Sent role by name. Tests: `OutboxSentFolderCreationTests` (FakeIMAPServer `requireExistingMailboxes()` + CREATE).
- UI: `AccountDetailView`'s "Folder Roles" section shows ALL folders for a role (joined) plus a `exclamationmark.triangle` warning icon when >1 — surfaces edge cases the migration didn't catch.
