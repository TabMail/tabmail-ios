
## OAuth / Google Cloud

- **iOS OAuth client ID**: iOS type, bundle ID `ai.tabmail.ios`, stored in `Secrets.xcconfig`
- **Credentials flow**: `Secrets.xcconfig` → loaded via `project.yml` configFiles → exposed in `Info.plist` → read at runtime by `OAuthConfig` in `GoogleAuthService.swift`
- Shares GCP project with Thunderbird (see `../PROJECT_MEMORY.md` for GCP details)
- **Merged OAuth flow (single prompt)**: Google/Microsoft sign-in uses direct OAuth → `signInWithIdToken` → auto-create email account. Google requires adding the iOS `GOOGLE_CLIENT_ID` as an Additional Client ID in Supabase dashboard (Auth → Providers → Google). Microsoft needs no extra setup — same application ID across platforms. See `SETUP.md` for details.
- **Account-add UI lag — refresh NavigationStore BEFORE navigating away from the add screen (fixed 2026-06-25). Affects BOTH the onboarding router AND Settings → Add Account.** Shared root cause: `navigationStore.accounts` is repopulated only ~100ms after an add, via the **debounced** `.backgroundDataDidChange` listener in `NavigationStore.loadInitialData` (100ms `Task.sleep` — debounced to coalesce sync-burst notifications; do NOT remove it, the fix is view-side). All `add…` functions in `AccountManagerSetup.swift` `await dbPool.write` (committed) BEFORE `return account`, so an *immediate* `await navigationStore.refresh()` (the RenderGate-free `refreshNow`) right after the add reliably reads the new row.
  - **Onboarding (`RootView.routedContent`):** the `if/else` chain re-evaluates synchronously the moment `PendingAccountAdd.shared.clear()` runs; in the 100ms gap it falls through to `else if navigationStore.accounts.isEmpty { AddAccountGeneralView() }`, briefly **flashing the generic "Add Account" screen** before the next gate (AI consent). Fix: `RootView.finishPendingAccountAdd()` = `await refresh()` *then* `withAnimation { clear() }`. `pending` stays non-nil across the `await`, so the router keeps showing the add gate (no premature flash) until accounts is populated. Both the iCloud `onConnected` closure and `commitGmailOutlookAdd` route through it. `AddAccountICloudView.onConnected` was made `() async -> Void` so the Connect spinner stays up until the screen actually changes.
  - **Settings (`AddAccountGeneralView` pushed from `SettingsView` via `NavigationLink`):** on success each handler `dismiss()`ed back to the `ForEach(navigationStore.accounts)` list — which was still stale for 100ms, so the new account wasn't there on return ("blink, nothing happened"). Fix: `AddAccountGeneralView.finishAddAndDismiss()` = `await navigationStore.refresh()` *then* `dismiss()`; all four handlers (gmail/outlook/icloud/imap) route through it. Required injecting `@Environment(NavigationStore.self)` — its preview (`AddAccountGeneralView+Preview.swift`) now injects a bare `NavigationStore()` or it crashes (non-optional env). NB `dismiss()` is a harmless no-op when this view is the onboarding `RootView:159` branch (not presented); the refresh re-routes RootView forward there too.
  - **Rule: any account-add success path MUST refresh the nav store BEFORE navigating away (route through `finishPendingAccountAdd` / `finishAddAndDismiss`).** A more systemic alternative (a non-debounced `.accountsDidChange` for structural account add/remove) was considered but declined — it risks the sync-burst coalescing the debounce exists for.
  - Note `.calendarOnly` legitimately keeps `accounts` empty (calendar accounts filtered out of `sidebarRequest`: `isActive && !calendarOnly`) → it correctly proceeds to `AddAccountGeneralView` for email setup; that is NOT the bug.
  - **iCloud CalDAV-failure handling (fixed 2026-06-25, same work).** `addICloudAccount` commits the email account + registers its provider BEFORE `setupCalDAV`, which can throw. Old behavior: the whole add threw → email account stranded behind a "failed" message (and the onboarding form has no Mail-only option, so a transient CalDAV hiccup could block iCloud Mail entirely). Now:
    - **`addICloudAccount`** — calendar is **best-effort**: a CalDAV failure is caught, the email account is kept, and the failure is *recorded* on the account via a new persisted `Account.calendarSetupFailed: Bool` column (migration **`v61_addCalendarSetupFailedToAccount`**, additive, default false). The catch sets it in-memory (returned account → drives the alert) AND `UPDATE account SET calendarSetupFailed = 1` (row → drives the Settings note); write failure is debug-logged, in-memory flag still shows the alert.
    - **Surfacing** — both add screens read `account.calendarSetupFailed` after the add: if true they show a single-button **`.alert("Calendar Not Connected") { Button("Continue") }`** whose Continue proceeds (onConnected / finishAddAndDismiss); else they navigate immediately. Persistent indicator: **`SettingsView` account row shows a `Label("Calendar not connected", systemImage: "calendar.badge.exclamationmark")` in `.orange` below the "Primary" tag** whenever `account.calendarSetupFailed`.
    - **`addCalDAVAccount`** (calendar-only) stays **atomic** — rolls back the synthetic account on CalDAV failure (calendar IS the account there; no email to keep). `setupCalDAV` self-cleans its Keychain entry on failure (config.id is a fresh UUID, unreachable by `removeAccount` cleanup).
    - **Dead code removed (was audit finding F1):** `AddAccountGeneralView.connectICloud`'s `catch CalDAVError.authFailed` (unreachable once `addICloudAccount` swallows CalDAV errors). The same catch in `AddAccountICloudView` is KEPT — still reachable via the `.calendarOnly` → `addCalDAVAccount` (rethrows) path.
    - **Not built (follow-up):** nothing CLEARS `calendarSetupFailed` (no retry-calendar UI); since `addICloudAccount` has no dedup, re-adding makes a fresh row (flag false) and leaves the old flagged duplicate. A "Reconnect Calendar" action in `AccountDetailView` (set flag false on `setupCalDAV` success) is the clean fix.
