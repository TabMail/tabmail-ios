- **Mark-read-on-archive/delete composition pattern (feature, 2026-07-15; Undo/invalidation amended 2026-07-29).** `AccountManager.markReadOnArchiveDeleteKey` defaults ON via the missing-key idiom (`object(forKey:) == nil → true`, same as `ProactiveNotifyService.isEnabled`; `@AppStorage(... ) = true` mirrors it in Settings). Every archive/delete origin composes a plain `.isRead(true)` journal record immediately before `.move`, so the fold executes reads before moves and unread counts change once. Reversible Inbox, Detail, and Settings bulk producers capture unread restoration as exact per-account `(hybrid member identity, original header id)` ownership only for members this action actually changed. Undo resolves through the existing identity/location guards, records ordinary `.isRead(false)` for owned members, then issues the inverse move. A later accepted or retry-owned ordinary in-app read-state action removes matching older ownership while preserving the move Undo; automatic reads and Undo inverses do not self-invalidate. The map is process-local and member-scan-free and adds no SQL, schema, durable payload, provider branch, or new identity system. Tools and notifications remain outside the UI-local invalidation protocol. `IOS-UNDO-001` accepts rare notification overlap and rapid read→unread→archive fold-order overlap rather than adding a per-identity event ledger. Tests control the setting through the `AccountManager` instance resolver seam, never `UserDefaults.standard` (cross-suite parallel-run race — `.serialized` does not cross suites).

## Intention queue V2 — authoritative current direction (ADR-IOS-060, 2026-07-13)

- **One global durable message-action FIFO.** `PendingOperation` jobs embed account/folder/message command data and execute exactly one at a time in SQLite insertion order. No per-account drains, connected-component lanes, or parallel provider mutation. One offline/throttled account blocking later accounts is accepted in exchange for a single serial model. `OutboxMessage` and calendar remain separate queues.
- **Round C's shared mutation primitive is cancellation-safe at the ownership handoff (2026-07-14).** `PendingOperationMutationGate` uses `Synchronization.Mutex`, one in-memory owner UUID, and FIFO continuation waiters. Cancelling while queued removes the waiter synchronously; cancelling after release transfers ownership but before the waiter resumes reclaims that exact owner and advances the next waiter. `acquire()` returns an opaque in-memory lease and synchronous `release(lease)` accepts only that owner, so stale/double release cannot free a successor. Release is installed in `defer` immediately. The UUID/lease never persists and has no Undo/identity meaning. Never hold the permit across provider I/O, callbacks, sleeps, or retry delays. The primitive exists and is tested; durable writer/drain wiring proceeds in later Round C checkpoints.
- **RFC-first HYBRID operation identity (amended 2026-07-14, PLAN_IDENTITY_HYBRID — supersedes the universal-RFC refusal below).** Members are classified by shape via `MessageIdentity.durableMemberKind`: RFC members resolve exactly as described in the next bullet; identity-less/malformed messages admit their provider ID as an opaque TOKEN member resolved by exact provider-ID fetch + source-membership verification inside each adapter's `resolveTokenMember` (Gmail exact GET + action-scope labels; Exchange exact GET + `parentFolderId`, 404/410/`ErrorInvalidIdMalformed` = stale; IMAP canonical `UInt32` exact `UID FETCH` in the recorded source mailbox). Tail members get released-level semantics: Exchange/IMAP undo after ID churn is a stale no-op; IMAP token moves skip the rfc822 destination probe/post-verify; sibling expansion never applies to tokens. Sync protection is permanently two-key (`containsAnyKey`: provider `messageId` leg + normalized RFC leg). The finite B3 converter, its startup gate, `resolveLegacyMessageActionIdentity`, and `LegacyMessageActionIdentityResolution` are DELETED — released bare provider-ID rows are tail members by construction and drain through the token path directly.
- **Universal RFC operation identity (historical framing; RFC leg still accurate).** Every Gmail, Exchange, and IMAP durable message-action member uses normalized `rfc822MessageId`; account + recorded source folder scope the lookup. Gmail resolves through `rfc822msgid:` to its current resource ID, Exchange resolves Graph `internetMessageId` to the current resource ID, and IMAP resolves `Message-ID` to the current UID. Exactly one authoritative source match mutates; zero/multiple no-op; failed lookup retries. Provider IDs remain transient for sync/fetch/draft/outbox/APNs and never fall back into message-action jobs. A forward move and inverse carry the same RFC identity, so Graph immutable-ID migration, subscription handshakes, receipts, aliases, and recovery handles are unnecessary.
- **IMAP durable action resolution is exact-FETCH verified (B2, 2026-07-13).** IMAP HEADER SEARCH is only a candidate generator because servers may return substring matches. `IMAPProvider` therefore validates the durable RFC value, searches the selected source mailbox, FETCHes every candidate, and accepts exactly one complete exact match. Missing/ambiguous/invalid is a terminal no-op; incomplete or contradictory FETCH and command failure throw. Flag/keyword batches preflight completely before STORE; move preflights all sources and then all destinations before its first mutation. The queue does not see UIDs or destination probes. Provider-local retry idempotency may clean a source when exactly one destination copy already exists; ambiguous destination state is never guessed.
- **The durable queue no longer classifies IMAP UID failures (B2, 2026-07-13).** `executeSingleOp` contains no concrete-provider cast, destination probe, `uidResolutionFailed` split/cap, or provider-specific stale decision. Adapter return is terminal applied/authoritative no-op; adapter throw is generic unchanged-row retry. v67's released `uidResolutionRetryCount` remains only as an inert physical SQLite column; it is absent from the runtime model/config and must not influence terminal failure.
- **Physical-device migration boundary (2026-07-13).** The user clarified that the installed-and-needed schema ends at `07a4bb7`, through v67. Do not start further audits of v67-and-earlier migrations during the intention-queue simplification. V68 `undoToken` and v69 are the only post-boundary migration candidates; remove v68's fresh-schema migration when its runtime Undo formula is deleted rather than preserving it for compatibility. V69's queue-only `queueParentRowId` column may be removed with batch splitting, but retain `pendingFTSRekeySourceIdsJSON` and its sparse index: history audit proved ordinary sync uses them as a GRDB-to-FTS crash journal, and the user explicitly chose crash recovery over deleting that normally-empty sparse schema. The original index keyed the JSON marker, so SQLite ignored it for the id-ordered startup cursor and scanned the primary-key index; v69 now keys the partial index by `id WHERE pendingFTSRekeySourceIdsJSON IS NOT NULL`. A migration test pins `EXPLAIN QUERY PLAN` to that sparse index. In a synthetic one-million-row empty-journal check, 100 correlated recovery probes took 4.93 s with the old shape and below the timer's 0.01 s resolution with the id-keyed sparse index.
- **Completed v70 index correction remains accepted (2026-07-13).** Before the scope clarification, a bounded evidence-backed audit had already proved two concrete costs: v62's old two-column unread tree was redundant, and v66's full-provider numeric CAST tree indexed Gmail/Exchange identities that never use the IMAP UID query. V70 creates the numeric-only UID partial replacement before dropping the old v66 tree, drops the unread tree superseded by v62's date-suffixed composite, and runs `ANALYZE`; the `.uid` query repeats the exact partial predicate. A 250K mixed fixture dropped from 72.0 MB to 60.6 MB logical pages and improved mass read/date mutation from 0.709 s to 0.416 s without a meaningful unread-count regression. Never startup-`VACUUM`; freed pages are reusable. Keep this completed benefit, but do not use it to justify further older-migration audits.
- **HISTORICAL/DELETED — Released provider-ID rows used a finite provider-assisted RFC cutover (B3, 2026-07-13; deleted 2026-07-14 by the hybrid amendment above).** `EmailProvider.resolveLegacyMessageActionIdentity` receives the legacy provider ID plus explicit recorded source and optional optimistic destination, and defaults to throwing so an unsupported adapter cannot discard work. Gmail exact-fetches the old resource, accepts valid current membership in either scope (including provider-local synthetic All Mail semantics), and returns normalized RFC identity; omitted `labelIds` means the canonical empty label set, so a valid unlabelled archived resource resolves rather than blocking startup. Exchange exact-fetches the old Graph resource, strictly encodes its path segment, validates exact returned-ID correlation plus canonical folder/RFC metadata, and accepts exact source or optimistic-destination membership. For both HTTP providers, exact 404/410 or valid out-of-scope metadata is stale, while malformed/contradictory metadata and every other request failure throw. Keep source and destination distinct: Graph IDs are account-scoped and may be checked in either, but an IMAP UID is mailbox-scoped and is exact-FETCHed only in the recorded source because the same destination UID can name another message. Local Gmail/Graph evidence may come from source or optimistic destination, while IMAP/iCloud evidence is source-only. - **Dumb durable pipe.** One cancellation-safe async mutation gate coordinates append, bounded Undo reconciliation, drain claim/completion, and startup recovery.
