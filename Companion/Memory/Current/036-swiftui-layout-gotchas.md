> **Current routing note (chat view, 2026-11):** six more gotchas, added after this fragment was pinned. The chat view first built its list as a `LazyVStack`, against the rule below about chat-style lists with `scrollTo`, and needed a landing hold to land reliably. The rebuild (2026-11-09) went back to a plain `VStack`: rows have real heights, so one `scrollTo` lands; it is re-issued on container size, content size or scroll inset changes until the user's scroll or a jump-button tap (since 2026-11-18; the user's scroll is `tracking`/`interacting` only, because a programmatic re-pin can report `animating` or `decelerating`, and ending the pin on those left the chat short of the bottom when a late height arrived, ADR-IOS-114). In a plain stack `onAppear` fires for every row at once, so a row that must know it is on screen reports it itself: first through `onScrollVisibilityChange`, and since 2026-11-16 through `onGeometryChange` against the scroll view's bounds (`ChatRowVisibility`), because `onScrollVisibilityChange` needs half of the row and a row taller than twice the screen never shows half (ADR-IOS-114 decision 9). The findings stay true of SwiftUI:
>
> **`onScrollTargetVisibilityChange` can end on an empty id list and never follow it up** (iOS 27 simulator runtime). After a jump to a part of a `LazyVStack` that is not laid out yet, and while a `ScrollViewProxy.scrollTo` is re-issued inside `onScrollGeometryChange`, the whole-list callback reported zero visible ids, sometimes as its last report with the rows already on screen; on iOS 26.5 it always recovered. Do not read which rows are on screen from that callback: a row laid out on screen reports itself through its own `onScrollVisibilityChange`. A simulator created without a runtime argument gets the newest runtime, so a test that passes on one simulator can fail on another.
>
> **A landing `scrollTo` into a `LazyVStack` can end short of its place, and the re-issue can be lost** (iOS 27 runtime). The first scroll lands on the rows' estimated heights; as they measure, the list drifts (up to 22 points off the bottom in the screen tests), and iOS 27 drops `onScrollGeometryChange` callbacks ("OnScrollGeometryChange tried to update multiple times per frame"). A long scroll to a far row was sometimes never applied. This is why the chat went back to a plain `VStack`.
>
> **`scrollTo` ignored a non-row view that carried `.onScrollVisibilityChange` after its `.id`** (same runtime). Giving the chat's Unread line visibility reporters made `ScrollViewProxy.scrollTo` to its id do nothing on every run, while email rows with the same modifiers still scrolled. The cause is unknown. The Unread line stays a plain view with an id.
>
> **A plain `VStack` in a `ScrollView` lays out rows that sit under the navigation bar and under a `safeAreaInset(edge: .top)` header; a `LazyVStack` may not build them.** So a screen test that asks "which rows are on screen" by intersecting row frames with the scroll view's frame counts rows hidden under the bars and the header once the list is a plain stack, and passed before only because the lazy stack had not built them. Measure against the visible area instead: the scroll view's frame inset by its `adjustedContentInset` (142 points at the top in the chat's screen tests). The same holds for a field that grows: compare the newest row's bottom with the field's on-screen top, not how far the content moved, because a field's text centred in its starting height rises a few points more than the field grows.
>
> **The first pass's bottom-anchor fill moves a landed chat past the bottom when it goes** (2026-11-20; mechanism measured 2026-11-21 with a debug-gated geometry log, after a first reading blamed the top bar). The chat's first pass shows the opened email alone, before its thread is read, and `defaultScrollAnchor(.bottom)` sits that short content at the bottom with a **top inset that fills the rest of the screen**: screen height = fill + content + bottom inset, **624.33 + 215.67 + 12 = 852 and 522.67 + 317.33 + 12 = 852** in the screen tests (a two-email chat keeps its fill, following the short content from 624 to 522). The fill reaches the scroll view as part of its `safeAreaInsets` (`contentInset` stays 0), and `ScrollGeometry.containerSize` does not change with it. The whole thread is laid out while the fill is still there, and the landing puts the chat at its bottom under it. **The fill goes in the next layout pass after the landing scroll**, leaving the real top bar's 136.33, and **on that inset change the platform keeps `contentOffset.y` plus the top inset** (3366.67 + 624.33 = 3854.67 + 136.33), so the chat shows past its bottom by exactly the fill: 488 and 386 points measured. A landing re-issued only on container and content size left the offset there until some later platform update clamped it (173 to 206 ms later in the logs) or for good. Re-issued on the scroll geometry's `contentInsets.top` as well, the landing came back 2 ms after the jump. **The gap between the landing and that pass is timing, not order**, which is why the failures were intermittent. In a two-email chat it was 3 ms (the jump and the re-issue's correction fell within 1 ms of each other). In 40-email chats with the geometry log on, main-thread stalls of a quarter to most of a second (`[MainStall]` 242 to 835 ms) held the pass back 150 to 310 ms after the landing scroll applied. In hosted test runs without the log, the landing and the fill's removal fell in the same display frame and nothing showed. The signed-in and ready AI Reply states add no update of their own: the chat views never read `hasTabMailSession`, and when this was measured the ready text sat on the newest header, which the first pass already shows (its content height matched, and stayed the same from the thread pass until the fill went). Since ADR-IOS-114 decision 16 the AI Suggestion appears only once the thread and accounts have loaded (`suggestionText(on:thread:)`), so it is never part of the first pass; a later arrival is a content size change, which re-issues the landing. **A real top bar that shrinks keeps the bottom by itself**: a bar made taller through a DEBUG header seam and dropped right after the landing never showed past the bottom with the re-issue removed, so a bar shrink cannot show this bug (the seam and its test were dropped). **A screen test that waits for settled values cannot see it either**: when the clamp comes, it restores them, so a settled check passes with or without the re-issue (three such tests, two of them on Unread-line and searched-email landings, stayed green with it removed and were dropped). **No automated test fails without the re-issue on the insets** (2026-11-21). A hosted test that held the chat's thread lookup (`ThreadDetection.related`'s first read) until a display frame showed the fill, then counted display frames past the bottom, saw the fill go in the same frame as the landing, with or without the fix, in every run: only a main-thread stall between the landing and the next layout pass shows the bug, and a test can make one only by blocking the main thread, so the test was dropped. The fix rests on the geometry log (488 and 386 points past the bottom without the re-issue, back 2 ms after the jump with it), and a phone check before the chat view merges to main is the check. The re-issue key also carries the bottom inset, but no measurement has shown a bottom inset change moving a held landing (`defaultScrollAnchor(.bottom)` kept the bottom in a settled check, and the reply field's growth left the scroll view's bottom inset at 12 points), so no test fails without that term. A top inset that grew after the landing (through `additionalSafeAreaInsets.top`) also kept the chat at the bottom in a settled check without the re-issue.
>
> **The root hosting controller's `additionalSafeAreaInsets.top` grows a `NavigationStack`-hosted SwiftUI scroll view's top inset but does not shrink it back** (2026-11-20, `ChatThreadViewLifecycleTests`). Set back to zero, the controller view's `safeAreaInsets.top` returned to 62 while the chat's scroll view kept `safeAreaInsets.top` and `adjustedContentInset.top` at 536.33 (`contentInset.top` 0) until the test's wait timed out; the bottom edge followed both ways. A screen test that must shrink a top inset drives the SwiftUI header's own height instead (a DEBUG padding on the header did that; it was removed once a real bar shrink proved unable to show the fill bug above).
>
> **Also (2026-11-22): a `TimelineView` does not redraw at its schedule's last date.** The chat's Sending bubble scheduled its redraws up to its Undo deadline and ended there; a mounted bubble kept "Undo 1s" past the deadline (the hosted tests `mountedBubbleCrossesItsDeadline` and the Reduce Motion delivery test went red), while every test that re-hosted the view or changed its data passed. Apple's developer forums report the same for `.explicit` schedules. A finite custom schedule therefore closes with `Date.distantFuture`, an instant the timeline never reaches, after the last date it needs (`ChatUndoSendSchedule.Entries`).

### SwiftUI Layout Gotchas
- **Label width in compose rows**: `labelWidth` constant in ComposeView must accommodate the longest label ("From" = 4 chars). Currently 42pt at `.subheadline`. If adding longer labels, increase this.
- **Custom Layout (FlowLayout)**: Unlike built-in views, custom `Layout` protocol implementations don't fill available width. Always add `.frame(maxWidth: .infinity, alignment: .leading)` on the container.
- **HStack baseline alignment**: Use `.firstTextBaseline` (not `.top`) when mixing labels with text fields of different font sizes — avoids manual padding hacks.
- **Menu vs Picker for full-width dropdowns**: Use `Menu` instead of `Picker` when you need the collapsed label to fill available width with truncation. `Picker` auto-sizes its label to content width.
- **Menu tint override**: SwiftUI `Menu` applies the default accent (blue) tint to its label, overriding any `.foregroundStyle()` on the label content. Always add `.tint(.primary)` on the `Menu` itself when you want non-blue icons.
- **NEVER nest `.animation(_:value:)` modifiers** on ancestor views of a ScrollView+LazyVStack — multiple parent `.animation()` modifiers create competing animation contexts that cause layout feedback loops (infinite hang). Use explicit `withAnimation` at state change sites instead. ComposeView (one `.animation()` at root) works; InboxView/MessageDetailView (multiple nested `.animation()`) caused hangs.
- **ScrollView bottom-pinning**: Use `.defaultScrollAnchor(.bottom)` + `ScrollPosition` with `.scrollPosition($pos)` for chat-style scroll. Use `pos.scrollTo(edge: .bottom)` in `onChange` handlers for discrete events (message count, isWorking, expand, keyboard focus). Avoids manual per-line `scrollTo` which causes layout feedback at high frequency.
- **NEVER use LazyVStack in chat-style ScrollView with `scrollTo`**: LazyVStack recycles off-screen cells, causing `contentHeight` to fluctuate wildly (e.g. 4513→917→3148) when scroll position changes. This creates visible jumps. Use regular `VStack` instead — chat pills have <20 messages so lazy loading provides no benefit. ([Apple Forums thread](https://developer.apple.com/forums/thread/685461))
- **ProgressView + `.geometryGroup()` + `.background(.regularMaterial)` in ScrollView**: this combination can cause layout loops. Removing `.geometryGroup()` and parent `.animation()` modifiers fixes it. `.geometryGroup()` is rarely needed if expand/collapse uses explicit `withAnimation`.
- **No sticky/floating section headers** — `List` pins section headers on scroll; `Form` does not. Always use `Form` (not `List`) for settings-style screens to avoid floating headers. This is a design rule.
- **A one-shot `ScrollViewReader.scrollTo` on a List's first appearance can be silently dropped** (measured on an iPhone 14 Pro, 2026-10-25, guided tutorial): `onChange(of: target, initial: true)` fired as the inbox appeared, while the List was still laying out and an overlay above it was settling its height; the content offset stayed 0. The simulator settled in time and passed, so a green simulator walkthrough does not prove it. Re-issue the scroll on `onScrollGeometryChange` of the container and content sizes while the target holds (`TutorialInboxScroll`).
