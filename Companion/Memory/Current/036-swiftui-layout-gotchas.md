
### SwiftUI Layout Gotchas
- **Label width in compose rows**: `labelWidth` constant in ComposeView must accommodate the longest label ("From" = 4 chars). Currently 42pt at `.subheadline`. If adding longer labels, increase this.
- **Custom Layout (FlowLayout)**: Unlike built-in views, custom `Layout` protocol implementations don't fill available width. Always add `.frame(maxWidth: .infinity, alignment: .leading)` on the container.
- **HStack baseline alignment**: Use `.firstTextBaseline` (not `.top`) when mixing labels with text fields of different font sizes — avoids manual padding hacks.
- **Menu vs Picker for full-width dropdowns**: Use `Menu` instead of `Picker` when you need the collapsed label to fill available width with truncation. `Picker` auto-sizes its label to content width.
- **Menu tint override**: SwiftUI `Menu` applies the default accent (blue) tint to its label, overriding any `.foregroundStyle()` on the label content. Always add `.tint(.primary)` on the `Menu` itself when you want non-blue icons.
- **NEVER nest `.animation(_:value:)` modifiers** on ancestor views of a ScrollView+LazyVStack — multiple parent `.animation()` modifiers create competing animation contexts that cause layout feedback loops (infinite hang). Use explicit `withAnimation` at state change sites instead. ComposeView (one `.animation()` at root) works; InboxView/MessageDetailView (multiple nested `.animation()`) caused hangs.
- **ScrollView bottom-pinning**: Use `.defaultScrollAnchor(.bottom)` + `ScrollPosition` with `.scrollPosition($pos)` for chat-style scroll. Use `pos.scrollTo(edge: .bottom)` in `onChange` handlers for discrete events (message count, isWorking, expand, keyboard focus). Avoids manual per-line `scrollTo` which causes layout feedback at high frequency.
- **NEVER use LazyVStack in chat-style ScrollView with `scrollTo`**: LazyVStack recycles off-screen cells, causing `contentHeight` to fluctuate wildly (e.g. 4513→917→3148) when scroll position changes. This creates visible jumps. Use regular `VStack` instead — chat pills have <20 messages so lazy loading provides no benefit. ([Apple Forums thread](https://developer.apple.com/forums/thread/685461))
- **ProgressView + `.geometryGroup()` + `.background(.regularMaterial)` in ScrollView**: this combination can cause layout loops. Removing `.geometryGroup()` and parent `.animation()` modifiers fixes it. `.geometryGroup()` is rarely needed if expand/collapse uses explicit `withAnimation`.
- **No sticky/floating section headers** — `List` pins section headers on scroll; `Form` does not. Always use `Form` (not `List`) for settings-style screens to avoid floating headers. This is a design rule.
- **A one-shot `ScrollViewReader.scrollTo` on a List's first appearance can be silently dropped** (measured on an iPhone 14 Pro, 2026-10-25, guided tutorial): `onChange(of: target, initial: true)` fired as the inbox appeared, while the List was still laying out and an overlay above it was settling its height; the content offset stayed 0. The simulator settled in time and passed, so a green simulator walkthrough does not prove it. Re-issue the scroll on `onScrollGeometryChange` of the container and content sizes while the target holds (`TutorialInboxScroll`).
- **Inside a `Button` (`.borderless`, in a List or Form), `.foregroundStyle(.secondary)` is a lighter shade of the tint, not grey.** The hierarchical `.secondary` style is the second level of the current content style, and in a button's label that is the tint. For a grey value or caption inside a tappable row use `.foregroundStyle(Color.secondary)` (a fixed semantic colour). Seen on Settings' Optimize Storage row (#1448, 2026-11-26 simulator screens): its size and its line under the title were light blue.
- **A `Button` centres its label's multi-line text.** A caption that wraps inside a button's label gets its second line centred. Put `.multilineTextAlignment(.leading)` on the content INSIDE the label (nearer the Text than the button's own setting). One-line Text is placed by its stack's alignment instead.
- **An `HStack` of title, `Spacer()` and trailing value can wrap the title even when the row could hold both.** The stack splits the width between its flexible children rather than giving each its ideal width (#1448: "Optimize Storage" wrapped beside "Can drop to 7 MB" with about 30 pt to spare). Give the title `.lineLimit(1)` and `.layoutPriority(1)`: the stack then offers it its whole width first, so it is the last to truncate (it still truncates when the row cannot hold it plus the others' minimum widths). For text sizes where both cannot fit, a `ViewThatFits(in: .horizontal) { HStack {...}; VStack(alignment: .leading) {...} }` was tried first and did NOT switch inside a borderless `Button` in a List row (AX1 simulator screen, 2026-11-26: it kept the side-by-side layout although that was about 45 pt too wide). **A text-size switch cannot stand in for a width test either.** `@Environment(\.dynamicTypeSize)` `.isAccessibilitySize` is true only for AX1 to AX5, not for the larger standard sizes (xLarge to xxxLarge), and the overflow depends on width and text size together: "Optimize" plus "Can drop to 380 MB" fits a 375-pt phone's row (about 311 pt) at xLarge with 11 to 16 pt left (4 to 8 pt for a four-digit size such as "1023 MB"), needs about 310 to 330 pt at xxLarge and 335 to 360 pt at xxxLarge; and Display Zoom ("Larger Text") lays the smaller phones out about 320 pt wide, a row of about 256 pt, which the same pair (about 271 pt) overflows already at the default text size (system-font widths measured on macOS, within about 1% of the simulator's). So when a trailing value beside a title can overflow on some width, put it under the title at every size: OptimizeStorageRow puts the size and its line under the title's text below the accessibility sizes, and under the title from the row's leading edge at AX1 to AX5. A stacked label is only as wide as its widest line, so give it `.frame(maxWidth: .infinity, alignment: .leading)` before `.contentShape(Rectangle())` for a full-width tap area.
- **A Label in a List row centres its icon on its whole title view.** Not documented by Apple; seen on a simulator screen (#1448, 2026-11-26): a title that wrapped to two lines ("Optimize / Storage") had its icon halfway down the two lines, within about 1 pt. So a Label whose title is a VStack of title and caption is expected to put the icon halfway down the block. To keep the icon on the title's line and still start a caption at the title's text, the caption can be its own Label with the same symbol `.hidden()` as its icon (OptimizeStorageRow `underTitle`): the list gives both Labels the same icon column, as long as the caption's font is set inside the Label's title closure, not on the Label. **At the accessibility text sizes a List draws a Label's icon inline with its text, so a wrapped title continues under the icon** (a plain Label row does this: Settings' "Delete All Email Index Data" reads "Delete All Email / Index Data" at AX1, its second line under the icon); a hidden-icon caption then has an empty icon space on its first line only. At those sizes put the caption under the title from the row's leading edge instead (OptimizeStorageRow switches on `isAccessibilitySize`). **And let the title wrap there:** a `.lineLimit(1)` title is cut short at the largest sizes on a narrow row ("Optimize" read "Optim…" at AX5 in a 320-pt window, a hosted render, 2026-11-27, while the rows around it wrapped), so OptimizeStorageRow holds its title to one line below the accessibility sizes only.
