
### "Searchable but can't open / no snippet / not in its folder" — GRDB-side stuck headers (NOT FTS orphans), IMAP (under investigation 2026-06-22)
- **These are NOT FTS orphans.** For IMAP, `SearchView.ftsResultsToSearchResults` DROPS an FTS hit whose GRDB header is missing (`droppedNoHeader`, returns nil — the Gmail/Outlook drift recovery at `:509-527` is gated off for IMAP). So any message that still SHOWS in local search has a live `MessageHeader`. The breakage is in the header's STATE, not the index.
- **Signature** (the row exists → searchable; but): `bodyComplete=0` (→ no snippet; open fails because the stored `messageId`/UID is stale for the folder it now claims) AND/OR a folder anomaly: `folderId` matches no `folder` row (empty/orphan → invisible in every browse, which filters strictly on `folderId == fid`, `InboxViewModel.swift:756/878`), or the PK `id` ("accountId:folderPath:messageId") disagrees with the current `folderPath`/`messageId` columns (optimistic-move remnant). `optimisticMoveToFolder` (`AccountManagerActions.swift:211-215`) updates folderId/folderPath/isInInbox but leaves `id`+`messageId` (stale UID) untouched.
- **Why it never recovers on IMAP:** the only two reconcilers both have gaps. Orphan-reclaim (`SyncEngineFullSync.swift:976`) matches by **id-key** → misses UID changes. UID-remap (`:568-613`) matches by **rfc822MessageId** but ONLY inside the sync **overlap window** (`:499/:513`) → an older archived message, or one with no Message-ID (`rfc822MessageId==nil`, common on IMAP), is never compared. **"Smart Reindex" (`resetCrawlState`) does NOT fix it** — resets crawl cursors + retries body fetch, never touches folderId/messageId, so the re-fetch fails identically.
- **Confirmed secondary bug (FTS scoped search):** `SearchIndex.rekeyHeaders` (`SearchIndex.swift:986-993`) moves `message_ids.headerId`+`message_meta.headerId`+FTS `msgId` but **NOT `message_meta.folderId`**. The SYNC-side callers (`SyncEngineFullSync.swift:116/280`, `DraftStore.swift:287`) don't follow with `updateFolderIds` — only the search-side heal (`SearchView.swift:587`) and one backfill path (`SyncEngineFTS.swift:572`) do. So even a successful UID-remap leaves the FTS folder tag stale → folder-scoped search misses these (global search still finds them). Candidate fix: have `rekeyHeaders` carry `newFolderId` (single source of truth) so meta.folderId moves with the headerId.
- **Diagnostic (READ-ONLY, debug-gated):** `StuckMessageDiagnostics.run()` → Debug menu ▸ "Stuck Message Diagnostics" ▸ Scan; report on the `stuck_messages` `BackgroundSyncLogger` channel (shareable). Counts + bounded samples per signature (NOT-browsable / PK-mismatch / bodyless-in-Archive) + a per-folder **per-month histogram** + each folder's `bfComplete`/`cursor`/date-range. Each sample row tagged `folderExists`/`role`/`sibling`(healthy copy elsewhere → safe-to-delete leftover)/`inFTS`/`rfc822`. Mutates nothing.
