
### `bodyComplete` = FTS-indexed truth; display cache has NO flag (ADR-IOS-050, 2026-07-02)
- **`bodyComplete` means exactly one thing: body text is indexed in FTS.** Set only after a confirmed FTS write; cleared only when the indexed truth is invalidated (user Refetch, FTS-loss self-heal, Smart Reindex). The rendered-HTML cache (`messageBody` row + `BodyAssetStore` files) has no flag — **the row's existence IS the cache state**; detail view fetches on cache-miss. All three cache evictors (`runEvictStaleBodies` TTL, `runPruneIfOverBudget` storage budget, `BodyAssetMaintenance` asset cap) delete rows WITHOUT touching `bodyComplete`.
- **The bug this fixed ("indexing goes backwards then forwards")**: `BodyAssetMaintenance` used to flip `bodyComplete=0` per eviction victim → every victim re-entered the backfill body queue → refetch → asset cache refilled past its 1 GB cap → evicted again. Closed loop; `backfill.log` showed pending 6,788→9,347 while batches completed. NEVER reintroduce a `bodyComplete` write in any cache-eviction path, and never add a "cache present" flag (drift). Regression: `BodyCompleteRestoreTests`.
- **One-time reverse heal** `oneTimeBodyCompleteRestore` (gate `bodyCompleteRestore.v1.done`, runs in the startup healTask): pending rows with FTS body text (`SearchIndex.headerIdsWithFTSBody`, length>1) AND no `messageBody` row → `bodyComplete=1`, zero network. The no-cached-HTML guard keeps NSE unresolved-CID mail (no FTS body anyway) and suspension-aborted flag writes on the refetch path.
- Asset evictions now log to `backfill.log` (`[AssetEvict] reason: N messages, X MB reclaimed`). `EmailReadTool` body fallback: MessageBody → FTS `bodyText` → snippet.
