# Background refresh shares grant ownership

Issue #129 routes Gmail/Outlook credentials through `ProviderCredentialStore` in both the app and the Notification Service Extension. The app's account lifecycle actor installs an activation; refresh updates only its existing grant record. Access and refresh tokens are one encoded value. Refresh responses with an explicitly empty replacement grant are refused without changing the stored pair; an omitted grant retains the current one. A replacement login gets a new activation, including for the same account. When an interactive response omits a refresh token, its new access token selects the retained grant; an older owner may persist that grant's received rotation without replacing the interactive access token.

`CredentialRefreshGate` permits a response to update only the credential snapshot that requested it. A nonblocking App Group `flock` covers the synchronous read/check/update, never HTTP or an `await`. Conditional Keychain attribute matching alone is not treated as a cross-process compare-and-set guarantee. The app obtains background execution time before refresh; the extension uses its notification allowance. Duplicate requests are allowed across processes, and transient failures do not disable subsequent foreground retries. Credential deletion does not acquire the refresh lock: update-only writes either finish before deletion or fail afterward, so sign-out can erase credentials even during lock contention. The existing account-cleanup job retries failed provider credential deletion. New mail accounts commit their account row before their first secret write, so interrupted or failed activation retains a durable retry/removal owner. Initial activation rolls back provisional pointer and grant independently; failed replacement-pointer writes delete only a newly created, never-selected grant; foreground migration sweeps unselected grants when no activation survived.

`TabMailSessionRefresh` shares the complete session decoder and refresh exchange between the processes while preserving `TabMailSessionStore`'s generation pointer. A received refresh cannot recreate a deleted generation or select a session. NSE recovery requires durable persistence and the captured active generation. Foreground provider accessors resolve activation on each invocation so a retained provider can recover after a temporary Keychain failure or delayed credential installation. IMAP/iCloud passwords are not OAuth credentials: reconnect refreshes the TabMail session, preserves the password, and reports restoration only after an active subscribe response and revalidation of session, account, password, and reconnect context. Notification expiry cancels the root processing task; a received credential rotation may still be saved, but cannot authorize another operation after cancellation.
