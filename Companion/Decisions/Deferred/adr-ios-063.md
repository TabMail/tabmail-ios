
## ADR-IOS-063: Account-Removal Orphan-Frontier Hardening — DEFERRED Out of F2b L4 (Fix-Pack FIX 5)

**Context (2026-07-24, F2b L4 fix-pack, codex whole-L4-review G8-r-fixpack round):** the L4 wake-lifecycle work (G1–G8) gated the account-removal `PendingOperation` delete (§9.3 Fix 4) and added the G8-1 post-removal redrive — a real improvement over the pre-L4 state (a bare unsynchronized `dbPool.write`, "the one linearizability hole" the pre-L4 review flagged). codex's round-3 deeper pass on the fix-pack found the improvement is not a full closure: a residual ORPHAN-FRONTIER risk survives account removal. This entry records the scoping decision to DEFER the full closure rather than build it into the fix-pack, and preserves codex's exact requirements so the work is not lost.

**The residual risk, precisely:** `pendingOperation.accountId` has NO foreign key to `account`. A gated admission that is already IN FLIGHT behind the removal — e.g. `queueDraftDelete` resolving the Drafts folder, then inserting its `PendingOperation` row UNCONDITIONALLY — can land its insert AFTER `removeAccount` has already run push-unsubscribe/revoke, deleted the Keychain credentials, and torn down the provider registration via `disconnectAccount` (`AccountManagerSetup.swift:461-476`), AND after the gated delete transaction has already COMMITTED (`:514`) — inserting a fresh row for an account that no longer exists and whose provider is already gone. That row is an orphan: nothing will ever claim it (no registered provider), and nothing purges it (the removal's own gated delete already ran). It sits in the global FIFO as a permanent, silent drain-stall for every OTHER account's queue too (the protected-frontier law stops the whole FIFO at an unclaimable row, not just that account's share of it).

**Why this is DEFERRED, not fixed here (codex-verified, Claude-reconciled):**
1. **L4 did not regress this path — it improved it.** The gated delete + G8-1 redrive are strict improvements over the pre-L4 unsynchronized write. The residual is a PRE-EXISTING class of problem (present before L4, narrowed but not eliminated by L4), not something the fix-pack introduced.
2. **The full closure is a substantial standalone change, not fix-pack-scoped hardening.** Three separate pieces, none of them a small patch:
   - **(a) An atomic post-delete ADMISSION FENCE.** Either give `pendingOperation.accountId` a real foreign key + cascade-delete (a schema migration), OR add an account-existence check INSIDE every gated admission transaction (every `queueXxx` call site, not just drafts) — both are cross-cutting changes touching every admission path in `AccountManagerQueue.swift`/`AccountManagerActions.swift`/`DraftStore.swift`, not a localized fix.
   - **(b) A durable cleanup TOMBSTONE/JOURNAL.** CalDAV credential IDs (`caldav_password_<id>` in the keychain) live only in the deleted account/calendar rows plus ephemeral in-memory state during removal — a crash after the row-cascade commits but before the matching keychain deletes run strands a credential with no durable record to sweep it up later. Outbox attachment files already have an orphan-sweep mechanism; CalDAV credentials do not, and building one is a new durable-teardown subsystem, not a fix.
   - **(c) Push unsubscribe/revoke ordering.** Should run strictly AFTER the DB commit (revoke-before-commit risks revoking a subscription for an account whose removal txn then fails and rolls back) — a re-ordering that interacts with (a) and (b), not an independent one-line change.
3. **SEVERITY CORRECTION (fix-pack ROUND 2, SF4): NEITHER account-removal orphan race is automatically self-healing — the original "LOW/self-healing" assessment above was wrong.** (a) The admission-race orphan (a gated admission inserting a pending row AFTER the account row was deleted) is a PERMANENT global-FIFO wedge: the account never re-registers, so nothing will ever claim that row, and nothing purges it — it sits forever, stalling every OTHER account's queue behind it too (the protected-frontier law stops the whole FIFO at an unclaimable row, not just that account's share). (b) The whole-transaction-delete-FAILURE case is ALSO not self-healing: `removeAccount` tears down the push subscription, mail+CalDAV credentials, and the provider registration BEFORE the best-effort gated delete transaction runs (`AccountManagerSetup.swift:461` onward — unsubscribe/revoke, Keychain deletes, `disconnectAccount`, CalDAV Keychain cleanup, THEN the single-attempt `retryGatedQueueWrite` delete at `:514`) — so a failed delete leaves the account row AND its pending rows in place, but with credentials/provider GONE. The next launch cannot be assumed to auto-re-register (that requires the user to explicitly re-add/reauth the account); until then the pending frontier stays blocked exactly like case (a). Neither race "heals on the next app launch" as originally claimed — both are PERMANENT wedges absent an explicit fix or user reauth/re-removal. The deferral itself still stands (pre-existing; L4 did not introduce this ordering; the full fix is genuinely substantial, see below) — only the severity label changes, from "low-severity/self-healing" to "permanent wedge in both races."
4. **A partial fix would be WORSE than no fix.** codex explicitly refuted retry-the-admission, compensating-transaction, and even a bare reorder-without-the-admission-fence as false-safety patches — each either doesn't close the race or introduces a new one. The correct fix is (a)+(b)+(c) together, PLUS the teardown-ordering/journal requirement below; anything less creates a false sense of closure.
5. **Teardown-ordering/journal requirement (fix-pack ROUND 2, SF4 addition).** Closing (b) above needs more than reordering (c) push-unsubscribe-after-commit: EVERY irreversible external teardown step `removeAccount` performs (push unsubscribe/revoke, Keychain token/CalDAV-password deletes, provider disconnect/unregistration) must be either sequenced strictly AFTER the committed DB deletion (so a failed delete leaves the external state intact and the account still fully functional) OR recorded in the durable cleanup journal from (b) so an interrupted teardown can be resumed/completed on next launch rather than silently stranding the account in a half-torn-down, non-re-registering state. This is a §6/7-scope requirement alongside the schema FK/admission-fence (a) and the durable cleanup journal (b) — not an independent one-line reorder, since naively moving teardown after the commit reopens the credential-still-valid-after-removal window item (c) above already flagged.

**Also folded in (fix-pack ROUND 2, SF4): two wake-lifecycle-scoped (not account-removal-scoped) residuals, recorded here per the fix-pack spec's instruction to fold them into this ADR rather than opening a new one.** Both are never-drop-safe wake-PRECISION degradations, never never-drop violations — the durable G8 timer is a promptness optimization over the next-external-trigger baseline, and both residuals fall back to exactly that baseline:

1. **B2-scenario-1 (transient claim-write failure, non-cancelled owner).** A non-cancelled drain owner (T1) whose re-pass `claimFrontierOperation` GRDB write throws (transient) rolls back to `.queued` while a coalescing timer (T2) has already been marked delivered; T1 is not cancelled, so no fresh redrive is launched, and the op — now overdue-ELIGIBLE rather than deadline-blocked — arms no timer of its own. The row persists `.queued` and drives on the next incidental trigger; pre-existing (`AccountManagerQueueDrainTests.swift:3072` already documents `needsRedrain` consumed-and-dropped in this exact awaited re-prep path "relying on a later external drain"). Closing it fully needs the DRAIN (not the wake timer) to cover overdue-stuck ops with backoff-retry — a scope expansion with spin risk.
2. **B2-scenario-2 (cancelled owner) — code fix REVERTED, fix-pack ROUND 2.** A drain owner cancelled mid-pass (e.g. `durableRecoveryTimerTask` cancel-replaced by a re-arm while it was a fired drain owner) does not itself re-drive a wake token it coalesced. An auto-spawned redrive was implemented and red-proven, but REVERTED after full-suite verification showed it violates the system's existing cancelled-drain-quiesces contract (`AccountManagerQueueDrainTests.cancelledDrainDoesNotStrandClaimedFrontier` asserts `!pendingOperationMutationGate.isHeldForTesting` immediately after a cancelled drain AND drives remaining work via its OWN subsequent `drainPendingQueue()` call — an unstructured auto-redrive races both). Per that contract, the op stays durably queued and drives on the next external trigger (foreground/push/sync).

Both residuals are deferred with the same drain-hardening follow-up as the account-removal closure above.

**Decision:** leave the account-removal path exactly as F2b L4 left it (gated delete + G8-1 redrive — both harmless, both improvements). Make NO further change to `AccountManagerSetup.removeAccount` in the fix-pack. Leave the wake-lifecycle cancelled-owner path exactly as F2b L4 left it too (no auto-redrive; the reverted fix-pack ROUND 2 attempt is documented above, not re-attempted without a design that also satisfies the cancelled-drain-quiesces contract). Track the full closure — schema FK/admission-fence (a), durable cleanup journal (b), push-ordering (c), the teardown-ordering/journal requirement above, and BOTH B2-scenario wake-precision residuals — as a single follow-up (owner may re-scope it into a future L-series pass; flagged in the fix-pack completion report for visibility). This entry is the durable record so the requirements are not lost between now and whenever that follow-up is scheduled.

**Relates:** ADR-IOS-018 (PendingOperation queue), ADR-IOS-060 (durable message-action FIFO — the protected-frontier law this residual can wedge), ADR-IOS-019 (outbox attachment orphan-sweep — the pattern (b) should mirror for CalDAV credentials).
