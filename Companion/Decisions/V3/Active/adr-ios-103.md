## ADR-IOS-103: Four Graph Requests per Outlook Mailbox, and Retry-After Is Honoured

**Status:** Active (2026-11-08, tabmail-ios #426).

**Context:** Microsoft Graph's Outlook service limits apply per app ID and mailbox: "Four concurrent requests", and 10,000 requests in a 10-minute period (learn.microsoft.com/graph/throttling-limits, "Outlook service limits"). The limit is documented there, so no live measurement is needed: the gate stays at four whatever Graph would answer to a fifth request, and a `Retry-After` in a form the app does not read falls back to the exponential back-off. A throttled request gets 429 with a `Retry-After` header, and Graph asks the client to "Wait the number of seconds specified in the Retry-After header" (learn.microsoft.com/graph/throttling); 503 Service Unavailable is also documented as retryable after a delay (learn.microsoft.com/graph/errors). The app sent Outlook body fetches 25 at a time during backfill, on top of sync, actions, sends and calendar calls for the same mailbox, so concurrency was the limit it reached first. `performHTTPRequestWithRetry` ignored `Retry-After` (fixed 1 s, 2 s, 4 s back-off) and the Graph policy retried 429 only.

**Decision:**
1. **One FIFO `HTTPConcurrencyGate` per mailbox** (`Shared/HTTP/HTTPConcurrencyGate.swift`), limit `GraphConfig.maxConcurrentRequestsPerMailbox` (4). `GraphMailboxGates.gate(for:)` keys it by the lowercased address; `AccountManager` hands the same gate to the mailbox's `ExchangeProvider` and `ExchangeCalendarProvider`, so mail and calendar count against the same four. A provider built without one gets its own gate (tests stay independent).
2. **A slot is held only while a request is on the wire.** `performHTTPRequest` wraps `session.data(for:)` in `gate.withSlot`; a retry's sleep and a token refresh hold none, so a throttled request never blocks the mailbox while it waits. The upload-session `PUT` of a large attachment holds a slot too. Waiters are served in arrival order.
3. **`Retry-After` is honoured.** `HTTPRequestResult.retryAfter` carries delta-seconds (an HTTP-date is ignored). A retry waits that long; when it is above `HTTPConfig.maxHonouredRetryAfterSeconds` (10) the request is not retried and the refusal goes back to the caller, whose own retry (next sync pass, next queue drain) comes later. Without the header the exponential back-off is unchanged.
4. **`HTTPRetryPolicy.graph` retries 429 and 503.** Other 5xx are not retried by the HTTP layer.
5. **Outlook body fan-out is `GraphConfig.bodyFetchConcurrency` (2)**, below the limit, so a send, an action or a sync request waits behind at most two background fetches (`fetchTextBodies`, and the Exchange arm of the backfill walk).
6. **A send refused with 429 or 503 is transient** (`AccountManager.isTransientSendError`): it stays queued with no strike. Other 5xx stay strikes, because a server error can repeat for the same message every time.

**Known and bounded:** the notification service extension is a separate process and cannot share the app's gate. It makes one short fetch per notification, so at worst a fifth request is briefly in flight for that mailbox; Graph answers it with 429 and `Retry-After`, which the shared retry code honours, and the next request goes through. Nothing is lost, and it heals on its own. The sign-in profile probe (`MicrosoftAuthService`, one `GET /me` before the account exists) is outside it too. Gmail keeps its own policy (`[429, 403]`), now also honouring `Retry-After`. The ordinary action queue still counts a final 429/5xx toward `SyncConfig.pendingOperationServerRefusalRetryLimit` (the bounded fifth exit of the never-drop rule); the HTTP-layer retries make reaching it rarer, they do not change it.

**Rejected:** a global request-rate limiter (the binding limit is concurrency, and the 10,000-per-10-minutes budget is not approached by one device); retrying every 5xx (a deterministic 500 would be sent four times per attempt); holding the slot through the retry sleep (one throttled request would idle a quarter of the mailbox's capacity for its whole `Retry-After`).

**Tests:** `GraphThrottlingTests` — gate limit, FIFO order and release on throw; per-mailbox gate identity; `Retry-After` honoured, capped and parsed; 503 retried and 500 not under `.graph`; no slot held during a retry sleep; mail and calendar providers sharing one gate never exceed four requests on the wire under backfill, actions, sends and calendar listings; 429/503 sends transient, 500 not; a seeded fuzz with random latency and 429/503 refusals (`GRAPH_THROTTLE_FUZZ_SEED` replays one seed). A test that injects a transient Graph refusal to see what its caller does answers `FakeHTTP.CannedResponse.graphUnavailableBeyondRetry` (503 with a `Retry-After` above the cap), so the HTTP layer does not retry it away inside the one request.
