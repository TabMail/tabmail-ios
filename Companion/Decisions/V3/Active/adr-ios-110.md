## ADR-IOS-110: Calendar Recurrence Math Stays In-House, Checked Against libical and ical.js

**Status:** Active (2026-11-11).

**Context:** TabMail works out the occurrences of a repeating CalDAV event on the device
(ADR-IOS-108: `CalDAVOccurrences`, `RecurrenceTail.Rule`) and computes split ends, split caps and
occurrence lookups for Google, Outlook and CalDAV (`RecurrenceTail.newSeriesRule`/`newSeriesEnd`,
`GoogleCalendarProvider.googleUntilString`, `RecurrenceOccurrenceResolver`). Google
(`singleEvents=true`) and Outlook (`calendarView`) expand on their servers. We looked for a library
to take this over. No maintained Swift library reads an RRULE, expands it, applies EXDATE and
RECURRENCE-ID, and handles time zones. The mature engines are libical (C) and ical.js (JavaScript,
Thunderbird's), both MPL 2.0. Most recent calendar issues are about how each provider stores and
edits a series, which no library covers.

**Decision:**
1. The recurrence math stays in our own Swift code.
2. It is checked in tests against expected occurrences generated by libical and by Thunderbird's
   ical.js on a developer Mac (`Scripts/cal-oracle/`). The results are committed as fixtures
   (`TabMailTests/Fixtures/CalendarOracle/`). Neither engine is linked into the app or run in CI.
3. Where the two engines disagree, both answers are kept, and the fixture names the one the test
   follows and why (an RFC 5545 section, an ADR of this repo, or an upstream fix). Google
   Calendar's behaviour is also a valid reason for a fixture's answer, since Google Calendar is the
   reference for what the user sees. The generator refuses a disagreement with no recorded decision.
4. A rule shape TabMail does not expand stays one row marked not listed (ADR-IOS-108).

**Alternatives rejected:**
- *Foundation `Calendar.RecurrenceRule`:* it can't read an RRULE string. It has no WKST (it uses the
  calendar's first weekday), no EXDATE, RDATE or RECURRENCE-ID, and no floating times. It has open
  bugs on ordinal weekdays with a Monday week start (swift-foundation #1387), a rule that never
  returns (#2389), and 29 February turning into 1 March (#2224). Fixes arrive only with OS updates.
- *libical in the app:* a C XCFramework and a Swift bridge we would write and keep up. The existing
  calendar code would be rebuilt from `main` and its tests re-pinned. We would still merge
  RECURRENCE-ID overrides ourselves, and it would not help with Google or Outlook. To revisit only if
  bugs in reading and rewriting CalDAV calendar text keep growing.
- *A unified calendar API (Nylas, Cronofy, Aurinko and similar):* every user's calendar and tokens
  would pass through a third party, which would be a new sub-processor, and one of them stores event
  data. None writes "this and following" correctly on every provider. Ruled out for good.
- *Swift RRULE ports:* abandoned, or wrappers of Foundation's rule.
- *Server-side expansion (`CALDAV:expand`):* rejected in ADR-IOS-108.

**Consequences:**
- No app dependency and no size change. A developer who regenerates fixtures needs Homebrew
  libical and Node. The ical.js file is fetched by URL and checked against a pinned SHA-256.
- The fixtures pin RFC 5545 behaviour. This first slice asserts CalDAV listings and read-back by
  occurrence key (`CalDAVOccurrences.listing`, `CalDAVOccurrences.occurrence(key:)`). The fixtures
  also carry each RRULE's rule-only days, which no test reads yet; the rule-day and split-count
  suites of a later slice read them. Split caps (`RecurrenceTail.newSeriesRule`/`newSeriesEnd`,
  `GoogleCalendarProvider.googleUntilString`), naming an occurrence by its start
  (`RecurrenceOccurrenceResolver`), RDATE and RECURRENCE-ID overrides have no oracle case yet; the
  hand-written CalDAV occurrence tests still cover them. Outlook's own counting
  (`Anchor.patternStart`, `MissingMonthDay.lastDay`, measured) and the server-expanded Google and
  Outlook listings are outside the fixtures.
- Fixture dates are fixed, because the engines run on a developer Mac and not at test time, so
  their answers cannot be relative to `Date()`. The dates run from 1896 to 2019 (every event's
  DTSTAMP is 2020-01-01), all under the testing rules' exception for dates in 2020 and earlier.
  They go back that far because the cases do: the century leap pair is a yearly 29 February series
  across 1896–1904 (1900 is not a leap year) and across 1996–2004 (2000 is one), and the RFC 5545
  §3.8.5.3 examples start in 1996–1997. Time-zone cases use 1996–2019, settled history (a zone's past changes are fixed data; its future rules can still change), and a
  test checks Foundation's zone data against the fixtures' offsets. The VTIMEZONE blocks inside the
  calendar text carry each zone's rules as libical writes them, including later years; they are zone
  data, not test dates.
- A case that fails on `main` is parked under its filed issue and enters the suite with its fix.

**Detail (first slice, 2026-11-11):**
- Generator: `Scripts/cal-oracle/` (`generate.sh`, `generate.mjs`, `libical-expand.c`,
  `oracle-lock.json`, hand-written `cases.json` inputs and `resolutions.json` decisions; README
  there). Pinned: Homebrew libical 4.0.7 (system zoneinfo), ical.js `Ical.sys.mjs` from comm-central
  `226a299e` (SHA-256 `968a5892…173e`, the bytes the Thunderbird add-on's tests pin), Node 26. A
  third witness, Node's own zone data, must agree with both engines' UTC offsets; the RFC 5545
  §3.8.5.3 examples also carry the RFC's printed answer, which the generator checks.
- A decision may follow one engine (`follows`), take named days from the other (`except`), keep
  the other's occurrence length (`lengthFrom`), or assert nothing (`excluded`, with an issue).
  First slice: RFC 5545 §3.8.5.3 examples, spring-forward gaps, fall-back repeats and the century
  leap pair (27 cases, 15 decisions). Both engines misplace a time a change skips or repeats in different ways (libical
  4.0.7: the occurrence after a gap drifts an hour, a repeated-hour occurrence gets no length;
  ical.js: a skipped time reads with the offset after the change, a repeated one names the second
  instant, ical.js #1051; and `YEARLY;BYDAY=20MO` gives every Monday). libical's listing converts
  times to seconds since 1970, which it defines only from 1902, so with a window starting in 1896
  it lists nothing; its own rule iterator gives the same days as ical.js there. Each decision cites the RFC section and the
  upstream changelog, issue or header.
- Tests: `TabMailTests/Providers/CalendarOracle/` (`CalendarOracleIntegrityTests`,
  `CalendarOracleListingTests`; parked-case table in `CalendarOracleFixtures.swift`).
