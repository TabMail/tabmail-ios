## ADR-IOS-060: Durable Message Actions Are One Dumb Global FIFO

**Status:** Accepted (2026-07-13). Supersedes the queue/Undo mechanics identified above in ADR-IOS-018, ADR-IOS-058, and ADR-IOS-059; amends ADR-IOS-026B with universal RFC Message-ID operation identity.

### Context

The intention-journal work began as a test-coverage and GRDB-write reduction effort. The in-memory journal succeeded at that goal, but durable Undo retained a hybrid “cancel if queued, otherwise restore/move back” protocol. Tests then exposed real races in that protocol. Successive fixes added member-level cancellation, durable lineage tokens, recorded destinations, provider receipts, Graph alias/recovery handles, dependent-job rewrites, queue-owned GRDB/FTS recovery, and provider-specific branches. `AccountManagerQueue.swift` grew from roughly 965 committed lines to roughly 2,622 in the Round 53 working tree.

The root error was architectural: a generic action queue became responsible for Undo identity and provider recovery. The queue should carry ordinary account/folder/message commands in order. Provider peculiarities belong below the `EmailProvider` boundary, and Undo should be evaluated by its final serial effect rather than by preserving one internal cancellation formula.

### Decision

1. **One global queue, one job at a time.** The durable message-action queue is a single global insertion-order FIFO. Each job embeds its account and ordinary command data. There are no per-account drains, connected-component lanes, or parallel message-action execution. A transient failure blocks all later jobs until the frontier can retry. This deliberate throughput trade-off keeps execution and reasoning serial.

2. **One shared mutation gate and one protected frontier.** Durable append, bounded Undo reconciliation, drain claim, drain completion/requeue, and startup reconciliation coordinate through one cancellation-safe max-one async gate. The first active job in insertion order is never touched by Undo, even if its persisted status still says `queued`, because drain may already be claiming it. Exactly one drain owner exists, and provider/network I/O never runs while the gate is held. Gate release is guaranteed on every success, error, cancellation, and early-return path.

3. **The durable executor is a dumb pipe.** A persisted semantic payload is never rewritten, split, re-parented, merged with another payload, advanced through provider aliases, or interpreted through Undo identity. The executor claims the first job, calls the generic provider operation, deletes on applied/authoritative-no-op completion, and restores the unchanged job to `queued` on transient failure. Crash recovery may reset abandoned `inFlight` lifecycle state before a live drainer exists.

4. **General coalescing exists only in memory.** The `IntentionJournal` may fold rapid actions before GRDB/durable output to reduce database and provider work. Once ordinary work is durable, there is no background compactor or drain-time latest-intent register. The sole admission-time exception is bounded Undo reconciliation under the mutation gate: safely queued work behind the protected frontier may be removed or replaced when doing so preserves the same final state as serial action-then-Undo execution.

5. **Undo is an ordinary inverse command, not a recovery protocol.** Undo stores only enough generic command data to issue the inverse and render its UI. No `.undoRestore`, full-row resurrection, durable `undoToken`, provider receipt, destination ledger, alias graph, recovery handle, or provider-specific matcher participates. Reversible move/archive/delete-to-trash operations invert source and destination; idempotent read/flag/remote-label operations invert their desired state. Permanent deletion remains non-undoable.

6. **The exact durable Undo formula is replaceable.** Every formula must hold the mutation gate, leave the protected first job untouched, remain provider-blind, avoid persisted-payload mutation/partial batch rewriting, and produce the serially correct final state. ADR-IOS-060 deliberately does not specify newest-related scanning, `flipped()` equality, or move-delete versus setter-replace choreography. Those are implementation choices recorded in `PLAN_INTENTION_QUEUE_AUDIT_V2.md` and may change without an ADR revision.

7. **Stale is terminal; uncertainty retries.** A locally vanished/ambiguous target drops before durable output. At execution, a successful authoritative provider lookup showing missing source membership, a missing message/folder, or a non-unique target unsafe to mutate returns normally as a no-op and the job leaves the queue. Transport/auth/throttle/timeout or a failed/incomplete lookup throws and retains the unchanged frontier for retry. No retry budget converts uncertainty into absence.

8. **Provider peculiarities stop at `EmailProvider`.** The queue sees normalized RFC Message-ID members and generic account/folder/message operations. Gmail ID/label resolution, Graph `internetMessageId` to current resource-ID resolution, IMAP UID resolution, and provider-specific stale classification remain inside adapters. The queue contains no concrete-provider casts, receipts, aliases, destination probes, header/body re-keying, or FTS recovery.

9. **Universal RFC operation identity is the prerequisite.** Before generic queue/Undo simplification proceeds, every Gmail, Exchange, and IMAP durable message-action admission path must require normalized RFC Message-ID and every adapter must resolve it authoritatively inside the recorded source scope. Local RFC presence/syntax validation precedes optimistic mutation, so refused members are not changed locally; authoritative exact-one provider resolution remains deferred to drain. Provider resource IDs are transient execution details. Missing/non-unique resolution no-ops and ordinary sync reconciles optimistic state to provider truth; failed lookup retries. There is no provider-ID fallback, Graph immutable-ID migration, move receipt, runtime alias ledger, or permanent dual-format executor. Released provider-ID rows are converted once before the new drain starts. The finite conversion passes recorded source and optional optimistic destination separately: Gmail and account-scoped Graph IDs may be corroborated in either, but a mailbox-scoped legacy IMAP UID is exact-FETCHed only in the source because the same numeric destination UID can identify another message. The IMAP cutover terminally omits noncanonical/out-of-range UID encodings and exact source members that cannot supply a valid RFC Message-ID; failed SELECT/FETCH or contradictory correlation throws. Unsupported provider conversion throws. This cutover reuses existing exact header indexes and adds no schema, token, or new durable migration state.

10. **Undo queue tests are black-box end-to-end tests.** Tests drive public action and `UndoService` entry points through the real journal, local GRDB transaction, durable queue, drain, and deterministic stateful provider doubles. They assert final local/provider state, overlay clearance, unrelated-action preservation, and queue idle. They do not assert durable row counts, which row was removed/replaced, candidate selection, `flipped()` output, temporary inverse rows, cancellation status, or private call order. Changing one correct formula to another must not require test changes. Narrow low-level tests may cover the generic gate, single-drainer ownership, insertion-order FIFO, and startup recovery only.

11. **Audit convergence is historical and explicit.** The inherited Round 53 working tree is first committed as an explicitly rejected recovery checkpoint together with this ADR and the V2 plan, establishing a clean audit trail. Every subsequent implementation/audit round starts and ends clean, has its own signed DCO commit, and is not squashed until convergence. Completion requires two consecutive independent clean audit rounds.

### Scope

This ADR governs the durable message-action `PendingOperation` queue. `OutboxMessage` send reliability remains governed by ADR-IOS-019 and is not merged into this queue. Calendar persistence remains separate. If a draft-related operation is represented as a `PendingOperation`, it obeys this FIFO but is not made undoable by this ADR.

### Consequences

- One offline or throttled account can block later actions for other accounts. This is accepted; cross-account parallelism is intentionally rejected as unnecessary complexity.
- Universal source-scoped RFC resolution must be solved before queue simplification; provider-ID churn is never compensated for with queue-visible recovery after MOVE.
- Runtime ownership and the fresh-schema migration of unreleased v68 `undoToken` are removed; the installed-and-needed schema boundary is `07a4bb7`/v67, and older migrations are out of scope. V69's queue-only `queueParentRowId` state is removed with batch splitting. Its independently live ordinary-sync `pendingFTSRekeySourceIdsJSON` crash journal remains because it closes the GRDB-to-FTS interruption gap and is not queue receipt state; its partial index is keyed by `id` so the id-ordered recovery cursor probes only marked rows. Legacy email `cancelled` rows may be cleaned at startup, but new email code never creates them.
- Existing tests that pin token/cancellation/receipt choreography are rewritten around final serial outcomes or deleted.
- Sync may retain only the smallest provider-agnostic pending/recent-completion shield proven by real-path tests; it does not become an execution receipt ledger.
- The initial matching formula can evolve freely behind the ADR invariants and end-to-end suite.

**B3 implementation checkpoint (2026-07-14).** The finite released-row converter performs provider-assisted resolution outside GRDB, then one guarded transaction raw-updates only member identity JSON or deletes an all-stale row. It revalidates the full active legacy row set, semantic payload, account provider, and local header evidence after provider awaits; any uncertainty or concurrent change leaves every convertible row unchanged. It preserves rowid/FIFO and the inert physical v67 field, excludes dead/no-op/draft/local-only types, reuses the v64 exact header index, and adds no schema or permanent dual executor. Every message execution entry is gated by one process-local preparation flight bound to the exact active `AppDatabase`: conversion runs first, crash recovery second, and no drain owner, claim, or provider action exists until both succeed. Uncertainty blocks all message work but not independent Outbox/calendar reconciliation. Database-instance readiness/handoff and caller cancellation are fail-closed; an authorized drain keeps the prepared database frozen through its full DB lifecycle and draft persistence even if the process-global database changes. The queue has no post-drain sync tail; ordinary sync independently owns provider-ID re-key and local reconciliation. One structured owner stays active across requested re-drains and retries the newest database when an awaited replacement preparation becomes obsolete, preventing rapid replacement from clearing the newest trigger. Recovery resets abandoned `inFlight` rows and deletes legacy email cancelled/no-op rows with debug-gated counts. **Round C mutation-gate checkpoint (2026-07-14; this commit).** `PendingOperationMutationGate` is the one process-local, max-one permit that later Round C checkpoints use for every bounded durable message-action selection or GRDB mutation. Its `Mutex` state carries an in-memory owner UUID plus FIFO continuation waiters; these UUIDs are synchronization bookkeeping only and never enter persistence, identity, or Undo. Acquisition removes a queued cancellation synchronously. If cancellation races after ownership transfer but before continuation resumption, it reclaims that exact owner and hands the permit to the next waiter before throwing. Acquisition returns an opaque in-memory lease, and synchronous release accepts only that exact lease, so a stale or duplicated release cannot free a successor's permit. Every callsite installs release in `defer` immediately. The API deliberately exposes acquire/lease-release instead of an unrestricted async-body wrapper: provider I/O, callbacks, sleeps, and retry delays must remain structurally outside the permit. Eight primitive tests cover FIFO exclusion, queued cancellation, pre-cancelled acquisition, deterministic cancellation at the handoff boundary with and without a successor, stale-lease rejection, cancellation after entry, and throwing-callsite release. The global drain and durable writers are not yet switched in this checkpoint; that wiring remains the next Round C work.

**Round C global-FIFO checkpoint (2026-07-14; this commit; decisions 1–3 now live).** Message actions execute as one global, one-job-at-a-time FIFO. Connected-component lanes, the parallel per-lane task fan-out, the multi-pass drain, lane halting, and batch splitting are deleted. Durable order is SQLite insertion order (`rowid`); wall-clock `createdAt` no longer participates in any queue ordering, so a clock rollback cannot reorder work. The claim selects the first active row under one gate acquisition and one bounded transaction, physically deleting legacy `cancelled` rows as it walks, and it neither steals nor skips an `inFlight` frontier. A frontier whose account has no registered provider is returned to `queued` and stops the drain instead of being skipped: account removal already purges that account's rows, so this blocks only on a not-yet-connected provider, and per-account failure isolation is deliberately given up for the single serial model of decision 1. A transient failure requeues the unchanged payload and stops the drain; a batch is retried whole and never split; `retryCount` is diagnostics only and never a drop policy. Provider I/O and retry backoff are structurally outside the permit. **Terminal durable writes are cancellation-immune by construction:** the gate's `acquire()` throws the instant its caller is cancelled, so a drain cancelled while completing its claimed frontier would strand that row `inFlight`, and because decision 2's protected frontier refuses to steal or skip such a row while crash recovery only runs once per database instance, one stranded row would wedge the entire FIFO until the next process start. The gated write helper therefore runs its attempts on a detached task, re-binding `PriorityGate`'s write-tier task-locals so detaching cannot silently re-tier a queue write. All fifteen durable append sites — gestures, moves, setters, Undo's inverse, drafts, outbox replied/forwarded, remote user labels, cold notification actions, and the released-row converter's closing compare-and-swap — now commit their local optimistic mutation and their durable insert in one gated transaction, making local state, queue state, and the drain frontier a single linearizable sequence. The helper is `nonisolated` because `AccountManager` being an actor does not by itself supply this exclusion: its methods are reentrant across awaited GRDB calls. Terminal provider-error classification and the queue-owned confirmed-gone header delete are deliberately unchanged here; they move below the `EmailProvider` boundary in Round E and are removed in Round F. Decisions 5–6 are NOT yet live: Undo still uses the pre-V2 durable token/status-cancellation formula, which Round D replaces.

**Queue-liveness amendment to decision 2 (2026-07-14).** The protected frontier means a row stranded `inFlight` by a departed owner blocks the whole FIFO, so the abandoned-row reset of decision 3 is generalized from process start to **ownership** start. This preserves §9.4's stated precondition exactly — "before any drain owner or provider call can exist" — because exactly one drain owner exists at a time (a second caller becomes a re-drain signal, never a second claimant) and a departed owner can have no outstanding provider call or unlanded terminal write. Any `inFlight` row observed as a new ownership begins is therefore provably abandoned, and resetting it is not stealing. The NSE never touches `PendingOperation`, so this invariant holds across processes. The rule to keep in mind: **a blocked queue must still be a live queue.** Head-of-line blocking on an unresolved frontier is intended (decision 1); a leaked permit, leaked owner, leaked claim, or unrecoverable `inFlight` row is not, and every one of those is now pinned by a liveness suite that also proves a fresh op still drains. The accepted cost of decision 1 is that a persistently failing or unregistered provider blocks other accounts' actions; the old per-account failure isolation is deliberately given up, and must not be reintroduced as lanes without a new ADR.

**Round D Undo checkpoint (2026-07-14; this commit; decisions 4–6 now live).** Undo is an ordinary inverse command issued through the same journal/fold/gated-admission path as every other gesture. The undo entry carries per-account generic command data only (normalized RFC members, per-member source folder, forward destination, plus a UI-local pre-move id used solely to un-dismiss the hidden row); the full-row snapshot, durable `undoToken` (runtime property and all writers — the released-schema-compatible v68 column stays inert until Round F), `.undoRestore`/`IntentionUndoPayload`, fold checkpoints, the second post-undo resolve, the destination receipt ledger, and email production of `PendingStatus.cancelled` are deleted. The initial replaceable formula (decision 6) is `reconcileUndoAdmission`: inside the same gated transaction as the local inverse mutation, exclude the protected first row, scan newest→oldest, stop at the first related row, and physically delete only a still-queued exact whole-flip match — a move appends nothing, a setter re-appends the inverse, everything else appends the ordinary inverse. Local resolution accepts a member only at its two serial-intent locations (forward destination after the fold, or its own source before it); anywhere else is a stale drop, pinning the §19 rule that undo never drags a message back from an unrelated folder. The token's original raison d'être — undoing a delete that followed an archive must not cancel the archive — is now guaranteed structurally by the newest-related stop rule and pinned red/green by an end-to-end final-state test. Tag behavior needs no undo handling at all: Round D-0 retains tags across moves, so the inverse move re-reveals them.

**Persistent-failure chain-demotion amendment to decision 1 (2026-07-15; owner-directed).** Decision 1's "a transient failure blocks all later jobs" is amended with a THIRD failure class between transient and authoritative-terminal: **persistent** — a provider failure that is permanent-SHAPED but not authoritative-terminal (e.g. an unrecognized structural REST 400 whose body matches none of the adapter's known terminal shapes). Before this amendment such a failure retried forever at the frontier and wedged the entire global FIFO for every account; the rejected alternative (shipped briefly in an earlier release) dropped all 400s — self-healing but silently discarding intent. The owner chose demotion: *"fail and move the failure to the end of the queue — we'd have to move the whole chain related to the failing message though — so that it lets other moves go through. But also report the error loudly."* Classification stays below `EmailProvider` (Law 5/decision 8): Gmail throws `ProviderError.persistentActionFailure` for an action-path 400 whose body matches NONE of its known terminal shapes — invalid-label, and invalid-id-value on the token-member GET (both stay authoritative no-ops); Exchange for an action-path 400 other than `ErrorInvalidIdMalformed` (which stays authoritative — the PATCH setter path now classifies it as such too, consistent with move/token resolution), including its RFC `$filter` action search; IMAP has no persistent class (its terminal shapes are already classified; protocol errors stay transient). Coverage note (final audit 2026-07-15): the classification exists exactly where the body-preserving request variant is wired — every Gmail/Exchange action-path resolution and mutation site as of this amendment; a bodyless-400 arrival elsewhere (e.g. Graph nextLink pagination) stays plain transient by design. 401/403/429/5xx/transport are NEVER persistent — they stay plain transient and keep blocking the frontier (auth/throttle heal on their own). The queue reacts generically in ONE gated transaction: it computes the failing op's exact RELATED CHAIN — the transitive closure over same-account active rows whose member sets intersect, including the failing op — and re-inserts the chain at the queue TAIL, preserving `id` and every MODELED payload field byte-for-byte (delete + insert; only the rowid position changes — unmodeled inert physical columns, i.e. the v67 diagnostics counter and dev-only legacy columns absent from the model, reset to their column defaults on re-insert; all diagnostics-only, and the payload-immutability test asserts modeled fields by construction), keeping intra-chain relative order, all rows `queued`. Per-message serial order is never violated — where "message" means MEMBER STRING: relatedness (for both chain closure and undo reconciliation) is member-string intersection. [CORRECTED by the Round 2 amendment below, 2026-07-15: the original text here claimed cross-shape reordering (a provider-token row vs a later RFC row for the same physical message) "resolves to an authoritative stale no-op at worst" — that is FALSE for stable-ID providers: a Gmail token (and an unmoved Graph id) resolves and APPLIES late, so a demoted token op really could land after a newer RFC op and stick. Closed by admission shape-stickiness + the account-scoped zombie fence; see the Round 2 amendment.] Cross-message reordering within an account is likewise the accepted cost, exactly like a user re-issuing the other actions after the failing one. No retry budget ever drops an intention — the chain retries at the tail on every future drain, ONE provider attempt per drain PASS (the spin-guard set lives on the per-pass `DrainContext`, so a `needsRedrain` re-pass inside one ownership grants a fresh attempt; re-passes only arise from external append triggers, so a lone failing chain still cannot spin — demote → guard-requeue → drain stops). The error is reported loudly (ungated `[Queue] ERROR: persistent provider failure — demoted N-op chain …` plus the once-per-drain `[QueueDiag]` deep dump). Undo reconciliation is unaffected: its newest-related scan is rowid-based and a demoted chain's newest member is still its newest. Pinned by `AccountManagerQueueDemotionTests` (demotion/recovery/spin-guard/closure/payload-immutability/undo-vs-demoted) and adapter cells in `GmailProviderMockTests`/`ExchangeProviderMockTests`.

**Timeout-demotion amendment to the chain-demotion amendment above (2026-07-15; owner-directed, external-audit Round 1).** An external audit of the chain-demotion amendment found that `executeSingleOp` wraps `executeOperation` in `withTimeout(seconds: SyncConfig.pendingOperationTimeoutSeconds)` (15s), and `withTimeout` cancels-and-ABANDONS the operation Task on timeout without awaiting its termination — the cancelled Task is not killed, just disowned. `TimeoutError` was previously falling into the plain-transient branch (requeue at the frontier, `.stopDrain`), which has two consequences beyond the ordinary "one hung op wedges the FIFO for 15s per drain" cost: (a) the frontier never advances past a hung op even though decision 1's chain-demotion machinery already exists for exactly this shape of problem; (b) worse, the abandoned ("zombie") Task may still be issuing a real provider mutation — a fully-sent HTTP request awaiting a response, a NIO connect still resolving — while a LATER retry of the same op, or an INVERSE (undo) of the same message, runs concurrently. If the zombie's mutation lands AFTER the later retry/inverse, it silently overwrites the newer intention: e.g. a timed-out forward move's zombie could complete and re-apply itself after the user's undo has already moved the message back, leaving it at the wrong folder with no error surfaced. The old ownership-reset proof's premise — "a previous owner cannot still have a provider call outstanding" — was falsified by this exact mechanism.

**The fix has two parts, both owner-approved exactly as designed.** (1) `TimeoutError` joins `persistentActionFailure` as a THIRD demotion trigger in `executeSingleOp`'s catch — same once-per-(drain, opId) diagnostic, same `demoteRelatedChainToTail`, same loud ungated report, same "0 demoted → fall through to transient requeue" safety net. The related chain moving together (not just the timed-out op) is what preserves per-email order across the demotion — the owner's original directive for the chain-demotion amendment ("move the whole chain related to the failing message") already covers the timeout case for free. (2) A new in-memory **zombie registry** (`AccountManager.zombieOperationsBox`, a `Mutex<[UUID: (accountId: String, members: Set<String>)]>`) restores the invariant the ownership-reset proof needs: **at most one in-flight provider mutation per (account, member) EVER.** `withTimeout` gained an `onAbandon` callback (the single implementation is unchanged otherwise — the existing 2-arg `withTimeout` delegates to the 3-arg form with a no-op `onAbandon`) that fires SYNCHRONOUSLY on the timeout-timer's own Task, strictly BEFORE `TimeoutError` is thrown — registration always happens-before any caller (this attempt's own catch block, or a future drain ownership) can observe the timeout, so the queue can never retry ahead of registration. `executeSingleOp` registers the zombie's `(accountId, members)` footprint in `onAbandon`, spawns a reaper Task (`await task.result` then unregister — the ONLY remover besides process death), and — the actual guard — checks `zombieIntersects(accountId:members:)` BEFORE any provider I/O for every claimed op; a hit demotes the chain WITHOUT ever touching the provider (same loud-report pattern, different message). Direct member intersection (not full chain-relatedness) is the correct guard scope: an op whose members are disjoint from the zombie's touches a different email and may run immediately; a chain-related-but-disjoint-member op is protected anyway by the chain-demotion machinery preserving its own relative order. The per-pass `DrainContext` spin guard (already shipped for persistent-failure demotion) applies unchanged — a chain demoted this pass is requeued untouched, not re-demoted, on re-claim within the same pass.

**The ownership-reset proof (`resetAbandonedInFlightRowsAtOwnershipStart`) now cites the zombie registry** rather than claiming no provider call can be outstanding: a previous owner's OWN gated terminal writes are still guaranteed landed (unchanged — `retryGatedQueueWrite`'s detached task is awaited before `isDraining` flips false), but a previous owner CAN leave an abandoned provider mutation running past that point. Resetting `inFlight -> queued` is still safe because the reset only makes a row RE-CLAIMABLE — `executeSingleOp`'s zombie guard is what refuses to let a re-claim reach the provider until the zombie's reaper observes the abandoned task's actual termination. Reclaimable and executable are now two different gates, not one.

**Residual risk (explicitly accepted, not closed by this fix).** Once a provider request has been fully SENT over the wire, the client cannot un-send it — if the server applies it after the client has already timed out and moved on, that is inherent to any at-least-once retry system talking to a server that doesn't expose idempotency tokens for these specific mutations, and is UNCLOSABLE from the client side. This fix eliminates the CLIENT-SIDE race (no second attempt starts while a zombie could still be running), but a slow-but-eventually-successful zombie completion can still race a legitimate LATER attempt that started only after the zombie was confirmed gone, if the server itself reorders or delays delivery. This residual class is covered the same way every other server/client state mismatch in this codebase is covered: remote-state-wins-on-conflict (ADR-IOS-001) and ordinary sync reconciliation heal a wrong final folder/flag the same as if a second client had raced the same message.

**Rejected alternative: strict await-termination (never abandon the Task).** Change `withTimeout` to await the operation Task's actual completion instead of returning `TimeoutError` while it's still running. Rejected because `withTimeout` exists specifically to bound UNCOOPERATIVE transports — a NIO `connect()` that never resolves, a raw continuation with no cancellation hook — where "await termination" means "wait however long the OS TCP stack takes to give up," observed in the field as multi-minute hangs. Requiring termination before returning would turn one hung IMAP connect into a multi-minute wedge of the ENTIRE global FIFO (every account, not just the one with the bad connection) — strictly worse than the bug being fixed. The zombie registry gets the same safety (no concurrent mutation against the same member) without paying that latency: the DRAIN moves on immediately, and only a NEW attempt against the SAME member is held back, not the whole queue.

Timeout-path pinned by `AccountManagerQueueDemotionTests.timeoutDemotesChainAndUnblocksUnrelatedWork` (Part A) and `AccountManagerQueueLivenessTests`' three zombie-registry tests (Part B: repeated-drain zero-additional-calls, the forward-move/queued-inverse race, and the stranded-inFlight-plus-live-zombie ownership-reset interaction).

**Cross-shape identity amendment (2026-07-15; owner-directed, external-audit Round 2).** Round 2 confirmed a defect in the amendments above: hybrid identity lets ONE physical message be addressed by a provider-token member in one op (admitted while its header lacked an RFC id — the cold-notification-before-sync window) and by an RFC member in a later op (`durableActionMemberIdentity` prefers RFC the moment it exists). Those strings never intersect, so chain demotion could reorder them, the zombie fence missed them, and undo relatedness was blind to them — and because Gmail token IDs are stable (and Graph ids are stable while unmoved), a demoted token op executing late APPLIES rather than no-ops: token `markRead` demoted → newer RFC `markUnread` runs → token `markRead` lands from the tail → final state read, FIFO violated. A second defect: undo annihilation's protected-first-row exclusion was a structural PROOF pre-demotion (only the frontier is ever attempted; a failed frontier stays first), but demotion moves ATTEMPTED rows (timed-out, outcome unknown) behind the frontier where they became annihilable — deleting the only inverse a completed zombie mutation would get. **Owner-approved fix, three parts:** (1) the zombie fence widens to ACCOUNT scope — while any zombie is live for an account, no provider operation for that account starts (other accounts drain); zombies are short-lived, so the cost is negligible and every cross-shape concurrency case is closed including the direction no producer can detect. (2) **Admission shape-stickiness** (amends PLAN_IDENTITY_HYBRID §9's "new actions simply queue RFC members"): inside the same gated insert transaction, if the message's provider id already appears as a member of any ACTIVE row for the account, the new op admits the provider-token member instead of the RFC member — member-string intersection becomes a complete same-message relatedness oracle for the token→RFC direction, so demotion drags cross-shape siblings in order and undo sees them. Nothing is stored: no aliases, no receipts, no in-place member rewrites; once the token rows drain, new ops admit RFC as before. Undo inverses are exempt (they reuse the forward's exact member string — same-shape by construction). Residual (accepted, documented): the REVERSE direction — RFC rows active, then an identity-less cold token op for the same message — is undetectable without alias machinery; its dangerous concurrent variant is covered by the account fence, and its ordering variant requires a no-RFC push payload + active RFC rows + a demotion, essentially theoretical. (3) **Annihilation requires provably-never-attempted:** v73 adds `pendingOperation.everAttempted` (backfilled TRUE for pre-existing rows — the conservative direction, since annihilation is an optimization: a false `true` costs two provider round-trips, a false `false` can delete the inverse of an applied mutation). The flag is persisted in a gated write strictly BEFORE any provider I/O for the claimed op (not at claim — a zombie-guard-demoted op made no attempt), so a crash mid-attempt leaves `true`. `reconcileUndoAdmission` annihilates an exact flip only when `everAttempted == false`; an attempted exact flip stops the scan and falls through to appending the ordinary inverse — always serially correct. **Rejected alternative: account-scoped DEMOTION** (the auditor's original recommendation) — demoting all of an account's rows as one block is airtight but regresses decision 1's amendment's core goal: one persistently-poisoned op would stall EVERY action on that account indefinitely, the exact intra-account wedge demotion was built to eliminate; the fence is account-scoped only because zombies are transient. **Also (owner-approved, same round):** the destination-missing move self-heal no longer DROPS the op — it demotes the chain loudly instead; with demotion available, never-drop-user-intention is honorable without the retry-forever wedge the drop was originally built to avoid (Law 4 usually resolves the parked op: e.g. Gmail invalid-label 400 is an authoritative no-op).

**Cross-shape amendment refinement (2026-07-15; owner-directed, external-audit Round 2b).** The audit's second pass found two confirmed defects in the amendment above. (1) **Stickiness was provider-blind, and IMAP tokens are MAILBOX-scoped:** after an optimistic move the header row keeps its stale UID until sync re-keys it, so account-scoped stickiness could rewrite a CORRECT RFC member into a stale UID paired with the post-move folder — and `resolveTokenMember`'s exact UID FETCH in that wrong mailbox can mutate an UNRELATED message (Gmail ids are account-scoped+stable — worst case a late apply; Graph ids churn on move — worst case a stale no-op; only IMAP/iCloud can wrong-message). The same audit surfaced a PRE-EXISTING released-parity variant needing no stickiness at all: an identity-less IMAP message acted on in the post-optimistic-move window naturally admits its stale UID with the new folder — which also falsified the hybrid claim "worst case zero-match no-op, never a wrong-message mutation" for IMAP in that window. (2) **The undo stickiness exemption was unsound:** `UndoMember.memberIdentity` is captured at GESTURE time while the forward's substitution happens at FOLD-INSERT time, so a sticky-substituted forward (token) and its inverse (RFC) stopped chain-intersecting — no annihilation match, and the forward/inverse pair itself became reorderable cross-shape. **Owner-approved fix, three parts:** (1) stickiness is PROVIDER-AWARE — `stickyDurableMember` returns the preferred RFC member unchanged for `.imap`/`.icloud` accounts (Account fetched in the same gated txn; missing account fails open to RFC). The IMAP cross-shape ORDERING residual is accepted and documented: post-move token ops zero-match (UIDs are never reused within a UIDVALIDITY), and the only landing case — a setter with no intervening move, after a bare-notification token admission plus a demotion — is the same essentially-theoretical class as the accepted reverse direction. (2) undo inverses get the SAME substitution AT ADMISSION instead of an exemption: inside the undo's gated txn, each inverse member runs through `stickyDurableMember` using the RESOLVED header's provider id (available from the undo path's own header resolution), and the inverse op is built with the substituted members BEFORE `reconcileUndoAdmission` compares flips — so a sticky forward and its inverse share a shape again (annihilation and chain-intersection restored); once the forward has drained, no token row is active and the inverse admits RFC as before. (3) **IMAP source-mailbox grouping:** at admission, an IMAP/iCloud token member that appears in an ACTIVE `.move` row's member set is grouped under that move's SOURCE folderPath (lowest-rowid move if several) — the mailbox where the UID was actually observed — instead of the header's post-optimistic-move folder. Every branch improves: if the move executed, the follow-up is a stale zero-match no-op instead of a potential wrong-message mutation; if the move never executes (demoted/failed), the follow-up lands on the CORRECT message in the CORRECT mailbox. This exceeds released fidelity and restores the "never a wrong-message mutation" guarantee for IMAP tokens (the code-comment claim is re-qualified accordingly). **Rejected alternative (auditor's proposal): dual identity** — separating ordering identity from provider execution identity on each row is airtight but is exactly the alias/lineage machinery the hybrid stop-signs forbid (the receipt spiral), for a corner that closes without it. **UIDVALIDITY residual — CLOSED same day (owner-directed full closure, 2026-07-15).** The Round 2b text originally accepted the UIDVALIDITY-reset residual as documentation-only. The owner then observed the app KNOWS about resets — and it does, in two places: sync maintains `Folder.lastKnownUidValidity` (force-resync on change) *(claim corrected in ADR-IOS-061: at the time of this text the ONLY writer was the reconcile-walk bootstrap and no force-resync existed — ADR-IOS-061's ledger + reaction are what made this true)*, and the IMAP SELECT response carries the live value on the wire immediately before any UID FETCH. The residual existed only because the two halves sat on opposite sides of the adapter boundary. Closure, two composing checks covering both discovery orderings: **(A)** IMAP/iCloud token members are SEGREGATED from RFC members at admission (a token-only op can be killed whole without dropping RFC intent); v74 adds `pendingOperation.observedUidValidity`, stamped at admission from the effective folder's `lastKnownUidValidity`; at claim time, stamp ≠ the folder's current stored value ⇒ sync already saw a reset postdating the token ⇒ authoritative stale no-op before any provider I/O (loud one-liner; the reset's force-resync heals optimistic state). **(B)** `IMAPProvider.init` gains a DEFAULTED expected-uidValidity closure (only the drain's registration site supplies it — all other call sites compile unchanged, which is why the earlier "20-call-site widening" objection dissolved); the queue publishes the in-flight op's ADMISSION-era stamp via a Mutex slot (sound under the single-op-at-a-time FIFO; the stamp, not the current Folder row, is the baseline — the row could be rewritten by a sync landing between the claim check and the SELECT), and `resolveTokenMember` no-ops when the live SELECT UIDVALIDITY differs. Case coverage: sync-noticed-first → A kills at claim; drain-first → stored still equals the stamp so B's live-vs-stamp mismatch no-ops; no reset → all equal, proceeds; post-resync fresh token → stamped with the new value, proceeds. Restart-instead-of-drop was considered and rejected: a post-reset token is unrecoverable by construction (no RFC to re-derive), so authoritative-stale is the only correct semantic. "Never a wrong-message mutation" for IMAP tokens is now UNCONDITIONAL (pre-v74 rows carry a NULL stamp and keep the old, released-parity exposure for their short remaining lifetime — fail-open by design). (b) The explicit fidelity cost: after a successful IMAP token move, a later token-only action executes against the old source mailbox and stale-no-ops — deliberately losing that action's fidelity rather than risking another message; an RFC-capable follow-up stays safe modulo the documented demotion-ordering residual. Per-member grouping is mandatory: a mixed batch whose token members were observed in different mailboxes SPLITS into one op per observation mailbox (`partitionByEffectiveOpFolder`).

**Gesture→fold identity amendment (2026-07-15; owner-directed, external-audit Round 2d).** A further external pass found the one layer the UIDVALIDITY closure could not protect: the closure's "never a wrong-message mutation" claim held for the QUEUED phase (admission→execution) but not for the gesture→fold phase UPSTREAM of it. The intention journal recorded only composite row-id strings (accountId:folderPath:messageId) and `executeFold` re-resolved FRESH rows from them — so an IMAP UIDVALIDITY reset whose force-resync replaced the row the user saw with a different physical message under the SAME composite key (only possible via an epoch swap; provider ids are never reused so Gmail/Graph are immune) let the fold act on the impostor, and every downstream check then correctly authenticated the impostor. The interaction-freeze rule's deferred reloads make the window seconds-wide. **Owner-approved fix — snapshot-identity verification, in-memory only:** journal records optionally carry a per-id `ExpectedMessageIdentity` (rfc822MessageId + envelope date) captured for free from the visualized snapshot the producer already holds — the snapshot IS the user's intention target and gesture paths stay ZERO-DB. At fold time each (record, id) contribution is applied only if the re-resolved row matches (both-rfc-non-nil → rfc equality, else envelope-date equality — nil→non-nil rfc can be the same message whose rfc a later in-place update filled in); mismatches drop with the existing vanished-row semantics (no optimistic mutation, no durable admission, overlay entry cleaned). Coalescing keys are UNCHANGED — per-record application-time filtering makes "(rowID, generation)" connectivity unnecessary. Undo tier-1 gains an identity guard (resolved row must match `UndoMember.memberIdentity`; mismatch = tier-1 miss, falls to the inherently identity-matched tier-2). Missing identities fail open (verification skipped — current behavior), so producers without headers cannot regress. **Rejected alternative (external agent's proposal): per-intention generation pins** carrying observed mailbox + UIDVALIDITY at record time — gesture paths are ZERO-DB by hard rule, so those pins cannot be captured where they'd be true, and capturing at fold time reads the wrong epoch; identity comparison also strictly dominates the epoch pin (a reset that re-lists the SAME message at the SAME UID identity-matches and correctly proceeds, where an epoch pin would false-refuse). The external agent's ~2k-line partial implementation was preserved unmerged on `wip/generation-pins-external-20260715` (local, never push). With this amendment the wrong-message guarantee is end-to-end: gesture→fold (snapshot identity), admission (segregation+stamp), claim (stamp-vs-Folder), execution (live SELECT vs stamp), all providers. *(Scoped by ADR-IOS-061: the fold-resolve→action-txn seam and the in-flight body-persist path were still open when this was written; both are closed there, along with the root cause.)*
