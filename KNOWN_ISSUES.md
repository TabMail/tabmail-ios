# TabMail iOS Known Issues

This is the searchable register for deliberately deferred iOS behavior. Read it before planning or reviewing a matching subsystem. Resolved items do not remain here; their history belongs in ADRs, audit plans, and Git. The release policy is: restoring sync/list state after a fail-closed edge is acceptable; mutating the wrong message or draft is not.

| ID | Status | Subsystem / keywords | Deferred policy |
|---|---|---|---|
| IOS-EPOCH-001 | Accepted fail-closed window (T1.3) | IMAP; iCloud; UIDVALIDITY; `Folder.lastKnownUidValidity`; durable admission; first sync; silent no-op; archive; delete; move; mark read; flag; user label; draft save; demo mode; orphaned header | **What the user observes:** on an IMAP or iCloud account, a gesture made against a brand-new folder *during that folder's very first sync* appears to do nothing — the message does not animate away, the flag does not stick, and no error is shown. Repeating the gesture once the folder has finished its first sync works normally. **Why:** a durable IMAP action is refused when the target folder's `Folder.lastKnownUidValidity` is nil, because `MessageHeader.stableId` falls back to a bare numeric UID for any header lacking an `rfc822MessageId` and `IMAPProvider.resolveUID` treats a numeric id as a literal UID — executing that under an unknown epoch risks mutating a DIFFERENT message (constraint C3). Failing closed is always acceptable; mutating the wrong message is not. The refusal is a **silent no-op** by owner decision §9 D6(a) — no dialog, no toast. **The bound:** T1.2b (`7c71f6c7b`) persists the epoch from the `Mailbox.Selection` of SELECTs the sync and folder-open paths already perform, and `OK [UIDVALIDITY n]` is core IMAP4rev1 rather than a UIDPLUS extension, so every server reports it on SELECT even when it never answers a UIDVALIDITY STATUS. Audit round 7 closed a hole in that bound: a **custom NON-FAVOURITE folder** is excluded from `syncableFolders`, so no *scheduled* pass (full sync, delta sync, self-heal) ever SELECTs it, while `runBackfill` crawls it and makes its mail account-wide searchable — on a non-UIDPLUS server its epoch stayed nil and every gesture on it was refused. ⚠ **Round 7 called that refusal PERMANENT and a "brick"; round 8 RETRACTS the absolute.** On-demand navigation reaches ANY folder: `InboxView.onAppear` → `InboxViewModel.startSync()` → `performSync()` → `AccountManager.syncFolders(_:)` (`AccountManagerFetch.swift`, filtering on `!folder.path.isEmpty` alone — no role, no favourite predicate) → `SyncEngine.syncFolderMessages` → `syncMessages` → `runSyncMessages`, which carries the T1.2b SELECT-sourced bootstrap; `SyncEngineFullSync.swift` states it three lines under the `syncableFolders` construction (*"Custom non-favorited folders sync on-demand when the user navigates to them"*). The refusal was therefore **indefinite until the user opens that folder**, not permanent — still a real bug for mail reachable only through account-wide search in a folder the user never opens, which is why the crawl-sourced bootstrap stays. **Round 8 also replaced the VALUE that bootstrap writes.** Round 7 took ONE post-walk sample of `IMAPProvider.lastObservedUidValidity`, and the walk's own SELECTs were raw, so the mirror held the epoch observed when the pinned connection was CREATED and tracked no turnover during the crawl — on a resumed crawl it could be an epoch the mailbox rolled to AFTER an earlier pass's headers were written, and since this guard tests only for nil it then ADMITTED bare-UID gestures that resolved against a different message (C3). The crawl's three SELECTs (`getUidNext`, `searchExistingUIDs(folder:from:to:)`, `fetchMessageHeaders(folder:uids:…)`) now route through `IMAPProvider.selectMailboxTracked`; the walk captures its epoch ONCE at walk start, refuses (never confirms) any chunk whose own SELECT disagrees, and stamps through `SyncEngine.bootstrapCrawledFolderUidValidity`, which is **bootstrap-only AND gated on the folder holding no local header yet** — evaluated inside the write transaction, so the epoch it asserts is the epoch of every UID it unlocks. A folder that already holds rows of unproven epoch is NOT stamped: v3 has not ported ADR-IOS-061's purge-and-resync reaction, so failing closed there is the only C3-safe answer (C6). A folder whose mailbox turned over is also DECLINED for the rest of that `runBackfill` call (`epochDeclinedFolderIds`) and on every later call whose walk epoch disagrees with the stored one (`SyncEngine.crawlEpochAgrees`) — without that the outer folder loop simply re-walked the still-incomplete folder under the new epoch and inserted the mixed population the per-chunk guard had just refused. **Carve-outs and inversions (audit rounds 6–7) — do not "simplify" these away:** (1) Gmail and Exchange never populate `FolderInfo.uidValidity` at all, so their epoch is nil forever; the refusal is provider-scoped to `.imap`/`.icloud` and must never be widened to "the column is nil", which would permanently brick every Gmail and Exchange account. (2) The **demo account is excluded by id** (`DemoSeed.demoAccountId`): it is stored as `provider: .imap` but served by `DemoProvider`, which has no server and can never stamp an epoch, so without the carve-out every guarded gesture in Demo Mode was refused forever. (3) A missing `Folder` row now fails **CLOSED**, inverting what this row said before commit `8f20ab2f4`. An orphaned header (folder row deleted by `fullSync` while its headers survive — no FK since migration v2) carries a bare OLD-epoch UID under no metadata at all, and admitting it is precisely C3. The two callers that once justified the fail-open no longer reach the guard with a guessed path: `UserLabelMenuModel.resolvedFolderPath()` returns nil instead of guessing `"INBOX"`, and the draft sites guard only the id shapes that resolve an EXISTING UID. (4) The two **draft** guards are classified by what the provider DOES with the id, not by the op's name — `serverDraftId` nil ⇒ pure APPEND (admit), non-numeric ⇒ Message-ID SEARCH, epoch-immune (admit), numeric ⇒ literal-UID `STORE \Deleted` + `EXPUNGE` (guard). The numeric case is re-classified again at EXECUTION time in `DraftStore.pushDraftToServer`, because two saves queued while the id was still nil are both admitted as APPEND-only and the second one executes against a live row that has since become numeric. A refused draft save loses nothing of the user's: the local `Draft` row keeps the content and only the server copy stays stale. (5) A synthesized/fake epoch was proposed and REJECTED (owner, 2026-07-30). **Residual:** until the D5 purge-and-resync reaction (T4.S6) lands, `lastKnownUidValidity` is bootstrap-only for VALUES and never advances past a real UIDVALIDITY turnover, so this admission guard must NOT be read as "the epoch model is now sound". Do not close T4.S6's row by pointing at T1.3. **Round 10 corrections, all user-visible:** (1) an EMPTY folder whose mailbox turned over mid-crawl used to be refused on every later pass forever — the stored epoch could never agree with the live one again and no writer could advance it, so the folder never gained mail again and no Smart Reindex recovered it. `SyncEngine.resetEmptyFolderCrawlEpoch` now CLEARS the stamp and the cursor (writes NULLs only, so the VALUE-writer set stays at three) when the folder holds zero headers, and the next iteration re-derives both from the live mailbox; a folder holding rows stays refused, which is still T4.S6's case. (2) A pass that could not observe the folder's epoch — a failed walk-start SELECT, or a server that stops reporting `UIDVALIDITY` — no longer walks a folder that HAS a stored epoch; **new accepted user-visible bound:** if a server reports an epoch once and then permanently stops, that folder's crawl re-declines every cycle (one SELECT per cycle) and its un-crawled mail stays un-indexed **indefinitely — not permanently**: one SELECT that reports again clears it. An account whose server NEVER reports `UIDVALIDITY` is unaffected (its folders have a nil stored epoch and are crawled normally). (3) A transient failure of the crawl's epoch-bootstrap WRITE used to leave the folder durably unstampable — the failing pass inserted headers, which made its own retry precondition false — so every gesture on that folder's mail became a permanent silent no-op with no way back; the throw now declines the folder before the walk inserts anything. |
