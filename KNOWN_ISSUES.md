# TabMail iOS Known Issues

This is the searchable register for deliberately deferred iOS behavior. Read it before planning or reviewing a matching subsystem. Resolved items do not remain here; their history belongs in ADRs, audit plans, and Git. The release policy is: restoring sync/list state after a fail-closed edge is acceptable; mutating the wrong message or draft is not.

| ID | Status | Subsystem / keywords | Deferred policy |
|---|---|---|---|
| IOS-EPOCH-001 | Accepted fail-closed window (T1.3) | IMAP; iCloud; UIDVALIDITY; `Folder.lastKnownUidValidity`; durable admission; first sync; silent no-op; archive; delete; move; mark read; flag; user label; draft save; demo mode; orphaned header | **What the user observes:** on an IMAP or iCloud account, a gesture made against a brand-new folder *during that folder's very first sync* appears to do nothing — the message does not animate away, the flag does not stick, and no error is shown. Repeating the gesture once the folder has finished its first sync works normally. **Why:** a durable IMAP action is refused when the target folder's `Folder.lastKnownUidValidity` is nil, because `MessageHeader.stableId` falls back to a bare numeric UID for any header lacking an `rfc822MessageId` and `IMAPProvider.resolveUID` treats a numeric id as a literal UID — executing that under an unknown epoch risks mutating a DIFFERENT message (constraint C3). Failing closed is always acceptable; mutating the wrong message is not. The refusal is a **silent no-op** by owner decision §9 D6(a) — no dialog, no toast. **The bound:** T1.2b (`7c71f6c7b`) persists the epoch from the `Mailbox.Selection` of SELECTs the sync and folder-open paths already perform, and `OK [UIDVALIDITY n]` is core IMAP4rev1 rather than a UIDPLUS extension, so every server reports it on SELECT even when it never answers a UIDVALIDITY STATUS. Audit round 7 closed the one hole in that bound: a **custom NON-FAVOURITE folder** is excluded from `syncableFolders`, so no sync pass ever SELECTs it, while `runBackfill` crawls it and makes its mail searchable — its epoch stayed nil FOREVER on a non-UIDPLUS server and every gesture on it was refused permanently. `SyncEngine.runBackfill`'s IMAP branch now bootstraps the epoch from the pinned connection's own SELECT — one post-walk sample, **bootstrap-only**, carrying exactly the residual `runSyncMessages`' T1.2b bootstrap already carries. The window is therefore bounded to the first crawl/sync of a folder and cannot become permanent. **Carve-outs and inversions (audit rounds 6–7) — do not "simplify" these away:** (1) Gmail and Exchange never populate `FolderInfo.uidValidity` at all, so their epoch is nil forever; the refusal is provider-scoped to `.imap`/`.icloud` and must never be widened to "the column is nil", which would permanently brick every Gmail and Exchange account. (2) The **demo account is excluded by id** (`DemoSeed.demoAccountId`): it is stored as `provider: .imap` but served by `DemoProvider`, which has no server and can never stamp an epoch, so without the carve-out every guarded gesture in Demo Mode was refused forever. (3) A missing `Folder` row now fails **CLOSED**, inverting what this row said before commit `8f20ab2f4`. An orphaned header (folder row deleted by `fullSync` while its headers survive — no FK since migration v2) carries a bare OLD-epoch UID under no metadata at all, and admitting it is precisely C3. The two callers that once justified the fail-open no longer reach the guard with a guessed path: `UserLabelMenuModel.resolvedFolderPath()` returns nil instead of guessing `"INBOX"`, and the draft sites guard only the id shapes that resolve an EXISTING UID. (4) The two **draft** guards are classified by what the provider DOES with the id, not by the op's name — `serverDraftId` nil ⇒ pure APPEND (admit), non-numeric ⇒ Message-ID SEARCH, epoch-immune (admit), numeric ⇒ literal-UID `STORE \Deleted` + `EXPUNGE` (guard). The numeric case is re-classified again at EXECUTION time in `DraftStore.pushDraftToServer`, because two saves queued while the id was still nil are both admitted as APPEND-only and the second one executes against a live row that has since become numeric. A refused draft save loses nothing of the user's: the local `Draft` row keeps the content and only the server copy stays stale. (5) A synthesized/fake epoch was proposed and REJECTED (owner, 2026-07-30). **Residual:** until the D5 purge-and-resync reaction (T4.S6) lands, `lastKnownUidValidity` is bootstrap-only and never advances past a real UIDVALIDITY turnover, so this admission guard must NOT be read as "the epoch model is now sound". Do not close T4.S6's row by pointing at T1.3. |
