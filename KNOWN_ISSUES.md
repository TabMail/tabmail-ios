# TabMail iOS Known Issues

This is the searchable register for deliberately deferred iOS behavior. Read it before planning or reviewing a matching subsystem. Resolved items do not remain here; their history belongs in ADRs, audit plans, and Git. The release policy is: restoring sync/list state after a fail-closed edge is acceptable; mutating the wrong message or draft is not.

| IOS-EPOCH-001 | Accepted fail-closed window (T1.3) | IMAP; iCloud; UIDVALIDITY; `Folder.lastKnownUidValidity`; durable admission; first sync; silent no-op; archive; delete; move; mark read; flag; user label; draft save; demo mode; orphaned header | **What the user observes:** on an IMAP or iCloud account, a gesture made against a brand-new folder *during that folder's very first sync* appears to do nothing — the message does not animate away, the flag does not stick, and no error is shown. Repeating the gesture once the folder has finished its first sync works normally. **Why:** a durable IMAP action is refused when the target folder's `Folder.lastKnownUidValidity` is nil, because `MessageHeader.stableId` falls back to a bare numeric UID for any header lacking an `rfc822MessageId` and `IMAPProvider.resolveUID` treats a numeric id as a literal UID — executing that under an unknown epoch risks mutating a DIFFERENT message (constraint C3). Failing closed is always acceptable; mutating the wrong message is not. The refusal is a **silent no-op** by owner decision §9 D6(a) — no dialog, no toast. **The bound:** T1.2b (`7c71f6c7b`) persists the epoch from the `Mailbox.Selection` of SELECTs the sync and folder-open paths already perform, and `OK [UIDVALIDITY n]` is core IMAP4rev1 rather than a UIDPLUS extension, so every server reports it on SELECT even when it never answers a UIDVALIDITY STATUS. Audit round 7 closed a hole in that bound: a **custom NON-FAVOURITE folder** is excluded from `syncableFolders`, so no *scheduled* pass (full sync, delta sync, self-heal) ever SELECTs it, while `runBackfill` crawls it and makes its mail account-wide searchable — on a non-UIDPLUS server its epoch stayed nil and every gesture on it was refused. ⚠ **Round 7 called that refusal PERMANENT and a "brick"; round 8 RETRACTS the absolute.** On-demand navigation reaches ANY folder: `InboxView.onAppear` → `InboxViewModel.startSync()` → `performSync()` → `AccountManager.syncFolders(_:)` (`AccountManagerFetch.swift`, filtering on `!folder.path.isEmpty` alone — no role, no favourite predicate) → `SyncEngine.syncFolderMessages` → `syncMessages` → `runSyncMessages`, which carries the T1.2b SELECT-sourced bootstrap; `SyncEngineFullSync.swift` states it three lines under the `syncableFolders` construction (*"Custom non-favorited folders sync on-demand when the user navigates to them"*). The refusal was therefore **indefinite until the user opens that folder**, not permanent — still a real bug for mail reachable only through account-wide search in a folder the user never opens, which is why the crawl-sourced bootstrap stays. **Round 8 also replaced the VALUE that bootstrap writes.** Round 7 took ONE post-walk sample of `IMAPProvider.lastObservedUidValidity`, and the walk's own SELECTs were raw, so the mirror held the epoch observed when the pinned connection was CREATED and tracked no turnover during the crawl — on a resumed crawl it could be an epoch the mailbox rolled to AFTER an earlier pass's headers were written, and since this guard tests only for nil it then ADMITTED bare-UID gestures that resolved against a different message (C3). The crawl's three SELECTs (`getUidNext`, `searchExistingUIDs(folder:from:to:)`, `fetchMessageHeaders(folder:uids:…)`) now route through `IMAPProvider.selectMailboxTracked`; the walk captures its epoch ONCE at walk start, refuses (never confirms) any chunk whose own SELECT disagrees, and stamps through `SyncEngine.bootstrapCrawledFolderUidValidity`, which is **bootstrap-only AND gated on the folder holding no local header yet** — evaluated inside the write transaction, so the epoch it asserts is the epoch of every UID it unlocks. A folder that already holds rows of unproven epoch is NOT stamped: v3 has not ported ADR-IOS-061's purge-and-resync reaction, so failing closed there is the only C3-safe answer (C6). A folder whose mailbox turned over is also DECLINED for the rest of that `runBackfill` call (`epochDeclinedFolderIds`) and on every later call whose walk epoch disagrees with the stored one (`SyncEngine.crawlEpochAgrees`) — without that the outer folder loop simply re-walked the still-incomplete folder under the new epoch and inserted the mixed population the per-chunk guard had just refused. **Carve-outs and inversions (audit rounds 6–7) — do not "simplify" these away:** (1) Gmail and Exchange never populate `FolderInfo.uidValidity` at all, so their epoch is nil forever; the refusal is provider-scoped to `.imap`/`.icloud` and must never be widened to "the column is nil", which would permanently brick every Gmail and Exchange account. (2) The **demo account is excluded by id** (`DemoSeed.demoAccountId`): it is stored as `provider: .imap` but served by `DemoProvider`, which has no server and can never stamp an epoch, so without the carve-out every guarded gesture in Demo Mode was refused forever. (3) A missing `Folder` row now fails **CLOSED**, inverting what this row said before commit `8f20ab2f4`. An orphaned header (folder row deleted by `fullSync` while its headers survive — no FK since migration v2) carries a bare OLD-epoch UID under no metadata at all, and admitting it is precisely C3. The two callers that once justified the fail-open no longer reach the guard with a guessed path: `UserLabelMenuModel.applyLabel(_:)`/`removeLabel(_:)` resolve the header inside their own admission write transaction and abort when it is missing (T4.V13 deleted the `resolvedFolderPath()` helper that once guessed `"INBOX"`; resolving in-transaction is strictly stronger, since the helper still read the header in an earlier transaction and a MOVE landing in between could name the folder the message had already left), and the draft sites guard only the id shapes that resolve an EXISTING UID. (4) The two **draft** guards are classified by what the provider DOES with the id, not by the op's name — `serverDraftId` nil ⇒ pure APPEND (admit), non-numeric ⇒ Message-ID SEARCH, epoch-immune (admit), numeric ⇒ literal-UID `STORE \Deleted` + `EXPUNGE` (guard). The numeric case is re-classified again at EXECUTION time in `DraftStore.pushDraftToServer`, because two saves queued while the id was still nil are both admitted as APPEND-only and the second one executes against a live row that has since become numeric. A refused draft save loses nothing of the user's: the local `Draft` row keeps the content and only the server copy stays stale. (5) A synthesized/fake epoch was proposed and REJECTED (owner, 2026-07-30). **Residual:** until the D5 purge-and-resync reaction (T4.S6) lands, `lastKnownUidValidity` is bootstrap-only for VALUES and never advances past a real UIDVALIDITY turnover, so this admission guard must NOT be read as "the epoch model is now sound". Do not close T4.S6's row by pointing at T1.3. **Round 10 corrections, all user-visible:** (1) an EMPTY folder whose mailbox turned over mid-crawl used to be refused on every later pass forever — the stored epoch could never agree with the live one again and no writer could advance it, so the folder never gained mail again and no Smart Reindex recovered it. `SyncEngine.resetEmptyFolderCrawlEpoch` now CLEARS the stamp and the cursor (writes NULLs only, so the VALUE-writer set stays at three) when the folder holds zero headers, and the next iteration re-derives both from the live mailbox; a folder holding rows stays refused, which is still T4.S6's case. (2) A pass that could not observe the folder's epoch — a failed walk-start SELECT, or a server that stops reporting `UIDVALIDITY` — no longer walks a folder that HAS a stored epoch; **accepted user-visible bound, CORRECTED in round 12:** if a server reports an epoch for a folder once and then stops reporting it on SELECT, that folder's crawl re-declines every cycle (one SELECT per cycle) and its un-crawled mail stays un-indexed **PERMANENTLY for as long as the server keeps omitting it** — round 11 wrote "indefinitely — not permanently", and that was wrong in the way that matters: `.refuseUnobservedEpoch` mutates nothing, so the state (stored epoch present, none observed) is re-created on every later call, i.e. a per-call decline container with a DURABLE re-entry condition, which is the same "transient container + durable re-entry ⇒ permanent refusal" shape `resetEmptyFolderCrawlEpoch` exists to break. What IS true is only that the condition is a property of the server, not a local latch: one conformant SELECT clears it (`BackfillOnlyFolderEpochTests.aFolderWithAStoredEpochIsNeverWalkedUnderAnUnobservedOne` now asserts both halves — the refusal recurring across calls, and the recovery). **Round 12 also retracts the reasoning round 11 gave for this refusal.** It argued that a non-nil stored epoch *proves the server reports UIDVALIDITY*, so refusing could only ever catch a transient failure. That inference is FALSE: the stored epoch can come from `IMAPProvider.fetchFolders`' STATUS command (through `SyncEngine.fullSync`'s folder-list upsert) while the walk's comes from SELECT, so a stamp proves the server reports UIDVALIDITY *somewhere*, not that SELECT does; and a SELECT that succeeds while reporting `UIDVALIDITY 0` normalises to nil too. The refusal stands on a stronger footing instead: RFC 3501 §6.3.1 lists UIDVALIDITY among SELECT's **REQUIRED** OK untagged responses (UNSEEN, PERMANENTFLAGS, UIDNEXT, UIDVALIDITY) and states that if it is missing the server does not support unique identifiers — RFC 9051 §6.3.2 the same. A server omitting it is nonconforming and is declaring it has no UIDs, which is an account this app cannot serve at all, so no bounded recovery is built for it and the fail-closed refusal is the whole answer (C3 outranks C6's tolerance for a stalled crawl). An account whose server NEVER reports `UIDVALIDITY` is unaffected (its folders have a nil stored epoch and are crawled normally). (3) A transient failure of the crawl's epoch-bootstrap WRITE used to leave the folder durably unstampable — the failing pass inserted headers, which made its own retry precondition false — so every gesture on that folder's mail became a permanent silent no-op with no way back; the throw now declines the folder before the walk inserts anything. **Round 12 corrections.** (1) TWO of the crawl's six IMAP-branch bookkeeping writes were UNGUARDED — the `case .fresh` completion write (`backfillComplete`/`lastKnownUidNext` when UIDNEXT ≤ 1) and the initial-cursor planting write — while the commit that added the guard and `SyncEngine.crawlWalkWriteAllowed`'s own doc both claimed *every* bookkeeping transaction re-read the folder row. `v2final` guards both (`uidValidityWalkWriteAllowed`, log strings *"skipping fully-crawled write"* / *"skipping initial cursor write"*), so this was a PORT GAP, not a v3 design choice. Unguarded, a folder re-stamped by a sibling pass while this one was on the network could be declared fully crawled by the stale pass (its mail then permanently outside automatic backfill, since every cycle selects on `backfillComplete == false`), or gain a cursor and rows from an epoch its stamp does not describe (C3). (2) `SyncEngine.crawlWalkWriteAllowed` now COMPARE-AND-SETs the folder's stamp against the premise the pass's bookkeeping was accounted under, instead of comparing it to the walk's epoch: `resetEmptyFolderCrawlEpoch` made value→nil reachable, and a nil stored epoch ADMITTED — the fail-open direction. (3) `resetEmptyFolderCrawlEpoch` was a TOCTOU across two overlapping `runBackfill` calls (the persistent worker `SyncEngine.startBackfill` launches, and `SyncScheduler`'s BGProcessing pass; `SyncEngine` is an actor, so they interleave). It checked only `headerCount == 0` and then updated by folder id, so a walk acting on an already-stale mismatch could clear a stamp a sibling had just re-derived, and the sibling's already-fetched batch — held outside SQLite, invisible to the count — then landed under a nil stamp whose final guard read the nil as agreement and marked the populated folder COMPLETE. Durable end state: rows present, no epoch, complete — excluded from every later crawl cycle and un-re-stampable, because the header-count gate refuses a populated folder, so not even Smart Reindex recovers it. It now re-validates, inside its own transaction, that the folder is still incomplete and still carries the stamp the gate saw disagree. (4) The initial-cursor write was a bare `try await`: a throw fell through to the folder loop's outer `catch`, which only logs, leaving the folder incomplete, cursor-less and undeclined, so the loop's fresh re-read handed back the same folder with no inter-folder delay — an unbounded network-rate SELECT loop under a persistent write failure (GRDB suspension / ADR-IOS-046, `SQLITE_FULL`, corruption). `v2final`'s counterpart write has the same shape, so this is a DELIBERATE divergence from the reference, not a port regression. **⚠ ROW RE-BASELINED 2026-08-02 — the second half of this row is what commit `3843940cb` actually SHIPPED, and it is FAIL-CLOSED. Earlier revisions of this row described only the admission-time nil-epoch refusal and left the reader to assume the reference's post-turnover behaviour, which was fail-OPEN across retries: the reference compares the live selection against a `Selection` minted inside the same call, so its refusal SILENTLY RE-ARMS on the next attempt and the op eventually executes under numbering it never observed. v3 does not do that.** **What the user observes (the shipped behaviour):** an IMAP or iCloud gesture that was already queued when the mailbox's UIDVALIDITY turns over never completes. It does not animate back, it does not error, and repeating the gesture after the turnover works normally. **Why:** v3 compares against the op's **durable** `PendingOperation.observedUidValidity`, stamped at admission from the header/snapshot that observed that exact UID (ADR-IOS-068), so **once the folder's epoch moves, every retry of that op fails identically and forever.** The intention is DROPPED rather than executed under numbering it never observed — the deliberate departure from never-drop that ADR-IOS-069 authorises as the queue's fourth exit and that `IOS-ACTION-002` records as a user-visible cost. Failing closed is always acceptable (C3); mutating the wrong message is not. `IMAPProvider.move` enforces this at **five** boundaries — A1 wrapper selection, A2 the post-destination-probe source re-SELECT, A3 pre-COPY, A4 pre-STORE, A5 pre-`UID EXPUNGE` — and a non-UIDPLUS server fails closed at copy-plus-soft-delete with no expunge of any kind. The UIDPLUS gate is checked BEFORE A5 deliberately: asserting first would let an epoch change refuse an already-complete op, and a refusal after a successful COPY retries into a duplicate at the destination. **The one ACCEPTED RESIDUAL, stated by that commit:** a turnover landing between the COPY and A4 leaves the copy at the destination and the original at the source. Sync reconciles it, and it is strictly safer than completing the delete. |
| IOS-ACTION-001 | Accepted one-time upgrade loss | Action queue; `pendingOperation`; migration `v74`; blanket purge; upgrade; legacy op | Migration `v74_purgeLegacyPendingOperations` runs `DELETE FROM pendingOperation` with no predicate. Any action op queued by a pre-v3 build and not yet drained at upgrade is gone: it removes every legacy row regardless of type, status, decodability or shape, including `.saveDraft` and `.deleteDraft`. Nothing user-authored is touched — `PendingOperation` owns no authored bytes and has no cascade into `Draft`, `Outbox`, `MessageBody` or attachment storage, so draft identity/body/recipients/attachments and Outbox sends remain byte-identical. A dropped `.saveDraft` loses only the automatic server-push intention (the local content stays; the user saves again); a dropped `.deleteDraft` may leave a stale server draft that sync shows again, which is safer than retaining an obsolete destructive address. Startup still runs Outbox reconciliation independently. See ADR-IOS-071. |
| IOS-ACTION-002 | Accepted fail-closed id-reset edge — **a deliberate departure from never-drop** | UIDVALIDITY; provider id reset; queued op; drop; rebind; quarantine; C2; C4; C5 | On a UIDVALIDITY change or a provider stable-id reset, every queued op that named an address in the affected space is **dropped** — not rebound, not re-resolved, not re-searched, not quarantined. The user repeats the gesture; sync reconciles the visible state. **This row exists precisely because the behaviour is a deliberate carve-out of "never drop user intention", not an accident:** the invariant still holds in full on the ordinary path (offline, retry, app kill, provider error, transient read failure) and only the id-reset boundary is carved out. It never extends past queue state — Outbox sends, drafts, bodies, attachments and FTS content are never dropped under it, and double-send prevention is unchanged. Owner: *"much better than a fragile and complicated codebase."* See ADR-IOS-069. |
| IOS-DATE-001 | Pre-existing / deferred; byte-identical to v1.6.38 | IMAP; missing INTERNALDATE; authored Date fallback; Inbox display; sort | When an IMAP server omits `INTERNALDATE`, the existing parser may fall back to the message-authored `Date` header. That exceptional fallback predates this work and remains byte-identical to v1.6.38; normal IMAP `INTERNALDATE`, Gmail `internalDate`, and Graph `receivedDateTime` remain authoritative. |
| IOS-IMAP-001 | Accepted fail-closed capability edge | IMAP; move; archive; no UIDPLUS; soft delete; relist; EXPUNGE; COPYUID; tagged OK; lane wedge | A server without UIDPLUS cannot target an EXPUNGE safely. Archive/move therefore copies the intended message and marks only its source UID `\\Deleted`; destination-exact recovery likewise soft-deletes only the source. The source can remain or relist until the server or another client safely expunges it. Do not restore mailbox-wide EXPUNGE or add provider-wide `\\Deleted` filtering: incomplete visible cleanup is safer than permanently deleting an unrelated pre-deleted message. **v3 re-baseline:** the mailbox-wide `EXPUNGE` that `v1.6.38` still reached — both directly and *through* SwiftMail's `move` fallback, which falls through to a bare, mailbox-wide `expunge()` whenever the UID branch lacks UIDPLUS — is gone. `IMAPProvider.move` no longer calls `server.move` (`3843940cb`) and `saveDraft`'s two former bare expunges now route through the scoped `expungeScopedToTargets`. No production call site issues an argument-less `EXPUNGE`; C3-I5 is enforced unconditionally. **Open decision D3:** nobody has verified whether a `\Deleted` source copy is even rendered today. Hiding `\Deleted` rows at the local merge layer is option (b) and destroys nothing server-side; a server-side mailbox-wide purge is FORBIDDEN. **⚠ AUDIT ROUND 3 — THIS ROW WAS BRIEFLY NOT WHAT THE CODE DID, AND THE CODE IS BACK.** Between `4e08ff720` and round 3, `IMAPProvider.move` opened with `guard await server.supportsUIDPlus else { throw … }`, so on this class of server the move did not "copy and soft-delete" — it **refused before any wire mutation, on every attempt, forever**, and because that refusal's drain arm returns `.haltLane` it also starved every later gesture naming the same message on every future drain. Neither the queued move nor the starved sibling had any user-visible resolution path. Round 3 deleted the guard. What authorizes the source cleanup on a non-UIDPLUS server is now the COPY's own **tagged OK**: RFC 3501 §6.4.7 requires that an unsuccessful COPY MUST restore the destination mailbox, so a tagged OK is a positive statement that the whole named set copied, and SwiftMail surfaces any tagged `NO`/`BAD` as a thrown `IMAPError.copyFailed` (`CommandHandler.processResponse` → `CopyHandler.handleTaggedErrorResponse`). A UIDPLUS server is still held to per-member `COPYUID` and still refuses without it. **The accepted cost is exactly the one this row already stated** — the source copy stays, `\Deleted`, and may remain visible or relist — and it is preferred over BOTH alternatives: over the permanent queue wedge, and over a folder-wide EXPUNGE that irreversibly destroys unrelated pre-deleted mail. This row, not a fresh judgement, is the governing decision for that choice. |
| IOS-IMAP-003 | Mitigated; closes with the upstream capability accessor | IMAP; MOVE; UIDPLUS; capability detection; SwiftMail; epoch assertion | On a UIDPLUS-but-no-MOVE server, SwiftMail's `move` runs COPY → STORE `\Deleted` → scoped `UID EXPUNGE` with **no epoch check between the steps**; a UIDVALIDITY reset after the COPY makes the internal STORE mark a *different* message. `capabilities` is `internal` while `supportsUIDPlus` is `public`, so app code could not detect MOVE support at all. **Mitigated by owning the sequence:** v3 never calls `server.move` on an action path and issues its own five-assertion COPY/STORE/scoped-EXPUNGE, at the cost of losing atomic `UID MOVE`. | IOS-IMAP-005 | Accepted two-generals edge | IMAP; COPYUID; `move`; committed-then-threw; `IMAPError.commandFailed`; retry | `CopyUID(nio:)` is constructed inside the tagged-OK handler, so a malformed COPYUID makes `move` **throw after the server already committed the move**. Upstream signals this as `IMAPError.commandFailed("COPYUID …")` while a genuine failure is `IMAPError.commandFailed("Move failed: …")` — the same case, separated only by a message prefix — so discriminating "possibly succeeded" from "failed" is string-based today. v3 therefore **fails toward "possibly succeeded"**: it does not retry the destructive half and drops the op for sync to reconcile. make D10 against what is actually there rather than against the plan's summary of it.

⚠️ **The plan's premise — "labels are not account-scoped" — is half wrong, and the half that is wrong
changes what the migration has to do.** The `userLabel` TABLE is already account-scoped: `accountId` is
a `.notNull()` column with `.references("account", onDelete: .cascade)`, and `UserLabel.accountId`
exists on the record type. Three of the five `UserLabelStore` readers already filter on it
(`allLabels(accountId:)`, `findByName(_:accountId:)`, `labelsSortedForMenu(accountId:)`). So D10 is
**not** "add an `accountId` column".

|---|---|---|---|
| IOS-LABEL-001 | Surfaced by orchestrator investigation while scoping T4.V14, not by an audit round; **class C** (shipped verbatim in `v1.6.38`); **REGISTRABLE**; **owner-gated — deliberately NOT fixed, needs decision D10 and a `v82` migration** | User labels; Gmail labels; IMAP keywords; `userLabel`; `messageUserLabel`; primary key; `t.primaryKey("id", .text)`; cross-account collision; `UserLabelStore.loadLabels(for:in:)`; `UserLabelStore.labelsForMessage(_:in:)`; `labels(ids:accountId:in:)`; `SyncEngineFullSync`; `.save(db)` upsert; `onConflict: .ignore`; `onDelete: .cascade`; multi-account | **`userLabel`'s primary key is the label id ALONE (`t.primaryKey("id", .text)`), but a label id is only unique WITHIN an account — so two accounts that share a label name share one row.** The id is provider-supplied and not namespaced: the Gmail arm of `SyncEngineFullSync` sets `labelId = info.path`, and the IMAP/keyword arms in `SyncEngineFullSync`, `SyncEngineBackfillDeep` and `SyncEngineDeltaSync` all set `UserLabel(id: labelId, accountId:, name: labelId, isSystem: false)` from the raw keyword. Two Gmail accounts each having a `Receipts` label, or two IMAP accounts each using a `work` keyword, therefore collide on the PK. **Three consequences, all verified at the tip.** **(1) The row's owner flaps.** The Gmail arm writes with `.save(db)` (an upsert, and its own comment says `// upsert`), so whichever account syncs last overwrites `accountId`, `name` and `isSystem` on the shared row. The IMAP arms write with `.insert(db, onConflict: .ignore)`, so there the FIRST writer wins permanently and later accounts silently bind to a row that names someone else's `accountId`. **(2) A cascade crosses the account boundary.** The Gmail stale sweep deletes with `staleLabelIds.contains(Column("id")) && Column("accountId") == account.id` — the FILTER is account-scoped, but the ROW it deletes is global, and `messageUserLabel.userLabelId` references `userLabel` with `onDelete: .cascade`. So account A removing a label server-side drops the shared row and, with it, **every association row for account B's messages**. **(3) The read path that the plan's `labels(ids:accountId:in:)` = 0 hits actually names.** `UserLabelStore.loadLabels(for messageIds:in:)` and `UserLabelStore.labelsForMessage(_:in:)` join `messageUserLabel → userLabel` by id **with no `accountId` predicate at all** — they are the two readers that are not scoped, and they are the ones that render a message's label chips. A message in account B is therefore displayed with whatever `name`/`isSystem` the shared row currently carries, which after (1) may be account A's. **Concrete reachability:** any user with two accounts on the same provider who uses the same label or keyword name in both — an ordinary configuration, not an exotic one. **Why REGISTRABLE and not BLOCKING:** no message is mutated, misattributed, or destroyed; no wire operation is issued; no queued intention is dropped or wedged. Consequence (3) is local display only, and consequence (2) is recovered by the next sync of the affected messages, because `SyncEngineDeltaSync` and `SyncEngineBackfillDeep` re-insert each association from the server's own `info.userLabelIds` — the server, not the local row, is the source of truth for which labels a message carries. It fails toward showing the wrong label NAME, never toward acting on the wrong message. **Why it is nonetheless owner-gated rather than shrugged off:** the fix is a data-model change, which is exactly what D10 is for. Making the identity account-unique means either a composite primary key `(accountId, id)` or a derived surrogate id, and **either choice must also rewrite every existing `messageUserLabel.userLabelId` value**, so it needs a real migration (next free number is `v82`; the shipped `v1.6.38` line ends at `v67`, and `v68`–`v81` are post-release). Scoping the two unscoped readers WITHOUT changing the key would not fix it — with one shared row there is nothing for an `accountId` predicate to disambiguate, and adding the predicate alone would make account B's chips vanish instead of showing the wrong name. **That ordering is the reason this row exists:** the smaller-looking change is not a partial fix, it is a different bug. |

| ID | Defect | Closed by |
|---|---|---|
| **IOS-IMAP-002** | **A duplicate RFC 822 Message-ID on IMAP made one swipe mutate EVERY copy.** `MessageHeader.stableId` returned the RFC whenever `messageId` was numeric, and `IMAPProvider.resolveUID` fell through to `searchByMessageId` and returned **the entire `UIDSet` with no cardinality check**; its consumer stored flags on that whole set. Reachable with aliases, which are common. **Latent at and before `v1.6.38` — not a post-`v1.6.38` regression.** | ADR-IOS-068 (D4 native-provider-id keying). ~~Under D4 there is no multi-match set to check, because nothing searches.~~ ⚠️ **THAT SENTENCE IS RETRACTED — it was FALSE at `60a8751cb` and the final audit train caught it.** `IMAPProvider.searchByMessageId` still had three live call sites, and one of them — `saveDraft`'s no-`APPENDUID` arm — converted a `SEARCH` result into a **draft mutation address** (`.created(.imap(…))`), which `DraftStore.applyPushCompletion` persisted and `deleteDraftStrong` later mutated with `STORE \Deleted` plus, on a UIDPLUS server, an **irreversible `UID EXPUNGE`**. The exact-verify and cardinality guards the candidate added prove *"exactly one message carries this Message-ID"*, **not** *"this is the message we appended"* — so a same-Message-ID sibling could be expunged instead. That was a **BLOCKING C3** finding and is **fixed separately** (the arm now returns `.unaddressable`; absence of `APPENDUID` yields no address at all). The lesson this register row should carry: **"nothing searches" is a claim about the whole tree and must be re-verified by grep, not inherited from an ADR's intent.** The rest of the row stands, and the original defect remains fixed. Pinned by a red-first invariant test. |
| **IOS-IMAP-004** | **Without `COPYUID` there was no proof our own COPY landed**, so a move interrupted after the COPY could not safely clean up the source, and with aliases a pre-existing sibling copy in the destination is indistinguishable from our own. | Closed by the SwiftMail upstream sync: `copy()`/`move()` now return a server-verified `CopyUID` carrying the destination UIDVALIDITY and a source→destination mapping. **Where the server advertises UIDPLUS, `COPYUID` is the only accepted witness — no weaker one is substituted.** ⚠️ **Narrowed, audit round 3 (2026-08-03).** The original sentence was categorical and, read that way, forbade source cleanup on any server without UIDPLUS — which wedged that entire class permanently (they can *never* furnish `COPYUID`, so the op could never reach a never-drop exit and starved every later gesture on that message). **Adjudication: on a non-UIDPLUS server the COPY's own tagged `OK` authorizes source cleanup.** It answers the question cleanup actually asks — *did my copy land?*: RFC 3501 §6.4.7 requires an unsuccessful COPY to restore the mailbox, and in the SwiftMail fork a tagged `NO`/`BAD` throws (`BaseIMAPCommandHandler.processResponse` → `BaseIMAPCommandHandler.handleTaggedErrorResponse`, overridden by `CopyHandler.handleTaggedErrorResponse` → `IMAPError.copyFailed`) and cannot return normally. `COPYUID` additionally says *where* the copy landed, which cleanup does not need. The rationale's second half — *"with aliases a pre-existing sibling copy is indistinguishable from our own"* — concerns a destination **SEARCH**, which this path never performs; it stays ADR-IOS-068/D4-clean. **Accepted cost:** without `COPYUID` the source UIDs cannot be named, so the source copy is left visible-and-`\Deleted` rather than expunged (a folder-wide `EXPUNGE` is forbidden by `IOS-IMAP-001`) until something else expunges the folder. The superseded fallback — *"drop the op and let sync reconcile"* — is **not** available under NEVER DROP USER INTENTION and must not be reinstated. ⚠️ **CORRECTED TWICE MORE, audit round 4 (2026-08-03).** (a) The round-3 wording above **overclaimed**: it said the tagged OK settles the question *"conclusively"* and, at the code, that it proves *"the whole named set"* copied. It does not. The command is a `UID COPY`, and RFC 3501 §6.4.8 states that *"a non-existent unique identifier is ignored without any error message generated. Thus, it is possible for a UID FETCH command to return an OK without any data or a UID COPY or UID STORE to return an OK without performing any operations."* A named-but-absent UID is simply not one of *"the specified message(s)"* §6.4.7 speaks about, so the OK is silent about it — and the op was retired as provider success anyway, which in a batch let an absent member ride out of the queue on a present sibling's OK. (b) The claim that `COPYUID` *"is the only accepted witness"* wherever UIDPLUS is advertised was itself a permanent wedge for part of that class: RFC 4315 §3 makes the response code a SHOULD **"with limited exceptions, discussed below"** — a mailbox the client may COPY or APPEND to but not SELECT or EXAMINE (*"SHOULD NOT send"*), and a `UIDNOTSTICKY` mail store (*"MAY omit"*) — both properties of the mailbox rather than of the attempt, so for those servers it never arrives, the op reached none of the four never-drop exits, its lane halted on every drain, and each drain re-issued the COPY and seated another destination duplicate. **What the fix now guarantees, per member and per mutation kind:** a source copy is marked `\Deleted` only when the member is proved to have been *in the source mailbox at the moment the COPY ran* — either because `COPYUID` names it, or because a `UID FETCH` of the op's own source UIDs (no `SEARCH`, no Message-ID: D4-clean) still returns it after the COPY, which under RFC 3501 §2.3.1.1's "MUST NOT refer to any other message … forever" and strictly-ascending UIDs means it was present during the COPY and so was covered by the tagged OK. A source copy is `UID EXPUNGE`d only on `COPYUID`; the widened evidence never authorizes an irreversible deletion, so against a non-conforming server the worst case is a message left `\Deleted`-but-present, never one destroyed. A member the `UID FETCH` proves is no longer in the source is the provider stating there is nothing left to move — exit 2, zero mutation, retired — which is what shipped `v1.6.38`'s `idempotentMove` did with its `if srcUIDs.isEmpty { … return }` early return. Every member therefore reaches a permitted exit on every attempt, so no move op can wedge its lane for want of evidence. |
