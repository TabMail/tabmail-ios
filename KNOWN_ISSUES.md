# TabMail iOS Known Issues

This is the searchable register for deliberately deferred iOS behavior. Read it before planning or reviewing a matching subsystem. Resolved items do not remain here; their history belongs in ADRs, audit plans, and Git. The release policy is: restoring sync/list state after a fail-closed edge is acceptable; mutating the wrong message or draft is not.

| ID | Status | Subsystem / keywords | Deferred policy |
|---|---|---|---|
| IOS-EPOCH-001 | Accepted fail-closed window (T1.3) | IMAP; iCloud; UIDVALIDITY; `Folder.lastKnownUidValidity`; durable admission; first sync; silent no-op; archive; delete; move; mark read; flag; user label | **What the user observes:** on an IMAP or iCloud account, a gesture made against a brand-new folder *during that folder's very first sync* appears to do nothing — the message does not animate away, the flag does not stick, and no error is shown. Repeating the gesture once the folder has finished its first sync works normally. **Why:** a durable IMAP action is refused when the target folder's `Folder.lastKnownUidValidity` is nil, because `MessageHeader.stableId` falls back to a bare numeric UID for any header lacking an `rfc822MessageId` and `IMAPProvider.resolveUID` treats a numeric id as a literal UID — executing that under an unknown epoch risks mutating a DIFFERENT message (constraint C3). Failing closed is always acceptable; mutating the wrong message is not. The refusal is a **silent no-op** by owner decision §9 D6(a) — no dialog, no toast. **The bound:** T1.2b (`7c71f6c7b`) persists the epoch from the `Mailbox.Selection` of SELECTs the sync and folder-open paths already perform, and `OK [UIDVALIDITY n]` is core IMAP4rev1 rather than a UIDPLUS extension, so every server reports it on SELECT even when it never answers a UIDVALIDITY STATUS. The window is therefore bounded to the first sync of a folder and cannot become permanent. **Explicitly NOT in scope:** Gmail and Exchange never populate `FolderInfo.uidValidity` at all, so their epoch is nil forever — the refusal is provider-scoped to `.imap`/`.icloud` and must never be widened to "the column is nil", which would permanently brick every Gmail and Exchange account. A missing `Folder` row likewise admits, because the draft and user-label paths synthesize `"Drafts"`/`"INBOX"` paths that may match no row, making a refusal there permanent rather than transient. A synthesized/fake epoch was proposed and REJECTED (owner, 2026-07-30). **Residual:** until the D5 purge-and-resync reaction (T4.S6) lands, `lastKnownUidValidity` is bootstrap-only and never advances past a real UIDVALIDITY turnover, so this admission guard must NOT be read as "the epoch model is now sound". Do not close T4.S6's row by pointing at T1.3. |
