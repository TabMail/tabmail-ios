## T1.3 — a NEW gesture fails CLOSED when the folder's UIDVALIDITY epoch is unknown (2026-07-30/31)

`AccountManager.newGestureRefusedForUnknownEpoch(accountId:folderPath:db:)` (in the FILE `AccountManagerActions.swift`, an `extension AccountManager` — there is no `AccountManagerActions` type to cite) refuses a new user gesture whose durable op would carry a bare numeric UID into a folder with no known epoch. `MessageHeader.stableId` falls back to the bare UID for any header with no `rfc822MessageId`, and `IMAPProvider.resolveUID` short-circuits a numeric id to a literal `UIDSet` with no SEARCH, so admitting one under an unknown epoch can STORE/COPY/EXPUNGE over an unrelated message — constraint C3, the one hard invariant. The refusal is a **silent no-op** (owner §9 D6(a)): no op row, no local mutation, no error. User-facing register entry: `IOS-EPOCH-001` in `KNOWN_ISSUES.md`. This deliberately drops one user intention, which the core philosophy otherwise forbids — do NOT "fix" it back to fail-open. **`v2final` fails OPEN here** (`observedUidValidityStampForTokenAdmission` returns a nil stamp and skips the checks) and could afford to, because it carried an epoch ledger plus a purge-and-resync reaction; v3 has neither.

The shape of the predicate is almost entirely CARVE-OUTS, and every one of them exists because a naive form bricked something. Do not simplify them away:

- **Provider-scoped, never "the column is nil".** `Folder.lastKnownUidValidity` is nil FOREVER on Gmail and Exchange (neither provider ever populates `FolderInfo.uidValidity`), so keying off the column alone silently no-ops every action on every Gmail/Exchange account. The partition mirrors `EmailProvider.staleWindowMode` (`.uid` for IMAP, `.date` for the rest), expressed against the `Account` row because admission runs inside a write transaction with no provider instance in hand. **`.icloud` is IMAP and MUST stay in the set** — several sync sites test `.imap` alone; do not copy those.
- **The demo account is excluded BY ID** (`DemoSeed.demoAccountId`). It is stored as `provider: .imap` but served by `DemoProvider` — pure GRDB, no network, no SELECT — so nothing can ever stamp an epoch on a demo folder. Without the carve-out every guarded gesture in Demo Mode (archive, delete, move, read/unread, flag, all three label paths) was refused forever. Placed in the predicate rather than papered over by seeding a synthetic epoch in `DemoSeed`, which would make the column lie for an account with no server (and re-brick the moment demo seeding changed). Same idiom as `setupOAuthAccount` / `addIMAPAccount` / `addICloudAccount`.
- **A missing `Folder` row fails CLOSED** (inverted by `8f20ab2f4`; `KNOWN_ISSUES.md` documented the pre-inversion behaviour until round 7). `SyncEngine.fullSync` deletes a vanished folder's row but RETAINS its headers (migration v2 dropped the `messageHeader.folderId` FK), so an orphaned header keeps a `folderPath` with no metadata and a later re-appearance of the path re-adopts it under a nil-epoch row. Orphans are reachable by real gestures — the notification path queries `messageHeader` without joining `folder`.
- **The two draft sites are classified by what the provider DOES with the id**, not by the op's name: `serverDraftId` nil ⇒ pure APPEND (admit), non-numeric ⇒ Message-ID SEARCH, epoch-immune (admit), numeric ⇒ literal-UID `STORE \Deleted` + `EXPUNGE`, both `try?`-swallowed (GUARD). `queueDraftSave` classifies at ENQUEUE time and that is **not the last word** — `PendingOperation` has a UUID primary key and no save-draft dedupe, so two saves queued while the id is still nil are both admitted as APPEND-only, the first stores the numeric UID its APPEND returned, and the second executes against a live row that has become numeric. `DraftStore.pushDraftToServer` therefore re-classifies at EXECUTION time, from the same snapshot whose `serverDraftId` it is about to hand the provider. A refusal there loses nothing of the user's: the local `Draft` row keeps the content, only the server copy stays stale.
- **⛔ A synthesized/fake epoch was PROPOSED AND REJECTED** (owner, 2026-07-30) — it would disable the check globally to paper over a case SELECT already covers.

**Bounding the window is what makes the trade acceptable, and it took three rounds.** T1.2b persists the epoch from the `Mailbox.Selection` of SELECTs sync and folder-open already perform (`OK [UIDVALIDITY n]` is core IMAP4rev1, NOT a UIDPLUS extension — so it answers where the STATUS attribute, which SwiftMail requests only on a UIDPLUS server, is nil forever). Round 7 then addressed a **custom NON-FAVOURITE folder**, which `syncableFolders` excludes (full sync, delta sync and self-heal all build that filter the same way: primary roles ∪ secondary roles ∪ favourites) while `runBackfill` DOES crawl it and makes its mail account-wide searchable.

⚠️ **RETRACTION (round 8) — round 7 called that refusal PERMANENT and said the folder "is reached by nothing except `runBackfill`". Both are FALSE.** On-demand navigation reaches ANY folder: `InboxView.onAppear` → `InboxViewModel.startSync()` → `performSync()` → `AccountManager.syncFolders(_:)` (in the FILE `AccountManagerFetch.swift`, an `extension AccountManager`; its filter is `!folder.path.isEmpty` and nothing else — no role, no favourite predicate) → `SyncEngine.syncFolderMessages` → `syncMessages` → `runSyncMessages`, carrying the T1.2b SELECT-sourced bootstrap. `SyncEngineFullSync.swift` states it three lines under the `syncableFolders` construction: *"Custom non-favorited folders sync on-demand when the user navigates to them."* The refusal was **indefinite until the user opens that folder**, not permanent — still a real bug for mail reachable only through account-wide search in a folder the user never opens, so the fix is right and only the absolute was wrong. Say "indefinite", never "permanent"/"forever", at all five sites that stated it (the walk's comment, `Folder.lastKnownUidValidity`, `SyncEngine.bootstrapFolderUidValidity`, `KNOWN_ISSUES.md` `IOS-EPOCH-001`, and here).

🚨 **Round 8 replaced the VALUE the crawl stamps — the write was always fine, the value was not.** Round 7 took ONE post-walk sample of `IMAPProvider.lastObservedUidValidity(folderPath:)`. But backfill's own SELECTs were RAW (`server.selectMailbox`) in `getUidNext`, `searchExistingUIDs(folder:from:to:)` and `fetchMessageHeaders(folder:uids:batchSize:interBatchDelay:)` — only `IMAPProvider.createFolderConnection` used `selectMailboxTracked` — so the mirror held the epoch observed when the pinned connection was CREATED and tracked no turnover during the walk. On a crawl resuming from a stored cursor that sample could be an epoch the mailbox rolled to AFTER an earlier pass's headers were written; `newGestureRefusedForUnknownEpoch` tests only `== nil` and never compares stored against live, so stamping it ADMITTED bare-UID gestures that then resolved against a different message (C3), and left the deletion-reconcile abort guard agreeing stored-with-live over old-epoch rows it would treat as ghosts.

The round-8 shape, which is the `v2final` approach ported properly:
1. All three backfill SELECTs now route through `IMAPProvider.selectMailboxTracked` (the tracked set is five call sites; ACTION SELECTs deliberately stay out — see that method's scope note).
2. The walk captures its epoch ONCE at walk start (`walkEpoch`), forcing a fresh `getUidNext` observation on the resumed branch because the pinned connection may predate this pass. It is NEVER re-read live after the workers join.
3. Every worker re-checks the mirror against `walkEpoch` right after its own SEARCH and again right after its own FETCH. A disagreement discards the fetched headers, marks the range FAILED (never confirmed) and stops the worker; the pass then skips its cursor/completeness bookkeeping entirely.
4. The stamp goes through `SyncEngine.bootstrapCrawledFolderUidValidity`, which is bootstrap-only **and** gated on `MessageHeader` count == 0 for the folder, evaluated INSIDE the write transaction, and it happens at walk START — in the same transaction as the initial-cursor plant (and as the `UIDNEXT < 1` early-out's completion write, which round 7 skipped entirely). With no local rows the claim "every local UID belongs to this epoch" is vacuously true, and rule 3 keeps it true for everything the walk then inserts.

5. 🚨 **The refusal has to persist for the rest of the CALL, and be re-checked on the NEXT one.** Rules 3–4 alone re-create the very defect they remove, and the round-8 adversarial test caught it: refusing a chunk leaves the folder incomplete, so `runBackfill`'s outer `while true` re-reads it as "still incomplete" and walks it AGAIN in the same call — with a fresh `walkEpoch` that now describes the NEW mailbox — inserting post-turnover UIDs into a folder stamped with the old epoch, one iteration after the guard prevented exactly that. So a folder that saw a turnover goes into a per-call `epochDeclinedFolderIds` set that the folder-selection filter honours, and every later call compares the folder's STORED epoch against the walk's through `SyncEngine.crawlEpochAgrees(stored:walk:)` before any write (either side nil ADMITS: nil-stored is the ordinary first crawl, nil-walk is a server that never reports UIDVALIDITY). That comparison is `v2final`'s `uidValidityWalkWriteAllowed` without its `uidValidityResetPendingAt` quarantine, which v3 has not ported. Cost of the refusal: one SELECT per cycle until the D5 reset reaction exists.

⛔ **A folder that already holds rows of unproven epoch is NOT stamped — deliberate, fail-closed (C6).** v3 has not ported ADR-IOS-061's quarantine → purge → stamp → resync reaction, so there is no sound way to assert an epoch of rows an earlier pass wrote. Folders left half-crawled by an OLDER build keep a nil epoch; C6 waives backward compatibility, and `SyncEngine.resetCrawlState` (Smart Reindex) does NOT recover them — it clears cursors without clearing headers.

⚠️ **RETRACTION (round 10) — round 8's "`backfillUidCursor != nil` implies the epoch was already bootstrapped (or the server reports none at all)" is FALSE, and it was the sentence that hid blocker 1.** Two reachable states falsify it, both with a non-nil cursor and a nil-or-wrong stamp: (a) the fresh-cursor transaction plants the cursor and calls `bootstrapCrawledFolderUidValidity`, which returns `false` — not throws — whenever `walkEpoch` is nil or the folder already holds a row, so the cursor lands with no stamp; (b) round 8's resumed-leg `catch` persisted the cursor and continued after a THROWN bootstrap write, by its own description. The corrected statement is bounded: *the fresh-cursor branch attempts the stamp in the same transaction as the cursor, so a cursor without a stamp means the attempt was refused or failed, never that it was skipped.*

⚠ Also fixed in round 8: the round-7 `catch` around the epoch write claimed *"the next backfill cycle re-observes and retries"*, which could not happen — the very next statements set `backfillComplete = true`, and both `runBackfill`'s initial folder query and its per-iteration re-read filter on `backfillComplete == false`. That is the same reasoning round 7 used to REJECT the before/after pairing, reproduced in its own error leg. The bootstrap now shares a transaction with the cursor/completion write on both fresh-cursor legs.

### Round 10 — the four corrections, and the one lesson that generated three of them

🚨 **THE LESSON: a TRANSIENT container plus a DURABLE re-entry condition is a PERMANENT refusal.** `epochDeclinedFolderIds` is function-local and dies with the call, which is what made rounds 8–9 read the decline as transient. It is not, if the condition that inserts the folder is stored in the database — the next call re-derives it and declines again, forever. Ask of every decline: *what re-evaluates the predicate on the next call, and can that answer ever change?*

1. **An EMPTY folder is no longer bricked by a mid-walk turnover (blocker 1).** The state: empty, incomplete, cursor-bearing, durably stamped E1, mailbox now at E2 — every later `runBackfill` re-derived the mismatch and re-declined. The ordering was the bug: agreement was checked before anything looked at the header count. `SyncEngine.resetEmptyFolderCrawlEpoch(_:folderId:)` now fires on mismatch, counts headers INSIDE the write transaction and, at zero, clears BOTH `lastKnownUidValidity` and `backfillUidCursor`; the next iteration re-enters the fresh-cursor branch and stamps the live epoch under the existing count gate. **The cursor must go too** — it is a position in a UID space that no longer exists, and re-planting it walks `[1…staleCursor]` in the new mailbox and never looks above it (`v2final`'s documented completeness gap). This is NOT the deferred T4.S6 carve-out: that one covers a folder holding ROWS whose epoch nothing can prove, where advancing the stamp asserts something false about real data. Zero rows means the stamp describes an empty set, so replacing it asserts nothing. Bounded to ONCE per folder per call (`epochReadoptedFolderIds`), or a mailbox turning over between the reset and the next SELECT spins the loop at network rate.
2. **A pass that could not OBSERVE the epoch no longer walks a folder that HAS one (blocker 2 / NB1).** `crawlEpochAgrees(stored:walk:)` admitted any nil on either side, so a failed walk-start observation left `walkEpoch` nil, `expectedEpoch` nil, and BOTH per-chunk checks unconditionally true — E2 headers into an E1-stamped folder, and the stamp is non-nil so `newGestureRefusedForUnknownEpoch` (which tests only `== nil`) keeps admitting bare-UID gestures on them (C3). Round 8's justification argued from ONE cause; `v2final` names TWO ("the resumed-branch fresh observation above failed, **or** a broken server never reports UIDVALIDITY at all") and refuses in both. `SyncEngine.crawlEpochGate(stored:walk:)` replaces the boolean with three outcomes — `.proceed` / `.refuseUnobservedEpoch` / `.refuseEpochMismatch` — and refuses when `walk == nil && stored != nil`. **The negative case is what keeps that safe:** a folder with a non-nil stored epoch PROVES the server reports UIDVALIDITY, so the epochless-server account round 8 protected has nil stored epochs everywhere and is untouched (`anEpochlessServerIsStillCrawled` pins it). Accepted, and stated as a bound not an absolute: a server that reported an epoch once and then permanently stops re-declines that folder every cycle at one SELECT per cycle — indefinite, not permanent, and it self-heals the moment one SELECT reports again.
3. **The epoch a sync pass stamps is now BOUND to the fetch it stamps for (blocker 3).** Round 8 routed the crawl's SELECTs through `IMAPProvider.selectMailboxTracked`, which gave the shared `lastObservedUidValidity(folderPath:)` mirror competing writers — and `runSyncMessages` read that mirror right after its own fetch. 🚨 **`v2final` consumes the same mirror read as a COMPARISON THAT ABORTS the merge; this port consumed it as a FIRST-EPOCH WRITE. That inversion of consumer direction is the defect** — a race can only force a false ABORT in the reference, but a false STAMP here, which is exactly the stamp-agrees-with-live-server-over-old-rows state that disarms the ADR-IOS-051 abort guard. New `EmailProvider.fetchMessagesWithObservedEpoch(folder:limit:offset:)` returns the epoch of the very `Mailbox.Selection` that served the fetch; the protocol default pairs `fetchMessages` with `lastObservedUidValidity` so no non-IMAP provider and no test double changes. Same shape for the walk: `IMAPProvider.getUidNext(folder:)` → `getUidNextWithEpoch(folder:)`.
4. **A `false` return and a `threw` outcome mean DIFFERENT things (blocker 4).** `bootstrapCrawledFolderUidValidity` returns `false` for "the precondition legitimately does not hold" (the common case) and throws for "the write failed". Round 8 conflated them: it caught the throw, continued the walk, inserted headers, and merely withheld `backfillComplete` "so this pass is retried" — but the pass it had already run made its own precondition false, so the retry found a non-zero header count, got `false`, read it as success, and marked the folder complete with a NIL stamp. A THROW now declines the folder BEFORE the walk inserts anything, leaving the next call the preconditions this one found.
5. **NB2/NB4 — the walk's bookkeeping writes are judged at WRITE time.** `runBackfill` reads the folder row once per iteration, before the walk-start round trip; the reachable skew is "snapshot nil, DB now stamped", and a nil stored epoch ADMITS, so the skew failed OPEN. `SyncEngine.crawlWalkWriteAllowed(_:folderId:walkEpoch:)` re-reads the row inside each write transaction — PORTED from `v2final`'s `uidValidityWalkWriteAllowed(db:folderId:observedEpoch:)` minus its `uidValidityResetPendingAt` quarantine term. It now guards the two THROTTLED in-worker cursor writes as well, which this port had left unguarded while the `if epochMovedMidWalk` comment claimed nothing had been persisted — those writes persist a cursor roughly once a second, so the claim was false; the intermediate cursors are nonetheless sound on their own terms (a cursor is a walk position, and the discarded chunk was never confirmed).

**Mirror images found by re-reading the round-10 diff for its own defect family:** the `initialCursor < 1` early-out and BOTH final bookkeeping writes used `try?`/ignored the outcome and then `continue`d — the same "a failed write leaves the folder in a state that re-enters the same leg next call" shape as NB3. All three now decline the folder when the write does not land.

⚠ Also corrected in round 10: bullet 5 above says *"either side nil ADMITS"* of `crawlEpochAgrees`. That is still true of `crawlEpochAgrees` itself (kept, and still used by `crawlWalkWriteAllowed`, where the stored side is the only nil that can occur), but it is NO LONGER the walk-start admission rule — `crawlEpochGate` is, and it refuses walk-nil against a non-nil stored epoch.

The VALUE-writer set of `Folder.lastKnownUidValidity` is still THREE (`bootstrapFolderUidValidity`, `fullSync`'s folder-list upsert, `persistFolderUidValidity`); the crawl reaches the first of them only through `bootstrapCrawledFolderUidValidity`, which must stay its only door. Round 10 adds ONE writer that is not in that set because it writes no value: `SyncEngine.resetEmptyFolderCrawlEpoch` CLEARS the column (and the cursor) to NULL for a folder holding zero headers. It is enumerated as a CLEARER on `bootstrapFolderUidValidity` and on the column's own doc comment; any new writer OR caller must be added to both, and a fourth path that wrote a VALUE would have to go in the set proper.

⚠ **UPDATE (T4.S6b, 2026-07-31) — the paragraph above is superseded on two points, kept for its derivation.** (1) `persistFolderUidValidity` is **DELETED**: `runDeletionReconcileWalk` no longer ADOPTS a first-SELECT epoch onto a nil-stored folder, it ABORTS with `"epoch unverified"` before the first SEARCH, so the walk's writer became unreachable. (2) The VALUE-writer set is still THREE, but the third member is now `SyncEngine.verifyAndBootstrapPrePopulatedFolderEpoch` → `bootstrapVerifiedFolderUidValidity` (`SyncEngineEpochVerify.swift`, an `extension SyncEngine` — no such TYPE). The invariant that changed: **a folder that HOLDS ROWS can no longer be stamped by assertion.** `bootstrapFolderUidValidity`'s statement carries `AND NOT EXISTS (SELECT 1 FROM messageHeader WHERE folderId = :folderId)` (in the SQL, not a Swift `if` — TOCTOU rule), and both `fullSync` folder-list upsert arms consume the same term via the new three-argument `uidValidityBootstrapWrite(observed:stored:folderHoldsRows:)`. The ONLY way a populated nil-epoch folder now gets an epoch is by PROOF: sample a spread of its own UIDs (highest N + lowest N, `SyncConfig.uidValidityVerify*`), FETCH them, and require ≥1 RFC-822 agreement with zero mismatches; otherwise arm `uidValidityResetPendingAt` and hand the folder to the purge-and-resync reaction. 🚨 **The one leg that must never change: if the SELECT serving the sample reports NO UIDVALIDITY, the door DOES NOTHING** — arming there is a permanent brick (the reaction purges, then its own step-5 fresh observation returns nil, aborts, and every abort leg leaves the quarantine SET by design). Doing nothing is the `IOS-EPOCH-001` accepted window: gestures refused, no data touched, self-healing on the first conformant SELECT. Tests: `EpochVerifiedBootstrapTests` (INV-1…INV-7, INV-5 is the anti-brick), and the two rewritten carriers in `UidValidityTurnoverDeletionGuardTests`.

**Presentation-side rule that came out of the same audit train: on a refused or failed optimistic write, RECONCILE the displayed state FROM THE DATABASE — never restore a captured snapshot, never undo a delta.** Both compose wrongly under two taps inside one write window, because the second tap's baseline is the first's UNPERSISTED optimistic state; a snapshot restore then re-publishes a state that was never durable (round 6's phantom-success fix re-created a phantom success this way). `UserLabelMenuModel.reconcileAppliedIdsFromDatabase` and `InboxViewModel.reconcileUserLabels` both re-read the join rows via `UserLabelStore.labelsForMessage`, and both run on EVERY completion, admitted or refused — reconciling only on refusal does not CONVERGE, because if the last overlapping gesture to finish was admitted nothing re-reads, and an earlier gesture's reconcile that raced ahead of that commit leaves a stale row standing. `UserLabelMenuModel` exists as a separate `@Observable` object purely so that invariant is testable — a `View`'s `@State` cannot be observed from a test.

## T4.S6 follow-up — SUPERSEDED v3 intermediate; retain for history, never implement from it (2026-07-31)

⛔ **CURRENT FORWARD-PORT RULING (2026-08-01) supersedes the two implementation prescriptions
below.** The old `v69` draft-op stamp and the later `v72` draft-specific queue epoch were
intermediate compatibility machinery, not the destination. The active frozen candidate uses the
native `(account, Drafts mailbox path, UIDVALIDITY, UID)` tuple, records the queue epoch in
`PendingOperation.observedUidValidity`, leaves the applied physical draft-specific queue column
inert, normalizes unsafe legacy Draft linkage in v73, and blanket-purges every legacy
`pendingOperation` in v74. There is no action-queue migration compatibility requirement; authored
Draft/body/recipient/attachment/ChatTurn bytes and Outbox obligations remain outside that purge.

Most importantly, **a mailbox-wide non-UIDPLUS EXPUNGE is never an acceptable fallback.** It can
destroy every co-resident message already marked `\Deleted`, including messages the action did not
name, and therefore violates C3. Without UIDPLUS, keep the soft delete/fail closed and let sync
reconcile; an orphan or a user-redone action is acceptable, a wrong-message deletion is not. Read
the historical derivation below only to understand how the rejected state arose.

Two independent confirmed defects on the draft path, fixed together. Both are C3 (never mutate the wrong message).

### 1. Historical intermediate: `PendingOperation.observedUidValidity` at migration `v69`

🚨 **THE LESSON, worth more than the fix: "carries a non-numeric id" is a property of the ROW; "resolves by SEARCH" is a property of the EXECUTOR, and the two can disagree.** `AccountManager.opIsAddressOnly` classifies by id shape and returns FALSE for any op carrying a non-numeric id alongside a UID. `queueDraftDelete` writes `messageIds = [numericUID, rfc822]` — the rfc822 is there for the SYNC FILTER (`pendingAllIds`), not for resolution — so the op read as identity-carrying, the reset reaction's step-5 sweep left it alone, and `executeOperation` then handed `messageIds.first` (the UID) to `provider.deleteDraft`, which for a numeric id short-circuits to a literal `UIDSet` with no SEARCH. Post-reaction the op unparked and expunged whichever message the NEW numbering had placed at that UID. This also **falsified the drain's own written safety argument** ("the same transaction that clears the flag also removes the address-only ops"), which is now corrected in place at `AccountManager.drainPendingQueue`'s claim transaction.

**Owner directive (verbatim, 2026-07-31):** *"The delete op should NOT survive a UIDVALIDITY reset — it cannot. The op should no-op once that validity gets invalid."* A live-epoch re-resolution / existence-FETCH machinery for the draft path was PROPOSED AND OVERRIDDEN — do not reintroduce it.

The shape (design (a), ported from `v2final`'s `v74_addPendingOperationObservedUidValidity`; design (b), widening the sweep's classifier, was REJECTED — see below):
- `PendingOperation.observedUidValidity: Int?` (migration `v69`, nullable, no backfill). Stamped INSIDE the same gated write transaction as the insert with the folder's `lastKnownUidValidity`.
- **Stamped by exactly ONE site today: `queueDraftDelete`, and only when `serverDraftId` is NUMERIC** — the same discriminator `newGestureRefusedForUnknownEpoch` already uses. Stamping an rfc822-addressed op would let the claim check drop intention that is still perfectly resolvable (Message-ID SEARCH is epoch-immune): the mirror-image bug, a permanent refusal. Non-IMAP accounts stamp nil for free — Gmail/Graph never populate the column.
- The claim transaction in `drainPendingQueue` DELETES the row (never parks — the old epoch never comes back, so a park is a permanent wedge) when the stamp and the folder's current epoch both exist and disagree. C5 blesses the drop.
- **FAILS OPEN on a nil live epoch**, same polarity as the reference. `SyncEngine.resetEmptyFolderCrawlEpoch` really does clear the column back to NULL, so "unknown" must not read as "different".
- Ordered AFTER the quarantine park: during quarantine the folder still holds the OLD epoch (step 5 owns advancing it), so the stamp agrees and the compare cannot fire.

**Why (b) — widening `opIsAddressOnly` — loses, in the words that matter for the next person tempted by it.** (i) It is a classifier over id shapes, so the next op shape that carries a non-address id beside a UID defeats it again; widening it to "ANY id numeric" over-drops a batch `.move` of `[rfc1, uid2]`, dropping rfc1's still-resolvable intention. (ii) **The sweep only runs inside the reaction's step-5 transaction, and there is a second door that never touches the reaction at all**: `resetEmptyFolderCrawlEpoch` clears the epoch to nil and `bootstrapCrawledFolderUidValidity` re-stamps a NEW value, with no `uidValidityResetPendingAt` ever set and no sweep ever run. A per-op stamp survives that route; a sweep cannot.

### 2. Historical defect: `IMAPProvider.deleteDraft` did a bare, mailbox-wide EXPUNGE

Independent of any epoch question. A bare `expunge()` is mailbox-WIDE (RFC 3501 §6.4.3) — it removes EVERY `\Deleted` message in the selected mailbox. In Drafts that population is not hypothetical: `saveDraft`'s old-copy delete marks messages `\Deleted` with BOTH the STORE and the EXPUNGE `try?`-swallowed, so every failed/interrupted save leaves exactly that residue, and another client's soft-deleted drafts qualify too. Deleting one draft destroyed all of them.

New private `IMAPProvider.expungeScopedToTargets(_:server:logDescription:)` — the UIDPLUS-conditional tail, shape taken from `idempotentMove` in the same file (the in-repo precedent for this exact decision). Applied at `deleteDraft` AND at both legs of `saveDraft`'s old-copy delete (scope only; their `try?` swallowing and reachability are unchanged).

⛔ **RETRACTION — this was never a valid deliberate deviation.** `v2final`'s
`storeDeletedAndMaybeExpunge` fails closed without UIDPLUS because bare EXPUNGE is mailbox-wide.
The claimed “bounded collateral” was unbounded with respect to the action's target set and was a
real wrong-message/data-loss defect. v3 follows the reference safety direction: no UIDPLUS means
no mailbox-wide purge. Do not restore this fallback even if the soft-deleted draft later
re-materializes; that fail-closed residue is the owner-approved simplification.

### Tests (both red-proven by in-place inversion)

`TabMailTests/Sync/DraftDeleteEpochBoundaryTests.swift` and `TabMailTests/Providers/IMAPDraftExpungeScopeTests.swift`. Both pin SYSTEM PROPERTIES, never the mechanism: *"an op recorded under a discarded numbering never executes"* (asserted on `MockEmailProvider`'s call log after a real `queueDraftDelete` → real `uidValidityResetArmFlag`/`uidValidityResetStampFreshEpoch` → real `drainPendingQueue`) and *"no mutation lands on a message whose identity differs from the gesture's target"* (delegated to the existing `FakeIMAPServer` wrong-message wire oracle, `expectMutation`/`wrongMessageViolations`). Three over-refusal controls guard the mirror image: unchanged epoch still deletes, rfc822-addressed delete survives an epoch change, and a non-UIDPLUS server still gets its draft deleted.

⚠️ **Test-harness trap worth remembering: one `await drainPendingQueue()` is NOT enough in a test that has just called a `queue*` method.** Those methods end with an unstructured `Task { await drainPendingQueue() }`; if that stray drain is still inside its three-pass loop, the `isDraining` guard turns the test's own call into a `needsRedrain` flag and returns IMMEDIATELY, so assertions run before anything executed. `DraftDeleteEpochBoundaryTests.drainUntilSettled` loops on (queue empty ∧ `pendingQueueIsQuiescentForTesting`). This made a CORRECT implementation fail its own control test on first run.
